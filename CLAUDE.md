## Packages

| Package           | Role                                                                                                                |
| ----------------- | ------------------------------------------------------------------------------------------------------------------- |
| `task-core`       | Storage: `TaskStore`, config loading, domain errors.                                                                |
| `task-service`    | Use cases shared by the CLI and the app-module. Pure: no console, no `process.exit`; returns results and events.    |
| `task-cli`        | `task` binary: arg parsing and output over task-service, updater, app-core registration.                            |
| `app-module-task` | app-core module (id `task`): routes `/api/modules/task/*` and dsl-views over task-service.                          |
| `dsl-lib-task`    | Browser components (React) the module ships as `task:<Name>`; no storage, service or Node API. See Task components. |

## Dependency direction

`task-core` <- `task-service` <- `task-cli` and `app-module-task`; `app-module-task` -> `dsl-lib-task` (loaded by its `src/dsl-components`, props only). The two adapters never import each other, and `task-service` knows no CLI, HTTP or app-core library, never prints or exits. `npm run test:architecture` (`architecture/`, part of `npm test`) enforces it on imports, `package.json` dependencies and source patterns.

`@wadeck-app/project-sdk` ("latest", lockfile pins it; zero dependencies) is imported by `task-service` only; the architecture test forbids it in the sources of the adapters and `task-core` (their tests may use its mutations for fixtures). Shared rules live in `task-service` (`resolveProject`, `resolveProjectReference`, `listKnownProjects`, `describeError` for the SDK errors), adapters only parse input and format output: `describeError` (error kind, message, hint; CLI maps to stderr, module to HTTP status), `selectDeleteTargets` / `describeDeleteEffects`, `openTaskContext`, `getTaskLogDir`, `countTasksByStatus`, `showTaskWithRelations`, the storage (`storage.ts`: `registryStorage`, `chooseDataLocation`; `openResolvedProject`; `loadTaskConfig`; `migrateData`; `legacyData.ts` is the ONLY module that knows the `.task` folder, see stage 2b-2), the per-project health (`inspectRegisteredProjects`), `listStatuses` (the valid statuses with `default` / `terminal`, from the same merged config as `setStatus`), and the cross-project reads `summarizeProjects` / `listTasksAcrossProjects` (per-project figures and tasks tagged with their project; unreadable projects reported, `NoReadableProjectsError` when none can be read; used by the app-module and by the CLI, see CLI parity below).

## Shared project registry (stage 2b-1)

Projects, data and config live in the registry of the `project` CLI (`@wadeck-app/project-sdk`, `$XDG_CONFIG_HOME/project`, else `~/.config/project`). Task never writes it (architecture rule `NO_REGISTRY_WRITE`: no SDK mutation import, no legacy writer); the registry lock covers the registry only: task data consistency is task's own concern (Q30), so task data has no lock, only atomic writes. **Stage 2b-1 (now)**: every legacy resolution path is gone (table). **Kept on purpose until stage 2b-2**: the unmigrated registered project, because live tools (the flows of `test-flow`) still read its `.task` directly; the list of what 2b-2 removes is at the end of this section.

- Resolution (`resolveProject`): `-p/--project <ref>` > `TASK_PROJECT` > the cwd looked up in the registry (deepest registered ancestor wins, no marker file, no walk-up; a subfolder with a `.task` of its own inside a registered folder is that project). `<ref>` is an id (or unique prefix >= 4), name or alias, case-insensitive, never a path. A reference that does not resolve, or a cwd in no registered project (the SDK's `NoProjectInScopeError`, rethrown with the folder in native separators), is an error, never a fallback. `ResolvedProject.id` is always set; `source` is `flag|env|cwd`; `storage` is `kind: 'registry'`; `path` is the MAIN path (a cwd in a secondary path resolves to it; absent for a virtual project).
- Storage (`storage.ts`): `TaskStore` gets `tasksDir = <data>/tasks`, its index is `<data>/task-index.json` (pinned by tests in task-core, storage and openContext). Reading a fresh project creates nothing; the first write creates `<data>` (the store's `ensureDirectory`, so no `{ensure:true}` on read). A registered project with no data anywhere is a fresh project. `openTaskContext({ storage, project })` needs a storage (no directory input).
- Data location (`chooseDataLocation`, called by `openTaskContext`, so by the CLI, the module and the overviews; result `ctx.storage` + `ctx.notices`): registry has task data and `.task` none -> registry, silent; registry none and `.task` has tasks/index (or a `config.yml` the registry lacks) -> UNMIGRATED: storage of kind `legacy` on the main path with the registry identity (id, name), notice = the `Deprecated: project ...` line (CLI: ONE stderr line per process, also with `--json`, and the task log; module: task log once); both have task data with the same task ids -> registry + the `old copy still in ...` note; both have task data with different ids -> `ProjectDataSplitError` (409 in the module) naming both folders and the two ways out. A fresh project (neither) uses the registry. `resolveProject` never refuses, so `migrate-data` can run in any state.
- Config (`projectConfig.ts`, `TASK_CONFIG_SCHEMA`): for a registered project every `config.yml` of the project chain (root first, own last) is read, validated (`validateLayer`, layer name = the file path) and merged (`mergeLayers`): `statuses`, `types`, `fields`, `hooks` are `local` (replace; a parent's values are valid there and never reach the child), `defaults` is `inherit` + `deep`. An unknown or misplaced key is a `ConfigSchemaError` naming the FILE and the key (`invalid`, 400); the status rules (>= 1, <= 1 default) apply to the merged value and name the file. Task keeps its global/project hooks separation: the task GLOBAL config (`~/.task/config.yml`: defaults, hooks) stays task's own file, merged separately (project value > global fallback for `defaults.priority`). `task type add|remove` write the project's OWN layer (created with its folder if missing). Unmigrated project: `TaskConfigLoader.load({ configDir, projectConfigFile })`, unknown keys ignored; the error names the file.
- `task status list [--json]` (`listStatuses`): the valid statuses of the resolved project in config order, from the merged config `set-status` validates against. Text: one per line, `name`, `name (default)`, `name (terminal)`, `name (default, terminal)`; JSON: `[{name, default, terminal}]`. `task status` / `--help` need no project. Exists for the flows, which used to parse `config.yml` with awk.
- Atomic writes: task files, `task-index.json` and `config.yml` go through the SDK's `writeFileAtomic` (temp file, fsync, rename) via `TaskStore`'s injectable `writeFile` (`atomicWrites.test.ts` spies the SDK).
- Migration, by the user (nothing breaks before it): install project-cli, `project add <dir> --name n` (the project keeps working on its `.task` with one stderr line), `task cli migrate-data -p n [--dry-run] [--json]`, check (`task list -p n --all`; from then on the registry copy is used and each command prints the old-copy note), delete `.task` by hand (the note stops). Anything else reading the `.task` directly (flows) must be moved to the registry data before that deletion. `migrate-data` is an ADDITIVE HELPER that deviates from Decision #17 ("by hand"), because hand-copying hundreds of task files is error-prone and the data-location rules above make a half-done migration visible (the split error, the old-copy note): it copies `tasks/*.json`, `task-index.json`, `config.yml` of `<main path>/.task` into the registry (COPY only, never moves or deletes the source), refuses when the registry already has task data or the own config (names both folders; no `--force`, move the registry data away by hand), verifies the file count and every byte size, rolls back what it created on any failure, rebuilds nothing (a missing index is a warning), lists what it left alone (`notCopied`), and prints the next step. A virtual project or a folder in no registered project gets an actionable error.
- Virtual project (registered, no path): data and config work (id-based); events cannot get a cwd, so the operation succeeds and the event is returned UNDELIVERED with a reason naming the virtual project and `project paths add` (never `process.cwd()`; no `taskProjectPath` key in the payload). Limit: cross-project views and the module do not list virtual projects, and `?project=<virtual>` answers 409 pointing to `task -p <name>`.
- Log: each command appends the resolution line (project, source flag/env/cwd, path, registry dir, data dir) to the task log (`task cli logs`).
- Events: `taskProjectId` (registry id) is in every payload; `taskProjectName` is the registry name; `taskProjectPath` stays the main path (the queue cwd).
- Cross-project views (`summarizeProjects`, `listTasksAcrossProjects`, `listKnownProjects`; CLI `--all-projects` / `projects summary`; module `/projects`, `/summary`): every registered project WITH a path (any project can hold tasks, so none is filtered for lack of a `.task`; a fresh one shows 0 tasks). None of them takes a config dir any more (they read the registry only). Rows carry `id`, `name`, `path`, `exists` (informational), figures, `error`; the `registered` marker and the summary's `initialized` flag are GONE (answers and JSON), as are the `registered:false` rows. A broken parent chain lists the project unreadable (`problem`), a registry that cannot be read is `registryProblem` (nothing is listed then; text mode warns `the shared project registry was not read, so no project is listed: <problem>`). `--all-projects` refuses `-p` / `TASK_PROJECT`.
- Module: `?project=` takes an id, name or alias (registry), page addresses and API queries use the id; the registry is read at every request (no cache); missing = first-use state, corrupt = typed error shown inline. `last-project.json` stores `{ "id": ... }`; an old `{ "path": ... }` file is ignored with ONE line in the task log (no problem shown, nothing preselected until the next creation).
- Tests: the SDK has no off switch. Every `vitest.setup.ts` (task-service, task-cli, app-module-task) points `XDG_CONFIG_HOME`, `HOME`, `USERPROFILE` at a temp dir (`registrySafetyNet.test.ts` proves it); fixtures build registries with the SDK's `addProject` in a temp dir (`createSharedRegistrySandbox`, `createTestWorld().registerShared`); a `.task` is written by hand only for the unmigrated-project tests. `task-core` has no setup and never touches the registry.
- Architecture rules (`architecture/rules.ts`, detection tests in `architecture.test.ts`): `NO_PROJECTS_JSON` (no non-test source names the legacy file) and `NO_LEGACY_DATA_PATH` (no `.task` PATH CONSTRUCTION (`'.task'`, `"/.task"`, `` `${dir}/.task` ``) outside task-service `legacyData.ts`; tests, comments, prose and the `~/.task` global config dir are out of scope). Everything else asks `legacyData.ts` (`legacyDirOf`, `legacyStorage`, `describeLegacyData`).
- Removed in 2b-1 (do not look for them): the `.task`-in-cwd resolution (`legacy()` of `resolveProject`, `ProjectSource` `legacy`, `legacyWarning`, the `projectDir` inputs of `resolveProject` / `openTaskContext`), `--project-dir` / `TASK_PROJECT_DIR` / `PROJECT_DIR`, the `projects.json` reading (`listRegisteredProjects`, `projectsRegistryPath`, `isSameProjectDir`, `ProjectsRegistryError`, `registryHint` / `registryNotice`, the module's slugs and absolute-directory `?project=`), `ProjectNotInitializedError` (misnamed: the SDK's `NoProjectInScopeError` is described directly) and `ConflictingProjectSelectionError`, `TaskConfigLoader.isInitialized` / `addType` / `removeType` / `load({ projectDir })`. Leftovers to `git rm` (the sandbox could not delete them): `packages/task-service/src/projectsRegistry.ts` (empty) and `projectsRegistry.test.ts` (one test of the new rule that can move elsewhere).

Stage 2b-2 (not started; on the owner's go, AFTER the flow owner adapted the flows of `test-flow` that read `.task` directly (they can use `task status list --json` and `task ... -p`) and the owner ran `migrate-data`): remove the unmigrated read of REGISTERED projects: the `legacy` branch and the `Deprecated` notice of `chooseDataLocation` (then the split check alone remains, or an error for any `.task` data left), `TaskStorage.kind: 'legacy'` and the legacy branch of `loadTaskConfig` / `TaskConfigLoader.load`, the old-copy note; decide whether `migrate-data` stays as a helper (it needs `legacyData.ts`) and then whether `legacyData.ts` and its architecture exception go; the pointer commands `task init` / `task projects add|remove|move|prune|list` once nobody needs them; the leftovers above.

## app-core registration

- `task cli register [--json]` / `task cli unregister [--json]`; `task cli update` registers by itself when the shipped app-module version changed. Task has no daemon, so nothing registers at start.
- Exit 0 when app-core took it or is absent/not running (deferred, skipped); exit 1 with app-core's reason when it refuses.
- `unconfirmed` (SDK >= 2026.10.24-094: app-core is up but gave no answer in time, or the connection broke, and `/api/modules` does not show the new version yet) is exit 0, `--json` `{ok: true, status: 'unconfirmed', message}`: the call may well have worked, so not a failure, but not `registered`. The message is the SDK's wording plus "To settle it, wait a few seconds and run: task cli register" (`unregister` for the removal); the updater and the rollback print it too. A script needing certainty tests `status === 'registered'`. `registered` with a `note` is a plain success.
- Manifest: `app-module/manifest.json` next to `task.cjs`, else `packages/app-module-task/dist-module/manifest.json` (source checkout: `BUNDLE_VERSION=0.0.0-local npm run bundle --workspace=packages/app-module-task`). Neither found is an error naming both paths.
- Staging: app-core stores the PATH of a manifest, and npm replaces the package folder on update (and removes it on uninstall). An installed module (`<pkg>/app-module/`) is therefore copied to `<config dir>/app-module/<manifest version>/` (`appModuleStaging.ts`: temp dir then rename, kept if already complete, error naming source and destination) and the STAGED manifest is registered, by `task cli register`, the post-update registration and the post-rollback registration (all via `attemptStagedRegistration`); `unregister` is unchanged. Older staged versions are removed only after the outcome is `registered` or `deferred`; any other status (refused, skipped, unconfirmed, an unknown one of a newer SDK) keeps them. A source checkout's `dist-module` is registered as is (a rebuild keeps the version, a staged copy would go stale). `appModuleStaging.ts` imports only fs/path and `registerAfterUpdate.ts` (the updater bundle must stay under 500 KB and free of the task runtime).
- The module has no cwd: projects come from the shared registry (read at every request), routes take `?project=<id|name|alias>` (an absolute folder or an old `name~hex` slug answers 404 `no project matches "<value>"`, hint: use the id, name or alias, GET `/projects` lists them; for a name the registry keeps its suggestions and the module adds that hint). A registry that cannot be read and no `?project=` answers 500 with the registry message (not "no project is registered"). See Shared project registry (stage 2b-1).
- Registry upkeep moved to the project CLI (Decision #20): `task init`, `task projects add|remove|move|prune|list` and the Projects page forms/routes are gone (the task commands answer exit 1, text or `{error, hint}`, with the replacement: `project add "<dir>"`, `project remove`, `project paths move`, `project list`; `task init` suggests the cwd). `task projects summary` stays. Deleted from `task-service`: `initProject`, `addProject`, `relocateProject`, `removeRegisteredProject`, `pruneMissingProjects`, `registerProject`, `unregisterProject`, `registerInitializedProject`, `validateProjectPath`, `registryLock`, and the errors `InvalidProjectPathError`, `ProjectNotRegisteredError`, `ProjectAlreadyRegisteredError`.
- `deferred` from the SDK means only "the POST failed" (refused, reset, or no answer within 3 s) and the config dir exists, not proof that app-core is down; the message says "not running" regardless. If app-core is up, run `task cli register`.
- Testing against a real app-core: set `APP_CORE_PORT` and `APP_CORE_CONFIG_DIR`; without a free `APP_CORE_PORT` the SDK talks to the app-core running on 4850.

## app-module-task routes and pages

Routes (`/api/modules/task/...`, all take `?project=<id|name|alias>`, typed errors mapped in `errors.ts`): GET `/projects` `/summary` `/tasks` `/tasks/:id` `/tasks/:id/{history,children,ancestors,links}` `/tree` `/types`; POST `/tasks` `/tasks/:id/{status,labels,links,parent,type,meta}` `/types` `/tasks/delete/plan` `/tasks/delete` (needs `confirm: true`, else 400 with the plan); DELETE `/tasks/:id/{labels/:label,links,parent}` `/types/:name`. Every route that changes a task produces queue events (create, status, labels, links, parent, type, meta, `POST /tasks/delete`; see Queue events) and answers `undelivered` / `undeliveredText`; `/types`, `/projects*` and the delete preview emit nothing. Every view that fires one of these routes shows `undeliveredText` in a warning badge bound to the action's `resultKey` (Task page: one per form section; New task; Delete, under `plan`, saying how many events were not delivered); `manifest.test.ts` fails when a mutating action has no such badge. `POST /tasks/delete` failing partway (`PartialDeleteError` from `executeDelete`: `deletedCount`, `plannedCount`, `failedTaskId`, `events`) delivers the events of the tasks already deleted, then answers 500 with `deletedCount`, `plannedCount`, `partial: true`, `undelivered`; `task delete` does the same and exits 1 naming how many were deleted. A failure before the first deletion is the plain original error.

Pages: nav `/tasks` `/tree` `/projects` `/types` (global, or the only project); global `/tasks/new` `/tasks/delete` (project chosen in a select); per project, the project being a PATH segment `:project` (read as `$route.project`): `/tasks/p/:project` (list), `/tasks/p/:project/:id`, `/tasks/p/:project/:id/history`, `/tasks/p/:project/new`, `/tasks/p/:project/delete`, `/tree/p/:project`, `/types/p/:project`; dashboard widget. A global page and its per-project twin share one view file. Why a path segment: the shell's breadcrumb links each crumb to the current address up to that page, path params substituted, QUERY DROPPED (`navHelpers.ts` `routeChain`, `href: match.pathnameBase`; confirmed in a browser on app-core-cli 075 and the prebuilt 128). `?project=` on a page address is ignored.

- `:project` is the registry id (8 hex) of the project, never a folder nor a slug (`projectRef.ts`: `pageRef` / `apiRef` return the id; `retiredRefKind` recognises the two retired spellings, the absolute folder and the `<dir name>~<6 hex>` slug, to answer them precisely): the crumb prints the value cut at 16 characters, so a folder would read the same for every project of a workspace. `GET /projects` resolves it (the views feed it with `$route.project`); `hrefs.ts` builds every page address; the route layer never writes `?project=` in a page link. A retired spelling or an unknown project on a page shows `unknownProjectText` (it names the retired spelling).
- Old addresses that no longer exist (shell answers "Page not found"): `/tasks/:id`, `/tasks/:id/history`, `/new`, `/delete`, and `?project=` on any page (the page shows the global scope). Not kept: a redirect cannot be declared, and a second route set would double the pages.

Projects page (`/projects`, no `?project`): a READ-ONLY list of the registry projects. `GET /projects` gives `projectRows` (`id`, `name`, `path`, `openText`, `problemText` with its fix; no `registered`, no registry column), `openLinks`/`hasOpenLinks` (the table has no row click), `attentionText`, `registryProblem` (the shared registry could not be read: no project is listed, danger badge on the page and the widget; also in `GET /summary`), `noProjectsText`. The routes `POST /projects`, `/projects/relocate`, `/projects/remove` and their forms/yaml are deleted (404); `?page=projects` is gone. The view has one source and no action.

Global view (all registered projects): the widget (`GET /summary` without `?project`: open/total plus `projectRows`, one row per project with its tasks link or its error; nothing registered is a 200 with `noProjects`, not an error) and the Tasks page without `?project` while several projects are registered (`GET /tasks?allProjects=true`, Project column, rows link to the per-project address; `/projects` gives `globalQuery`, `allProjectsHref`, `unknownProjectText`). With `?project`, or a single registered project, the Tasks page is the per-project page. Per page without `?project` and with several projects:

| Page     | Scope                                                                                                                                                                                                                                                                                                                           |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tasks    | global list, Project column                                                                                                                                                                                                                                                                                                     |
| Tree     | `GET /tree?allProjects=true`: `groups`, one `Section` per project (title with count, link to its tree, its forest as a table, children indented by a label prefix; the scope text counts open tasks and names the closed parents kept above them; an empty project has an explicit empty message); unreadable ones in `warning` |

An address naming an unregistered project shows `unknownProjectText` on every per-project page. The detail and history pages (`GET /tasks/:id`, `/history`, `/links`) answer `?blank=true` like the list routes.

CLI parity (task-cli `GlobalViewCommands.ts`, parsing and output only over the same service reads; neither needs a project):

- `task list --all-projects [--all] [--json]`: text table PROJECT / ID / STATUS / TITLE; `--json` is the `listTasksAcrossProjects` answer as is (`tasks` tagged with `project`, `readableCount`, `unreadable`). Unreadable projects: warning on stderr in text mode (in `unreadable` in JSON), the others are still listed; exit 1 (`NoReadableProjectsError`, reasons + fix) only when none can be read; nothing registered is exit 0 with the `project add <dir>` hint. Fails with an actionable error when combined with `--follow`/`-f`, `--tree`, `--parent`, `-p` or `TASK_PROJECT` (same exit code and message shape, the message names the source; empty value = unset). `--project-dir` is refused like everywhere (exit 1), `TASK_PROJECT_DIR` gets its one `Ignored` line and `PROJECT_DIR` nothing (see the table above). `--config` / `TASK_CONFIG` select no project and are untouched.
- `task projects summary` takes no project, so a project flag or variable there contradicts nothing and is left alone.
- `task projects summary [--json]`: totals line, by-status line, one line per project (`open / total`, or `[unreadable: reason]`, not counted); `--json` is the `summarizeProjects` answer. Exit 1 only when none can be read.
- `--follow` is not implemented for `--all-projects`. It would be feasible with `diffSnapshot` keyed by project path + task id over `listTasksAcrossProjects`, but needs decisions first: cost (every project re-read every 500 ms), and what to print when a project becomes (un)readable or all fail mid-follow.
- JSON errors are `{"error": ..., "hint": ...}` for every command going through `errorOutput` / `failure` (no `hint` key without one). `set-type` has no separate hint: its message already lists the valid types. `task cli register` and `task plugins config` keep their own error shapes.

View conventions (app-core DSL, checked against the real shell):

- Mutations: Form + `$actions` + `onSubmit: $ctx.<action>`; the form data is the body and fills `{placeholders}` of the action URL. Placeholders are not URL-encoded: forms carry `projectParam` (encoded by the route) and use `?project={projectParam}`.
- The shell drops the answer of a failed action and discards ALL source answers when one source fails (blank page). Every request of a view therefore adds `inlineErrors=true`: the route answers a failure as 200 with `failed`, `httpStatus` and `errorText` (message, plus the hint unless it explains the JSON API), and the view shows `errorText` in a `variant: danger` Badge. Actions publish with `resultKey` per section, so the message sits next to its form.
- Zero registered projects: `/projects` answers `noProjects` + `noProjectsText` (the next step: `project add <dir>`, and `task cli migrate-data -p <name>` for old tasks) and `forms: null`; every page shows that text in an info Badge (a page with only a bound title and no badge renders blank). `forms` is also null when the selected project is unreadable (data split between the registry and the `.task`, invalid config). The widget shows its figures only `$if: summary.projectCount`, so a failure leaves the error alone. A registered project whose folder vanished stays readable (`exists: false`: its data is in the registry; `project paths move` fixes the path).
- Sources use `?{query}`. The shell keeps the last answer of a skipped source (reproduced: unknown project, Tasks menu, browser Back left the 6 rows of the global list), so no query may be empty: a page with several scopes (Tasks, Tree, Types) has ONE source fed by `scopeQuery` (project, global, or `blank=true`), the others (New, detail, history) by `projectQuery` (project or `blank=true`); a yaml test enforces it. `?blank=true` makes `/tasks`, `/tree`, `/types` answer `{blank: true}`, which replaces the previous scope's data (verified: global -> back -> unknown project leaves no rows).
- Forms (shell 2026.10.24-094): typing in the New task description, then waiting 12 s across `/api/modules` polls, kept the focus (`document.activeElement` is the textarea) and the value; the earlier "forms reset within seconds" does not reproduce. After a successful create the form is NOT cleared (the description stays): the reset after success needs dsl-ui >= 2026.10.24-177, not in a published app-core-cli yet (app-core's working tree has dsl 250).

## Queue events (current contract)

Operations in `task-service` return events; the caller hands them to the `EventSink`. The default sink (`queueEventSink.ts`) publishes each event through `@wadeck-app/queue-sdk` (`publishAndWait`) AFTER the change is saved, one event at a time, in order. The SDK is a dependency of `task-service` (the shared delivery adapter of both adapters; pinned version in its `package.json`, GitHub Packages, scope registry configured in the user `.npmrc`). It finds and authenticates the daemon, starts it with `queue start` when stopped, keeps the payload off the command line, and needs only `queue` on PATH. One publisher per sink (CLI: per command, created at the first delivery or declaration; module: per module lifetime, created at start by the declaration).

| Event                 | Emitted by (CLI, route)                                                                                                                                                  | Payload (plus `taskProjectName`, `taskProjectPath`, and `taskProjectId` when registered, on all)                                                 | Not fired when                                                                         |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| `onTaskCreated`       | `new`, `POST /tasks`                                                                                                                                                     | `taskId, status, description, parentId, type, labels`                                                                                            | later changes                                                                          |
| `onStatusChange`      | `set-status`, `POST /tasks/:id/status`                                                                                                                                   | `taskId, oldStatus, newStatus, status, type, labels`; `status` = `newStatus` (additive copy, so `payload.status` works like on the other events) | unchanged status (`TaskStore.updateStatus` throws `TaskConflictError`)                 |
| `onTaskLinked`        | `link`, `POST /tasks/:id/links`                                                                                                                                          | `taskId` (holder of the stored link), `linkType` (canonical), `targetId`                                                                         | link refused                                                                           |
| `onTaskUnlinked`      | `unlink`, `DELETE /tasks/:id/links`                                                                                                                                      | `taskId, linkType, targetId`                                                                                                                     | task deleted (see `removedLinkCount`)                                                  |
| `onTaskUnblocked`     | `set-status`, `POST /tasks/:id/status`: status change to a terminal status from a non-terminal one, once per task whose last open blocker it was, after `onStatusChange` | `taskId` (the unblocked task), `blockerId, status, type, labels`                                                                                 | another blocker still open                                                             |
| `onTaskTypeChanged`   | `set-type`, `POST /tasks/:id/type`                                                                                                                                       | `taskId, oldType, newType` (`oldType` absent for a task without type)                                                                            | same type (the store still rewrites the file), unknown type                            |
| `onTaskLabelAdded`    | `add-label`, `POST /tasks/:id/labels`                                                                                                                                    | `taskId, label`                                                                                                                                  | label already there                                                                    |
| `onTaskLabelRemoved`  | `remove-label`, `DELETE /tasks/:id/labels/:label`                                                                                                                        | `taskId, label`                                                                                                                                  | label absent                                                                           |
| `onTaskMetaChanged`   | `set-meta`, `POST /tasks/:id/meta`                                                                                                                                       | `taskId, key, oldValue, newValue` (`oldValue` absent for a new key; an existing empty value is `""`)                                             | same value                                                                             |
| `onTaskParentChanged` | `set-parent`, `remove-parent`, `POST` / `DELETE /tasks/:id/parent`                                                                                                       | `taskId, oldParentId, newParentId` (absent = root task)                                                                                          | same parent, cycle, `remove-parent` of a root task (refused)                           |
| `onTaskDeleted`       | `delete` (every selector, `--cascade-delete`), `POST /tasks/delete` with `confirm: true`: one per deleted task, after the deletion                                       | `taskId, description, status, parentId, orphanedChildIds, removedLinkCount`                                                                      | `--dry-run`, `POST /tasks/delete/plan`, unconfirmed or refused delete, nothing matched |

- Undefined fields (`parentId`, `type`, `oldType`, `oldValue`, `oldParentId`, `newParentId`) are absent from the JSON. Operations other than create/status/link return `{ task, events }` (`TaskChangeResult`; delete: `{ deletedCount, events }`); nothing fires when nothing changed.
- `onTaskDeleted` order: deepest first, so a cascade fires leaves before parents (each event then still has its `parentId`, `orphanedChildIds` is empty); tasks of the same depth keep the plan order. `removedLinkCount` counts links held by the tasks still present at that moment (a holder deleted later in the same plan counts). A task absent from the store at execution time gets no event. Events are delivered one by one after all deletions (a large `--all` costs one publish each). Filter syntax of a subscriber `when:` (queue `PayloadFilter`, on the envelope): `payload.newStatus=done` (dot path, `=`, string/number compare) or a JSONPath starting with `$` that must return a truthy value (`$.payload.newStatus`). `$.status == 'x'` is NOT valid (no operators in the JSONPath form; the status is under `payload`).
- cwd: each publish passes `{ cwd: payload.taskProjectPath }` (= `ctx.project.path`: the main path of a registered project); queue finds `<project>/.queue/subscribers.yml` by walking up from it. A payload without a non-empty string `taskProjectPath` is undelivered (`dropped`) with an explicit reason, never published with the current cwd: a virtual project (payload with `taskProjectId`, no path) gets a reason naming it and how to fix it (`project paths add`), anything else is reported as a producer bug.
- Outcome mapping (SDK `PublishResult.status`):

    | SDK status                                    | Task result                                                                            | Replay text                                                                                                      |
    | --------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
    | `queued`, `dispatched`                        | delivered                                                                              | none                                                                                                             |
    | `dropped` (not recorded)                      | undelivered, `status: 'dropped'`, SDK `reason` (or an explicit "no reason" text)       | `cd '<taskProjectPath>' && queue push <event> '<json>'` (POSIX quotes; no eventId exists)                        |
    | `unknown` (may be recorded)                   | undelivered, `status: 'unknown'`, reason says the event MAY be recorded; never retried | check `queue history` from the project dir; if listed `queue replay <eventId>`; if absent the `queue push` above |
    | publisher throws (SDK promises it never does) | same as `unknown`                                                                      | same as `unknown`                                                                                                |

- Failure never fails the command or the route: stderr line, error line in `<config dir>/logs/*.ndjson` (`task cli logs`; the replay text, hence the payload JSON, is in the file), module answers carry `undelivered` (each with `status`) / `undeliveredText`. The SDK `onError` (kind, message, event, outcome) is written to the same log at level `warn`, not to stderr (the SDK is created `silent`).
- Shutdown: `EventSink.flush()` (optional) waits for the pushes in flight. The CLI calls it at the end of `runTaskCommand`, before `process.exit`; the module returns `{ flush }` from its backend and `lifecycle.teardown` (`teardown.ts`) calls it.
- Tests inject the publisher (`createQueueEventSink({ publisher | createPublisher })`); `queueEventSink.integration.test.ts` runs the real SDK against `startFakeQueueDaemon()` from `@wadeck-app/queue-sdk/testing` (free port, temp config dir; `pushes()`, `respondNext`, `resetNext`, `resetNextRegistration`) with no `queue` on PATH. The real queue daemon is never started by a test.
- Safety net (also registry isolation, see Shared project registry): every `vitest.setup.ts` (task-service, task-cli, app-module-task) sets `QUEUE_SDK_OFF=1` (SDK sends nothing, answers `dropped`; inherited by spawned CLI/app-core processes), so a default sink can never reach a real queue. The SDK honours it even with an explicit `configDir`: the integration test deletes it for its own duration. Never set it outside tests/dev runs (events would be silently dropped; the SDK announces it once).

Event declaration (queue event catalog, SDK >= 2026.10.24-190, protocol 1.1.0; older SDKs and daemons keep working):

- Single source of truth: `queueEventDeclarations` (`task-service/queueEventDeclarations.ts`, source `task`): name, description (<= 500 chars: when it fires, what does NOT), JSON Schema, example, `correlationKey: 'payload.taskId'`. Only `onTaskDeleted` is `terminal: true, outcome: 'info'` (SDK `Declaring your events`: terminal = the event ends the entity it is about; nothing more happens to that `taskId`, and a deletion is neither success nor failure). `onStatusChange` to `done` ends nothing by itself. Tests tie it to the code: one declaration per `TaskEvent` name, examples fit their schema, the payloads really produced by every operation above fit the schemas (`jsonSchemaCheck.ts`, a minimal checker of the subset used, no dependency), daemon limits. Adding or changing an event means editing that file; its hash (`queueEventDeclarationsHash`) is what triggers a new CLI declaration.
- `declareTaskEvents(publisher)` / `sink.declareEvents()`: never throws; outcome `registered | rejected | unsupported | dropped | unknown`. Task log (`task cli logs`): `rejected` error (with the `problems` paths), `unsupported` info (old daemon: update queue-cli), `dropped` / `unknown` warn; stderr only for `rejected` (a bug in our declaration). `registered` is quiet. `flush()` waits for a declaration in flight.
- Module: declared once per start (`registerTaskRoutes`), fire and forget; only with the default sink (an injected `eventSink` has no publisher).
- CLI: declared lazily before the FIRST event delivered by a process, when `<config dir>/queue-events.json` (`{ hash, taskVersion, declaredAt }`) does not hold the current hash (`QueueEventsDeclaration.ts`). Why lazy: the CLI has no start hook, the queue is about to be contacted anyway, and `task-updater.cjs` must stay free of the SDK (it never declares). The marker is written only after `registered`; any other outcome retries at the next event (an old daemon costs one extra request per delivering process until updated). A command without event never declares. Never fails the command. `task cli declare-events [--json]` forces it (exit 1 with the next step otherwise): use it after updating queue-cli or if the queue lost its catalog (the marker cannot know).
- Tests: `daemon.registrations()`, `respondNextRegistration` and `resetNextRegistration(times = 1)` of the SDK fake (SDK >= 2026.10.24-191): one reset still ends `registered` (the SDK retries a registration once, it is idempotent), two in a row end `unknown`. A scripted publisher remains only for a `dropped` without reason and a publisher that throws. `QUEUE_SDK_OFF` also switches `registerEvents` off (`dropped`, reason names the variable): tested in each package's safety net. A test that starts the default module backend must set `XDG_CONFIG_HOME` (the declaration logs in the task config dir).

Decided:

- `onStatusChange` gained `status` (= `newStatus`); `newStatus` stays, so no subscriber breaks.
- `taskFile` is NOT in any payload: the task data path moved with the shared project registry (and a virtual project has no folder to resolve it against).
- No comment event: tasks have no comments. No event for type add/remove: they edit the project config, not a task.
- A changed declaration re-declares by itself (marker hash, test in `TaskIndex.events.test.ts`).

Open decisions (the owner's, nothing implemented):

- Replay text for cmd.exe / PowerShell, or a `--cwd` option in `queue push` (queue repo) to drop the `cd`.
