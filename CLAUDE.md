## Packages

| Package           | Role                                                                                                             |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| `task-core`       | Storage: `TaskStore`, config loading, domain errors.                                                             |
| `task-service`    | Use cases shared by the CLI and the app-module. Pure: no console, no `process.exit`; returns results and events. |
| `task-cli`        | `task` binary: arg parsing and output over task-service, updater, app-core registration.                         |
| `app-module-task` | app-core module (id `task`): routes `/api/modules/task/*` and dsl-views over task-service.                       |

## Dependency direction

`task-core` <- `task-service` <- `task-cli` and `app-module-task`. The two adapters never import each other, and `task-service` knows no CLI, HTTP or app-core library, never prints or exits. `npm run test:architecture` (`architecture/`, part of `npm test`) enforces it on imports, `package.json` dependencies and source patterns.

Shared rules live in `task-service`, adapters only parse input and format output: `describeError` (error kind, message, hint; CLI maps to stderr, module to HTTP status), `selectDeleteTargets` / `describeDeleteEffects`, `openTaskContext`, `getTaskLogDir`, `countTasksByStatus`, `showTaskWithRelations`, the projects registry (`listRegisteredProjects`, `unregisterProject`, `inspectRegisteredProjects`, `pruneMissingProjects`, `registerInitializedProject`: shared by `task init` and `task projects add`; `initProject`, `addProject`, `relocateProject`, `removeRegisteredProject`), and the cross-project reads `summarizeProjects` / `listTasksAcrossProjects` (per-project figures and tasks tagged with their project; unreadable projects reported, `NoReadableProjectsError` when none can be read; used by the app-module and by the CLI, see CLI parity below).

## app-core registration

- `task cli register [--json]` / `task cli unregister [--json]`; `task cli update` registers by itself when the shipped app-module version changed. Task has no daemon, so nothing registers at start.
- Exit 0 when app-core took it or is absent/not running (deferred, skipped); exit 1 with app-core's reason when it refuses.
- Manifest: `app-module/manifest.json` next to `task.cjs`, else `packages/app-module-task/dist-module/manifest.json` (source checkout: `BUNDLE_VERSION=0.0.0-local npm run bundle --workspace=packages/app-module-task`). Neither found is an error naming both paths.
- Staging: app-core stores the PATH of a manifest, and npm replaces the package folder on update (and removes it on uninstall). An installed module (`<pkg>/app-module/`) is therefore copied to `<config dir>/app-module/<manifest version>/` (`appModuleStaging.ts`: temp dir then rename, kept if already complete, error naming source and destination) and the STAGED manifest is registered, by `task cli register`, the post-update registration and the post-rollback registration (all via `attemptStagedRegistration`); `unregister` is unchanged. Older staged versions are removed only after the outcome is `registered` or `deferred`; any other status (refused, skipped, an unknown one of a newer SDK) keeps them. A source checkout's `dist-module` is registered as is (a rebuild keeps the version, a staged copy would go stale). `appModuleStaging.ts` imports only fs/path and `registerAfterUpdate.ts` (the updater bundle must stay under 500 KB and free of the task runtime).
- The module has no cwd: projects come from `<config dir>/projects.json` (written by `task init` and `task projects add`), routes take `?project=<dir>`.
- Registry upkeep, no project needed: `task projects add [dir] [--json]` (default cwd; needs a `.task` there, else error with the `task init` hint; idempotent: `Already registered`; registers projects initialized before the registry existed), `task projects list [--json]` (path, `[ok]` / `[missing]` / `[not initialized]` / `[unreadable: reason]`), `task projects remove <dir>` (relative to cwd, case-insensitive on Windows; unknown dir is an error), `task projects prune [--dry-run]` (drops entries whose directory is gone; a directory that cannot be stat'ed, e.g. permissions, is kept).
- Registry edits (`task-service`; the CLI and the module are thin adapters): `initProject(dir, configDir)` (= `task init`: `.task/tasks` + `config.yml`, idempotent, creates missing parents, a registry failure is returned in `registration`, not thrown), `addProject(configDir, {path, mode: 'register' | 'init', createDirectory?})` (UI add), `relocateProject(configDir, old, new)` (= `task projects move <old-dir> <new-dir> [--json]`: replaces the entry in place under the registry lock; the new dir must exist and hold a `.task`, the old one may be gone; not registered -> `ProjectNotRegisteredError` 404, new already registered -> `ProjectAlreadyRegisteredError` 409, bad path -> `InvalidProjectPathError` 400, nothing written), `removeRegisteredProject` (= `task projects remove`). Removing and moving touch the registry ONLY: a project's `.task` and directory are never deleted or moved. `validateProjectPath` refuses non-absolute, `.`/`..` segments, NUL, surrounding whitespace, Windows `\x` and `C:x`; it normalises with `path.resolve`.
- UI add of a missing directory: refused with an actionable error unless mode is `init` AND `createDirectory: true` AND the parent exists (one level created): a typo in a path must not leave a stray directory tree. `createDirectory` with `register` is an error.
- Threat model of the UI add: the web UI can init a task project in any directory app-core can write to, which equals `task init` for the same user (app-core listens on 127.0.0.1 only). No path is ever executed; the registry is never followed to delete data.
- `deferred` from the SDK means only "the POST failed" (refused, reset, or no answer within 3 s) and the config dir exists, not proof that app-core is down; the message says "not running" regardless. If app-core is up, run `task cli register`.
- Testing against a real app-core: set `APP_CORE_PORT` and `APP_CORE_CONFIG_DIR`; without a free `APP_CORE_PORT` the SDK talks to the app-core running on 4850.

## app-module-task routes and pages

Routes (`/api/modules/task/...`, all take `?project=<dir>`, typed errors mapped in `errors.ts`): GET `/projects` `/summary` `/tasks` `/tasks/:id` `/tasks/:id/{history,children,ancestors,links}` `/tree` `/types`; POST `/tasks` `/tasks/:id/{status,labels,links,parent,type,meta}` `/types` `/tasks/delete/plan` `/tasks/delete` (needs `confirm: true`, else 400 with the plan); DELETE `/tasks/:id/{labels/:label,links,parent}` `/types/:name`. Every route that changes a task produces queue events (create, status, labels, links, parent, type, meta, `POST /tasks/delete`; see Queue events) and answers `undelivered` / `undeliveredText`; `/types`, `/projects*` and the delete preview emit nothing. Every view that fires one of these routes shows `undeliveredText` in a warning badge bound to the action's `resultKey` (Task page: one per form section; New task; Delete, under `plan`, saying how many events were not delivered); `manifest.test.ts` fails when a mutating action has no such badge. `POST /tasks/delete` failing partway (`PartialDeleteError` from `executeDelete`: `deletedCount`, `plannedCount`, `failedTaskId`, `events`) delivers the events of the tasks already deleted, then answers 500 with `deletedCount`, `plannedCount`, `partial: true`, `undelivered`; `task delete` does the same and exits 1 naming how many were deleted. A failure before the first deletion is the plain original error.

Pages: nav `/tasks` `/tree` `/projects` `/types` (global, or the only project); global `/tasks/new` `/tasks/delete` (project chosen in a select); per project, the project being a PATH segment `:project` (read as `$route.project`): `/tasks/p/:project` (list), `/tasks/p/:project/:id`, `/tasks/p/:project/:id/history`, `/tasks/p/:project/new`, `/tasks/p/:project/delete`, `/tree/p/:project`, `/types/p/:project`; dashboard widget. A global page and its per-project twin share one view file. Why a path segment: the shell's breadcrumb links each crumb to the current address up to that page, path params substituted, QUERY DROPPED (`navHelpers.ts` `routeChain`, `href: match.pathnameBase`; confirmed in a browser on app-core-cli 075 and the prebuilt 128). `?project=` on a page address is ignored.

- `:project` is a slug (`projectRef.ts`: `<dir name>~<6 hex of the dir>`), not the directory: the crumb prints the value cut at 16 characters, so a directory would read the same for every project of a workspace. `findProjectByRef` resolves a slug OR an absolute directory (one resolution, in `GET /projects`, which the views feed with `$route.project`); the API routes keep `?project=<dir>`. `hrefs.ts` builds every page address; the route layer never writes `?project=` in a page link.
- Old addresses that no longer exist (shell answers "Page not found"): `/tasks/:id`, `/tasks/:id/history`, `/new`, `/delete`, and `?project=` on any page (the page shows the global scope). Not kept: a redirect cannot be declared, and a second route set would double the pages.

Projects page (`/projects`, registry management, no `?project`): POST `/projects` `{path, mode, createDirectory?}` (201 when something was added/initialised, else 200), POST `/projects/relocate` `{from, to}`, POST `/projects/remove` `{path, confirm: true}` (without `confirm: true` 400 saying what would happen, nothing removed; an unknown project is 404 first). Answers carry `messageText` and the refreshed `projects`; the views use `?inlineErrors=true`. GET `/projects` adds `projectForm`, `modeOptions`, `manageRows` (each row carries what the Edit/Remove steps send: `from`, `to`, `path`, `confirm: true`, `editPrompt`, `confirmText`, `confirmLabel`, `needsRepair`, `problemText`), `openLinks`/`hasOpenLinks`, `attentionText`. The table has no row click (buttons fire it): readable projects are linked by `openLinks` buttons. Checked in a real browser (isolated app-core): register, init (with and without `createDirectory`), refusal keeps typed values, Edit after moving the dir, Remove with confirm, vanished project. Known: after a success the add form keeps its values (button disabled until a change) and old success badges stay until reload.

Global view (all registered projects): the widget (`GET /summary` without `?project`: open/total plus `projectRows`, one row per project with its tasks link or its error; nothing registered is a 200 with `noProjects`, not an error) and the Tasks page without `?project` while several projects are registered (`GET /tasks?allProjects=true`, Project column, rows link to the per-project address; `/projects` gives `globalQuery`, `allProjectsHref`, `unknownProjectText`). With `?project`, or a single registered project, the Tasks page is the per-project page. Per page without `?project` and with several projects:

CLI parity (task-cli `GlobalViewCommands.ts`, parsing and output only over the same service reads; neither needs a project):

- `task list --all-projects [--all] [--json]`: text table PROJECT / ID / STATUS / TITLE; `--json` is the `listTasksAcrossProjects` answer as is (`tasks` tagged with `project`, `readableCount`, `unreadable`). Unreadable projects: warning on stderr in text mode (in `unreadable` in JSON), the others are still listed; exit 1 (`NoReadableProjectsError`, reasons + fix) only when none can be read; nothing registered is exit 0 with the `task init` hint. Fails with an actionable error when combined with `--follow`/`-f`, `--tree`, `--parent`, `--project-dir` or `TASK_PROJECT_DIR` (same exit code and message shape, the message names the source; empty value = unset). `PROJECT_DIR` is generic (a parent tool may set it ambiently), so it is not an error: one `Note: ... is ignored` line on stderr, in `--json` too (stdout stays the pure answer). `--config` / `TASK_CONFIG` select no project and are untouched.
- `task projects add` refuses `--project-dir` (it would be swallowed and the cwd registered); the other `task projects` commands take no project, so a project flag or variable there contradicts nothing and is left alone.
- `task projects summary [--json]`: totals line, by-status line, one line per project (`open / total`, or `[unreadable: reason]`, not counted); `--json` is the `summarizeProjects` answer. Exit 1 only when none can be read.
- `--follow` is not implemented for `--all-projects`. It would be feasible with `diffSnapshot` keyed by project path + task id over `listTasksAcrossProjects`, but needs decisions first: cost (every project re-read every 500 ms), and what to print when a project becomes (un)readable or all fail mid-follow.
- JSON errors are `{"error": ..., "hint": ...}` for every command going through `errorOutput` / `failure` (no `hint` key without one). `set-type` has no separate hint: its message already lists the valid types. `task cli register` and `task plugins config` keep their own error shapes.

View conventions (app-core DSL, checked against the real shell):

- Mutations: Form + `$actions` + `onSubmit: $ctx.<action>`; the form data is the body and fills `{placeholders}` of the action URL. Placeholders are not URL-encoded: forms carry `projectParam` (encoded by the route) and use `?project={projectParam}`.
- The shell drops the answer of a failed action and discards ALL source answers when one source fails (blank page). Every request of a view therefore adds `inlineErrors=true`: the route answers a failure as 200 with `failed`, `httpStatus` and `errorText` (message, plus the hint unless it explains the JSON API), and the view shows `errorText` in a `variant: danger` Badge. Actions publish with `resultKey` per section, so the message sits next to its form.
- Zero registered projects: `/projects` answers `noProjects` + `noProjectsText` (the next step: `task init` / `task projects add <dir>`) and `forms: null`; every page shows that text in an info Badge (a page with only a bound title and no badge renders blank). `forms` is also null when the selected project is unreadable. The widget shows its figures only `$if: summary.projectCount`, so a failure leaves the error alone. A registered directory that vanished is told apart (`exists: false`; fix: `task projects remove <dir>` / `prune`).
- Sources use `?{query}`. The shell keeps the last answer of a skipped source (reproduced: unknown project, Tasks menu, browser Back left the 6 rows of the global list), so no query may be empty: a page with several scopes (Tasks, Tree, Types) has ONE source fed by `scopeQuery` (project, global, or `blank=true`), the others (New, detail, history) by `projectQuery` (project or `blank=true`); a yaml test enforces it. `?blank=true` makes `/tasks`, `/tree`, `/types` answer `{blank: true}`, which replaces the previous scope's data (verified: global -> back -> unknown project leaves no rows).
- In the dev shell, forms were observed to reset (element refs change, typed values vanish) within seconds of page load, next to repeated `/api/modules` requests (cause not verified): drive forms in one fast command sequence with semantic locators.
- The shell reloads on a URL change only the sources naming a `$urlParam.*`/`$route.*`: a source waiting for `projects` also takes `reload: $urlParam.reload` (always empty, so never sent), else filter links and project choice leave the page stale or blank until F5.
- Installed shell (app-core-cli 2026.10.18-035, dsl-ui 2026.10.18-101): a YAML DataTable column keeps only `key`/`field` and `label` (`normalizeColumn`); `mono`, `muted`, `width`, `truncate`, `nowrap`, `format`, `sortable`, `badge` are dropped without a message. Working: `type: actions` columns (`items`: label, action, variant, condition), `navigateTo`, `onRowClick`, `onAction`, `expansion`, `selectable`/`batchActions`, `fontMono`, `emptyMessage`. No row styling or grouping exists, installed or in dsl-ui 123 (app-core working tree). dsl-ui >= 2026.10.20 (published app-core-cli 2026.10.22-065 and later) honours the column options and substitutes `{key}` of the clicked row in row action URLs. Columns of short codes carry `nowrap: true` (test-enforced) so that an upgrade fixes the one-character-per-line wrapping (`break-all`) without a change; routes give display texts (`titleText`, `created`, `time`, `projectText`). A `PageHeader` with `headerActions` drops its `subtitle`.
- A `FieldSelect` showing its first option while the form holds `''` makes picking that option a no-change (Save stays off): selects that act on an existing item (remove label/type) need a `placeholder`.
- `FieldSelect` crashes the page until its options load: guard with `$if`. `$if` has no negation and `[]` is truthy: routes give boolean flags (`hasLabels`, `noTypes`...).
- A row action WITHOUT url stores the clicked row under its `resultKey` (`$ctx.<key>`): used by the Types Remove button (pick the row, then a confirm form takes it as `initialData`; the removal answer shares the key and clears the confirm). A row action WITH url requests `{id}` unsubstituted in the installed shell (404 on `/tasks/%7Bid%7D`, verified). A button in a row also fires the row click (installed and 123): a table with row actions has no `navigateTo`.
- A form cannot cascade: `FieldSelect` has no dependent options, no component publishes `$outputs`, sources read only `$ctx`/`$vars`/`$source`/`$urlParam`/`$route` (no `$form`). Pick-then-confirm (above) replaces a dependent select.
- A view cannot loop: a block repeated per project (Tree) is a list of DSL nodes built by the route (`dslNodes.ts`: `Section`, `ButtonLink`, `DataTable`; a text starting with `$` is made literal) rendered by `ExtensionSlot` `items`.
- Persisted state: none for views (no `$persist`, `$vars` live in memory, nav links drop `?project`, shell localStorage is internal). The last created-in project is kept by the module in `ctx.dataDir/last-project.json`; a corrupt file is reported (`lastProjectProblem`), a failed write is a warning on the create answer.
- Narrow screens (390px): the table wrapping is the `nowrap` point above; `PageHeader` has no wrap or gap (title and actions touch, actions stack), and the installed navbar overflows: both are app-core fixes.
- Breadcrumb: minimum shell for it is app-core-cli >= 2026.10.19-063 (062 only behind a dev A/B test); older shells have no back navigation on New/Delete/History. Rule: no back link anywhere (see Pages above); the project lives in the path so every crumb keeps it. Trail read in a browser: `Task > Tasks > Project <slug> > <id capitalised> > History` (the label "Task" of `/tasks/p/:project/:id` and the module prefix of "Task history" are dropped by the shell), `Task > Tasks > Project <slug> > New task`, `Task > Tree > Project <slug>`, `Task > Tasks > New task` (global). A yaml test replays the shell's trail algorithm on the manifest. Known: the crumb of a vanished or unknown project is still shown (and links to a page saying so); per-project pages highlight their section in the menu; two projects with the same directory name read `alpha`/`alpha` in lists and selects (slug differs, label does not).
- `GET /projects?page=projects` (both sources of the Projects page) makes `noProjectsText` point at the form below instead of at the Projects page.
- Not expressible: URL-writing filters, TreeView navigation (installed; `CompactSelect`/`SearchBar` `urlParam` exist in dsl-ui >= 2026.10.19).
- Test against a real shell: `app-core-cli dev packages/app-module-task --watch` with `APP_CORE_PORT`, `XDG_CONFIG_HOME` and a PATH without `queue` (events end up undelivered instead of pushed).

## Queue events (current contract)

Operations in `task-service` return events; the caller hands them to the `EventSink`. The default sink (`queueEventSink.ts`) publishes each event through `@wadeck-app/queue-sdk` (`publishAndWait`) AFTER the change is saved, one event at a time, in order. The SDK is a dependency of `task-service` (the shared delivery adapter of both adapters; pinned version in its `package.json`, GitHub Packages, scope registry configured in the user `.npmrc`). It finds and authenticates the daemon, starts it with `queue start` when stopped, keeps the payload off the command line, and needs only `queue` on PATH. One publisher per sink (CLI: per command, created at the first delivery or declaration; module: per module lifetime, created at start by the declaration).

| Event                 | Emitted by (CLI, route)                                                                                                                                                  | Payload (plus `taskProjectName`, `taskProjectPath` on all)                                                                                       | Not fired when                                                                         |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| `onTaskCreated`       | `new`, `POST /tasks`                                                                                                                                                     | `taskId, status, description, parentId, type, labels`                                                                                            | later changes                                                                          |
| `onStatusChange`      | `set-status`, `POST /tasks/:id/status`                                                                                                                                   | `taskId, oldStatus, newStatus, status, type, labels`; `status` = `newStatus` (additive copy, so `payload.status` works like on the other events) | unchanged status (`TaskStore.updateStatus` throws `TaskConflictError`)                 |
| `onTaskLinked`        | `link`, `POST /tasks/:id/links`                                                                                                                                          | `taskId` (holder of the stored link), `linkType` (canonical), `targetId`                                                                         | link refused                                                                           |
| `onTaskUnlinked`      | `unlink`, `DELETE /tasks/:id/links`                                                                                                                                      | `taskId, linkType, targetId`                                                                                                                     | task deleted (see `removedLinkCount`)                                                  |
| `onTaskUnblocked`     | `set-status`, `POST /tasks/:id/status`: status change to a terminal status from a non-terminal one, once per task whose last open blocker it was, after `onStatusChange` | `taskId` (the unblocked task), `blockerId, status, type, labels`                                                                                 | another blocker still open                                                             |
| `onTaskTypeChanged`   | `set-type`, `POST /tasks/:id/type`                                                                                                                                       | `taskId, oldType, newType` (`oldType` absent for a task without type)                                                                            | same type (the store still rewrites the file), unknown type                            |
| `onTaskLabelAdded`    | `add-label`, `POST /tasks/:id/labels`                                                                                                                                    | `taskId, label`                                                                                                                                  | label already there                                                                    |
| `onTaskLabelRemoved`  | `remove-label`, `DELETE /tasks/:id/labels/:label`                                                                                                                        | `taskId, label`                                                                                                                                  | label absent                                                                           |
| `onTaskMetaChanged`   | `set-meta`, `POST /tasks/:id/meta`                                                                                                                                       | `taskId, key, oldValue, newValue` (`oldValue` absent for a new key; an existing empty value is `""`)                                             | same value                                                                             |
| `onTaskParentChanged` | `set-parent`, `remove-parent`, `POST` / `DELETE /tasks/:id/parent`                                                                                                       | `taskId, oldParentId, newParentId` (absent = root task)                                                                                          | same parent, cycle, `remove-parent` of a root task (refused)                           |
| `onTaskDeleted`       | `delete` (every selector, `--cascade-delete`), `POST /tasks/delete` with `confirm: true`: one per deleted task, after the deletion                                       | `taskId, description, status, parentId, orphanedChildIds, removedLinkCount`                                                                      | `--dry-run`, `POST /tasks/delete/plan`, unconfirmed or refused delete, nothing matched |

- Undefined fields (`parentId`, `type`, `oldType`, `oldValue`, `oldParentId`, `newParentId`) are absent from the JSON. Operations other than create/status/link return `{ task, events }` (`TaskChangeResult`; delete: `{ deletedCount, events }`); nothing fires when nothing changed.
- `onTaskDeleted` order: deepest first, so a cascade fires leaves before parents (each event then still has its `parentId`, `orphanedChildIds` is empty); tasks of the same depth keep the plan order. `removedLinkCount` counts links held by the tasks still present at that moment (a holder deleted later in the same plan counts). A task absent from the store at execution time gets no event. Events are delivered one by one after all deletions (a large `--all` costs one publish each). Filter syntax of a subscriber `when:` (queue `PayloadFilter`, on the envelope): `payload.newStatus=done` (dot path, `=`, string/number compare) or a JSONPath starting with `$` that must return a truthy value (`$.payload.newStatus`). `$.status == 'x'` is NOT valid (no operators in the JSONPath form; the status is under `payload`).
- cwd: each publish passes `{ cwd: payload.taskProjectPath }` (= `ctx.project.path`: the CLI project dir incl. `--project-dir` / `TASK_PROJECT_DIR` / `PROJECT_DIR`, the module's `?project`); queue finds `<project>/.queue/subscribers.yml` by walking up from it. A payload without a non-empty string `taskProjectPath` is undelivered (`dropped`) with an explicit reason, never published with the current cwd.
- Outcome mapping (SDK `PublishResult.status`):

    | SDK status                                    | Task result                                                                            | Replay text                                                                                                      |
    | --------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
    | `queued`, `dispatched`                        | delivered                                                                              | none                                                                                                             |
    | `dropped` (not recorded)                      | undelivered, `status: 'dropped'`, SDK `reason` (or an explicit "no reason" text)       | `cd '<taskProjectPath>' && queue push <event> '<json>'` (POSIX quotes; no eventId exists)                        |
    | `unknown` (may be recorded)                   | undelivered, `status: 'unknown'`, reason says the event MAY be recorded; never retried | check `queue history` from the project dir; if listed `queue replay <eventId>`; if absent the `queue push` above |
    | publisher throws (SDK promises it never does) | same as `unknown`                                                                      | same as `unknown`                                                                                                |

- Failure never fails the command or the route: stderr line, error line in `<config dir>/logs/*.ndjson` (`task cli logs`; the replay text, hence the payload JSON, is in the file), module answers carry `undelivered` (each with `status`) / `undeliveredText`. The SDK `onError` (kind, message, event, outcome) is written to the same log at level `warn`, not to stderr (the SDK is created `silent`).
- Shutdown: `EventSink.flush()` (optional) waits for the pushes in flight. The CLI calls it at the end of `runTaskCommand`, before `process.exit`; the module returns `{ flush }` from its backend and `lifecycle.teardown` (`teardown.ts`) calls it.
- Tests inject the publisher (`createQueueEventSink({ publisher | createPublisher })`); `queueEventSink.integration.test.ts` runs the real SDK against `startFakeQueueDaemon()` from `@wadeck-app/queue-sdk/testing` (free port, temp config dir; `pushes()`, `respondNext`, `resetNext`) with no `queue` on PATH. The real queue daemon is never started by a test.
- Safety net: every `vitest.setup.ts` (task-service, task-cli, app-module-task) sets `QUEUE_SDK_OFF=1` (SDK sends nothing, answers `dropped`; inherited by spawned CLI/app-core processes), so a default sink can never reach a real queue. The SDK honours it even with an explicit `configDir`: the integration test deletes it for its own duration. Never set it outside tests/dev runs (events would be silently dropped; the SDK announces it once).

Event declaration (queue event catalog, SDK >= 2026.10.24-190, protocol 1.1.0; older SDKs and daemons keep working):

- Single source of truth: `queueEventDeclarations` (`task-service/queueEventDeclarations.ts`, source `task`): name, description (<= 500 chars: when it fires, what does NOT), JSON Schema, example, `correlationKey: 'payload.taskId'`. Only `onTaskDeleted` is `terminal: true, outcome: 'info'` (SDK `Declaring your events`: terminal = the event ends the entity it is about; nothing more happens to that `taskId`, and a deletion is neither success nor failure). `onStatusChange` to `done` ends nothing by itself. Tests tie it to the code: one declaration per `TaskEvent` name, examples fit their schema, the payloads really produced by every operation above fit the schemas (`jsonSchemaCheck.ts`, a minimal checker of the subset used, no dependency), daemon limits. Adding or changing an event means editing that file; its hash (`queueEventDeclarationsHash`) is what triggers a new CLI declaration.
- `declareTaskEvents(publisher)` / `sink.declareEvents()`: never throws; outcome `registered | rejected | unsupported | dropped | unknown`. Task log (`task cli logs`): `rejected` error (with the `problems` paths), `unsupported` info (old daemon: update queue-cli), `dropped` / `unknown` warn; stderr only for `rejected` (a bug in our declaration). `registered` is quiet. `flush()` waits for a declaration in flight.
- Module: declared once per start (`registerTaskRoutes`), fire and forget; only with the default sink (an injected `eventSink` has no publisher).
- CLI: declared lazily before the FIRST event delivered by a process, when `<config dir>/queue-events.json` (`{ hash, taskVersion, declaredAt }`) does not hold the current hash (`QueueEventsDeclaration.ts`). Why lazy: the CLI has no start hook, the queue is about to be contacted anyway, and `task-updater.cjs` must stay free of the SDK (it never declares). The marker is written only after `registered`; any other outcome retries at the next event (an old daemon costs one extra request per delivering process until updated). A command without event never declares. Never fails the command. `task cli declare-events [--json]` forces it (exit 1 with the next step otherwise): use it after updating queue-cli or if the queue lost its catalog (the marker cannot know).
- Tests: `daemon.registrations()` and `respondNextRegistration` of the SDK fake; the fake cannot reset a registration, so `unknown` is tested with a scripted publisher. `QUEUE_SDK_OFF` also switches `registerEvents` off (`dropped`, reason names the variable): tested in each package's safety net. A test that starts the default module backend must set `XDG_CONFIG_HOME` (the declaration logs in the task config dir).

Decided:

- `onStatusChange` gained `status` (= `newStatus`); `newStatus` stays, so no subscriber breaks.
- `taskFile` is NOT in any payload: the task data path will move with the shared project registry.
- No comment event: tasks have no comments. No event for type add/remove: they edit the project config, not a task.
- A changed declaration re-declares by itself (marker hash, test in `TaskIndex.events.test.ts`).
