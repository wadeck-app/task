## Packages

| Package           | Role                                                                                                                |
| ----------------- | ------------------------------------------------------------------------------------------------------------------- |
| `task-core`       | Storage: `TaskStore`, config loading, domain errors.                                                                |
| `task-service`    | Use cases shared by the CLI and the app-module. Pure: no console, no `process.exit`; returns results and events.    |
| `task-cli`        | `task` binary: arg parsing and output over task-service, updater, app-core registration.                            |
| `app-module-task` | app-core module (id `task`): routes `/api/modules/task/*` and dsl-views over task-service.                          |
| `dsl-lib-task`    | Browser components (React) the module ships as `task:<Name>`; no storage, service or Node API. See Task components. |

## Dependency direction

`task-core` <- `task-service` <- `task-cli` and `app-module-task`; `app-module-task` -> `dsl-lib-task` (loaded by its `src/dsl-components`, props only). The two adapters never import each other, and `task-service` knows no CLI, HTTP or app-core library, never prints or exits. `npm run test:architecture` (`architecture/`, part of `npm test`) enforces it on imports, `package.json` dependencies and source patterns.

`@wadeck-app/project-sdk` ("latest", lockfile pins it; zero dependencies) is imported by `task-service` only; the architecture test forbids it in the sources of the adapters and `task-core` (their tests may use its mutations for fixtures). Shared rules live in `task-service` (`resolveProject`, `resolveProjectReference`, `listKnownProjects`, `describeError` for the SDK errors), adapters only parse input and format output: `describeError` (error kind, message, hint; CLI maps to stderr, module to HTTP status), `selectDeleteTargets` / `describeDeleteEffects`, `openTaskContext`, `getTaskLogDir`, `countTasksByStatus`, `showTaskWithRelations`, the storage (`storage.ts`: `registryStorage`; `openResolvedProject`; `loadTaskConfig`), the per-project health (`inspectRegisteredProjects`), `listStatuses` (the valid statuses with `default` / `terminal`, from the same merged config as `setStatus`), and the cross-project reads `summarizeProjects` / `listTasksAcrossProjects` (per-project figures and tasks tagged with their project; unreadable projects reported, `NoReadableProjectsError` when none can be read; used by the app-module and by the CLI, see CLI parity below).

## Shared project registry

The registry of the `project` CLI (`@wadeck-app/project-sdk`, `$XDG_CONFIG_HOME/project`, else `~/.config/project`) is the single source of projects, data and config: `<registry>/projects/<id>/task/{data,config}`. Task reads it only and never writes it (architecture rule `NO_REGISTRY_WRITE`); the registry lock covers the registry only, task data has no lock, only atomic writes (Q30). Registering, moving and removing projects belongs to the project CLI (`project add|remove|paths|list`): `task init` and `task projects add|remove|move|prune|list` do not exist (unknown command, exit 1). No code reads a project folder for task data, so there is no detection and no "registry wins silently" case.

- User-facing rules: a folder in no registered project is not a project (`no project in scope for <dir>. Registered: ...` + hint `... register this folder with: project add "<dir>"`, native path form, exit 1, `{error, hint}` with `--json`; nothing is read, written or printed besides). `--project-dir` is an unknown option, exit 1 wherever typed (`--project-dir x`, `--project-dir=x`, bare): the CLI does not reject unknown options in general, and without this check the flag would be taken for an argument and the command would run on the cwd's project. `TASK_PROJECT_DIR` and `PROJECT_DIR` are not read. `?project=` takes id, name or alias. The Projects page is a read-only list: id, name, main path, open count, the problem with its fix.
- Resolution (`resolveProjectFromArgs`, `resolveProject` for a caller holding the reference): `-p/--project <ref>` > `TASK_PROJECT` > the cwd looked up in the registry (deepest registered ancestor wins, no marker file, no walk-up). `<ref>` is an id (or unique prefix >= 4), name or alias, case-insensitive, never a path. A reference that does not resolve, or a cwd in no registered project (the SDK's `NoProjectInScopeError`, rethrown with the folder in native separators), is an error, never a fallback. The flag and the variable are read by the SDK (`extractProjectOption` / `resolveProjectFromArgs`, wrapped in task-service as `readProjectOption` / `resolveProjectFromArgs`; task-cli never parses them, `parseArgs` ignores `-p`): `-p x`, `--project x`, `--project=x` anywhere before `--` (nothing after `--` is read), a blank `TASK_PROJECT` is unset. A flag without value (last, or followed by a `-` argument) or repeated is a `ProjectOptionError` (`describeError`: `invalid`, hint, exit 1, `{error, hint}`). It is raised only by a command that needs a project or by `list --all-projects`; help, `status`, `cli`, `plugins`, `projects` do not look at a malformed flag (`projects summary -p` alone then fails as an unexpected argument). `TaskIndex.projectOption.test.ts` replays a table of argv/env through the SDK and the CLI. `ResolvedProject.id` is always set; `source` is `flag|env|cwd`; `path` is the MAIN path (a cwd in a secondary path resolves to it; absent for a virtual project). A valid `-p`/`--project` flag typed for a command that never resolves a project (no command, `--help`, `--version`/`-V`, `cli`, `plugins`, `projects`, `status --help`) is accepted and stripped, with one stderr line `note: <flag as typed> ignored: this command is not scoped to a project` (stdout and exit code unchanged); `TASK_PROJECT` alone prints nothing, a malformed flag keeps its error.
- Storage (`storage.ts`): `TaskStore` gets `tasksDir = <data>/tasks`, its index is `<data>/task-index.json` (pinned by tests in task-core, storage and openContext). Reading a fresh project creates nothing; the first write creates `<data>` (the store's `ensureDirectory`, so no `{ensure:true}` on read). A registered project with no data anywhere is a fresh project. `openTaskContext({ storage, project })` needs a storage (no directory input).
- Config (`projectConfig.ts`, `TASK_CONFIG_SCHEMA`): for a registered project every `config.yml` of the project chain (root first, own last) is read, validated (`validateLayer`, layer name = the file path) and merged (`mergeLayers`): `statuses`, `types`, `fields`, `hooks` are `local` (replace; a parent's values are valid there and never reach the child), `defaults` is `inherit` + `deep`. An unknown or misplaced key is a `ConfigSchemaError` naming the FILE and the key (`invalid`, 400); the status rules (>= 1, <= 1 default) apply to the merged value and name the file. Task keeps its global/project hooks separation: the task GLOBAL config (`~/.task/config.yml`: defaults, hooks) stays task's own file, merged separately (project value > global fallback for `defaults.priority`). `task type add|remove` write the project's OWN layer (created with its folder if missing). `TaskConfigLoader.load({ configDir })` is the global config alone.
- `task status list [--json]` (`listStatuses`): the valid statuses of the resolved project in config order, from the merged config `set-status` validates against. Text: one per line, `name`, `name (default)`, `name (terminal)`, `name (default, terminal)`; JSON: `[{name, default, terminal}]`. `task status` / `--help` need no project. Exists for the flows, which used to parse `config.yml` with awk.
- Atomic writes: task files, `task-index.json` and `config.yml` go through the SDK's `writeFileAtomic` (temp file, fsync, rename) via `TaskStore`'s injectable `writeFile` (`atomicWrites.test.ts` spies the SDK).
- Virtual project (registered, no path): data and config work (id-based); events cannot get a cwd, so the operation succeeds and the event is returned UNDELIVERED with a reason naming the virtual project and `project paths add` (never `process.cwd()`; no `taskProjectPath` key in the payload). Limit: cross-project views and the module do not list virtual projects, and `?project=<virtual>` answers 409 pointing to `task -p <name>`.
- Log: each command appends the resolution line (project, source flag/env/cwd, path, registry dir, data dir) to the task log (`task cli logs`).
- Events: `taskProjectId` (registry id) is in every payload; `taskProjectName` is the registry name; `taskProjectPath` stays the main path (the queue cwd).
- Cross-project views (`summarizeProjects`, `listTasksAcrossProjects`, `listKnownProjects`; CLI `--all-projects` / `projects summary`; module `/projects`, `/summary`): every registered project WITH a path (any project can hold tasks; a fresh one shows 0 tasks). None of them takes a config dir (they read the registry only). Rows carry `id`, `name`, `path`, `exists` (informational), figures, `error`. A broken parent chain lists the project unreadable (`problem`), a registry that cannot be read is `registryProblem` (nothing is listed then; text mode warns `the shared project registry was not read, so no project is listed: <problem>`). `--all-projects` refuses `-p` / `TASK_PROJECT`.
- Module: `?project=` takes an id, name or alias (registry), page addresses and API queries use the id; the registry is read at every request (no cache); missing = first-use state, corrupt = typed error shown inline. `last-project.json` stores `{ "id": ... }`; a file without an `id` is reported as `lastProjectProblem` (nothing preselected until the next creation rewrites it).
- Tests: the SDK has no off switch. Every `vitest.setup.ts` (task-service, task-cli, app-module-task) points `XDG_CONFIG_HOME`, `HOME`, `USERPROFILE` at a temp dir (`registrySafetyNet.test.ts` proves it); fixtures build registries with the SDK's `addProject` in a temp dir (`createSharedRegistrySandbox`, `createTestWorld().registerShared`). `task-core` has no setup and never touches the registry.
- Temp dirs: a run leaves nothing in the OS temp dir. `scripts/testTemp.ts` holds the list of our `mkdtemp` prefixes (`OWN_TEMP_PREFIXES`, a guard test fails on a prefix missing from it), `trackTempDirs()` removes what the process created (end of each test file, exit, SIGINT/SIGTERM) and `sweepStaleTempDirs()` runs at the start of every run (vitest `globalSetup` of each package and `architecture/`): it removes top-level directories of the OS temp dir named `<our prefix><6 chars>` and older than 15 minutes (a full `npm test` takes under a minute), which covers a killed run. New `mkdtemp` prefix: add it to the list. Test sandboxes seed `autoUpdate: false` in `app-core-cli/config.yml`, else `app-core-cli package|dev` starts a detached updater that runs a real `npm install -g`.
- Architecture rules (`architecture/rules.ts`, detection tests in `architecture.test.ts`): `NO_PROJECT_DATA_DIR` (no non-test source names `.task` as a path segment: `'.task'`, `"/.task"`, `` `${dir}/.task` ``; the only allowed spelling is the global config dir default `path.join(os.homedir(), '.task')`, the prose `~/.task` and comments), `NO_REGISTRY_WRITE` (no SDK mutation import), `NO_PROJECT_SDK_OUTSIDE_SERVICE`. Everything else works on `TaskStorage` (`dataDir`, `configFiles`).

## app-core registration

- `task cli register [--json]` / `task cli unregister [--json]`; `task cli update` registers by itself when the shipped app-module version changed. Task has no daemon, so nothing registers at start.
- Exit 0 when app-core took it or is absent/not running (deferred, skipped); exit 1 with app-core's reason when it refuses.
- `unconfirmed` (SDK >= 2026.10.24-094: app-core is up but gave no answer in time, or the connection broke, and `/api/modules` does not show the new version yet) is exit 0, `--json` `{ok: true, status: 'unconfirmed', message}`: the call may well have worked, so not a failure, but not `registered`. The message is the SDK's wording plus "To settle it, wait a few seconds and run: task cli register" (`unregister` for the removal); the updater and the rollback print it too. A script needing certainty tests `status === 'registered'`. `registered` with a `note` is a plain success.
- Manifest: `app-module/manifest.json` next to `task.cjs`, else `packages/app-module-task/dist-module/manifest.json` (source checkout: `BUNDLE_VERSION=0.0.0-local npm run bundle --workspace=packages/app-module-task`). Neither found is an error naming both paths.
- Staging: app-core stores the PATH of a manifest, and npm replaces the package folder on update (and removes it on uninstall). An installed module (`<pkg>/app-module/`) is therefore copied to `<config dir>/app-module/<manifest version>/` (`appModuleStaging.ts`: temp dir then rename, kept if already complete, error naming source and destination) and the STAGED manifest is registered, by `task cli register`, the post-update registration and the post-rollback registration (all via `attemptStagedRegistration`); `unregister` is unchanged. Older staged versions are removed only after the outcome is `registered` or `deferred`; any other status (refused, skipped, unconfirmed, an unknown one of a newer SDK) keeps them. A source checkout's `dist-module` is registered as is (a rebuild keeps the version, a staged copy would go stale). `appModuleStaging.ts` imports only fs/path and `registerAfterUpdate.ts` (the updater bundle must stay under 500 KB and free of the task runtime).
- The module has no cwd: projects come from the shared registry (read at every request), routes take `?project=<id|name|alias>` (an unknown reference, a folder or a `name~hex` slug included, answers 404 with the registry message and its suggestions; the hint says to use the id, name or alias, GET `/projects` lists them). A registry that cannot be read and no `?project=` answers 500 with the registry message (not "no project is registered"). See Shared project registry.
- Registry upkeep belongs to the project CLI (Decision #20): task has no command, route or form to register, move, remove or list registry projects; `task projects summary` and `task list --all-projects` are read-only figures.
- `deferred` from the SDK means only "the POST failed" (refused, reset, or no answer within 3 s) and the config dir exists, not proof that app-core is down; the message says "not running" regardless. If app-core is up, run `task cli register`.
- Testing against a real app-core: set `APP_CORE_PORT` and `APP_CORE_CONFIG_DIR`; without a free `APP_CORE_PORT` the SDK talks to the app-core running on 4850.

## app-module-task routes and pages

Routes (`/api/modules/task/...`, all take `?project=<id|name|alias>`, typed errors mapped in `errors.ts`): GET `/projects` `/summary` `/tasks` `/tasks/search` `/labels` `/tasks/:id` `/tasks/:id/{history,children,ancestors,links}` `/tree` `/types`; PATCH `/tasks/:id` `{title?, description?}` (empty description clears it; `onTaskTextChanged` per changed field); PUT `/tasks/:id/{meta/:key,meta-keys/:key}` (value in the body, else `?value=`; an empty value is valid; `meta-keys/:key` = key as base64url, for keys holding `/` or `%`); POST `/tasks` `{title?, description?, parent?}` (at least one text; a long `description` alone is split into headline + description) `/tasks/:id/{status,labels,links,parent,type,meta}` `/types` `/tasks/delete/plan` `/tasks/delete` (needs `confirm: true`, else 400 with the plan); DELETE `/tasks/:id/{labels/:label,label-keys/:key,links,parent,type,meta/:key,meta-keys/:key}` (removing an absent meta key or an unset type is a 200 with no event; `label-keys/:key` = `labels/:label` with the label as base64url, for labels holding `/` or `%`; an invalid key is a 400 naming the format) `/types/:name`. `GET /tasks/search?q&limit&exclude=a,b&excludeDescendantsOf=<id>` reads the index only and answers `[{id, headline, status, statusText, tone, href}]` (`limit` default 8, above 20 is a 400, never clamped); `GET /labels` answers `[{label, count}]` and `GET /meta-keys` the sorted metadata keys in use (both read every task file, ~130 ms on 1000 tasks: pickers call them on focus, never the detail route). Lists, trees, pickers and the related card label a task by its headline (`shortTitle` = `headlineOf`, <= 90 chars), never by a long legacy title. `GET /tasks/:id` also gives `headline`, `body`, `bodyAddsInfo`, `statusOptions` `[{value,label,tone,terminal}]`, `typeOptions` (a "None" entry with value '' first; [] when the project has no types), `metaEntries` (`keyId` = base64url key), `deleteImpact`, `pills` (about 20 ms on 1000 tasks: the index plus the task's own, parent, children and linked files, never a scan; a test makes 200 other files unreadable); `titleShort` / `hasShortTitle` stay only until the old yaml is gone (see `taskViews.ts`), and `descriptionText` / `hasDescription` are now set only when the body adds information. Every route that changes a task produces queue events (create, status, labels, links, parent, type, meta, text, `POST /tasks/delete`; see Queue events) and answers `undelivered` / `undeliveredText`; `/types`, `/projects*` and the delete preview emit nothing. Every view that fires one of these routes shows `undeliveredText` in a warning badge bound to the action's `resultKey` (Task page: one per form section; New task; Delete, under `plan`, saying how many events were not delivered); `manifest.test.ts` fails when a mutating action has no such badge. `POST /tasks/delete` failing partway (`PartialDeleteError` from `executeDelete`: `deletedCount`, `plannedCount`, `failedTaskId`, `events`) delivers the events of the tasks already deleted, then answers 500 with `deletedCount`, `plannedCount`, `partial: true`, `undelivered`; `task delete` does the same and exits 1 naming how many were deleted. A failure before the first deletion is the plain original error.

Provider route for the project module (see Extension points): GET `/related/project/:projectId` (not `?project=`; `:projectId` resolved like `?project=`: id, prefix, name, alias), read only, no event.

Pages: nav `/tasks` `/tree` `/projects` `/types` (global, or the only project); global `/tasks/new` `/tasks/delete` (project chosen in a select); per project, the project being a PATH segment `:project` (read as `$route.project`): `/tasks/p/:project` (list), `/tasks/p/:project/:id`, `/tasks/p/:project/:id/history`, `/tasks/p/:project/new`, `/tasks/p/:project/delete`, `/tree/p/:project`, `/types/p/:project`; dashboard widget. A global page and its per-project twin share one view file. Why a path segment: the shell's breadcrumb links each crumb to the current address up to that page, path params substituted, QUERY DROPPED (`navHelpers.ts` `routeChain`, `href: match.pathnameBase`; confirmed in a browser on app-core-cli 075 and the prebuilt 128). `?project=` on a page address is ignored.

- `:project` is the registry id (8 hex) of the project, never a folder nor a slug (`projectRef.ts`: `pageRef` / `apiRef` return the id): the crumb prints the value cut at 16 characters, so a folder would read the same for every project of a workspace. `GET /projects` resolves it (the views feed it with `$route.project`); `hrefs.ts` builds every page address; the route layer never writes `?project=` in a page link. An unknown project on a page shows `unknownProjectText`.

Projects page (`/projects`, no `?project`): a READ-ONLY list of the registry projects. `GET /projects` gives `projectRows` (`id`, `name`, `path`, `openText`, `problemText` with its fix; no registry column), `openLinks`/`hasOpenLinks` (the table has no row click), `attentionText`, `registryProblem` (the shared registry could not be read: no project is listed, danger badge on the page and the widget; also in `GET /summary`), `noProjectsText`. The view has one source and no action.

Global view (all registered projects): the widget (`GET /summary` without `?project`: open/total plus `projectRows`, one row per project with its tasks link or its error; nothing registered is a 200 with `noProjects`, not an error) and the Tasks page without `?project` while several projects are registered (`GET /tasks?allProjects=true`, Project column, rows link to the per-project address; `/projects` gives `globalQuery`, `allProjectsHref`, `unknownProjectText`). With `?project`, or a single registered project, the Tasks page is the per-project page. Per page without `?project` and with several projects:

| Page     | Scope                                                                                                                                                                                                                  |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tasks    | global list, Project column                                                                                                                                                                                            |
| Tree     | `GET /tree?allProjects=true`: `projects` (see Tree page), `task:ProjectAccordion`; the scope text counts open tasks and names the closed parents kept above them; `warning` is one line naming the unreadable projects |

No page has a back link ("All projects", "All tasks", "Back to the task" are gone, with `allProjectsHref`, `globalHrefs`, `tasksHref`): the breadcrumb carries the context (yaml test `no link whose purpose is going back` has an allowlist of the links kept: forward features only). An address naming an unregistered project shows `unknownProjectText` on every per-project page. The detail and history pages (`GET /tasks/:id`, `/history`, `/links`) answer `?blank=true` like the list routes.

Title and description (`taskText.ts`, `createTask`, `setTaskText`): `description` is stored in the task file only when it differs from `title`; readers use `taskDescription` (`description ?? title`), old files holding the title twice stay valid. The CLI JSON of a task record (`show`, and the record printed by `new`, `set-status`, `link`/`unlink`, `set-title`, ...) ALWAYS has `description` (`withDescription`: the resolved text), whatever is stored; summaries (`list`, `tree`, `children`, `parents`, `links`, `find`) never had it. `createTask({title?, description?})`: a single text (title alone, or description alone as the module and flows send it) longer than `HEADLINE_MAX_LENGTH` (90) is split by `splitHeadline` (first line, else first sentence, else a word boundary + `...`; description = full text); an explicit title + description is stored as given. `task new <text> [--description <text> | --description-file <path|->]`, `set-title`, `set-description` (empty clears), `unset-meta`, `unset-type`, `find <query> [--limit 1-20] [--json]` (`searchTasks`, index only, rank id prefix > title word prefix > substring; text lines or JSON `{id, headline, status}`), `labels [--json]` (`listLabels`, reads every task file: 1 000 tasks measured 60-190 ms median, so no label index, see D3 in the page review plan). `find` and `labels` print text unless `--json`.

CLI parity (task-cli `GlobalViewCommands.ts`, parsing and output only over the same service reads; neither needs a project):

- `task list --all-projects [--all] [--json]`: text table PROJECT / ID / STATUS / TITLE; `--json` is the `listTasksAcrossProjects` answer as is (`tasks` tagged with `project`, `readableCount`, `unreadable`). Unreadable projects: warning on stderr in text mode (in `unreadable` in JSON), the others are still listed; exit 1 (`NoReadableProjectsError`, reasons + fix) only when none can be read; nothing registered is exit 0 with the `project add <dir>` hint. Fails with an actionable error when combined with `--follow`/`-f`, `--tree`, `--parent`, `-p` or `TASK_PROJECT` (same exit code and message shape, the message names the source; empty value = unset). `--project-dir` is an unknown option like everywhere (exit 1). `--config` / `TASK_CONFIG` select no project and are untouched.
- `task projects summary` takes no project, so a project flag or variable there contradicts nothing and is left alone.
- `task projects summary [--json]`: totals line, by-status line, one line per project (`open / total`, or `[unreadable: reason]`, not counted); `--json` is the `summarizeProjects` answer. Exit 1 only when none can be read.
- `--follow` is not implemented for `--all-projects`. It would be feasible with `diffSnapshot` keyed by project path + task id over `listTasksAcrossProjects`, but needs decisions first: cost (every project re-read every 500 ms), and what to print when a project becomes (un)readable or all fail mid-follow.
- JSON errors are `{"error": ..., "hint": ...}` for every command going through `errorOutput` / `failure` (no `hint` key without one). `set-type` has no separate hint: its message already lists the valid types. `task cli register` and `task plugins config` keep their own error shapes.

View conventions (app-core DSL, checked against the real shell):

- Mutations: Form + `$actions` + `onSubmit: $ctx.<action>`; the form data is the body and fills `{placeholders}` of the action URL. Placeholders are not URL-encoded: forms carry `projectParam` (encoded by the route) and use `?project={projectParam}`.
- The shell drops the answer of a failed action and discards ALL source answers when one source fails (blank page). Every request of a view therefore adds `inlineErrors=true`: the route answers a failure as 200 with `failed`, `httpStatus` and `errorText` (message, plus the hint unless it explains the JSON API), and the view shows `errorText` in a `variant: danger` Badge. Actions publish with `resultKey` per section, so the message sits next to its form.
- Zero registered projects: `/projects` answers `noProjects` + `noProjectsText` (the next step: `project add <dir>`) and `forms: null`; every page shows that text in an info Badge (a page with only a bound title and no badge renders blank). `forms` is also null when the selected project is unreadable (invalid config, broken parent chain). The widget shows its figures only `$if: summary.projectCount`, so a failure leaves the error alone. A registered project whose folder vanished stays readable (`exists: false`: its data is in the registry; `project paths move` fixes the path).
- Sources use `?{query}`. The shell keeps the last answer of a skipped source (reproduced: unknown project, Tasks menu, browser Back left the 6 rows of the global list), so no query may be empty: a page with several scopes (Tasks, Tree, Types) has ONE source fed by `scopeQuery` (project, global, or `blank=true`), the others (New, detail, history) by `projectQuery` (project or `blank=true`); a yaml test enforces it. `?blank=true` makes `/tasks`, `/tree`, `/types` answer `{blank: true}`, which replaces the previous scope's data (verified: global -> back -> unknown project leaves no rows).
- Forms (shell 2026.10.24-094): typing in the New task description, then waiting 12 s across `/api/modules` polls, kept the focus (`document.activeElement` is the textarea) and the value; the earlier "forms reset within seconds" does not reproduce. Shell 147 (app-core-cli 2026.10.31-147, dsl-ui 306; browser, isolated app-core): after a successful add the forms ARE reset (New task: description empty AND parent back to "No parent"; label, metadata and link forms of the task page: fields empty, relation back to the first option). Not checked: the other forms (types, delete).
- The shell reloads on a URL change only the sources naming a `$urlParam.*`/`$route.*`: a source waiting for `projects` also takes `reload: $urlParam.reload` (always empty, so never sent), else filter links and project choice leave the page stale or blank until F5.
- Installed shell (app-core-cli 2026.10.24-094, dsl-ui 2026.10.24-175; verified in a browser on an isolated app-core): a YAML DataTable column honours `mono`, `nowrap`, `truncate` (ellipsis) and `title` (tooltip, `{field}` of the row); the ID columns render monospace. `width`, `muted`, `format`, `sortable`, `badge` are accepted by the compiler but were not exercised. Also working: `type: actions` columns, `navigateTo`, `onRowClick`, `onAction`, `expansion`, `selectable`/`batchActions`, `fontMono`, `emptyMessage`. Title columns (`titleText`) carry `truncate: true, title: '{title}'` (test-enforced); routes still give display texts (`titleText`, `created`, `time`, `projectText`). Columns of short codes carry `nowrap: true` (test-enforced). Row action URLs substituting the clicked row's `{key}` (dsl-ui >= 2026.10.20) were not re-tested: the Types Remove button keeps pick-then-confirm. A row action without `icon` renders a text button and logs `[DataTable] action "pickRemove" has no icon` once per render: kept on purpose (an icon would make it icon-only, unlabeled). ## Task links (service, CLI, module, views)

- Model (`task-core`): stored types `blockedBy`, `duplicateOf` (one target), `causedBy`, acyclic per type, same project only; the inverses `blocks`, `duplicates`, `causes` are derived from the other tasks. Deleting a task removes the links pointing to it (`removedLinkCount`; `danglingLinkCount` in the delete plan).
- Service (`links.ts`): `linkTasks` / `unlinkTasks` accept stored or inverse names (an inverse name stores the link on the other task; the event `taskId` is the holder, `linkType` canonical); `getTaskLinks` gives the six relations; `describeBlockers` the open `blockedBy`. A link to a task missing from the index (data edited outside task) is a `DanglingLinkError` from `getTaskLinks` (conflict, hint `task unlink <id> <type> <target>`); `readTaskLinks` reports it instead (`{ links, dangling: [{relation, targetId, fix}], warnings }`) and is what the module uses; `describeBlockers` and `TaskStore.getOpenBlockers` skip it (`TaskStore.getLinksLenient`). `unlink` removes it given the exact id of the vanished task.
- CLI: `link` / `unlink <id> <type> <target>` print the HOLDER task (the target for an inverse name); the usage lists the six names. `links <id>` prints the six relations (JSON); `show` has only the stored `links` array.
- Module: `POST` / `DELETE /tasks/:id/links` (body; query for DELETE) answer `{ task: holder, undelivered }`. `GET /tasks/:id/links` answers `links`, `dangling`, `warnings`, `rows` (one per linked task, `direction` outgoing/derived, `meta` = label, `removeParams` `{id, projectParam, type, target}`), `groups` `[{relation, label, rows}]` (empty relations left out), `groupSections` (one `Section` per group: "<label> (<n>)" + `task:TaskRowList` with `removeAction: removeLinkRow`; built by `linkGroupSections` because a view cannot loop), `hasLinks` (true for a dangling link too) / `noLinks`. A dangling link is a row of its relation group (`missing: true`, title "missing task <id>", status `missing`, tone `danger`, no `href`, removable like the others). `GET /tasks/:id` stays 200 with the link warnings (message + fix) appended to `warnings`, like a dangling parent.
- Views: the Links section of the task page (`current`) and every variant render `$sources.links.groupSections` (shared fragment `links.groups`; a test forbids `$sources.links.rows` in any variant). Each row links to its task and has an x button beside it (`removeLinkRow`: `DELETE .../tasks/{id}/links?type={type}&target={targetEncoded}`, params from the row, no confirm; verified in the installed shell: a url action takes its placeholders from `params`). A DataTable could not do both (row actions with a url leave `{id}` unsubstituted; a table with row actions has no row click). The add / remove forms stay (relation select + free-text target id or prefix). The feedback of a row removal is the `linkResult` notice of the variant, which sits with the link forms: in a variant that folds them (seen in notion-b) it is hidden while they are folded.
- Not covered: no link indicator in the Tasks list, tree or widget (CLI `list` / `tree` neither); no target picker; links never cross projects (open question). CLI: `task show` / `task links` go through `readTaskLinks` (`ReadCommands.ts`): the JSON gains a `dangling` array (`relation`, `targetId`, `fix`) only when a link points to a vanished task, one `Warning: ... Fix with: task unlink <id> <type> <target>` line per link on stderr, exit 0. Both always print JSON (no text format exists).

## Activity log (core, service, CLI, module)

- Storage (`task-core`): optional `activity?: ActivityEntry[]` in the task file, oldest first; old files stay valid (no migration) and show their status history only. Entry `{ at, kind, field?, oldValue?, newValue?, target?, inverse? }`, only the keys that apply. Status changes stay in `history` (it holds the creation too), never duplicated here.
- Kinds and keys: `type` (old/new, either absent), `label-added` (new = label), `label-removed` (old = label), `meta-set` (field = key, old absent for a new key, an empty value is `""`), `meta-removed` (field, old), `parent` (old/new ids), `link-added` / `link-removed` (field = stored link type, target), `title` / `description` (previews of old and new, each at most `ACTIVITY_PREVIEW_MAX` = 200 characters, `...` included, never the full text; the old description of a task without one is its title).
- Every `TaskStore` mutator appends its entry in the SAME file write as the change (one `writeFile`), `at` = `updatedAt`. No entry when nothing changed (same type/label/meta value/parent/text), same rules as the events; the file is still rewritten as before. Deleting a task detaches its children: their file gets a `parent` entry; links dropped because their target was deleted get none.
- Links: the holder gets the entry; the target gets a mirror entry with `inverse: true` and `target` = holder, in a SECOND file (its `updatedAt` is untouched). Not atomic across the two files: the holder is saved first and a failure on the target throws "Link change saved on <id> but the activity entry of <id> could not be written". A vanished target gets none.
- Service (`taskActivity.ts`): `getTaskActivity(ctx, {id})` / `describeTaskActivity` return ONE list, newest first, merging `history` and `activity` by `at` (ISO text compare; equal instants: activity reads as newer). Row `{ id, source: history|activity, at, kind, icon (lucide), tone, text, from?, to?, details?, inverse? }`; `text` is a plain sentence ("Type changed from bug to feature", "Label billing added", "Linked: blocks <id> <headline>"), ids of readable tasks read `<id> <headline>`, no `actor` (no author model). An unknown kind (newer file) is shown as "Change recorded: <kind>", never dropped.
- CLI: `task history <id>` is unchanged (status array). `task history <id> --all` prints `<UTC minute>  <text>` lines, newest first; with `--json` the rows array. `--all` with `--follow` is an error. `task show` JSON gains `activity` when present.
- Module: `GET /tasks/:id/activity[?filter=all|history]` answers `{ id, filters: ['all','history'], filter, counts: {all, history}, rows }`, rows = service rows + `group` (UTC day) + `time`; another filter is 400; `?blank=true` and `inlineErrors` like `/history` (kept, unchanged). `GET /tasks/:id` `activity` (Timeline shape, oldest first, status rows keep their old wording) now includes every change (`kind` is the Timeline kind, `activityKind` the real one, `icon`), plus `activityCount`. `PATCH /tasks/:id` answers `task`, `headline`, `body`, `bodyAddsInfo` (same rules as the detail), `activityCount`, `undelivered`. No queue event changed.

## Comments (core, service, CLI, module, components)

- Storage: optional `comments?: TaskComment[]` in the task file, oldest first, no migration (`taskComments.ts` in task-core). `{ id (6 chars [0-9a-z], unique in the task), at, text, editedAt?, author? }`. Plain text: trimmed, newlines kept, 1..10000 characters (`COMMENT_TEXT_MAX`), nothing interpreted (no markdown, no auto-links, no HTML). `author` is a free string (max 100), absent by default: no user model, the CLI never falls back to the OS user. Store: `addComment` / `editComment` (`changed: false` and no write when the trimmed text is equal) / `removeComment` (key dropped with the last one), atomic like the other mutators. Errors: `InvalidCommentTextError` (400, hint with the limit), `CommentNotFoundError` (404, hint lists the valid ids, `details.validIds`). Deleting the task deletes its comments.
- Activity: an add writes NO `activity` entry (the comment is the record); edit and remove append `comment-edited` / `comment-removed` (`field` = comment id, texts cut to the 200-character preview). `getTaskActivity` rows: `kind: 'comment'` (`source: 'comments'`, `id: comment-<id>`, `text` = FULL text, `commentId`, `actor` = author, `editedAt`, icon `message-square`), `comment-edited` (`pencil`, `details`), `comment-removed` (`message-square-x`). A removed comment loses its `comment` row and keeps its `comment-removed` row. `GET /tasks/:id/activity` filters: `all`, `comments` (the `comment` rows), `history`; `counts` has the three.
- Service (`comments.ts`): `addComment`, `editComment`, `removeComment`, `listComments` (prefix ids accepted) return `{ task, comment, events }`. `showTask` JSON gains `commentCount`. `onTaskDeleted` gains `commentCount` only when the task had comments.
- CLI (`CommentCommands.ts`): `task comment <id> <text...> [--file <path|->] [--author <name>] [--json]` (words joined by a space; `--` before a text starting with `--`; text and `--file` together refused), `task comments <id> [--json]` (oldest first; text: `<id>  <UTC minute>  <author> (edited)` then the text indented; `No comments on task <id>.` for none), `task comment-edit <id> <comment-id> <text...> [--file]` (`unchanged` when equal), `task comment-rm <id> <comment-id>`. Text mode prints one confirmation line; `--json` prints `{taskId, comment}` (edit adds `changed`) or the comment array. Errors: `{error, hint}`, exit 1.
- Module routes: GET `/tasks/:id/comments` (`{project, id, comments: [{id, at, atText, text, author?, editedAt?, editedText?, edited}], commentCount, hasComments, noComments}`, `?blank=true`), POST `/tasks/:id/comments` `{text, author?}` (201), PATCH `/tasks/:id/comments/:commentId` `{text}` (`changed`), DELETE `/tasks/:id/comments/:commentId`. Mutations answer `{taskId, comment, commentCount, undelivered, undeliveredText}`. `GET /tasks/:id` has `commentCount`, `hasComments`; its Timeline entry for a comment is titled `Comment` / `Comment by <author>` with the text as detail.
- Components: `task:CommentThread` (`comments`, `editAction`, `removeAction`, `params`, `readOnly`, `emptyText`, `now`; edits through `InlineText`, delete asks a confirmation) and `task:CommentComposer` (`action`, `params`, `author`, `placeholder`, `buttonLabel`, `maxLength`; Ctrl+Enter sends, clears itself on success). `ActivityFeed` accepts `filters: ['all','comments','history']` and prints `comment` rows with their full text and `actor`.
- NOT WIRED into the Task page yet (the page agent's job). Needed in the view: `$actions` `addComment` (POST `/tasks/{id}/comments?project={projectParam}&inlineErrors=true`, sent with the body `{text, author?}`), `editComment` (PATCH `.../comments/{commentId}?...`, body `{text}`), `removeComment` (DELETE `.../comments/{commentId}?...`), each with a `resultKey` and a warning badge bound to `undeliveredText` (`manifest.test.ts` rule) plus the `errorText` badge. Sources: `GET /tasks/{id}/comments` for `CommentThread.comments` (reload after the actions), `activity` for the feed. Pass `params: { id: $route.id, projectParam: ... }`.

## Queue events (current contract)

Operations in `task-service` return events; the caller hands them to the `EventSink`. The default sink (`queueEventSink.ts`) publishes each event through `@wadeck-app/queue-sdk` (`publishAndWait`) AFTER the change is saved, one event at a time, in order. The SDK is a dependency of `task-service` (the shared delivery adapter of both adapters; pinned version in its `package.json`, GitHub Packages, scope registry configured in the user `.npmrc`). It finds and authenticates the daemon, starts it with `queue start` when stopped, keeps the payload off the command line, and needs only `queue` on PATH. One publisher per sink (CLI: per command, created at the first delivery or declaration; module: per module lifetime, created at start by the declaration).

| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |

- `onTaskCreated` / `onTaskDeleted` `description` is the FULL text (`description ?? title`), so subscribers are unaffected by the headline split; no `title` field in them.
- Undefined fields (`parentId`, `type`, `oldType`, `newType`, `oldValue`, `newValue`, `oldParentId`, `newParentId`) are absent from the JSON. Operations other than create/status/link return `{ task, events }` (`TaskChangeResult`; delete: `{ deletedCount, events }`); nothing fires when nothing changed.
- `onTaskDeleted` order: deepest first, so a cascade fires leaves before parents (each event then still has its `parentId`, `orphanedChildIds` is empty); tasks of the same depth keep the plan order. `removedLinkCount` counts links held by the tasks still present at that moment (a holder deleted later in the same plan counts). A task absent from the store at execution time gets no event. Events are delivered one by one after all deletions (a large `--all` costs one publish each). Filter syntax of a subscriber `when:` (queue `PayloadFilter`, on the envelope): `payload.newStatus=done` (dot path, `=`, string/number compare) or a JSONPath starting with `$` that must return a truthy value (`$.payload.newStatus`). `$.status == 'x'` is NOT valid (no operators in the JSONPath form; the status is under `payload`).
- cwd: each publish passes `{ cwd: payload.taskProjectPath }` (= `ctx.project.path`: the main path of a registered project); queue finds `<project>/.queue/subscribers.yml` by walking up from it. A payload without a non-empty string `taskProjectPath` is undelivered (`dropped`) with an explicit reason, never published with the current cwd: a virtual project (payload with `taskProjectId`, no path) gets a reason naming it and how to fix it (`project paths add`), anything else is reported as a producer bug.
- Outcome mapping (SDK `PublishResult.status`):

    | SDK status                                    | Task result                                                                            | Replay text                                                                                                      |
    | --------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
    | `queued`, `dispatched`                        | delivered                                                                              | none                                                                                                             |
    | `dropped` (not recorded)                      | undelivered, `status: 'dropped'`, SDK `reason` (or an explicit "no reason" text)       | `cd '<taskProjectPath>' && queue push <event> '<json>'` (POSIX quotes; no eventId exists)                        |
    | `unknown` (may be recorded)                   | undelivered, `status: 'unknown'`, reason says the event MAY be recorded; never retried | check `queue history` from the project dir; if listed `queue replay <eventId>`; if absent the `queue push` above |
    | publisher throws (SDK promises it never does) | same as `unknown`                                                                      | same as `unknown`                                                                                                |

- Failure never fails the command or the route: stderr line, error line in `<config dir>/logs/*.ndjson` (`task cli logs`; the replay text, hence the payload JSON, is in the file), module answers carry `undelivered` (each with `status`) / `undeliveredText`. The SDK `onError` (kind, message, event, outcome) is written to the same log at level `warn`, not to stderr (the SDK is created `silent`).
- Shutdown: `EventSink.flush()` (optional) waits for the pushes in flight. The CLI calls it at the end of `runTaskCommand`, before `process.exit`; the module returns `{ flush }` from its backend and `lifecycle.teardown` (`teardown.ts`) calls it.
- Tests inject the publisher (`createQueueEventSink({ publisher | createPublisher })`); `queueEventSink.integration.test.ts` runs the real SDK against `startFakeQueueDaemon()` from `@wadeck-app/queue-sdk/testing` (free port, temp config dir; `pushes()`, `respondNext`, `resetNext`, `resetNextRegistration`) with no `queue` on PATH. The real queue daemon is never started by a test.
- Safety net (also registry isolation, see Shared project registry): every `vitest.setup.ts` (task-service, task-cli, app-module-task) sets `QUEUE_SDK_OFF=1` (SDK sends nothing, answers `dropped`; inherited by spawned CLI/app-core processes), so a default sink can never reach a real queue. The SDK honours it even with an explicit `configDir`: the integration test deletes it for its own duration. Never set it outside tests/dev runs (events would be silently dropped; the SDK announces it once).

Event declaration (queue event catalog, SDK >= 2026.10.24-190, protocol 1.1.0; older SDKs and daemons keep working):

- Single source of truth: `queueEventDeclarations` (`task-service/queueEventDeclarations.ts`, source `task`): name, description (<= 500 chars: when it fires, what does NOT), JSON Schema, example, `correlationKey: 'payload.taskId'`. Only `onTaskDeleted` is `terminal: true, outcome: 'info'` (SDK `Declaring your events`: terminal = the event ends the entity it is about; nothing more happens to that `taskId`, and a deletion is neither success nor failure). `onStatusChange` to `done` ends nothing by itself. Tests tie it to the code: one declaration per `TaskEvent` name, examples fit their schema, the payloads really produced by every operation above fit the schemas (`jsonSchemaCheck.ts`, a minimal checker of the subset used, no dependency), daemon limits. Adding or changing an event means editing that file; its hash (`queueEventDeclarationsHash`) is what triggers a new CLI declaration.
- `declareTaskEvents(publisher)` / `sink.declareEvents()`: never throws; outcome `registered | rejected | unsupported | dropped | unknown`. Task log (`task cli logs`): `rejected` error (with the `problems` paths), `unsupported` info (old daemon: update queue-cli), `dropped` / `unknown` warn; stderr only for `rejected` (a bug in our declaration). `registered` is quiet. `flush()` waits for a declaration in flight.
- Module: declared once per start (`registerTaskRoutes`), fire and forget; only with the default sink (an injected `eventSink` has no publisher).
- CLI: declared lazily before the FIRST event delivered by a process, when `<config dir>/queue-events.json` (`{ hash, taskVersion, declaredAt }`) does not hold the current hash (`QueueEventsDeclaration.ts`). Why lazy: the CLI has no start hook, the queue is about to be contacted anyway, and `task-updater.cjs` must stay free of the SDK (it never declares). The marker is written only after `registered`; any other outcome retries at the next event (an old daemon costs one extra request per delivering process until updated). A command without event never declares. Never fails the command. `task cli declare-events [--json]` forces it (exit 1 with the next step otherwise): use it after updating queue-cli or if the queue lost its catalog (the marker cannot know).
- Tests: `daemon.registrations()`, `respondNextRegistration` and `resetNextRegistration(times = 1)` of the SDK fake (SDK >= 2026.10.24-191): one reset still ends `registered` (the SDK retries a registration once, it is idempotent), two in a row end `unknown`. A scripted publisher remains only for a `dropped` without reason and a publisher that throws. `QUEUE_SDK_OFF` also switches `registerEvents` off (`dropped`, reason names the variable): tested in each package's safety net. A test that starts the default module backend must set `XDG_CONFIG_HOME` (the declaration logs in the task config dir).

Decided:

- `onStatusChange` gained `status` (= `newStatus`); `newStatus` stays, so no subscriber breaks.
- `taskFile` is NOT in any payload: the task data path moved with the shared project registry (and a virtual project has no folder to resolve it against).
- Comments fire `onTaskCommentAdded` / `onTaskCommentEdited` / `onTaskCommentRemoved` (see Comments). No event for type add/remove: they edit the project config, not a task.
- A changed declaration re-declares by itself (marker hash, test in `TaskIndex.events.test.ts`).

Open decisions (the owner's, nothing implemented):

- Replay text for cmd.exe / PowerShell, or a `--cwd` option in `queue push` (queue repo) to drop the `cd`.

## Updater

- Version pin: `package-lock.json` must resolve `@wadeck-app/shared-updater` >= `2026.10.25-020` (interrupted-install recovery); `package.json` keeps `latest`. - Test isolation: every test spawn of `task.cjs`, `task-updater.cjs` or the CLI goes through `spawnIsolated` (`src/isolatedCliEnv.ts`): temp config dir/HOME/XDG, temp `NPM_CONFIG_PREFIX`, own npmrc files, unreachable registry (also `npm_config_@wadeck-app:registry`, which outranks a project `.npmrc`), cwd in the temp tree. It throws on any other env. Never spawn a bundle with `process.env`. Async twins `startIsolated` / `runIsolated` for tests that must keep answering (fake registry in the test process).
- Interrupted `npm install -g`, verified for real (`updater.interrupted.integration.test.ts`, `fakeNpmRegistry.ts`: loopback registry whose tarball hangs; shared-updater's `MockRegistry` cannot start, its server script is not published). npm moves the old package aside (`.task-cli-XXXX`) BEFORE fetching the new one, so a kill leaves the global package missing (tarball without body) or truncated (half body); the next updater run (explicit or the background one any command schedules) restores the previous version, state `rolled-back` ("interrupted install repaired"), retired dir gone. Killing only npm: the updater restores and records `failed`. On Windows `process.kill(updaterPid)` also ended npm (cause not checked), so the live-orphan-npm branch of the repair is NOT verified here.
- Bin shim (`ci/templates/bin-launcher.js.tmpl`): first checks `task.cjs` next to `bin/`; missing = "installation is incomplete" + `npm install -g @wadeck-app/task-cli`, exit 1 (was a raw Node MODULE_NOT_FOUND stack, or the Go launcher's "not a file"). The shim runs `npm install -g` of the platform package on every command when it is missing (pinned by `binShim.platformPackage.integration.test.ts`). A bare `task.exe` (no `LAUNCHER_BUNDLE_OVERRIDE`) cannot find the bundle even when installed, since `launcher-task.config.json` `nodeScript` is `task.cjs` (sibling-package specifier `@wadeck-app/task-cli/task.cjs` would be needed; needs a launcher rebuild, not verified).
