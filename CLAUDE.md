## CLI Development Workflow

`task-cli` is installed globally via CI (GitHub Packages). Source edits alone do nothing: the `task` on PATH is the published version. Never patch `node_modules`.

To deploy a change:

1. Verify locally: `npm test` (run it twice), `npm run lint`, `npm run check` in `packages/app-module-task`, `violations check` = 0. Windows-only green is not CI green: see "Tests, Linux CI" under Shared project registry (CI also runs `vitest run --bail=1`).
2. `git commit` + `git push` -> CI builds and publishes.
3. Wait for CI, never poll: `queue wait ci <sha> --name task.ci-<first 7 chars of sha> --cli-foreground`, with `run_in_background: true`, from this repository.
4. Check the registry, it is the proof of publish: `npm view @wadeck-app/task-cli versions --registry=https://npm.pkg.github.com`. A cancelled macOS smoke job (no runner) does not block publish; only a real smoke failure does (see Updater, incident).
5. `UPDATER_MANUAL=1 task cli update`, then `task -v` to confirm the version.

A source-checkout dev build (`BUNDLE_VERSION=0.0.0-local`, not CalVer) never updates the global install: `task cli update` refuses it (see Updater, dev build guard).

## Packages

| Package           | Role                                                                                                                |
| ----------------- | ------------------------------------------------------------------------------------------------------------------- |
| `task-core`       | Storage: `TaskBackend` port and `LocalFileBackend`, config loading, domain errors.                                  |
| `task-service`    | Use cases shared by the CLI and the app-module. Pure: no console, no `process.exit`; returns results and events.    |
| `task-cli`        | `task` binary: arg parsing and output over task-service, updater, app-core registration.                            |
| `app-module-task` | app-core module (id `task`): routes `/api/modules/task/*` and dsl-views over task-service.                          |
| `dsl-lib-task`    | Browser components (React) the module ships as `task:<Name>`; no storage, service or Node API. See Task components. |

Async port (stage 0 of `.claude/plans/2026-11-08_storage-strategies.md`; steps 0.1 to 0.6 done; 0.7, lifting the domain rules out of `TaskStore`, is closed without being done: the contract suite pins the rules on every backend, see the todo): `task-core/src/backend/` holds `TaskBackend`, `BackendCapabilities`, `UnsupportedByBackendError`, `StaleRevisionError` and `LocalFileBackend` (wraps the synchronous `TaskStore`, same bytes on disk: golden test). Every caller goes through it: `ctx.store` is a `TaskBackend` built by `createLocalBackend(tasksDir, options)`; the `TaskStore` class is not exported by task-core and no other package imports it (`NO_TASK_STORE_OUTSIDE_CORE`, tests included). Every backend must pass `runBackendContract` (`task-core/src/contract/`).

- Conventions: every use case that touches a task is `async` and returns the same answer as before. A write is awaited BEFORE its events are built, and events are delivered one by one after that (a forgotten `await` would emit early or never). Writes and the deletions of `executeDelete` are sequential awaits, never `Promise.all`; cross-project reads go project by project. The backend's `revision` never reaches an answer: use cases pass records through `plain()` (`plainRecord.ts`), so JSON and events carry no `revision`.
- Guards: `@typescript-eslint/no-floating-promises`, `no-misused-promises`, `await-thenable` (type-aware, `eslint.config.mjs`); the CLI entry installs an `unhandledRejection` handler (exit 1, actionable message). Architecture: `fsAllowlist` per package (`architecture/rules.ts`): a non-test file importing `fs` must be listed with its reason.
- `task list --follow` / `task history --follow` poll with a self-scheduling loop (`cli/follow.ts`): the next pause starts when the previous poll has ended; SIGINT stops it; a failing poll fails the command.
- Known: a use case is no longer atomic against other requests of the same process (the module); task data has no lock by design.

## Dependency direction

`task-core` <- `task-service` <- `task-cli` and `app-module-task`; `app-module-task` -> `dsl-lib-task` (loaded by its `src/dsl-components`, props only). The two adapters never import each other, and `task-service` knows no CLI, HTTP or app-core library, never prints or exits. `npm run test:architecture` (`architecture/`, part of `npm test`) enforces it on imports, `package.json` dependencies and source patterns.

`@wadeck-app/project-sdk` ("latest", lockfile pins it; zero dependencies) is imported by `task-service` only; the architecture test forbids it in the sources of the adapters and `task-core` (their tests may use its mutations for fixtures). Shared rules live in `task-service` (`resolveProject`, `resolveProjectReference`, `listKnownProjects`, `describeError` for the SDK errors), adapters only parse input and format output: `describeError` (error kind, message, hint; CLI maps to stderr, module to HTTP status), `selectDeleteTargets` / `describeDeleteEffects`, `openTaskContext`, `getTaskLogDir`, `countTasksByStatus`, `showTaskWithRelations`, the storage (`storage.ts`: `registryStorage`; `openResolvedProject`; `loadTaskConfig`), the per-project health (`inspectRegisteredProjects`), `listStatuses` (the valid statuses with `default` / `terminal`, from the same merged config as `setStatus`), and the cross-project reads `summarizeProjects` / `listTasksAcrossProjects` (per-project figures and tasks tagged with their project; unreadable projects reported, `NoReadableProjectsError` when none can be read; used by the app-module and by the CLI, see CLI parity below).

## Shared project registry

The registry of the `project` CLI (`@wadeck-app/project-sdk`, `$XDG_CONFIG_HOME/project`, else `~/.config/project`) is the single source of projects, data and config: `<registry>/projects/<id>/task/{data,config}`. Task reads it only and never writes it (architecture rule `NO_REGISTRY_WRITE`); the registry lock covers the registry only, task data has no lock, only atomic writes (Q30). Registering, moving and removing projects belongs to the project CLI (`project add|remove|paths|list`): `task init`, `task projects add|remove|move|prune|list` and `task plugins` do not exist (unknown command, exit 1). No code reads a project folder for task data, so there is no detection and no "registry wins silently" case.

- User-facing rules: a folder in no registered project is not a project (`no project in scope for <dir>. Registered: ...` + hint `... register this folder with: project add "<dir>"`, native path form, exit 1, `{error, hint}` with `--json`; nothing is read, written or printed besides). `--project-dir` is an unknown option, exit 1 wherever typed (`--project-dir x`, `--project-dir=x`, bare): the CLI does not reject unknown options in general, and without this check the flag would be taken for an argument and the command would run on the cwd's project. `TASK_PROJECT_DIR` and `PROJECT_DIR` are not read. `?project=` takes id, name or alias. The Projects page is a read-only list: id, name, main path, open count, the problem with its fix.
- Resolution (`resolveProjectFromArgs`, `resolveProject` for a caller holding the reference): `-p/--project <ref>` > `TASK_PROJECT` > the cwd looked up in the registry (deepest registered ancestor wins, no marker file, no walk-up). `<ref>` is an id (or unique prefix >= 4), name or alias, case-insensitive, never a path. A reference that does not resolve, or a cwd in no registered project (the SDK's `NoProjectInScopeError`, rethrown with the folder in native separators), is an error, never a fallback. The flag and the variable are read by the SDK (`extractProjectOption` / `resolveProjectFromArgs`, wrapped in task-service as `readProjectOption` / `resolveProjectFromArgs`; task-cli never parses them, `parseArgs` ignores `-p`): `-p x`, `--project x`, `--project=x` anywhere before `--` (nothing after `--` is read), a blank `TASK_PROJECT` is unset. A flag without value (last, or followed by a `-` argument) or repeated is a `ProjectOptionError` (`describeError`: `invalid`, hint, exit 1, `{error, hint}`). It is raised only by a command that needs a project or by `list --all-projects`; help, `status`, `cli`, `plugins`, `projects` do not look at a malformed flag (`projects summary -p` alone then fails as an unexpected argument). `TaskIndex.projectOption.test.ts` replays a table of argv/env through the SDK and the CLI. `ResolvedProject.id` is always set; `source` is `flag|env|cwd`; `path` is the MAIN path (a cwd in a secondary path resolves to it; absent for a virtual project). A valid `-p`/`--project` flag typed for a command that never resolves a project (no command, `--help`, `--version`/`-V`, `cli`, `plugins`, `projects`, `status --help`) is accepted and stripped, with one stderr line `note: <flag as typed> ignored: this command is not scoped to a project` (stdout and exit code unchanged); `TASK_PROJECT` alone prints nothing, a malformed flag keeps its error.
- Storage (`storage.ts`): `TaskStore` gets `tasksDir = <data>/tasks`, its index is `<data>/task-index.json` (pinned by tests in task-core, storage and openContext). Reading a fresh project creates nothing; the first write creates `<data>` (the store's `ensureDirectory`, so no `{ensure:true}` on read). A registered project with no data anywhere is a fresh project. `openTaskContext({ storage, project })` needs a storage (no directory input).
- Config (`projectConfig.ts`, `TASK_CONFIG_SCHEMA`): for a registered project every `config.yml` of the project chain (root first, own last) is read, validated (`validateLayer`, layer name = the file path) and merged (`mergeLayers`): `statuses`, `types`, `fields`, `hooks`, `strategy` are `local` (replace; a parent's values are valid there and never reach the child), `defaults` is `inherit` + `deep`. An unknown or misplaced key is a `ConfigSchemaError` naming the FILE and the key (`invalid`, 400); the status rules (>= 1, <= 1 default) apply to the merged value and name the file. Task keeps its global/project hooks separation: the task GLOBAL config (`~/.task/config.yml`: defaults, hooks) stays task's own file, merged separately (project value > global fallback for `defaults.priority`). `task type add|remove` write the project's OWN layer (created with its folder if missing). `TaskConfigLoader.load({ configDir })` is the global config alone.
- `task status list [--json]` (`listStatuses`): the valid statuses of the resolved project in config order, from the merged config `set-status` validates against. Text: one per line, `name`, `name (default)`, `name (terminal)`, `name (default, terminal)`, `name (terminal, negative)`; JSON: `[{name, default, terminal, outcome?}]` (`outcome` `positive|negative` on terminal statuses only). `task status` / `--help` need no project. Exists for the flows, which used to parse `config.yml` with awk.
- Status `outcome` (config.yml `statuses` entry `{name, terminal: true, outcome: positive|negative}`): valid on terminal statuses only, default `positive`. On a non-terminal status or with another value it is a `ConfigSchemaError` (`invalid`, 400) naming the file, key `statuses` and path `statuses.<name>.outcome` (`projectConfig.ts`; `TaskConfigLoader.resolve` throws a plain Error with the same text for direct use). `TaskResolvedConfig.negativeStatuses` is the negative subset of `terminalStatuses`. Both outcomes close the task and unblock what it blocks (`onTaskUnblocked` fires for `rejected` too). Module tones: terminal+positive `success`, terminal+negative `danger`, others unchanged (`statusTone`: pills, options, choices, children, links, tree rows, activity rows); `statusOptions` items gain `outcome` (terminal ones only) and keep `terminal` as data; no display text says "terminal" (the UI shows the colour). Real configs are untouched.
- Atomic writes: task files, `task-index.json` and `config.yml` go through the SDK's `writeFileAtomic` (temp file, fsync, rename) via `TaskStore`'s injectable `writeFile` (`atomicWrites.test.ts` spies the SDK).
- Virtual project (registered, no path): data and config work (id-based); events cannot get a cwd, so the operation succeeds and the event is returned UNDELIVERED with a reason naming the virtual project and `project paths add` (never `process.cwd()`; no `taskProjectPath` key in the payload). Limit: cross-project views and the module do not list virtual projects, and `?project=<virtual>` answers 409 pointing to `task -p <name>`.
- Log: each command appends the resolution line (project, source flag/env/cwd, path, registry dir, data dir) to the task log (`task cli logs`).
- Events: `taskProjectId` (registry id) is in every payload; `taskProjectName` is the registry name; `taskProjectPath` stays the main path (the queue cwd).
- Cross-project views (`summarizeProjects`, `listTasksAcrossProjects`, `listKnownProjects`; CLI `--all-projects` / `projects summary`; module `/projects`, `/summary`): every registered project WITH a path (any project can hold tasks; a fresh one shows 0 tasks). None of them takes a config dir (they read the registry only). Rows carry `id`, `name`, `path`, `exists` (informational), figures, `error`. A broken parent chain lists the project unreadable (`problem`), a registry that cannot be read is `registryProblem` (nothing is listed then; text mode warns `the shared project registry was not read, so no project is listed: <problem>`). `--all-projects` refuses `-p` / `TASK_PROJECT`.
- Module: `?project=` takes an id, name or alias (registry), page addresses and API queries use the id; the registry is read at every request (no cache); missing = first-use state, corrupt = typed error shown inline. `last-project.json` stores `{ "id": ... }`; a file without an `id` is reported as `lastProjectProblem` (nothing preselected until the next creation rewrites it).
- Tests: the SDK has no off switch. Every `vitest.setup.ts` (task-service, task-cli, app-module-task) points `XDG_CONFIG_HOME`, `HOME`, `USERPROFILE` at a temp dir (`registrySafetyNet.test.ts` proves it); fixtures build registries with the SDK's `addProject` in a temp dir (`createSharedRegistrySandbox`, `createTestWorld().registerShared`). `task-core` has no setup and never touches the registry.
- Tests, Linux CI (Windows hides these): a real token file is written with mode 0o600 plus `chmodSync` (POSIX refuses a file readable by others; the check takes an injected `platform`/`mode`, so its logic is tested on Windows too); tests reach servers via `127.0.0.1`, never `localhost` (may resolve to `::1`); never sort on `readdirSync` order; restore env with `delete`, not `= undefined`. CI runs `vitest run --bail=1`, which hides further failures behind the first.
- Temp dirs: a run leaves nothing in the OS temp dir. `scripts/testTemp.ts` holds the list of our `mkdtemp` prefixes (`OWN_TEMP_PREFIXES`, a guard test fails on a prefix missing from it), `trackTempDirs()` removes what the process created (end of each test file, exit, SIGINT/SIGTERM) and `sweepStaleTempDirs()` runs at the start of every run (vitest `globalSetup` of each package and `architecture/`): it removes top-level directories of the OS temp dir named `<our prefix><6 chars>` and older than 15 minutes (a full `npm test` takes under a minute), which covers a killed run. New `mkdtemp` prefix: add it to the list. Test sandboxes seed `autoUpdate: false` in `app-core-cli/config.yml`, else `app-core-cli package|dev` starts a detached updater that runs a real `npm install -g`.
- Architecture rules (`architecture/rules.ts`, detection tests in `architecture.test.ts`): `NO_PROJECT_DATA_DIR` (no non-test source names `.task` as a path segment: `'.task'`, `"/.task"`, `` `${dir}/.task` ``; the only allowed spelling is the global config dir default `path.join(os.homedir(), '.task')`, the prose `~/.task` and comments), `NO_REGISTRY_WRITE` (no SDK mutation import), `NO_PROJECT_SDK_OUTSIDE_SERVICE`. Everything else works on `TaskStorage` (`dataDir`, `configFiles`). Plugin rules: see Storage strategy.

## Storage strategy (stage 0b of `.claude/plans/2026-11-08_storage-strategies.md`)

Installed: `local` (the default), `github` (read and write, stage 2: next section), `gitlab` (read and write, stage 5, Free tier only, verified live on gitlab.com: "Storage strategy: gitlab") and `remote` (the tasks live behind a `task serve` on another computer, stage 4: "Storage strategy: remote"). A project chooses where its tasks live with the `strategy` section of its own `config.yml`; no section = `local`, silently, exactly as before. Opening a project (`openTaskContext`) resolves it; `ctx.store` is created by the strategy plugin at its FIRST call (`lazyBackend.ts`; `kind`/`capabilities` come from the plugin before that), `ctx.strategy` is the resolution, `ctx.dispose()` releases it (the CLI calls it after each command, the cross-project views per project; the module once per request, see the github section).

- Shape (`strategyConfig.ts`, scope `local`, nothing inherited; the SDK checks the key `strategy`, task checks everything inside): `strategy: { type, fidelity, options }`. `type`: `local` (default) or a plugin ref/alias. `fidelity`: `strict` (default) | `degrade`. `options`: read by the plugin (`validate`), except `fills`, which the host reads. Every problem is a `StrategyConfigError` (a `ConfigSchemaError`: file + dotted key + `hint`, `invalid`/400). A parent layer is checked structurally in its own file but only the own layer is resolved; a `strategy` in the global `~/.task/config.yml` is an error.
- `fills` (`options.fills`): `<capability>: <technique>` or `{ use, fidelity }`; keys are `BackendCapabilities` names (`BACKEND_CAPABILITY_NAMES` in task-core) that have a technique in `strategyFills.ts` (`status meta hierarchy delete history activity search ids`, and `linkTypes.<blockedBy|duplicateOf|causedBy>`); an unknown capability or technique lists the valid ones. A non-exact technique under `strict` needs its own `fidelity: degrade`. The plugin must implement the technique (`StrategyPlugin.fillTechniques`; `local` implements none, so any fill on `local` is an error).
- Secrets: a key named `token|password|secret|apiKey|...` with a value, or a credential-looking value (`ghp_`, `github_pat_`, `glpat-`, `xox`), is a hard error with the fix `tokenEnv: <VARIABLE_NAME>` / `tokenFile: <path>`; `tokenEnv` must be a variable NAME; `strategy.pluginsDir` is an error (no external plugins, R11).
- Types known to the schema (`BACKEND_KINDS`: github, gitlab, remote) but with no plugin (none in the built-in list now; the path stays for a registry built without one, tests use `registryWithout`): `strategy type <t> is declared but no plugin is installed; built-in types: ...`, never a local fallback. A `remote` strategy validates its `options.transport` slot first (`plain-http` options: `url`, `tokenEnv` or `tokenFile`, `timeoutSeconds`); both are real since stage 4 (next sections).
- Plugin host (`task-service/src/plugin-host/`, extractable seam): generic `Plugin` (`extensionPoint`, `validate` -> string with optional `key: ` prefix, `create(options, ctx)`, `describe()`), `createPluginRegistry` (instance, refs `plugins.<id>.<impl>` + aliases, conflicts throw and register nothing, unknown id lists the registered ones of that kind, wrong kind names the right one), `resolveSlot` (`{type, options}` -> `PluginSlotError` `<file>: <dotted key>: <problem>` + hint listing the plugin's options), `createInstance` (30 s limit, `Plugin "<ref>" failed to create its instance: ...` with cause, dispose once). Kinds (`plugins/kinds.ts`): `strategy` (instance = `{backend, describe(), check(), dispose()}`) and `transport`. Built-ins are listed once in `plugins/builtinPlugins.ts` (`createBuiltinRegistry()`); tests inject their own registry through `OpenTaskContextInput.registry`.
- Architecture rules: `plugin-host/` imports only its own files and `node:` (tests also vitest; `seam-imports-task`); `plugins/<id>/` imports the seam, `plugins/kinds`, its own files, task-core and `node:` (`plugin-imports-outside-seam`); `plugins/forge-common/` (code shared by github and gitlab, no plugin, nothing registers there) follows the same list and is imported by `plugins/github/` and `plugins/gitlab/` only (`forge-common-import`); only `builtinPlugins.ts` imports a `plugins/<id>/` folder (`plugin-folder-import`); no computed `import(...)` in any package (`NO_COMPUTED_IMPORT`).
- Commands (`StrategyCommand.ts` over `showStrategy` / `checkStrategy`; they open the project themselves so a config problem is an answer, not a failure before the command): `task strategy show [-p] [--json]` (type, fidelity, fills, tokens as NAME + set/unset, capability table native/emulated/unsupported; opens no backend, creates nothing) and `task strategy check [-p] [--json]` (lines `config strategy fills token security` plus the plugin's lines: local = data, writable, task counts; each warning/error has a `fix`; exit 1 on any error; warns on plain `http://` to a non-loopback host; a `tokenFile` must be absolute and, on POSIX, mode 600 (Windows: a warning, permissions cannot be read)). `--json` failures keep the full result on stderr with exit 1. `task plugins list|config` (the stale flow mirror) is removed: unknown command.
- Host additions of stage 1: `StrategyContext` also carries `source` (the config file), `statuses` / `types` (`ProjectFacts`, from `projectFactsOf(config)`) and `log` (task log writer); a plugin may implement `validateForProject(options, facts)`, run by `resolveStrategy` at load (message `key: problem` becomes file + `strategy.options.<key>`); a `StrategyInstance` may implement `takeNotices()` (`ReadNotice`: `stale`, `ignored`, or `emulated` for a write done through an approximate fill), exposed as `ctx.takeNotices()` (the CLI prints each as a `warning:` line on stderr, the module adds the texts as `readNotices`); a fill the plugin lacks says what it does implement (`describeImplemented`).
- Remaining: `GET /projects` does not expose `strategy`/`capabilities`; `fills` keys outside `BackendCapabilities` (`type`, `fields`, `events`, `writes`, `origin` of design 2A) are refused until the design maps them to capabilities (`writes` now IS a capability, with no fill: see below).

## Storage strategy: github (stage 2, read and write)

Reads AND writes (stage 2; stage 1 was read-only, R3). Every write is an official REST call (GraphQL only for `fills.delete: hard`); an operation GitHub cannot hold natively is an `UnsupportedByBackendError` that names the `strategy.options.fills` key to declare (R4, R5, R9, R10), never a silent emulation. Not done yet (migration: see Migration): `GET /projects` exposing `capabilities`, Projects v2, changes made ON GitHub emit no event (R7). Plan and what stage 3 needs: `.claude/plans/2026-11-08_storage-strategies.md`, "Stage 2 progress".

Shared with gitlab: `plugins/forge-common/` (`managedBlock.ts` block read/compose, `revisionParts.ts` hash/parts check, `forgeToken.ts` token reader, `httpHelpers.ts` redaction/limiter/write spacing/address checks, `optionParsing.ts`, `wantedLabels.ts`); each forge passes its names, field groups and case rule as parameters.

Code: `task-service/src/plugins/github/` (plugin `githubPlugin.ts`, backend `GitHubBackend.ts` (reads), writes `githubWrites.ts`, revision `githubRevision.ts`, labels `githubLabels.ts`, options `githubOptions.ts`, status map `statusMapping.ts`, JSON mapping `issueMapping.ts`, the one HTTP client `githubClient.ts`, cache `responseCache.ts`, token `githubToken.ts`, check `githubCheck.ts`). Official REST API through Node `fetch` only: no gh CLI, no octokit; one GraphQL mutation (`deleteIssue`, `fills.delete: hard`). Registered as `plugins.github.default` / `github`.

```yaml
strategy:
    type: github
    options:
        repo: owner/name # required
        baseUrl: https://api.github.com # GitHub Enterprise Server: https://HOST/api/v3 (REST base, sub-issues and dependencies need a version that has them: check probes)
        tokenEnv: GITHUB_TOKEN # the NAME of the variable (or tokenFile: <absolute path or ~/...>, POSIX mode 600); exactly one; fine-grained token: Issues read AND write, Metadata read
        statusMap: # EVERY status of the project; checked at load (file + key); exactly one open status has no label
            backlog: { state: open }
            in-progress: { state: open, label: 'status:in-progress' }
            done: { state: closed } # positive terminal -> closed completed (default reason)
            cancelled: { state: closed, reason: not_planned } # negative terminal -> not_planned (or duplicate)
        typePrefix: 'type:' # default; typeMap: { bug: { issueType: Bug } | { label: x } }
        metaPrefix: 'meta:' # default, used only with fills.meta: labels (labels meta:key=value)
        pageSize: 100 # 1..100
        maxPages: 50 # a read that needs more fails loudly (BackendLimitError), never a silent cut
        cache: { ttlSeconds: 60 } # 0 = revalidate every read
        timeoutSeconds: 15
        writeSpacingSeconds: 1 # least time between two writes (0..); GitHub asks integrators to go slowly
        fills: # optional; what GitHub cannot hold natively. NOTHING is emulated unless declared here (see the fills table)
            meta: labels # or { use: body-block, fidelity: degrade }
            delete: hard # or { use: tombstone, fidelity: degrade }
            linkTypes.duplicateOf: { use: duplicate-marker, fidelity: degrade }
```

Capabilities (`GITHUB_CAPABILITIES` = no fill; `githubCapabilities(fills)` adds what a declared fill enables and is what `ctx.store.capabilities` reports; `task strategy show` prints the static ones and the fills as `emulated via <technique> (<quality>, fidelity <f>)`): hierarchy `limited`, linkTypes `[blockedBy]` (+ `duplicateOf` with the marker fill), status `mapped`, history `derived`, activity `native`, delete `no` (`close-only` with tombstone, `yes` with hard), search `native`, concurrency `check-then-write`, ids `assigned`, labels yes, meta no (yes with a meta fill), comments yes (author = the token user), writes `full`, indexedGraph no. `strategy show` prints `hierarchy`, `history`, `activity`, `search` and `linkTypes.duplicateOf` as `partial` with a one-sentence note (`StrategyPlugin.capabilityNotes`), `delete` / `meta` / `linkTypes.causedBy` as `unsupported`.

Client (`githubClient.ts`, injectable `fetch`, clock and `sleep`): `write(method, path, body)` and `graphql(query, variables)` serialize writes (one in flight, `writeSpacingSeconds` between the start of two), wait out a secondary limit whose `retry-after` is <= 15 s (twice at most; the request was refused, so sending it again is safe) and otherwise throw `RateLimitedError(secondary, retryAt)`; a 5xx or a lost connection is never retried and never trusted (see Writes); every write expires the read cache (`ResponseCache.expire`, a marker file `.expired-at` in the cache folder shared by the processes; entries stay for their ETag and the stale fallback). Reads: `Authorization: Bearer`, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`, redirects followed only inside `baseUrl` (max 3), `Link rel=next` followed verbatim and refused when it leaves `baseUrl` (cursors the same); ETag cache (memory per process, plus files `<data dir>/cache/github/<sha256 of the URL>.json`, created at the first write, never holding a request header or the token); inside `ttlSeconds` a read costs nothing, then `If-None-Match` (a 304 costs no quota: measured); at most 6 requests in flight. Quota: `x-ratelimit-*` of the last answer per bucket; an empty bucket fails WITHOUT sending (no busy retry): `RateLimitedError(primary|search|secondary, retryAt)`; 403 with `retry-after` = secondary; 429; 403 otherwise = `BackendAuthError(forbidden)` naming `x-accepted-github-permissions`. 401 = `BackendAuthError(unauthenticated)` (names the variable and the permissions to give). Network failure = `BackendUnreachableError(host, cause code)`, no answer = `BackendTimeoutError`, 5xx = unreachable with the status. 404 on an issue = `TaskNotFoundError`. Stale: on unreachable / timeout / rate limit, and only then, a cached answer is served and labelled: `ReadNotice` `stale` (CLI: one `warning:` line on stderr, text and `--json`; module: `readNotices` in the answer), a record gets `stale: true` + `cachedAt`; never on a refused token.

Token: `githubToken.ts`. Missing or empty variable / file: `BackendAuthError(missing)` at the FIRST backend call (so reads fail too, no anonymous fallback) naming the project, the config file, the key, `export VAR=<token>` / `setx`, the permissions to give. The token appears in no message, no log, no cache file (`redactToken` on every error text; tested). `TASK_DEBUG=1` writes one line per request (`GET /path -> status (ms, rate limit remaining n)`, no header) to the task log.

Consistency (`githubRevision.ts`, `githubWrites.ts`):

- Every write first reads the issue again (a conditional GET, free when unchanged) and, with `expectedRevision`, compares the parts it changes (revision row above): `StaleRevisionError` (a `TaskConflictError`, kind `stale`) before anything is written; a revision this backend did not issue is stale for every write. GitHub has no conditional write, so a race of about the duration of the PATCH remains and `strategy check` says "optimistic, not atomic". The use cases do not pass a revision today (last write wins, like local); the backend honours it for the callers that do.
- A write made of several calls (create + close / attach, tombstone, duplicate marker + close) runs its steps in order; a failure after the first applied step, or a call whose outcome is unknown (5xx, lost connection: never retried), reads the issue again: a step that did apply counts, otherwise `PartialWriteError` (`applied`, `notApplied`, `hint` = the command that finishes it, `cause`; the module answers 500 with them, the CLI exits 1). A refusal of the first call is the original error (`BackendRejectedError` for a 4xx, nothing changed). After every write the record is read again and returned, so the caller gets what GitHub holds.
- Lags measured on the real API, handled: the issue LIST shows a new issue about 4 s late (task remembers its creations 30 s in the cache folder, `.recent.json`, and the reads of the whole list add them by number, so `list`, `delete`, forest, `find` see a task created a moment ago); the dependency COUNTS of an issue lag 1 to 2 s (the dependency lists do not: a read ignores the counts for 10 s after task changed them); the sub-issue counts (`sub_issues_summary`) of a parent lag the same way (the `/sub_issues` list does not), handled by the same memory (`RecentKind` `subIssues`, noted by `setParent` and `create` with a parent): for 10 s the children, tree, descendants, delete plan, tombstone detaching and the 100-children check read the list whatever the count says. Evidence in the recording: the answer of a sub-issue removal still carries the counts of before it (ledger G093); the lag after an ADD was reported by the owner, not isolated in the fixture. Updates do not lag.
- Activity: the timeline of GitHub is the only source (no local log): a write made through task shows in `history --all` after the re-read; GitHub mirrors a parent and a link on the other issue itself, so no `child-added` entry is written by task.
- Events: the use cases build them after the awaited write exactly as for a local project (same names and payload keys, `taskProjectId/Name/Path` included; `TaskIndex.githubEvents.test.ts`); the one difference is `onTaskCommentAdded.author`, always the token user. A refused or failed write emits none. A change made on GitHub emits nothing (R7).

Errors (`describeError`): `BackendRejectedError` = invalid / 400 (GitHub refused the content, nothing changed), `PartialWriteError` = internal / 500 (details `applied`, `notApplied`), `StaleRevisionError` = conflict, `UnsupportedByBackendError` = unsupported / 422 with the fill to declare in the hint, `RateLimitedError` (secondary: the `retry-after` instant), `BackendLimitError` (label name 50, labels 100, body 65536, sub-issue depth 8, 100 children), `BackendAuthError(forbidden)` for a token without Issues write (the hint names the header `x-accepted-github-permissions` or "Issues: Read and write").

Architecture: `plugins/github/responseCache.ts` and `plugins/forge-common/forgeToken.ts` are in the `fsAllowlist` of task-service (answers of GitHub as files in the project data folder; the token file). Nothing else in the plugin touches the file system.

| status                | `state` (opened/closed) + status labels through `statusMap`; a combination no status maps, or two status labels, is a `BackendDataError` naming the issue (the whole list fails)                                                                                                                                                                                        |
| labels / type         | labels minus status, type and (with the fill) meta labels; type = type label (`typePrefix`, `typeMap.label`) or native `incident` (`typeMap.<t>.issueType: incident`). `test_case` is refused at load (GitLab turns it into `issue` on create and ignores it on update), `task` too (a native Task is the hierarchy child, so it never defines a type)                  |
| meta (fill only)      | label `meta:key=value` (`::` prefixes allowed), or `body-block`                                                                                                                                                                                                                                                                                                         |
| parent, children      | native, depth 2 (below)                                                                                                                                                                                                                                                                                                                                                 |
| links                 | `relates_to` only. `blockedBy` is refused (paid tier); `duplicateOf` / `causedBy` exist only through `fills.linkTypes.<type>: relate-block` (managed block + `relates_to` link); items of other projects are skipped with a notice                                                                                                                                      |
| comments              | notes with `system: false`; author = the token user                                                                                                                                                                                                                                                                                                                     |
| history / activity    | status replayed from `resource_label_events` + `resource_state_events` (events within 1 s are one change: the state event of a PUT is about 0.5 s BEFORE its label events; GitLab does not record the initial state); activity = label events plus the system notes of title (HTML diff, read as from/to), description (no diff exists), type, parent and child changes |
| createdAt / updatedAt | `created_at` / `updated_at`                                                                                                                                                                                                                                                                                                                                             |
| revision              | `<updated_at>#<6 hashes>` (title, body, status, type, labels, meta); a write compares only the parts it changes; links and comments are not in it (a note does not move `updated_at`)                                                                                                                                                                                   |
| search                | `listPage({text})` sends `search=` (the server matches title AND description, every word must start a word, case-insensitive, no lag) and keeps the issues whose TITLE contains the text; `find` ranks over the full list                                                                                                                                               |

Capabilities (`gitlabCapabilities(fills)`): hierarchy `limited` (2 levels, 99 children per parent), `linkTypes` none natively, status `mapped`, history `derived`, activity `native`, search `native`, concurrency `check-then-write` (GitLab ignores `If-Match` / `If-Unmodified-Since` on a PUT), ids `assigned`, labels yes, comments yes, writes `full`, indexedGraph no. By fill: `meta` (`labels` exact, `body-block` approximate), `delete` (`hard` needs `Work Item: Delete`, `tombstone` is close-only), `linkTypes.duplicateOf|causedBy` (`relate-block`, approximate, needs `degrade`).

Hierarchy (GraphQL work items; no REST route, `project(fullPath)` is null without `Project: Read` so only `workItem(id:)` is used, with aliases to read a page in ONE request): parent = native Issue or Incident, child = native Task.

| Operation                | Rule                                                                                                                                                                                                                                                          |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `create` with `parentId` | the parent must be an Issue/Incident (a native Task parent is refused before anything is created); the child is created with `issue_type: task`, then attached; a failure after the creation is a `PartialWriteError` naming `task set-parent`                |
| `setParent`              | refused: self or cycle (`TaskConflictError`), parent already a child (depth), parent a native Task, child with children, Incident child; an Issue child is converted to a native Task first (`workItemConvert`), then attached; replacing a parent is allowed |
| `removeParent`           | `parentId: null`; the child stays a native Task (documented, not reverted)                                                                                                                                                                                    |
| reads                    | `list`/`listPage` carry `parentId` (one aliased query per 50 tasks, native Tasks only); `getChildren`, tree, ancestors, forest follow; without `Work Item: Read` for GraphQL the list degrades to "every task is a root" with ONE notice, never silently      |
| `delete`                 | children of a tombstoned parent are detached first                                                                                                                                                                                                            |

QUICK ACTIONS: GitLab RUNS and strips a `/command` line written in a description or a note (also case-insensitive), except in a code fence, backticks or after a backslash. Text with a line starting with `/` and a word is refused before any request (`BackendRejectedError`); no escape is promised.

Writes: every write re-reads the issue (a conditional GET), compares the parts it changes with `expectedRevision` (`StaleRevisionError`), sends, then reads the record again. `updateStatus`: ONE `PUT` with `state_event` and the WHOLE label set (old status label out, new in), so exclusivity is the wrapper's on every label style (`::` names are plain labels on Free). `create`: `POST` (unknown labels are created by GitLab with a default colour; `labels sync` creates them with colour and description), a terminal status then `PUT state_event=close` (a failure of the second step is a `PartialWriteError`). Label add/remove: `add_labels` / `remove_labels`; swaps: one `PUT labels`. `updated_at` is never sent (GitLab accepts it as a parameter and SETS the stamp). Refused before any request: more than 100 labels, a title over 255 characters, a description over 1 MiB or a comment over 1,000,000 characters, a label with a comma or an edge space, reserved labels (status, type, meta, `task:deleted`), a quick-action line. Delete: `hard` (204), or `tombstone` (ONE `PUT state_event=close, add_labels=task:deleted`; hidden from every read). Comments: `POST/PUT/DELETE .../notes`; an `--author` is refused; a system note cannot be edited or deleted.

Client (`gitlabClient.ts`, injectable `fetch`, clock, `sleep`): `PRIVATE-TOKEN` header. Reads cached in MEMORY only (TTL; `If-None-Match` with the weak ETag GitLab sends on every GET (a 304 is answered for an issue and for a list); every write expires the cache; stale served only after unreachable/timeout/rate limit, labelled). Rate limit (gitlab.com Free: 100 requests per window of about 60 s, `RateLimit-*` headers on every answer): when `ratelimit-remaining` is 0, or after a 429, the client WAITS for `ratelimit-reset` (not `Retry-After`, which is misleading: 2 s while the window stays closed) up to `rateLimit.maxWaitSeconds` (default 70; 0 = never wait), printing ONE notice line per wait on stderr; a longer wait is `RateLimitedError` with the reset time. Errors: 401 = `BackendAuthError(unauthenticated)`; 403 `insufficient_granular_scope` = `GitLabPermissionError` naming the denied permission and the fix; other 403 = `forbidden` with the role hint; 404 `Project Not Found` = `GitLabProjectNotFoundError` (unknown project, or a private one the token cannot see), other 404 on an issue = `TaskNotFoundError`; 5xx or a lost connection = unreachable, never retried and never trusted (multi-call writes re-read, then `PartialWriteError`); the token is in no message, log line or cache. `TASK_DEBUG=1` logs one line per request.

`task strategy check` (GET only, plus ONE no-op write): lines `reachable auth read`, then one line per row of `credentialRequirements.ts` (`write`, `delete`, `labels-read`, `labels-write`, `hierarchy`, `project-info`, `token-info`, `server-info`), then `limits statuses labels links writes verification`. A row is `enabled`, `disabled (missing <permission>)` with the exact fix and the docs link, or `not tested` when only a real change could prove it (`delete`, `labels-write`, `Work Item: Create`). The `write` probe is a PUT of the title the first issue already has: nothing in the issue changes, but an issue never edited since its creation gets its `updated_at` refreshed once (live behaviour). The optional rows (`Project: Read`, `Personal Access Token: Read`, `Metadata: Read`) only add facts (access level, expiry, version); "not readable with this token" is an `ok` line.

THE TOKEN (single source: `credentialRequirements.ts`; docs.gitlab.com/auth/tokens/fine_grained_access_tokens/, beta in GitLab 18.10, GA in 19.2): create it with Edit profile > Access > Personal access tokens > Generate token > Fine-grained token, group and project access limited to the project, an expiration date (default and maximum 365 days; the token expires at midnight UTC and the failure is a 401, so renew it before: `strategy check` shows the date only with `Personal Access Token: Read`), and the permissions `Work Item` (Create, Read, Update, Delete: issues, notes, links, events, work items) and `Label` (Create, Read, Update, Delete) on the project. The user of the token needs a role that may edit issues (the access level of the test user could not be read; deleting an issue needs the Planner or Owner role per the docs, and `Work Item: Delete`). A classic token needs the scope `api` (`read_api` reads only): DOCUMENTED, NOT LIVE. A denied call answers 403 `insufficient_granular_scope` naming `[Resource: Action]`; task prints it with the fix. The strategy never needs `Project`, `User`, `Metadata`, `Namespace` or `Member` permissions.

Migrate: `gitlabTraits.ts` (creation instant and comment author not kept, text limits, label rules, hierarchy depth 2, cost estimates); `locationOf` = `gitlab <baseUrl> <project as written>` (a path and the numeric id of one project count as two locations). Losses: history, created-at, `hierarchy:depth` for a third level, `links:blockedBy`.

## Storage strategy: remote (`task serve`, stage 4)

The tasks of a project live on ANOTHER computer. That computer runs `task serve -p <project>` over a project whose own strategy is `local`; this one has a project whose config says `type: remote`. The server is the single writer (R6) and the only emitter of the queue events of those tasks (R7); this computer raises none for the project. Plain HTTP on a trusted LAN in v1: TLS and tunnels are deferred (a wrapper plugs in later as a `transport` plugin). Verified on loopback only: no second real machine was available. Plan: `.claude/plans/2026-11-08_storage-strategies.md`, "Stage 4 progress".

```yaml
# client project (this computer)
strategy:
    type: remote
    options:
        project: shop # optional: id, unique id prefix (>= 4) or name of the project the server serves; checked before the first call
        transport:
            type: plain-http # default type
            options:
                url: http://nas.lan:7788 # no credentials in it; https:// is accepted for a wrapper that provides TLS
                tokenEnv: TASK_REMOTE_TOKEN # the NAME of the variable (or tokenFile: <absolute path>, POSIX mode 600); exactly one
                timeoutSeconds: 10 # whole exchange, default 10
```

```
# server computer
export TASK_SERVE_TOKEN=<>= 16 random characters>
task serve -p shop [--port 7788] [--host 127.0.0.1] [--allow-lan] [--token-env NAME | --token-file PATH] [--json]
```

`task serve` (`ServeCommand.ts` over `startTaskServer`): foreground until Ctrl+C / SIGTERM (finishes the writes in flight; no daemonizing, no daemon manager); serves ONE project, refused when its strategy is not `local` (no chaining); loopback by default; any other host needs `--allow-lan` and prints a loud stderr warning BEFORE binding (plain HTTP: traffic and token readable on the network, trusted LAN only); a token is required (default variable `TASK_SERVE_TOKEN`, at least 16 characters, never on the command line; `--token <value>` is an unknown option explaining why); prints the URL, protocol, project, token origin (never the value), events; `--json` prints one line `{listening, url, host, port, lan, protocol, project, auth, events}`. Port in use, short token, unreadable token file: exit 1 with the fix.

Code: protocol in `task-core/src/remote/` (`protocol.ts` route table + headers + payload types, the single source for both ends; `wireErrors.ts` error codec); server in `task-service/src/server/` (`taskServer.ts` node:http, `serverOperations.ts` operation + derived events, `requestValidation.ts`, `serverAuth.ts`, `writeQueue.ts`, `serverToken.ts`); client in `task-service/src/plugins/remote/` (`RemoteBackend.ts`, `remotePlugin.ts`, `remoteCheck.ts`) over the transport `plugins/plain-http/` (`plainHttpPlugin.ts`, `plainHttpTransport.ts`, `transportToken.ts`). Both ends meet only through task-core (architecture rules `server-imports-client-side`, `server-folder-import`, `node-network-outside-server`, `server-makes-requests`).

Protocol v1 (JSON only; `GET /v1/info` first, then one route per `TaskBackend` operation; the table is `ROUTES`):

| Group  | Routes                                                                                                                                                                                                                                                                                                                                                                                          |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| reads  | `GET /v1/info`, `/v1/tasks`, `/v1/tasks/:id`, `/v1/labels`, `/v1/forest[?parentId]`, `/v1/tasks/:id/{links,links/lenient,children,tree,descendants,full-tree,ancestors}`, `GET /v1/query/prefix/:prefix`, `POST /v1/query/{page,many}` (body = query)                                                                                                                                           |
| writes | `POST /v1/tasks`; `PUT /v1/tasks/:id/{status,title,description,type,parent}`; `DELETE /v1/tasks/:id/{type,parent}`; `POST /v1/tasks/:id/{labels,links,comments}`; `DELETE /v1/tasks/:id/labels/:label`; `PUT\|DELETE /v1/tasks/:id/meta/:key`; `DELETE /v1/tasks/:id/links/:type/:target`; `PUT\|DELETE /v1/tasks/:id/comments/:commentId`; `DELETE /v1/tasks/:id` (path parts percent-encoded) |

- Headers: `Authorization: Bearer <token>` and `X-Task-Protocol: 1` on every request (the server answers the header on every response, errors included); `If-Match: "<revision>"` on a write = `expectedRevision` (412 stale); `X-Task-Events: suppress` on a write whose events the caller does not want raised (a migration); `Content-Type: application/json` with a body. A write answers `{result, events: {enabled, delivered, undelivered[{event, reason, status}]}}`, a read the bare result; `create` is 201. Authentication is checked FIRST (an unauthenticated peer learns nothing about routes or versions), then the protocol (426 with `{supported: {min, max}}`), then the route (404 / 405 with `Allow`), then the body (415 not JSON, 413 over 1 MiB, 400 malformed or any unknown key), then the input.
- Errors: `{error: {type, message, hint?, ...}}`, no stack, the token and the server's data folder removed from every text. `not-found` 404 (`TaskNotFoundError`), `comment-not-found` 404, `ambiguous` 409, `conflict` 409 (`TaskConflictError`), `stale` 412 (`StaleRevisionError`), `invalid-comment` 400, `rejected` 400 (`BackendRejectedError`), `unsupported` 422 (`UnsupportedByBackendError`, said to be the remote backend's), `invalid-request` 400 (client side: `BackendRejectedError`), `unauthorized` 401 (`RemoteUnauthorizedError`), `incompatible` 426 (`RemoteIncompatibleError`: both versions, which machine to update), `too-large` 413, `unsupported-media` 415, `not-allowed` 405 and `unknown-route` 404 (client side: incompatible), `unavailable` 503 (shutting down), `internal` 500 (a plain `Error`, message kept). Transport failures: `RemoteUnreachableError` (refused, DNS, reset, a redirect: never followed, the token would follow it; or an answer without `X-Task-Protocol`), `RemoteTimeoutError` (a read can be repeated, a write MAY have been applied and the hint says to check with `task show`). `RemoteProjectMismatchError` when `options.project` is not what the server serves. All have hints; `describeError` maps them (unavailable / invalid), `isRemoteFailure` is true for them, so cross-project views list such a project as unreadable.
- Validation (server side, every input): ids match `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$` (the local store builds a file name from an id: `../x` never reaches it), statuses and types are checked against the SERVED project's config, link types against `LINK_TYPES`, labels / keys / comment ids are non-empty and at most 1024 characters, bodies hold exactly the keys of their operation.
- Single writer: writes run one at a time through a per-process promise queue (`writeQueue.ts`), in arrival order, a failed write does not block the next; reads are not queued (the local backend is synchronous inside). The queue protects against concurrent REQUESTS of this process only; nothing else may write the data folder (task data has no other lock, Q30). Events leave in the order the writes completed (a separate ordered chain; the answer waits for its delivery, the write queue does not). A client never retries automatically (a create is not idempotent).
- Events: the server derives them from the record before and after each write (`serverOperations.ts`) with ITS project in the payload (`taskProjectId/Name/Path` of the server machine, so the queue cwd is right); `serverEvents.parity.test.ts` runs one scenario through the use cases over a local backend and over a remote one and requires the same events from all three (local use cases, client use cases, server). The client sink is a no-op for a project whose capabilities say `events: 'server'` (`eventSinkFor`, CLI; `routeKit.deliver`, module). An event the server could not hand to its queue is saved-but-undelivered: the client prints `warning: the change is saved on <host>, but the server could not deliver the event ...` (and the module adds it to `readNotices`); the replay is on the server (its task log). The `capabilities.events` row (`client` | `server`) is new for every backend.
- Capabilities: `REMOTE_CAPABILITIES` = the local ones with `events: 'server'`. `getOpenBlockers`, `getUnblockedBy` and `getForest` with a predicate are computed on the client (a function cannot travel) by the store's own rules (tested against the server's store). `syncLabels` is absent.
- Identity: `locationOf` = `remote <origin><path>` of the URL (a server serves one project, so the address is the storage; two client projects on one server are refused by `task migrate`). The client stores nothing; `options.project` is only a safety check.
- `task strategy check` (remote): `reachable` (round trip in ms, warns above 500), `auth`, `protocol` (both versions), `project`, `capabilities` (equal to a local project's), `statuses` (names must be equal: the server refuses an unknown status; terminal flags and types are compared too), `events` (warns when the server has no queue), plus the generic `token` and `security` (plain `http://` to a non-loopback host is a warning). A wrong token, a stopped server, another protocol each stop the list at the line that explains it.
- Migration: `task migrate` works with a remote side (read, write, markers, read-back, resume). For a remote target the server is asked to raise nothing for the writes (`suppressEvents`, header `X-Task-Events: suppress`) unless `--emit-events`; the summary `onTasksMigrated` is NOT raised for a remote target (a warning says so), and with `--emit-events` the server raises the per-task events itself, the `migratedFrom` marker included. The journal stays on the migrating machine.
- Security (v1, plain HTTP, one shared token; full table in `docs/threat-model-task-serve.md`): threats and answers. Sniffing the LAN reveals the token and every task: accepted, warned loudly at start and by `strategy check`; use a trusted network or a TLS wrapper. Token replay by a sniffer: same exposure, no per-request signature in v1. Token guessing: constant-time compare, a 500 ms delay and a counter per address on every failure, logged without the token; no lockout (a typo must not lock the owner out), the token needs 16+ characters. Path traversal and injection: strict id pattern, exact-key bodies, JSON only, no shell, no file name from a payload. Resource exhaustion: 1 MiB body limit declared and streamed, 30 s to receive a request, 16 KiB of headers. Browser abuse: no CORS (a preflight is refused), `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`. Token in logs or bodies: never logged, removed from every error body, the server's data folder too. Deferred: TLS, tunnels (as transport plugins), per-token project scope and several users, rate limiting beyond the delay, request signing.
- THE TOKEN (single source: `plugins/remote/remoteRequirements.ts`): one shared bearer token, no read-only token, no per-capability permission (whoever holds it reads and writes the served project). `strategy check` prints one line per row; a failure is `disabled (<why>): <title>: <message>` with the fix, never silence. All rows verified on loopback only.

| Row            | Needs                                                                                         | Probe                                           |
| -------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| `reachable`    | server: `task serve` running; client: `transport.options.url`                                 | `GET /v1/info`                                  |
| `auth`         | server token and the SAME value in `tokenEnv` / `tokenFile` (401 = `RemoteUnauthorizedError`) | `GET /v1/info` with the bearer token            |
| `protocol`     | overlapping protocol ranges (426 = `RemoteIncompatibleError`)                                 | `GET /v1/info`, `X-Task-Protocol`               |
| `project`      | `strategy.options.project`, when set, equals what the server serves                           | `GET /v1/info`                                  |
| `server-token` | server: at least 16 characters, no spaces; token file absolute, mode 600 on POSIX             | none: `not tested` (only `task serve` knows it) |

How to create it: `openssl rand -hex 32` (any random text of 16+ characters without spaces); server: `export TASK_SERVE_TOKEN=<token>` (or `--token-env NAME` / `--token-file <absolute path>`, `chmod 600`), then `task serve -p <project>`; client: the SAME value in the variable named by `transport.options.tokenEnv` (or `tokenFile`).

- Testing: `plugins/remote/RemoteBackend.contract.test.ts` runs the shared `runBackendContract` through the real plain-http transport and a real server on a free loopback port over a `LocalFileBackend` (36 cases, writes included); `server/taskServer.test.ts` (auth, protocol, routes, bodies, traversal, every operation, typed errors, concurrency, events, shutdown, unhandled rejections), `plugins/plain-http/` (options, timeouts, unreachable, redirect, token sources, fake timers), `plugins/remote/remotePlugin.test.ts` (a swappable fake transport through the registry, `strategy check` lines), `migrate/migrateProjects.remote.test.ts` (local to remote, remote to local, resume), `TaskIndex.remote.test.ts` (the CLI over a remote project, no event from this process), `commands/ServeCommand.test.ts`, `remoteProject.routes.test.ts` (module). Test helpers: `server/testHelpers.ts`, `plugins/remote/testHelpers.ts`. Live check through the bundle: `scripts/live-remote-smoke.mjs` (steps in its header; not in CI).

## Migration (`task migrate`, stage 3 of the storage design)

`task migrate --from <project> --to <project> [--dry-run] [--allow-loss <kind>[,...]] [--resume] [--history-comment] [--emit-events] [--json]` copies every task between any two backends through the async port (local files, github). Both sides are REGISTERED projects (id, unique prefix >= 4, name, alias; never a path); each project's own `strategy` picks its backend. To move a project onto GitHub: `project add` a second project, give it a github `strategy`, migrate into it. Same project, or two projects on the same repository (`StrategyPlugin.locationOf`), is refused. `-p` is an error, `TASK_PROJECT` is not read. There is no `task import`: migrate covers it (decided, no alias). The source is only read, with fresh reads (`freshReads`: the github cache is bypassed); a source answered from a stale cache is refused.

- Code: engine `task-service/src/migrate/` (`migrateRun.ts` run, `migratePlan.ts` plan, `mapTask.ts` per-task mapping + losses, `hierarchyPlan.ts` order/limits, `lossLedger.ts` rows, `migrateJournal.ts` journal + lock, `migrateVerify.ts` read-back, `migrateProjects.ts` registry entry); CLI `task-cli/src/commands/MigrateCommand.ts` (parsing, text, progress). `BackendTraits` (task-core `backend/traits.ts`; `StrategyPlugin.traitsFor`) says what a backend keeps and its limits (creation instant, comment authors, text/label/hierarchy limits, cost per write); a plugin that declares none is assumed to keep nothing. `CreateTaskInput.createdAt` is honoured by the local backend only.
- Flow: read the source (paged), plan (mapping, loss table, estimate), `--dry-run` stops (exit 0, no write, no journal, no lock). Blocked plan = exit 1, nothing written. Run: tasks parents first (create with final status, then type, labels, metadata, marker), links once both ends exist (a status a link changed, e.g. GitHub duplicate, is put back), comments in order, then every task written to is read back and compared (differences are reported, never repaired; status `failed`, no resume command).
- Loss kinds (`--allow-loss`; a group covers its kinds, `all` everything): `status`, `status-outcome`, `type`, `labels`, `meta`, `comments`, `history` (history/activity cannot be replayed through the port), `created-at` (target assigns it), `marker`, `text-length`, `hierarchy:{unsupported,depth,children,orphan,cycle}`, `links:{blockedBy,duplicateOf,causedBy,dangling}`. `--history-comment` writes a note comment per task (creation instant, status history, counts) and so resolves `history` and `created-at` when the target has comments. Comments are written by the migrating user: first line `Originally posted <iso> [by <author>] [migrated from <qid>#<id>]` (author in the line only when the target cannot store it).
- Ids and marker: target ids are new; `meta.migratedFrom=<source project id>/<source task id>` is written when the target has metadata (github needs `fills.meta`), else kind `marker` applies. Texts are not rewritten (references counted in notes). `updatedAt` is the migration time.
- Journal: `<target data dir>/migrate-journal-<from id>-<to id>.json` (SDK `writeFileAtomic`): per source task `{target, phase: created|fielded|linked|done}`, `status` running|stopped|completed, `lastError`, `pending` (a creation started and not recorded: title + target clock; the next run takes back the one matching task, none = created again, several = refused). A creation is written to the journal at once, other phases at most every 250 ms. Damaged journal = loud `MigrationStateError`, never replaced. Lock `migrate.lock` (pid) in the same folder; a dead pid is taken over, an unreadable lock refused. Fields of a resumed task are only filled in, never replaced.
- Idempotence: journal first, else the marker (target tasks not in the journal are read to find it); a second run creates nothing and writes nothing. An unfinished journal needs `--resume` (refused otherwise, with the hint); `--resume` without journal is refused. Rate limit (`RateLimitedError`): stops cleanly, prints `Retry after <iso>` and the exact command; other failures stop at the first one (status `failed`, `resumeCommand`). Exit 0 = done or dry run; 1 = blocked, stopped, read-back differences, or error.
- Events (decided): none per task by default (a bulk copy is not a user editing tasks; a flow on `onTaskCreated` would run once per task, which R7's "no surprise events" spirit forbids). One `onTasksMigrated {fromProjectId, fromProjectName, toProjectId, toProjectName, created, resumed, skipped, failed, remaining, complete}` after the last write (project fields = the target's; none for dry run, blocked, or a run that did nothing), declared in `queueEventDeclarations` (new hash: the CLI redeclares by itself). `--emit-events` adds `onTaskCreated`, `...TypeChanged`, `...LabelAdded`, `...MetaChanged`, `...Linked`, `...CommentAdded` for what THIS run wrote, in order, before the summary (the marker raises no event); events of a run that crashed are lost.
- Estimate (dry run): writes counted from the plan; requests/time from the target's `cost` trait (github: 5 requests, spacing + 2 s per write, 5000/h; a warning when near the quota). Measured numbers: see the live run below.
- Tests: `migrateRun.test.ts` (two local backends, `RestrictedBackend` via `createRestrictedBackend`, wrappers that fail or lose answers), `migrateProjects.test.ts` (registry + fake GitHub both ways), `MigrateCommand.test.ts`. `migrate.testkit.ts` is in the `fsAllowlist`, `migrateJournal.ts` too.
- Live: `npm run build`, then `GH_TEST_TOKEN=<token> GH_TEST_REPO=<throwaway repo> node scripts/live-github-migrate.mjs` (not in CI; exit 2 when a variable is missing): seeds a local project, dry run (asserts no write request), blocked, real run into the repo (reads GitHub back through the API), again (0 created), back into a third local project (compared task by task), cleanup (issues closed `not_planned`, created labels deleted, both asserted). The target repository is read whole: its older issues are migrated back too, and a state no status maps (a duplicate close) fails the read with the fix, so the project config maps `duplicate`.
- Not done: `--follow`, per-task events for a crashed run, restoring links that other tasks held to a task deleted from the target.

## app-core registration

- `task cli register [--json]` / `task cli unregister [--json]`; `task cli update` registers by itself when the shipped app-module version changed. Task has no daemon, so nothing registers at start.
- Exit 0 when app-core took it or is absent/not running (deferred, skipped); exit 1 with app-core's reason when it refuses.
- `unconfirmed` (SDK >= 2026.10.24-094: app-core is up but gave no answer in time, or the connection broke, and `/api/modules` does not show the new version yet) is exit 0, `--json` `{ok: true, status: 'unconfirmed', message}`: the call may well have worked, so not a failure, but not `registered`. The message is the SDK's wording plus "To settle it, wait a few seconds and run: task cli register" (`unregister` for the removal); the updater and the rollback print it too. A script needing certainty tests `status === 'registered'`. `registered` with a `note` is a plain success.
- Manifest: `app-module/manifest.json` next to `task.cjs`, else `packages/app-module-task/dist-module/manifest.json` (source checkout: `BUNDLE_VERSION=0.0.0-local npm run bundle --workspace=packages/app-module-task`). Neither found is an error naming both paths.
- Staging: app-core stores the PATH of a manifest, and npm replaces the package folder on update (and removes it on uninstall). An installed module (`<pkg>/app-module/`) is therefore copied to `<config dir>/app-module/<manifest version>/` (`appModuleStaging.ts`: temp dir then rename, kept if already complete, error naming source and destination) and the STAGED manifest is registered, by `task cli register`, the post-update registration and the post-rollback registration (all via `attemptStagedRegistration`); `unregister` is unchanged. Older staged versions are removed only after the outcome is `registered` or `deferred`; any other status (refused, skipped, unconfirmed, an unknown one of a newer SDK) keeps them. A source checkout's `dist-module` is registered as is (a rebuild keeps the version, a staged copy would go stale). `appModuleStaging.ts` imports only fs/path and `registerAfterUpdate.ts` (the updater bundle must stay under 500 KB and free of the task runtime).
- The module has no cwd: projects come from the shared registry (read at every request), routes take `?project=<id|name|alias>` (an unknown reference, a folder or a `name~hex` slug included, answers 404 with the registry message and its suggestions; the hint says to use the id, name or alias, GET `/projects` lists them). A registry that cannot be read and no `?project=` answers 500 with the registry message (not "no project is registered"). See Shared project registry.
- Registry upkeep belongs to the project CLI (Decision #20): task has no command, route or form to register, move, remove or list registry projects; `task projects summary` and `task list --all-projects` are read-only figures.
- `deferred` from the SDK means only "the POST failed" (refused, reset, or no answer within 3 s) and the config dir exists, not proof that app-core is down; the message says "not running" regardless. If app-core is up, run `task cli register`.
- Testing against a real app-core: set `APP_CORE_PORT` and `APP_CORE_CONFIG_DIR`; without a free `APP_CORE_PORT` the SDK talks to the app-core running on 4850.

## Task links (service, CLI, module, views)

- Model (`task-core`): stored types `blockedBy`, `duplicateOf` (one target), `causedBy`, acyclic per type, same project only; the inverses `blocks`, `duplicates`, `causes` are derived from the other tasks. Deleting a task removes the links pointing to it (`removedLinkCount`; `danglingLinkCount` in the delete plan).
- Service (`links.ts`): `linkTasks` / `unlinkTasks` accept stored or inverse names (an inverse name stores the link on the other task; the event `taskId` is the holder, `linkType` canonical); `getTaskLinks` gives the six relations; `describeBlockers` the open `blockedBy`. A link to a task missing from the index (data edited outside task) is a `DanglingLinkError` from `getTaskLinks` (conflict, hint `task unlink <id> <type> <target>`); `readTaskLinks` reports it instead (`{ links, dangling: [{relation, targetId, fix}], warnings }`) and is what the module uses; `describeBlockers` and `TaskStore.getOpenBlockers` skip it (`TaskStore.getLinksLenient`). `unlink` removes it given the exact id of the vanished task.
- CLI: `link` / `unlink <id> <type> <target>` print the HOLDER task (the target for an inverse name); the usage lists the six names. `links <id>` prints the six relations (JSON); `show` has only the stored `links` array.
- Module: `POST` / `DELETE /tasks/:id/links` (body; query for DELETE) answer `{ task: holder, undelivered }`. `GET /tasks/:id/links` answers `links`, `dangling`, `warnings`, `rows` (one per linked task, `direction` outgoing/derived, `meta` = label, `removeParams` `{id, projectParam, type, target}`), `groups` `[{relation, label, rows}]` (empty relations left out), `groupSections` (one `Section` per group: "<label> (<n>)" + `task:TaskRowList` with `removeAction: removeLinkRow`; built by `linkGroupSections` because a view cannot loop), `hasLinks` (true for a dangling link too) / `noLinks`. A dangling link is a row of its relation group (`missing: true`, title "missing task <id>", status `missing`, tone `danger`, no `href`, removable like the others). `GET /tasks/:id` stays 200 with the link warnings (message + fix) appended to `warnings`, like a dangling parent.
- Views: the Links section of the task page (`current`) and every variant render `$sources.links.groupSections` (shared fragment `links.groups`; a test forbids `$sources.links.rows` in any variant). Each row links to its task and has an x button beside it (`removeLinkRow`: `DELETE .../tasks/{id}/links?type={type}&target={targetEncoded}`, params from the row, no confirm; verified in the installed shell: a url action takes its placeholders from `params`). A DataTable could not do both (row actions with a url leave `{id}` unsubstituted; a table with row actions has no row click). The add / remove forms stay (relation select + free-text target id or prefix). The feedback of a row removal is the `linkResult` notice of the variant, which sits with the link forms: in a variant that folds them (seen in notion-b) it is hidden while they are folded.
- Not covered: no link indicator in the Tasks list, tree or widget (CLI `list` / `tree` neither); no target picker; links never cross projects (open question). CLI: `task show` / `task links` go through `readTaskLinks` (`ReadCommands.ts`): the JSON gains a `dangling` array (`relation`, `targetId`, `fix`) only when a link points to a vanished task, one `Warning: ... Fix with: task unlink <id> <type> <target>` line per link on stderr, exit 0. Both always print JSON (no text format exists).

## Activity log (core, service, CLI, module)

- Storage (`task-core`): optional `activity?: ActivityEntry[]` in the task file, oldest first; old files stay valid (no migration) and show their status history only. Entry `{ at, kind, field?, oldValue?, newValue?, target?, inverse? }`, only the keys that apply. Status changes stay in `history` (it holds the creation too), never duplicated here.
- Kinds and keys: `type` (old/new, either absent), `label-added` (new = label), `label-removed` (old = label), `meta-set` (field = key, old absent for a new key, an empty value is `""`), `meta-removed` (field, old), `parent` (old/new ids), `link-added` / `link-removed` (field = stored link type, target), `title` / `description` (previews of old and new, each at most `ACTIVITY_PREVIEW_MAX` = 200 characters, `...` included, never the full text; the old description of a task without one is its title).
- Every `TaskStore` mutator appends its entry in the SAME file write as the change (one `writeFile`), `at` = `updatedAt`. No entry when nothing changed (same type/label/meta value/parent/text), same rules as the events; the file is still rewritten as before. Deleting a task detaches its children: their file gets a `parent` entry; links dropped because their target was deleted get none.
- Links: the holder gets the entry; the target gets a mirror entry with `inverse: true` and `target` = holder, in a SECOND file (its `updatedAt` is untouched). Not atomic across the two files: the holder is saved first and a failure on the target throws "Link change saved on <id> but the activity entry of <id> could not be written". A vanished target gets none.
- Parent changes: the child gets `parent` (same write as the change); each parent concerned gets a mirror entry in a SECOND file (`inverse: true`, `target` = child, `updatedAt` untouched): `child-added` on the new parent, `child-removed` on the old one (a move A -> B gives both). Texts: "Sub-task <id> <headline> added" / "... detached"; icon `git-branch`, tone `neutral`. Failure on the parent throws "Parent change saved on <child> but the activity entry of <parent> could not be written" (the module then answers an error although the child is saved and its `onTaskParentChanged` not delivered: same compromise as links). A deleted parent gets none (the children keep their `parent` entry). Components owner: add `child-added` / `child-removed` to the ActivityFeed HISTORY kinds. `DELETE /tasks/:id/parent` is addressed by the CHILD id (so a parent's sub-task row can call it), runs `removeParent` and answers `{task: child, undelivered, undeliveredText}` like `POST`.
- Service (`taskActivity.ts`): `getTaskActivity(ctx, {id})` / `describeTaskActivity` return ONE list, newest first, merging `history` and `activity` by `at` (ISO text compare; equal instants: activity reads as newer). Row `{ id, source: history|activity, at, kind, icon (lucide), tone, text, from?, to?, details?, inverse? }`; `text` is a plain sentence ("Type changed from bug to feature", "Label billing added", "Linked: blocks <id> <headline>"), ids of readable tasks read `<id> <headline>`, no `actor` (no author model). An unknown kind (newer file) is shown as "Change recorded: <kind>", never dropped.
- CLI: `task history <id>` is unchanged (status array). `task history <id> --all` prints `<UTC minute>  <text>` lines, newest first; with `--json` the rows array. `--all` with `--follow` is an error. `task show` JSON gains `activity` when present.
- Module: `GET /tasks/:id/activity[?filter=all|history]` answers `{ id, filters: ['all','history'], filter, counts: {all, history}, rows }`, rows = service rows + `group` (UTC day) + `time`; another filter is 400; `?blank=true` and `inlineErrors` like `/history` (kept, unchanged). `GET /tasks/:id` `activity` (Timeline shape, oldest first, status rows keep their old wording) now includes every change (`kind` is the Timeline kind, `activityKind` the real one, `icon`), plus `activityCount`. `PATCH /tasks/:id` answers `task`, `headline`, `body`, `bodyAddsInfo` (same rules as the detail), `activityCount`, `undelivered`. No queue event changed.

## Comments (core, service, CLI, module, components)

- Storage: optional `comments?: TaskComment[]` in the task file, oldest first, no migration (`taskComments.ts` in task-core). `{ id (6 chars [0-9a-z], unique in the task), at, text, editedAt?, author? }`. Plain text: trimmed, newlines kept, 1..10000 characters (`COMMENT_TEXT_MAX`), nothing interpreted (no markdown, no auto-links, no HTML). `author` is a free string (max 100), absent by default: no user model, the CLI never falls back to the OS user. Store: `addComment` / `editComment` (`changed: false` and no write when the trimmed text is equal) / `removeComment` (key dropped with the last one), atomic like the other mutators. Errors: `InvalidCommentTextError` (400, hint with the limit), `CommentNotFoundError` (404, hint lists the valid ids, `details.validIds`). Deleting the task deletes its comments.
- Activity: an add writes NO `activity` entry (the comment is the record); edit and remove append `comment-edited` / `comment-removed` (`field` = comment id, texts cut to the 200-character preview). `getTaskActivity` rows: `kind: 'comment'` (`source: 'comments'`, `id: comment-<id>`, `text` = FULL text, `commentId`, `actor` = author, `editedAt`, icon `message-square`), `comment-edited` (`pencil`, `details`), `comment-removed` (`message-square-x`). A removed comment loses its `comment` row and keeps its `comment-removed` row. `GET /tasks/:id/activity` filters: `all`, `comments` (the `comment` rows), `history`; `counts` has the three.
- Service (`comments.ts`): `addComment`, `editComment`, `removeComment`, `listComments` (prefix ids accepted) return `{ task, comment, events }`. `showTask` JSON gains `commentCount`. `onTaskDeleted` gains `commentCount` only when the task had comments.
- CLI (`CommentCommands.ts`): `task comment <id> <text...> [--file <path|->] [--author <name>] [--json]` (words joined by a space; `--` before a text starting with `--`; text and `--file` together refused), `task comments <id> [--json]` (oldest first; text: `<id>  <UTC minute>  <author> (edited)` then the text indented; `No comments on task <id>.` for none), `task comment-edit <id> <comment-id> <text...> [--file]` (`unchanged` when equal), `task comment-rm <id> <comment-id>`. Text mode prints one confirmation line; `--json` prints `{taskId, comment}` (edit adds `changed`) or the comment array. Errors: `{error, hint}`, exit 1.
- Module routes: GET `/tasks/:id/comments` (`{project, id, comments: [{id, at, atText, text, author?, editedAt?, editedText?, edited}], commentCount, hasComments, noComments}`, `?blank=true`), POST `/tasks/:id/comments` `{text, author?}` (201), PATCH `/tasks/:id/comments/:commentId` `{text}` (`changed`), DELETE `/tasks/:id/comments/:commentId`. Mutations answer `{taskId, comment, commentCount, undelivered, undeliveredText}`. `GET /tasks/:id` has `commentCount`, `hasComments`; its Timeline entry for a comment is titled `Comment` / `Comment by <author>` with the text as detail.
- Components: `task:CommentThread` (`comments`, `editAction`, `removeAction`, `params`, `readOnly`, `emptyText`, `now`; edits through `InlineText`, delete asks a confirmation) and `task:CommentComposer` (`action`, `params`, `author`, `placeholder`, `buttonLabel`, `maxLength`; Ctrl+Enter sends, clears itself on success). `ActivityFeed` accepts `filters: ['all','comments','history']` and prints `comment` rows with their full text and `actor`.
- Wired into the Task page (every design): `$actions` `addComment` / `editComment` / `removeComment` (one `commentResult` key, `task:Notice` for `errorText` and `undeliveredText`), sources `comments` (`CommentThread`) and `activity` (`GET .../activity?filter=all`, the feed filters and counts client side). See Task page designs.

## Queue events (current contract)

Operations in `task-service` return events; the caller hands them to the `EventSink`. The default sink (`queueEventSink.ts`) publishes each event through `@wadeck-app/queue-sdk` (`publishAndWait`) AFTER the change is saved, one event at a time, in order. The SDK is a dependency of `task-service` (the shared delivery adapter of both adapters; pinned version in its `package.json`, GitHub Packages, scope registry configured in the user `.npmrc`). It finds and authenticates the daemon, starts it with `queue start` when stopped, keeps the payload off the command line, and needs only `queue` on PATH. One publisher per sink (CLI: per command, created at the first delivery or declaration; module: per module lifetime, created at start by the declaration).

| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |

- `onTaskCreated` / `onTaskDeleted` `description` is the FULL text (`description ?? title`), so subscribers are unaffected by the headline split; no `title` field in them.
- Undefined fields (`parentId`, `type`, `oldType`, `newType`, `oldValue`, `newValue`, `oldParentId`, `newParentId`) are absent from the JSON. Operations other than create/status/link return `{ task, events }` (`TaskChangeResult`; delete: `{ deletedCount, events }`); nothing fires when nothing changed.
- `onTaskDeleted` order: deepest first, so a cascade fires leaves before parents (each event then still has its `parentId`, `orphanedChildIds` is empty); tasks of the same depth keep the plan order. `removedLinkCount` counts links held by the tasks still present at that moment (a holder deleted later in the same plan counts). A task absent from the store at execution time gets no event. Events are delivered one by one after all deletions (a large `--all` costs one publish each). Filter syntax of a subscriber `when:` (queue `PayloadFilter`, on the envelope): `payload.newStatus=done` (dot path, `=`, string/number compare) or a JSONPath starting with `$` that must return a truthy value (`$.payload.newStatus`). `$.status == 'x'` is NOT valid (no operators in the JSONPath form; the status is under `payload`).
- cwd: each publish passes `{ cwd: payload.taskProjectPath }` (= `ctx.project.path`: the main path of a registered project); queue finds `<project>/.queue/subscribers.yml` by walking up from it. A payload without a non-empty string `taskProjectPath` is undelivered (`dropped`) with an explicit reason, never published with the current cwd: a virtual project (payload with `taskProjectId`, no path) gets a reason naming it and how to fix it (`project paths add`), anything else is reported as a producer bug.
- Outcome mapping (SDK `PublishResult.status`):

    | SDK status                                    | Task result                                                                            | Replay text                                                                                                      |
    | --------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
    | `queued`, `dispatched`                        | delivered                                                                              | none                                                                                                             |
    | `dropped` (not recorded)                      | undelivered, `status: 'dropped'`, SDK `reason` (or an explicit "no reason" text)       | `cd '<taskProjectPath>' && queue push <event> '<json>'` (POSIX quotes; no eventId exists)                        |
    | `unknown` (may be recorded)                   | undelivered, `status: 'unknown'`, reason says the event MAY be recorded; never retried | check `queue history` from the project dir; if listed `queue replay <eventId>`; if absent the `queue push` above |
    | publisher throws (SDK promises it never does) | same as `unknown`                                                                      | same as `unknown`                                                                                                |

- Failure never fails the command or the route: stderr line, error line in `<config dir>/logs/*.ndjson` (`task cli logs`; the replay text, hence the payload JSON, is in the file), module answers carry `undelivered` (each with `status`) / `undeliveredText`. The SDK `onError` (kind, message, event, outcome) is written to the same log at level `warn`, not to stderr (the SDK is created `silent`).
- Shutdown: `EventSink.flush()` (optional) waits for the pushes in flight. The CLI calls it at the end of `runTaskCommand`, before `process.exit`; the module returns `{ flush }` from its backend and `lifecycle.teardown` (`teardown.ts`) calls it.
- Tests inject the publisher (`createQueueEventSink({ publisher | createPublisher })`); `queueEventSink.integration.test.ts` runs the real SDK against `startFakeQueueDaemon()` from `@wadeck-app/queue-sdk/testing` (free port, temp config dir; `pushes()`, `respondNext`, `resetNext`, `resetNextRegistration`) with no `queue` on PATH. The real queue daemon is never started by a test.
- Safety net (also registry isolation, see Shared project registry): every `vitest.setup.ts` (task-service, task-cli, app-module-task) sets `QUEUE_SDK_OFF=1` (SDK sends nothing, answers `dropped`; inherited by spawned CLI/app-core processes), so a default sink can never reach a real queue. The SDK honours it even with an explicit `configDir`: the integration test deletes it for its own duration. Never set it outside tests/dev runs (events would be silently dropped; the SDK announces it once).

Event declaration (queue event catalog, SDK >= 2026.10.24-190, protocol 1.1.0; older SDKs and daemons keep working):

- Single source of truth: `queueEventDeclarations` (`task-service/queueEventDeclarations.ts`, source `task`): name, description (<= 500 chars: when it fires, what does NOT), JSON Schema, example, `correlationKey: 'payload.taskId'`. Only `onTaskDeleted` is `terminal: true, outcome: 'info'` (SDK `Declaring your events`: terminal = the event ends the entity it is about; nothing more happens to that `taskId`, and a deletion is neither success nor failure). `onStatusChange` to `done` ends nothing by itself. Tests tie it to the code: one declaration per `TaskEvent` name, examples fit their schema, the payloads really produced by every operation above fit the schemas (`jsonSchemaCheck.ts`, a minimal checker of the subset used, no dependency), daemon limits. Adding or changing an event means editing that file; its hash (`queueEventDeclarationsHash`) is what triggers a new CLI declaration.
- `declareTaskEvents(publisher)` / `sink.declareEvents()`: never throws; outcome `registered | rejected | unsupported | dropped | unknown`. Task log (`task cli logs`): `rejected` error (with the `problems` paths), `unsupported` info (old daemon: update queue-cli), `dropped` / `unknown` warn; stderr only for `rejected` (a bug in our declaration). `registered` is quiet. `flush()` waits for a declaration in flight.
- Module: declared once per start (`registerTaskRoutes`), fire and forget; only with the default sink (an injected `eventSink` has no publisher).
- CLI: declared lazily before the FIRST event delivered by a process, when `<config dir>/queue-events.json` (`{ hash, taskVersion, declaredAt }`) does not hold the current hash (`QueueEventsDeclaration.ts`). Why lazy: the CLI has no start hook, the queue is about to be contacted anyway, and `task-updater.cjs` must stay free of the SDK (it never declares). The marker is written only after `registered`; any other outcome retries at the next event (an old daemon costs one extra request per delivering process until updated). A command without event never declares. Never fails the command. `task cli declare-events [--json]` forces it (exit 1 with the next step otherwise): use it after updating queue-cli or if the queue lost its catalog (the marker cannot know).
- Tests: `daemon.registrations()`, `respondNextRegistration` and `resetNextRegistration(times = 1)` of the SDK fake (SDK >= 2026.10.24-191): one reset still ends `registered` (the SDK retries a registration once, it is idempotent), two in a row end `unknown`. A scripted publisher remains only for a `dropped` without reason and a publisher that throws. `QUEUE_SDK_OFF` also switches `registerEvents` off (`dropped`, reason names the variable): tested in each package's safety net. A test that starts the default module backend must set `XDG_CONFIG_HOME` (the declaration logs in the task config dir).

Decided:

- `onStatusChange` gained `status` (= `newStatus`); `newStatus` stays, so no subscriber breaks.
- A project on the github strategy emits the same events from the same use cases, after the awaited write, with the same payload keys (`TaskIndex.githubEvents.test.ts`); only `onTaskCommentAdded.author` always exists there (the token user). A change made on GitHub itself emits nothing in v1 (R7).
- `taskFile` is NOT in any payload: the task data path moved with the shared project registry (and a virtual project has no folder to resolve it against).
- Comments fire `onTaskCommentAdded` / `onTaskCommentEdited` / `onTaskCommentRemoved` (see Comments). No event for type add/remove: they edit the project config, not a task.
- A changed declaration re-declares by itself (marker hash, test in `TaskIndex.events.test.ts`).

The supported list is passed explicitly at every call site (the scripts default to every platform they know, `darwin-x64` included): `PLATFORMS=win32-x64,darwin-arm64,linux-x64 generate-platform-packages.sh task:app-module/`, `restore-exec-bits.sh <packages dir> task win32-x64,darwin-arm64,linux-x64`, `smoke-packed.sh <packages dir> task <version> win32-x64,darwin-arm64,linux-x64` (`publishWorkflow.test.ts` pins them).
- Version pin: `package-lock.json` must resolve `@wadeck-app/shared-updater` >= `2026.10.25-020` (interrupted-install recovery); `package.json` keeps `latest`. Update only that entry: `npm install @wadeck-app/shared-updater@<exact> --workspace=packages/task-cli`, then restore `latest` in the lockfile workspace entry. `task-updater.cjs` bundles the locked version. `ensureVersion` is async there; we do not call it.
- Dev build guard (shared, `@wadeck-app/shared-cli/ReleaseVersion`: `isReleaseVersion`, `devBuildRefusalMessage('task', v)`; no local copy): a bundle whose version is not CalVer (`YYYY.MM.DD-BBB-xxxxxxxx`, e.g. `BUNDLE_VERSION=0.0.0-local`) never updates the global install. `task cli update` prints `dev build <v>: refusing to update the global install of task; ...` (shared wording, cross-CLI contract) and exits 1; `TaskIndex.ts` passes `VERSION` as 3rd argument of `scheduleBackgroundUpdate`, so `task.cjs` spawns no updater (silent, nothing logged); `task-updater.cjs` logs the line and exits 0 (1 when `UPDATER_FORCE`/`UPDATER_MANUAL`). Covered by `TaskIndex.devBuild.integration.test.ts`.
- Version pin: `package-lock.json` must resolve `@wadeck-app/shared-cli` >= `2026.10.25-044` (ReleaseVersion, versioned scheduling; 042/043 rejected the unpadded month/day npm publishes, e.g. `2026.9.1-028-hash`, so a real release built on day 1-9 or in Jan-Sep would have been treated as a dev build). It is a devDependency bundled by esbuild into both entry points.
- `update-state.json` status `applying` = journal written before `npm install -g`. Live `pid`: an install is running (silent; `cli rollback` refuses). Dead `pid`: interrupted, the next updater run repairs it (`cli version` and the notice say so, `cli rollback` refuses and points to `task cli update`). Never report it as an update (`src/cli/updateNotice.ts`, `src/updateStateWording.ts`).
- `task cli update --log [--json]` (`src/commands/updateLog.ts`): shared-updater writes `{ts, level, msg}` lines to `<configDir>/logs/<UTC date>.ndjson`. Prints the last 50 entries of today, completed with yesterday, minus the `cmd: ...` invocation lines that shared-cli's `logCliInvocation` writes to the same file. No `logs/` dir: message naming it (`[]` with `--json`). `task cli logs` is the unfiltered raw dump of today.
- Test isolation: every test spawn of `task.cjs`, `task-updater.cjs` or the CLI goes through `spawnIsolated` (`src/isolatedCliEnv.ts`): temp config dir/HOME/XDG, temp `NPM_CONFIG_PREFIX`, own npmrc files, unreachable registry (also `npm_config_@wadeck-app:registry`, which outranks a project `.npmrc`), cwd in the temp tree. It throws on any other env. Never spawn a bundle with `process.env`. Async twins `startIsolated` / `runIsolated` for tests that must keep answering (fake registry in the test process).
- Interrupted `npm install -g`, verified for real (`updater.interrupted.integration.test.ts`, `fakeNpmRegistry.ts`: loopback registry whose tarball hangs; shared-updater's `MockRegistry` cannot start, its server script is not published). npm moves the old package aside (`.task-cli-XXXX`) BEFORE fetching the new one, so a kill leaves the global package missing (tarball without body) or truncated (half body); the next updater run (explicit or the background one any command schedules) restores the previous version, state `rolled-back` ("interrupted install repaired"), retired dir gone. Killing only npm: the updater restores and records `failed`. On Windows `process.kill(updaterPid)` also ended npm (cause not checked), so the live-orphan-npm branch of the repair is NOT verified here.
- Bin shim (`ci/templates/bin-launcher.js.tmpl`, CommonJS, logic in `run(deps)` with injected side effects: `binShim.unit.test.ts`; real file: `binShim.platformPackage.integration.test.ts`): first checks `task.cjs` next to `bin/`; missing = "installation is incomplete" + `npm install -g @wadeck-app/task-cli`, exit 1. Every command but `start` runs `node task.cjs <args>` directly on ALL platforms (no launcher, no platform package needed); only `start` resolves the Go launcher, installs the platform package lazily when missing, and makes it executable if it is not. No failure is silent: an exec error without exit status prints code, path, platform and fix, exit 1.
- Incident (macOS arm64: after "platform package missing -- installing..." every command exited in ~60 ms with no output): the published `task-cli-darwin-arm64` tarball holds `task` as mode 0644 (checked with `npm pack` + `tar -tvzf`; Mach-O arm64 file, so the binary itself is right). `actions/upload-artifact`/`download-artifact` drop file modes and npm only chmods `bin` entries, so `execFileSync` threw EACCES and the old shim turned an error without numeric `status` into a silent exit 1. Fixed by the direct-node path, the chmod fallback, and `ci/scripts/restore-exec-bits.sh` before publish. CI job `packed-smoke` (matrix `macos-latest` arm64 and `ubuntu-latest`) runs `ci/scripts/smoke-packed.sh` on the packed tarballs, with and without the platform package, and gates `publish` on a real FAILURE only (`publish` runs unless the smoke result is `failure`). The label `macos-14` never got a runner (two runs cancelled, nothing published); `macos-latest` got one in run 43511114515 (green) but not in 43511865443 (no runner for 15 minutes, job `cancelled`), so an unavailable runner must not block a release. The registry is unreachable on purpose there, so `task cli version` (shared-cli prints only "Failed to fetch latest version" on stderr, exit 0, nothing on stdout) is judged on stdout + stderr and must name the package. The Go launcher itself (source: `@wadeck-app/singleton-daemon-kit/go-launcher`) runs node synchronously with inherited stdio on darwin and logs to stderr; it does not detach. A bare `task.exe` (no `LAUNCHER_BUNDLE_OVERRIDE`) cannot find the bundle even when installed, since `launcher-task.config.json` `nodeScript` is `task.cjs` (sibling-package specifier `@wadeck-app/task-cli/task.cjs` would be needed; needs a launcher rebuild, not verified).
