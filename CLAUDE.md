## Packages

| Package           | Role                                                                                                             |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| `task-core`       | Storage: `TaskStore`, config loading, domain errors.                                                             |
| `task-service`    | Use cases shared by the CLI and the app-module. Pure: no console, no `process.exit`; returns results and events. |
| `task-cli`        | `task` binary: arg parsing and output over task-service, updater, app-core registration.                         |
| `app-module-task` | app-core module (id `task`): routes `/api/modules/task/*` and dsl-views over task-service.                       |

## Dependency direction

`task-core` <- `task-service` <- `task-cli` and `app-module-task`. The two adapters never import each other, and `task-service` knows no CLI, HTTP or app-core library, never prints or exits. `npm run test:architecture` (`architecture/`, part of `npm test`) enforces it on imports, `package.json` dependencies and source patterns.

`@wadeck-app/project-sdk` ("latest", lockfile pins it; zero dependencies) is imported by `task-service` only; the architecture test forbids it in the sources of the adapters and `task-core` (their tests may use its mutations for fixtures). Shared rules live in `task-service` (`resolveProject`, `resolveProjectReference`, `listKnownProjects`, `describeError` for the SDK errors), adapters only parse input and format output: `describeError` (error kind, message, hint; CLI maps to stderr, module to HTTP status), `selectDeleteTargets` / `describeDeleteEffects`, `openTaskContext`, `getTaskLogDir`, `countTasksByStatus`, `showTaskWithRelations`, the storage (`storage.ts`: `registryStorage` / `legacyStorage`, `chooseDataLocation`; `openResolvedProject`; `loadTaskConfig`; `migrateData`), the READ-ONLY legacy list (`listRegisteredProjects`, `inspectRegisteredProjects`), and the cross-project reads `summarizeProjects` / `listTasksAcrossProjects` (per-project figures and tasks tagged with their project; unreadable projects reported, `NoReadableProjectsError` when none can be read; used by the app-module and by the CLI, see CLI parity below).

## Shared project registry (stage 2a)

Migration to the registry of the `project` CLI (`@wadeck-app/project-sdk`, `$XDG_CONFIG_HOME/project`, else `~/.config/project`). **Stage 2a (now)**: data and config of REGISTERED projects live in the registry (a registered project that still has its tasks in `.task` keeps working on them until it is migrated, because live tools read that `.task` directly), task no longer writes any registry, and every removal that breaks no read is done. **Stage 2b (later, on the owner's go once their machine is migrated)** removes the legacy read path, see the list at the end. Task never writes the registry (architecture rule `NO_REGISTRY_WRITE`: no SDK mutation import, no legacy writer) and the registry lock covers the registry only: task data consistency is task's own concern (Q30), so task data has no lock, only atomic writes.

What changed for the user:

| Before                                                                             | Now                                                                                                                                                                                                                                                                                                                                |
| ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `task init` creates `.task` and registers                                          | `project add <dir> [--name n]`; `task init` fails with that command                                                                                                                                                                                                                                                                |
| `task projects add\|remove\|move\|prune\|list`                                     | project CLI (`project add\|remove\|paths move\|list`); each answers exit 1 with the replacement; `task projects summary` and `task list --all-projects` stay                                                                                                                                                                       |
| tasks in `<dir>/.task`                                                             | registered project: `<registry>/projects/<id>/task/data` (`tasks/<id>.json` + `task-index.json`), config `<registry>/projects/<id>/task/config/config.yml`; BUT while the registry holds no task data and its `.task` holds data (or a config the registry lacks) the `.task` is still read and written, with one deprecation line |
| registered, tasks in `.task`, no copy yet                                          | works exactly as before; stderr (also `--json`): `Deprecated: project <name> still keeps its task data in <dir>/.task; copy it with: task cli migrate-data -p <name> (then delete .task by hand)`                                                                                                                                  |
| registered, tasks in both places, same task ids (state right after `migrate-data`) | registry used; one line `old copy still in <dir>/.task: delete it by hand once checked`                                                                                                                                                                                                                                            |
| registered, tasks in both places, ids differ (real split)                          | error naming both folders and the two ways out (keep one, remove the other by hand)                                                                                                                                                                                                                                                |
| Projects page: add / edit / remove forms                                           | read-only list (marker, registry id or the exact `project add "<dir>"`, problem with its fix)                                                                                                                                                                                                                                      |

- Resolution (`resolveProject`): `-p/--project <ref>` > `TASK_PROJECT` > the directory (`--project-dir` > `TASK_PROJECT_DIR` > `PROJECT_DIR` > cwd) looked up in the registry (deepest registered ancestor wins, no marker file, no walk-up). `<ref>` is an id (or unique prefix >= 4), name or alias, case-insensitive, never a path. A reference that does not resolve is an error (suggestions, candidates), never a fallback; `-p` with `--project-dir` is refused. The OUTCOME decides the storage: registered -> registry (`ResolvedProject.storage`, `kind: 'registry'`); legacy -> `<dir>/.task` as before. `path` is the MAIN path (a cwd in a secondary path resolves to it; absent for a virtual project).
- Storage (`storage.ts`): `TaskStore` gets `tasksDir = <data>/tasks`, its index is `<data>/task-index.json` (pinned by tests in task-core, storage and openContext). Reading a fresh project creates nothing; the first write creates `<data>` (the store's `ensureDirectory`, so no `{ensure:true}` on read). A registered project with no data anywhere is a fresh project.
- Data location (`chooseDataLocation`, called by `openTaskContext`, so by the CLI, the module and the overviews; result `ctx.storage` + `ctx.notices`): registry has task data and `.task` none -> registry, silent; registry none and `.task` has tasks/index (or a `config.yml` the registry lacks) -> UNMIGRATED: legacy storage of the main path with the registry identity (id, name), exactly stage 1, notice = the `Deprecated: project ...` line (CLI: ONE stderr line per process, also with `--json`, and the task log; module: task log once); both have task data with the same task ids -> registry + the `old copy still in ...` note; both have task data with different ids -> `ProjectDataSplitError` (409 in the module) naming both folders and the two ways out. A fresh project (neither) uses the registry. `resolveProject` never refuses, so `migrate-data` can run in any state.
- Config (`projectConfig.ts`, `TASK_CONFIG_SCHEMA`): for a registered project every `config.yml` of the project chain (root first, own last) is read, validated (`validateLayer`, layer name = the file path) and merged (`mergeLayers`): `statuses`, `types`, `fields`, `hooks` are `local` (replace; a parent's values are valid there and never reach the child), `defaults` is `inherit` + `deep`. An unknown or misplaced key is a `ConfigSchemaError` naming the FILE and the key (`invalid`, 400); the status rules (>= 1, <= 1 default) apply to the merged value and name the file. Task keeps its global/project hooks separation: the task GLOBAL config (`~/.task/config.yml`: defaults, hooks) stays task's own file, merged separately (project value > global fallback for `defaults.priority`). `task type add|remove` write the project's OWN layer (created with its folder if missing). Legacy projects: `TaskConfigLoader.load` unchanged (unknown keys ignored).
- Atomic writes: task files, `task-index.json` and `config.yml` go through the SDK's `writeFileAtomic` (temp file, fsync, rename) via `TaskStore`'s injectable `writeFile`, for registered AND legacy projects (`atomicWrites.test.ts` spies the SDK). A vanished legacy `.task` is still an error on `type add` (the directory is only created for registry projects).
- Migration, by the user (nothing breaks before it): install project-cli, `project add <dir> --name n` (the project keeps working on its `.task` with one stderr line), `task cli migrate-data -p n [--dry-run] [--json]`, check (`task list -p n --all`; from then on the registry copy is used and each command prints the old-copy note), delete `.task` by hand (the note stops). Anything else reading the `.task` directly (flows) must be moved to the registry data before that deletion. `migrate-data` is an ADDITIVE HELPER that deviates from Decision #17 ("by hand"), because hand-copying hundreds of task files is error-prone and the data-location rules above make a half-done migration visible (the split error, the old-copy note): it copies `tasks/*.json`, `task-index.json`, `config.yml` of `<main path>/.task` into the registry (COPY only, never moves or deletes the source), refuses when the registry already has task data or the own config (names both folders; no `--force`, move the registry data away by hand), verifies the file count and every byte size, rolls back what it created on any failure, rebuilds nothing (a missing index is a warning), lists what it left alone (`notCopied`), and prints the next step. A legacy folder or a virtual project gets an actionable error.
- Virtual project (registered, no path): data and config work (id-based); events cannot get a cwd, so the operation succeeds and the event is returned UNDELIVERED with a reason naming the virtual project and `project paths add` (never `process.cwd()`; no `taskProjectPath` key in the payload). Limit: cross-project views and the module do not list virtual projects, and `?project=<virtual>` answers 409 pointing to `task -p <name>`.
- Legacy path (removed in 2b): a directory holding a `.task` that the registry does not resolve (or a registry that cannot be read) works as before, with ONE `Deprecated: ...` line on stderr per command (also with `--json`) naming the dir, `project add "<dir>"` and `task cli migrate-data`. A subfolder with its own `.task` inside a registered folder keeps its own data (never switched silently). `--project-dir`, `TASK_PROJECT_DIR`, `PROJECT_DIR` still work.
- Log: each command appends the resolution line (project, source flag/env/cwd/legacy, path, registry dir, data dir) to the task log (`task cli logs`).
- Events: `taskProjectId` (registry id) is in every payload of a registered project, absent for the legacy path; `taskProjectName` is then the registry name; `taskProjectPath` stays the main path (the queue cwd).
- Cross-project views (`summarizeProjects`, `listTasksAcrossProjects`, `listKnownProjects`; CLI `--all-projects` / `projects summary`; module `/projects`, `/summary`): every registered project WITH a path (any project can hold tasks, so none is filtered for lack of a `.task`; a fresh one shows 0 tasks), then `projects.json` entries not matching a registered main path, each with `registered`. The legacy `projects.json` is READ ONLY (`projectsRegistry.ts`, validation errors kept; writers and `registryLock` deleted). A broken parent chain lists the project unreadable (`problem`), a registry that cannot be read is `registryProblem`. Unregistered ones: JSON key + stderr `Deprecated` line (text mode) in the CLI; `registryHint`, Registry column and `registryNotice` badge in the module. `--all-projects` refuses `-p` / `TASK_PROJECT` like `--project-dir`.
- Module: `?project=` takes an id, name, alias (registry), the old slug or the absolute dir (deprecated); page addresses and API queries use the id for registered projects; the registry is read at every request (no cache); missing = first-use state, corrupt = typed error shown inline. `last-project.json` stores `{ "id": ... }`; an old `{ "path": ... }` file is ignored with ONE line in the task log (no problem shown, nothing preselected until the next creation); a legacy project (no id) is not remembered.
- Tests: the SDK has no off switch. Every `vitest.setup.ts` (task-service, task-cli, app-module-task) points `XDG_CONFIG_HOME`, `HOME`, `USERPROFILE` at a temp dir (`registrySafetyNet.test.ts` proves it); fixtures build registries with the SDK's `addProject` in a temp dir (`createSharedRegistrySandbox`, `createTestWorld().registerShared`); the legacy list and a legacy `.task` are written by hand (`addLegacyEntry`, `initLegacyProject`, `addLegacyListEntry`). `task-core` has no setup and never touches the registry.

Stage 2b (nothing started; on the owner's explicit go): remove the legacy `.task`-in-cwd fallback, the unmigrated read of REGISTERED projects (the `legacy` branch and notices of `chooseDataLocation`: then the split check alone remains, or an error for any `.task` data left) (`legacy()` in `resolveProject`, `legacyStorage`, `ProjectNotInitializedError` for it), `--project-dir`, `TASK_PROJECT_DIR`, `PROJECT_DIR` (and the `--all-projects` refusals/notes about them), the reading of `projects.json` (`projectsRegistry.ts`, the legacy rows of the cross-project views, `registryHint` / `registryNotice` for them, the Deprecated lines), the path slugs of the module (`projectSlug`, absolute-dir `?project=`), `task init` / `task projects add|remove|move|prune|list` pointer commands once nobody needs them; then add the architecture rule "no `.task` in the sources" and decide whether `migrate-data` stays as a helper.

## app-core registration

- `task cli register [--json]` / `task cli unregister [--json]`; `task cli update` registers by itself when the shipped app-module version changed. Task has no daemon, so nothing registers at start.
- Exit 0 when app-core took it or is absent/not running (deferred, skipped); exit 1 with app-core's reason when it refuses.
- Manifest: `app-module/manifest.json` next to `task.cjs`, else `packages/app-module-task/dist-module/manifest.json` (source checkout: `BUNDLE_VERSION=0.0.0-local npm run bundle --workspace=packages/app-module-task`). Neither found is an error naming both paths.
- Staging: app-core stores the PATH of a manifest, and npm replaces the package folder on update (and removes it on uninstall). An installed module (`<pkg>/app-module/`) is therefore copied to `<config dir>/app-module/<manifest version>/` (`appModuleStaging.ts`: temp dir then rename, kept if already complete, error naming source and destination) and the STAGED manifest is registered, by `task cli register`, the post-update registration and the post-rollback registration (all via `attemptStagedRegistration`); `unregister` is unchanged. Older staged versions are removed only after the outcome is `registered` or `deferred`; any other status (refused, skipped, an unknown one of a newer SDK) keeps them. A source checkout's `dist-module` is registered as is (a rebuild keeps the version, a staged copy would go stale). `appModuleStaging.ts` imports only fs/path and `registerAfterUpdate.ts` (the updater bundle must stay under 500 KB and free of the task runtime).
- The module has no cwd: projects come from the shared registry first, then `<config dir>/projects.json` (read only, deprecated), routes take `?project=<id|name|alias>` (or the legacy absolute dir, deprecated). See Shared project registry (stage 2a).
- Registry upkeep moved to the project CLI (Decision #20): `task init`, `task projects add|remove|move|prune|list` and the Projects page forms/routes are gone (the task commands answer exit 1, text or `{error, hint}`, with the replacement: `project add "<dir>"`, `project remove`, `project paths move`, `project list`; `task init` honours `--project-dir` / `TASK_PROJECT_DIR` / `PROJECT_DIR` in the suggested directory). `task projects summary` stays. Deleted from `task-service`: `initProject`, `addProject`, `relocateProject`, `removeRegisteredProject`, `pruneMissingProjects`, `registerProject`, `unregisterProject`, `registerInitializedProject`, `validateProjectPath`, `registryLock`, and the errors `InvalidProjectPathError`, `ProjectNotRegisteredError`, `ProjectAlreadyRegisteredError`.
- `deferred` from the SDK means only "the POST failed" (refused, reset, or no answer within 3 s) and the config dir exists, not proof that app-core is down; the message says "not running" regardless. If app-core is up, run `task cli register`.
- Testing against a real app-core: set `APP_CORE_PORT` and `APP_CORE_CONFIG_DIR`; without a free `APP_CORE_PORT` the SDK talks to the app-core running on 4850.

## app-module-task routes and pages

Routes (`/api/modules/task/...`, all take `?project=<id|name|alias>`, legacy dir still accepted, typed errors mapped in `errors.ts`): GET `/projects` `/summary` `/tasks` `/tasks/:id` `/tasks/:id/{history,children,ancestors,links}` `/tree` `/types`; POST `/tasks` `/tasks/:id/{status,labels,links,parent,type,meta}` `/types` `/tasks/delete/plan` `/tasks/delete` (needs `confirm: true`, else 400 with the plan); DELETE `/tasks/:id/{labels/:label,links,parent}` `/types/:name`. Every route that changes a task produces queue events (create, status, labels, links, parent, type, meta, `POST /tasks/delete`; see Queue events) and answers `undelivered` / `undeliveredText`; `/types`, `/projects*` and the delete preview emit nothing. Every view that fires one of these routes shows `undeliveredText` in a warning badge bound to the action's `resultKey` (Task page: one per form section; New task; Delete, under `plan`, saying how many events were not delivered); `manifest.test.ts` fails when a mutating action has no such badge. `POST /tasks/delete` failing partway (`PartialDeleteError` from `executeDelete`: `deletedCount`, `plannedCount`, `failedTaskId`, `events`) delivers the events of the tasks already deleted, then answers 500 with `deletedCount`, `plannedCount`, `partial: true`, `undelivered`; `task delete` does the same and exits 1 naming how many were deleted. A failure before the first deletion is the plain original error.

Pages: nav `/tasks` `/tree` `/projects` `/types` (global, or the only project); global `/tasks/new` `/tasks/delete` (project chosen in a select); per project, the project being a PATH segment `:project` (read as `$route.project`): `/tasks/p/:project` (list), `/tasks/p/:project/:id`, `/tasks/p/:project/:id/history`, `/tasks/p/:project/new`, `/tasks/p/:project/delete`, `/tree/p/:project`, `/types/p/:project`; dashboard widget. A global page and its per-project twin share one view file. Why a path segment: the shell's breadcrumb links each crumb to the current address up to that page, path params substituted, QUERY DROPPED (`navHelpers.ts` `routeChain`, `href: match.pathnameBase`; confirmed in a browser on app-core-cli 075 and the prebuilt 128). `?project=` on a page address is ignored.

- `:project` is the registry id (8 hex) of a registered project, else (project only in the legacy list) a slug (`projectRef.ts`: `<dir name>~<6 hex of the dir>`), never the directory (old slugs of now-registered projects still resolve): the crumb prints the value cut at 16 characters, so a directory would read the same for every project of a workspace. `findProjectByRef` resolves a slug OR an absolute directory (one resolution, in `GET /projects`, which the views feed with `$route.project`); the API routes keep `?project=<dir>`. `hrefs.ts` builds every page address; the route layer never writes `?project=` in a page link.
- Old addresses that no longer exist (shell answers "Page not found"): `/tasks/:id`, `/tasks/:id/history`, `/new`, `/delete`, and `?project=` on any page (the page shows the global scope). Not kept: a redirect cannot be declared, and a second route set would double the pages.

Projects page (`/projects`, no `?project`): a READ-ONLY list. `GET /projects` gives `projectRows` (name, path, `registered`, `registryText` = `shared registry (<id>)` or the exact `Not in the shared project registry: project add "<dir>"`, `openText`, `problemText` with its fix), `openLinks`/`hasOpenLinks` (the table has no row click), `attentionText`, `registryNotice`, `noProjectsText`. The routes `POST /projects`, `/projects/relocate`, `/projects/remove` and their forms/yaml are deleted (404); `?page=projects` is gone. The view has one source and no action.

Global view (all registered projects): the widget (`GET /summary` without `?project`: open/total plus `projectRows`, one row per project with its tasks link or its error; nothing registered is a 200 with `noProjects`, not an error) and the Tasks page without `?project` while several projects are registered (`GET /tasks?allProjects=true`, Project column, rows link to the per-project address; `/projects` gives `globalQuery`, `allProjectsHref`, `unknownProjectText`). With `?project`, or a single registered project, the Tasks page is the per-project page. Per page without `?project` and with several projects:

| Page     | Scope                                                                                                                                                                                                                                                                                                                           |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tasks    | global list, Project column                                                                                                                                                                                                                                                                                                     |
| Tree     | `GET /tree?allProjects=true`: `groups`, one `Section` per project (title with count, link to its tree, its forest as a table, children indented by a label prefix; the scope text counts open tasks and names the closed parents kept above them; an empty project has an explicit empty message); unreadable ones in `warning` |
| Types    | `GET /types?allProjects=true`: Project/Type rows with a Remove button each (the row carries project and type, no cascading select; no row click); add through a project select (readable only, none preselected)                                                                                                                |
| New task | project select (readable only; preselected when exactly one is readable, else the project of the last created task if still readable); parent list only when the URL names the project                                                                                                                                          |
| Delete   | never global: project select without default; the project is named in the preview, in a banner and in the confirm button label; `allProjects` is ignored by the delete routes                                                                                                                                                   |

No page has a back link ("All projects", "All tasks", "Back to the task" are gone, with `allProjectsHref`, `globalHrefs`, `tasksHref`): the breadcrumb carries the context (yaml test `no link whose purpose is going back` has an allowlist of the links kept: forward features only). An address naming an unregistered project shows `unknownProjectText` on every per-project page. The detail and history pages (`GET /tasks/:id`, `/history`, `/links`) answer `?blank=true` like the list routes.

CLI parity (task-cli `GlobalViewCommands.ts`, parsing and output only over the same service reads; neither needs a project):

- `task list --all-projects [--all] [--json]`: text table PROJECT / ID / STATUS / TITLE; `--json` is the `listTasksAcrossProjects` answer as is (`tasks` tagged with `project`, `readableCount`, `unreadable`). Unreadable projects: warning on stderr in text mode (in `unreadable` in JSON), the others are still listed; exit 1 (`NoReadableProjectsError`, reasons + fix) only when none can be read; nothing registered is exit 0 with the `project add <dir>` hint. Fails with an actionable error when combined with `--follow`/`-f`, `--tree`, `--parent`, `--project-dir` or `TASK_PROJECT_DIR` (same exit code and message shape, the message names the source; empty value = unset). `PROJECT_DIR` is generic (a parent tool may set it ambiently), so it is not an error: one `Note: ... is ignored` line on stderr, in `--json` too (stdout stays the pure answer). `--config` / `TASK_CONFIG` select no project and are untouched.
- `task projects summary` takes no project, so a project flag or variable there contradicts nothing and is left alone.
- `task projects summary [--json]`: totals line, by-status line, one line per project (`open / total`, or `[unreadable: reason]`, not counted); `--json` is the `summarizeProjects` answer. Exit 1 only when none can be read.
- `--follow` is not implemented for `--all-projects`. It would be feasible with `diffSnapshot` keyed by project path + task id over `listTasksAcrossProjects`, but needs decisions first: cost (every project re-read every 500 ms), and what to print when a project becomes (un)readable or all fail mid-follow.
- JSON errors are `{"error": ..., "hint": ...}` for every command going through `errorOutput` / `failure` (no `hint` key without one). `set-type` has no separate hint: its message already lists the valid types. `task cli register` and `task plugins config` keep their own error shapes.

View conventions (app-core DSL, checked against the real shell):

- Mutations: Form + `$actions` + `onSubmit: $ctx.<action>`; the form data is the body and fills `{placeholders}` of the action URL. Placeholders are not URL-encoded: forms carry `projectParam` (encoded by the route) and use `?project={projectParam}`.
- The shell drops the answer of a failed action and discards ALL source answers when one source fails (blank page). Every request of a view therefore adds `inlineErrors=true`: the route answers a failure as 200 with `failed`, `httpStatus` and `errorText` (message, plus the hint unless it explains the JSON API), and the view shows `errorText` in a `variant: danger` Badge. Actions publish with `resultKey` per section, so the message sits next to its form.
- Zero registered projects: `/projects` answers `noProjects` + `noProjectsText` (the next step: `project add <dir>`, and `task cli migrate-data -p <name>` for old tasks) and `forms: null`; every page shows that text in an info Badge (a page with only a bound title and no badge renders blank). `forms` is also null when the selected project is unreadable (data split between the registry and the `.task`, invalid config, legacy directory gone). The widget shows its figures only `$if: summary.projectCount`, so a failure leaves the error alone. A legacy directory that vanished is told apart (`exists: false`; fix: delete the line of `projects.json` by hand, or `project add` the new folder).
- Sources use `?{query}`. The shell keeps the last answer of a skipped source (reproduced: unknown project, Tasks menu, browser Back left the 6 rows of the global list), so no query may be empty: a page with several scopes (Tasks, Tree, Types) has ONE source fed by `scopeQuery` (project, global, or `blank=true`), the others (New, detail, history) by `projectQuery` (project or `blank=true`); a yaml test enforces it. `?blank=true` makes `/tasks`, `/tree`, `/types` answer `{blank: true}`, which replaces the previous scope's data (verified: global -> back -> unknown project leaves no rows).
- In the dev shell, forms were observed to reset (element refs change, typed values vanish) within seconds of page load, next to repeated `/api/modules` requests (cause not verified): drive forms in one fast command sequence with semantic locators.
- The shell reloads on a URL change only the sources naming a `$urlParam.*`/`$route.*`: a source waiting for `projects` also takes `reload: $urlParam.reload` (always empty, so never sent), else filter links and project choice leave the page stale or blank until F5.
- Installed shell (app-core-cli 2026.10.18-035, dsl-ui 2026.10.18-101): a YAML DataTable column keeps only `key`/`field` and `label` (`normalizeColumn`); `mono`, `muted`, `width`, `truncate`, `nowrap`, `format`, `sortable`, `badge` are dropped without a message. Working: `type: actions` columns (`items`: label, action, variant, condition), `navigateTo`, `onRowClick`, `onAction`, `expansion`, `selectable`/`batchActions`, `fontMono`, `emptyMessage`. No row styling or grouping exists, installed or in dsl-ui 123 (app-core working tree). dsl-ui >= 2026.10.20 (published app-core-cli 2026.10.22-065 and later) honours the column options and substitutes `{key}` of the clicked row in row action URLs. Columns of short codes carry `nowrap: true` (test-enforced) so that an upgrade fixes the one-character-per-line wrapping (`break-all`) without a change; routes give display texts (`titleText`, `created`, `time`, `projectText`). A `PageHeader` with `headerActions` drops its `subtitle`.
- A `FieldSelect` showing its first option while the form holds `''` makes picking that option a no-change (Save stays off): selects that act on an existing item (remove label/type) need a `placeholder`.
- `FieldSelect` crashes the page until its options load: guard with `$if`. `$if` has no negation and `[]` is truthy: routes give boolean flags (`hasLabels`, `noTypes`...).
- A row action WITHOUT url stores the clicked row under its `resultKey` (`$ctx.<key>`): used by the Types Remove button (pick the row, then a confirm form takes it as `initialData`; the removal answer shares the key and clears the confirm). A row action WITH url requests `{id}` unsubstituted in the installed shell (404 on `/tasks/%7Bid%7D`, verified). A button in a row also fires the row click (installed and 123): a table with row actions has no `navigateTo`.
- A form cannot cascade: `FieldSelect` has no dependent options, no component publishes `$outputs`, sources read only `$ctx`/`$vars`/`$source`/`$urlParam`/`$route` (no `$form`). Pick-then-confirm (above) replaces a dependent select.
- A view cannot loop: a block repeated per project (Tree) is a list of DSL nodes built by the route (`dslNodes.ts`: `Section`, `ButtonLink`, `DataTable`; a text starting with `$` is made literal) rendered by `ExtensionSlot` `items`.
- Persisted state: none for views (no `$persist`, `$vars` live in memory, nav links drop `?project`, shell localStorage is internal). The last created-in project (registry id) is kept by the module in `ctx.dataDir/last-project.json`; a corrupt file is reported (`lastProjectProblem`), a failed write is a warning on the create answer.
- Narrow screens (390px): the table wrapping is the `nowrap` point above; `PageHeader` has no wrap or gap (title and actions touch, actions stack), and the installed navbar overflows: both are app-core fixes.
- Breadcrumb: minimum shell for it is app-core-cli >= 2026.10.19-063 (062 only behind a dev A/B test); older shells have no back navigation on New/Delete/History. ## Queue events (current contract)

Operations in `task-service` return events; the caller hands them to the `EventSink`. The default sink (`queueEventSink.ts`) publishes each event through `@wadeck-app/queue-sdk` (`publishAndWait`) AFTER the change is saved, one event at a time, in order. The SDK is a dependency of `task-service` (the shared delivery adapter of both adapters; pinned version in its `package.json`, GitHub Packages, scope registry configured in the user `.npmrc`). It finds and authenticates the daemon, starts it with `queue start` when stopped, keeps the payload off the command line, and needs only `queue` on PATH. One publisher per sink (CLI: per command, created at the first delivery or declaration; module: per module lifetime, created at start by the declaration).

| Event                 | Emitted by (CLI, route)                                                                                                                                                  | Payload (plus `taskProjectName`, `taskProjectPath`, and `taskProjectId` when registered, on all)                                                 | Not fired when                                                                         |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| `onTaskCreated`       | `new`, `POST /tasks`                                                                                                                                                     | `taskId, status, description, parentId, type, labels`                                                                                            | later changes                                                                          |
| `onStatusChange`      | `set-status`, `POST /tasks/:id/status`                                                                                                                                   | `taskId, oldStatus, newStatus, status, type, labels`; `status` = `newStatus` (additive copy, so `payload.status` works like on the other events) | unchanged status (`TaskStore.updateStatus` throws `TaskConflictError`)                 |
| `onTaskLinked`        | `link`, `POST /tasks/:id/links`                                                                                                                                          | `taskId` (holder of the stored link), `linkType` (canonical), `targetId`                                                                         | link refused                                                                           |
| `onTaskUnlinked`      | `unlink`, `DELETE /tasks/:id/links`                                                                                                                                      | `taskId, linkType, targetId`                                                                                                                     | task deleted (see `removedLinkCount`)                                                  |
| `onTaskUnblocked`     | `set-status`, `POST /tasks/:id/status`: status change to a terminal status from a non-terminal one, once per task whose last open blocker it was, after `onStatusChange` | `taskId` (the unblocked task), `blockerId, status, type, labels`                                                                                 | another blocker still open                                                             |
| `onTaskTypeChanged`   | `set-type`, `POST /tasks/:id/type`                                                                                                                                       | `taskId, oldType, newType` (`oldType` absent for a task without type)                                                                            | same type (the store still rewrites the file), unknown type                            |
| `onTaskLabelAdded`    | `add-label`, `POST /tasks/:id/labels`                                                                                                                                    | `taskId, label`                                                                                                                                  | label already there                                                                    |
| `onTaskLabelRemoved`  | `remove-label`, `DELETE /tasks/:id/labels/:label`                                                                                                                        | `taskId, label`                                                                                                                                  | label absent                                                                           |
| `onTaskMetaChanged`   | `set-meta`, `POST /tasks/:id/meta`                                                                                                                                       | `taskId, key, oldValue, newValue` (`oldValue` absent for a new key; an existing empty value is `""`)                                             | same value                                                                             |
| `onTaskParentChanged` | `set-parent`, `remove-parent`, `POST` / `DELETE /tasks/:id/parent`                                                                                                       | `taskId, oldParentId, newParentId` (absent = root task)                                                                                          | same parent, cycle, `remove-parent` of a root task (refused)                           |
| `onTaskDeleted`       | `delete` (every selector, `--cascade-delete`), `POST /tasks/delete` with `confirm: true`: one per deleted task, after the deletion                                       | `taskId, description, status, parentId, orphanedChildIds, removedLinkCount`                                                                      | `--dry-run`, `POST /tasks/delete/plan`, unconfirmed or refused delete, nothing matched |

- Undefined fields (`parentId`, `type`, `oldType`, `oldValue`, `oldParentId`, `newParentId`) are absent from the JSON. Operations other than create/status/link return `{ task, events }` (`TaskChangeResult`; delete: `{ deletedCount, events }`); nothing fires when nothing changed.
- `onTaskDeleted` order: deepest first, so a cascade fires leaves before parents (each event then still has its `parentId`, `orphanedChildIds` is empty); tasks of the same depth keep the plan order. `removedLinkCount` counts links held by the tasks still present at that moment (a holder deleted later in the same plan counts). A task absent from the store at execution time gets no event. Events are delivered one by one after all deletions (a large `--all` costs one publish each). Filter syntax of a subscriber `when:` (queue `PayloadFilter`, on the envelope): `payload.newStatus=done` (dot path, `=`, string/number compare) or a JSONPath starting with `$` that must return a truthy value (`$.payload.newStatus`). `$.status == 'x'` is NOT valid (no operators in the JSONPath form; the status is under `payload`).
- cwd: each publish passes `{ cwd: payload.taskProjectPath }` (= `ctx.project.path`: the main path of a registered project, else the legacy project dir); queue finds `<project>/.queue/subscribers.yml` by walking up from it. A payload without a non-empty string `taskProjectPath` is undelivered (`dropped`) with an explicit reason, never published with the current cwd: a virtual project (payload with `taskProjectId`, no path) gets a reason naming it and how to fix it (`project paths add`), anything else is reported as a producer bug.
- Outcome mapping (SDK `PublishResult.status`):

    | SDK status                                    | Task result                                                                            | Replay text                                                                                                      |
    | --------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
    | `queued`, `dispatched`                        | delivered                                                                              | none                                                                                                             |
    | `dropped` (not recorded)                      | undelivered, `status: 'dropped'`, SDK `reason` (or an explicit "no reason" text)       | `cd '<taskProjectPath>' && queue push <event> '<json>'` (POSIX quotes; no eventId exists)                        |
    | `unknown` (may be recorded)                   | undelivered, `status: 'unknown'`, reason says the event MAY be recorded; never retried | check `queue history` from the project dir; if listed `queue replay <eventId>`; if absent the `queue push` above |
    | publisher throws (SDK promises it never does) | same as `unknown`                                                                      | same as `unknown`                                                                                                |

- Failure never fails the command or the route: stderr line, error line in `<config dir>/logs/*.ndjson` (`task cli logs`; the replay text, hence the payload JSON, is in the file), module answers carry `undelivered` (each with `status`) / `undeliveredText`. The SDK `onError` (kind, message, event, outcome) is written to the same log at level `warn`, not to stderr (the SDK is created `silent`).
- Shutdown: `EventSink.flush()` (optional) waits for the pushes in flight. The CLI calls it at the end of `runTaskCommand`, before `process.exit`; the module returns `{ flush }` from its backend and `lifecycle.teardown` (`teardown.ts`) calls it.
- Tests inject the publisher (`createQueueEventSink({ publisher | createPublisher })`); `queueEventSink.integration.test.ts` runs the real SDK against `startFakeQueueDaemon()` from `@wadeck-app/queue-sdk/testing` (free port, temp config dir; `pushes()`, `respondNext`, `resetNext`, `resetNextRegistration`) with no `queue` on PATH. The real queue daemon is never started by a test.
- Safety net (also registry isolation, see Shared project registry): every `vitest.setup.ts` (task-service, task-cli, app-module-task) sets `QUEUE_SDK_OFF=1` (SDK sends nothing, answers `dropped`; inherited by spawned CLI/app-core processes), so a default sink can never reach a real queue. The SDK honours it even with an explicit `configDir`: the integration test deletes it for its own duration. Never set it outside tests/dev runs (events would be silently dropped; the SDK announces it once).

Event declaration (queue event catalog, SDK >= 2026.10.24-190, protocol 1.1.0; older SDKs and daemons keep working):

- Single source of truth: `queueEventDeclarations` (`task-service/queueEventDeclarations.ts`, source `task`): name, description (<= 500 chars: when it fires, what does NOT), JSON Schema, example, `correlationKey: 'payload.taskId'`. Only `onTaskDeleted` is `terminal: true, outcome: 'info'` (SDK `Declaring your events`: terminal = the event ends the entity it is about; nothing more happens to that `taskId`, and a deletion is neither success nor failure). `onStatusChange` to `done` ends nothing by itself. Tests tie it to the code: one declaration per `TaskEvent` name, examples fit their schema, the payloads really produced by every operation above fit the schemas (`jsonSchemaCheck.ts`, a minimal checker of the subset used, no dependency), daemon limits. Adding or changing an event means editing that file; its hash (`queueEventDeclarationsHash`) is what triggers a new CLI declaration.
- `declareTaskEvents(publisher)` / `sink.declareEvents()`: never throws; outcome `registered | rejected | unsupported | dropped | unknown`. Task log (`task cli logs`): `rejected` error (with the `problems` paths), `unsupported` info (old daemon: update queue-cli), `dropped` / `unknown` warn; stderr only for `rejected` (a bug in our declaration). `registered` is quiet. `flush()` waits for a declaration in flight.
- Module: declared once per start (`registerTaskRoutes`), fire and forget; only with the default sink (an injected `eventSink` has no publisher).
- CLI: declared lazily before the FIRST event delivered by a process, when `<config dir>/queue-events.json` (`{ hash, taskVersion, declaredAt }`) does not hold the current hash (`QueueEventsDeclaration.ts`). Why lazy: the CLI has no start hook, the queue is about to be contacted anyway, and `task-updater.cjs` must stay free of the SDK (it never declares). The marker is written only after `registered`; any other outcome retries at the next event (an old daemon costs one extra request per delivering process until updated). A command without event never declares. Never fails the command. `task cli declare-events [--json]` forces it (exit 1 with the next step otherwise): use it after updating queue-cli or if the queue lost its catalog (the marker cannot know).
- Tests: `daemon.registrations()`, `respondNextRegistration` and `resetNextRegistration(times = 1)` of the SDK fake (SDK >= 2026.10.24-191): one reset still ends `registered` (the SDK retries a registration once, it is idempotent), two in a row end `unknown`. A scripted publisher remains only for a `dropped` without reason and a publisher that throws. `QUEUE_SDK_OFF` also switches `registerEvents` off (`dropped`, reason names the variable): tested in each package's safety net. A test that starts the default module backend must set `XDG_CONFIG_HOME` (the declaration logs in the task config dir).

Decided:

- `onStatusChange` gained `status` (= `newStatus`); `newStatus` stays, so no subscriber breaks.
- `taskFile` is NOT in any payload: the task data path moved with the shared project registry (and a virtual project has no folder to resolve it against).
- No comment event: tasks have no comments. No event for type add/remove: they edit the project config, not a task.
- A changed declaration re-declares by itself (marker hash, test in `TaskIndex.events.test.ts`).

Open decisions (the owner's, nothing implemented):

- Replay text for cmd.exe / PowerShell, or a `--cwd` option in `queue push` (queue repo) to drop the `cd`.
