# Threat model: `task serve` and the `remote` strategy

Scope: protocol v1 and v2 (v2 adds priority, assignee, claim and release; plain HTTP, one shared bearer token, one project per server). Source of the behaviours: CLAUDE.md "Storage strategy: remote" and `packages/task-service/src/server/`. Verified on loopback only; no second machine, no TLS.

## Assets

| Asset                             | Why it matters                                                                |
| --------------------------------- | ----------------------------------------------------------------------------- |
| Tasks of the served project       | Read and write access to every task, comment, link and label of that project. |
| The bearer token                  | Single credential: whoever holds it can read and change everything served.    |
| The server's data folder          | Task files; never exposed by a path, never named in an error body.            |
| Queue events raised by the server | A write raises events on the server machine (flows may react).                |

## Trust boundaries

- Client machine to server: plain HTTP. The network between them is trusted or wrapped (TLS/tunnel/forward port) by something outside task.
- Server process to its data folder: single writer; nothing else may write that folder (task data has no other lock).
- Loopback hop of a forwarder (for example a `machine` forward port): any local process of that machine can reach it; the token is the only protection there.

## Threats and answers

| Id  | Threat                                                                   | Answer in v1                                                                                                                                                                                                                                     | Residual                                                                                                                                                                                   |
| --- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| T1  | Sniffing the network (token, tasks)                                      | Loopback by default; any other host needs `--allow-lan` and a loud stderr warning BEFORE binding; `strategy check` warns on non-loopback `http://`.                                                                                              | Accepted: readable on a hostile network. Fix = TLS wrapper (deferred).                                                                                                                     |
| T2  | Token replay after a sniff                                               | None beyond T1.                                                                                                                                                                                                                                  | No per-request signature (deferred).                                                                                                                                                       |
| T3  | Token guessing                                                           | Constant-time compare, 500 ms delay and a per-address counter on every failure (logged without the token), token of at least 16 characters, required to start.                                                                                   | No lockout (a typo must not lock the owner out).                                                                                                                                           |
| T4  | Unauthenticated probing                                                  | Authentication is checked FIRST: an unauthenticated peer learns nothing about routes or versions.                                                                                                                                                |                                                                                                                                                                                            |
| T5  | Path traversal, injection                                                | Strict id pattern, exact-key JSON bodies, JSON only, no shell, no file name taken from a payload.                                                                                                                                                |                                                                                                                                                                                            |
| T6  | Resource exhaustion                                                      | 1 MiB body limit (declared and streamed), 30 s to receive a request, 16 KiB of headers.                                                                                                                                                          | No rate limiting beyond the failure delay (deferred).                                                                                                                                      |
| T7  | Browser abuse (CSRF, cross-origin read)                                  | No CORS (a preflight is refused), `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, bearer header required.                                                                                                                          |                                                                                                                                                                                            |
| T8  | Token or data folder leaking in output                                   | Token never logged and removed from every error body; the server's data folder removed too; no stack in errors.                                                                                                                                  |                                                                                                                                                                                            |
| T9  | Redirect used to steal the token                                         | The client never follows a redirect (the token would follow it).                                                                                                                                                                                 |                                                                                                                                                                                            |
| T10 | Lost update (two writers)                                                | One writer: writes queued one at a time in arrival order; `If-Match` revision gives 412 on a stale write.                                                                                                                                        | Nothing else may write the data folder.                                                                                                                                                    |
| T11 | Lost or duplicated write on timeout                                      | A client never retries automatically; a write timeout says to check with `task show`.                                                                                                                                                            | A timed-out write may have been applied.                                                                                                                                                   |
| T12 | Token passed on a command line                                           | `--token <value>` is an unknown option with an explanation; token comes from an environment variable or a file.                                                                                                                                  |                                                                                                                                                                                            |
| T13 | Token file readable by others                                            | A `tokenFile` must be absolute and, on POSIX, mode 600 (checked); on Windows a warning (permissions cannot be read).                                                                                                                             | Windows ACLs not checked.                                                                                                                                                                  |
| T14 | Local process abusing a loopback forwarder                               | The bearer token is still required on every request.                                                                                                                                                                                             | Any local process holding the token (or reading its file/env) has full access.                                                                                                             |
| T15 | Assignee spoofing: a token holder claims, releases or forces as any name | None: an assignee is free text, not an identity; `force` is a flag any token holder may send.                                                                                                                                                    | Accepted: same trust as the token (T14). A claim is a coordination aid between cooperating workers, not access control.                                                                    |
| T16 | Lease manipulation, client clock skew                                    | The server is the only clock: the client sends a duration (`leaseMs`, 1 s to 7 days, whole number; any `now` / `leaseUntil` key is refused), the server computes start and end.                                                                  | A client can still ask for 7 days or `force`; `task list --available` and `task next` pick candidates with the CLIENT clock, a skewed client may try a task the server then refuses (409). |
| T17 | Local write lock held by a CLI process on the SERVER machine             | The store's `<data>/.write-lock` is taken by every write; the wait is synchronous, so a lock held by another process blocks the server event loop for up to 10 s, then the write fails with 503 `lock-timeout` (holder pid, host, age; no path). | Documented limit: requests (reads too) stall meanwhile. Do not run task commands on the served project while it is served; use the remote client.                                          |
| T18 | `task serve --stdio` has NO token: whoever can start the process gets the whole pipeline | The entry point reads ONE request from stdin and answers once; it opens no port. The trust boundary is OUTSIDE the process: the caller (`machine run`, authenticated by its mutual TLS channel) runs a command an admin allow-listed. The request goes through the same strict pipeline as HTTP (exact keys, id pattern, 1 MiB body, typed errors, server folder redacted); the envelope accepts only `method`, `path`, `headers`, `body`; a malformed request is an answer (400/413), never a stack. | Anyone who may run the command (shell access, or a peer allowed to) reads and writes the project exactly like a token holder (T14); allow the command to a peer only knowingly, and never expose it to a caller that did not authenticate its peer. Nothing in task enforces who the caller is. |
| T19 | Transport `machine`: the project name or peer put in the command line of the peer injects a shell command; a huge or cut answer; a request lost in a timeout | The peer and the project are validated against `[A-Za-z0-9][A-Za-z0-9._-]{0,63}` at config time and again before every run (no space, quote, `;`, `&`, `|`, `$`, backtick, redirect, newline, non-ASCII, leading dash), the command is one printable-ASCII line of at most 2048 characters built only from them, and the request travels on stdin, never in the command line; `machine` is spawned without a shell of ours (Windows: the `.cmd` shim goes through `cmd.exe /d /s /c`, safe for the same reason). The trust boundary is `machine` (mutual TLS, an exact allow-list entry, a declared stdin). Answers over the 1 MiB `machine run` keeps are refused with the smaller-page fix; a timeout or cut answer of a write says it MAY have been applied. No token, no secret, no request content in any error or log. | Anyone allowed to run the command on the peer has the whole project (T18); the allow entry is the only gate, and stays a human decision on the admin machine. The stdin channel itself (declared in the allow entry: `--stdin json --stdin-max 64k --stdin-chars <families>`, size and hash in the signed request, replay) is `machine`'s (decision 114, not shipped): the runner finds out from the local `machine run --help` and refuses until `--stdin` is there. Input cap: a request over 64 KiB (UTF-8 bytes; 512 KiB planned) is refused before any run, so a long text cannot be cut or half-sent; machine validates size and shape, the business validation stays in `task serve --stdio`. Failures of `machine` are told apart by their text (exit 255 for all), which can drift. |

## Cleartext policy compared with sibling tools

`task serve` accepts plain HTTP on a trusted LAN (warning, explicit `--allow-lan`); flow's worker availability model and `machine` fail closed on cleartext. Task does not refuse cleartext: it warns at start and in `strategy check`. A fail-closed mode (refuse non-loopback without a TLS wrapper) is a possible change, not decided.

## Deferred (not in v1)

TLS and tunnels (as `transport` plugins), per-token project scope and several users, rate limiting beyond the delay, request signing, multi-project serve, discovery of served projects.
