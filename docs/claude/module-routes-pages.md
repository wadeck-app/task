## app-module-task routes and pages

Routes (`/api/modules/task/...`, all take `?project=<id|name|alias>`, typed errors mapped in `errors.ts`): GET `/projects` `/summary` `/tasks` `/tasks/search` `/labels` `/tasks/:id` `/tasks/:id/{history,children,ancestors,links}` `/tree` `/types`; PATCH `/tasks/:id` `{title?, description?}` (empty description clears it; `onTaskTextChanged` per changed field); PUT `/tasks/:id/{meta/:key,meta-keys/:key}` (value in the body, else `?value=`; an empty value is valid; `meta-keys/:key` = key as base64url, for keys holding `/` or `%`); POST `/tasks` `{title?, description?, parent?}` (at least one text; a long `description` alone is split into headline + description) `/tasks/:id/{status,labels,links,parent,type,meta}` `/types` `/tasks/deletion-plans` (preview: a plan computed from the selection, nothing stored or deleted); DELETE `/tasks` (deletes the selection; REST: the selection is `?ids=a,b` | `?all=true` | `?filter=f=glob` plus `cascade`, `confirm` in the query string, or the same fields as a JSON body because the shell's forms send a body; a field given in both is a 400; needs `confirm=true`, else 400 with the plan; `effect: 'sensitive'`, the host asks for the PIN) and DELETE `/tasks/:id/{labels/:label,label-keys/:key,links,parent,type,meta/:key,meta-keys/:key}` (removing an absent meta key or an unset type is a 200 with no event; `label-keys/:key` = `labels/:label` with the label as base64url, for labels holding `/` or `%`; an invalid key is a 400 naming the format) `/types/:name`. `GET /tasks/search?q&limit&exclude=a,b&excludeDescendantsOf=<id>` reads the index only and answers `[{id, headline, status, statusText, tone, href}]` (`limit` default 8, above 20 is a 400, never clamped); `GET /labels` answers `[{label, count}]` and `GET /meta-keys` the sorted metadata keys in use (both read every task file, ~130 ms on 1000 tasks: pickers call them on focus, never the detail route). Lists, trees, pickers and the related card label a task by its headline (`shortTitle` = `headlineOf`, <= 90 chars), never by a long legacy title. `GET /tasks/:id` also gives `headline`, `body`, `bodyAddsInfo`, `statusOptions` `[{value,label,tone,terminal}]`, `typeOptions` (a "None" entry with value '' first; [] when the project has no types), `metaEntries` (`keyId` = base64url key), `deleteImpact`, `pills` (about 20 ms on 1000 tasks: the index plus the task's own, parent, children and linked files, never a scan; a test makes 200 other files unreadable); `titleShort` / `hasShortTitle` stay only until the old yaml is gone (see `taskViews.ts`), and `descriptionText` / `hasDescription` are now set only when the body adds information. Every route that changes a task produces queue events (create, status, labels, links, parent, type, meta, text, `DELETE /tasks`; see Queue events) and answers `undelivered` / `undeliveredText`; `/types`, `/projects*` and the delete preview emit nothing. Every view that fires one of these routes shows `undeliveredText` in a warning badge bound to the action's `resultKey` (Task page: one per form section; New task; Delete, under `plan`, saying how many events were not delivered); `manifest.test.ts` fails when a mutating action has no such badge. `DELETE /tasks` failing partway (`PartialDeleteError` from `executeDelete`: `deletedCount`, `plannedCount`, `failedTaskId`, `events`) delivers the events of the tasks already deleted, then answers 500 with `deletedCount`, `plannedCount`, `partial: true`, `undelivered`; `task delete` does the same and exits 1 naming how many were deleted. A failure before the first deletion is the plain original error.

Provider route for the project module (see Extension points): GET `/related/project/:projectId` (not `?project=`; `:projectId` resolved like `?project=`: id, prefix, name, alias), read only, no event.

Pages: nav `/tasks` `/tree` `/projects` `/types` (global, or the only project); global `/tasks/new` `/tasks/delete` (project chosen in a select); per project, the project being a PATH segment `:project` (read as `$route.project`): `/tasks/p/:project` (list), `/tasks/p/:project/:id` (history is the Activity block of this page: there is no `/history` page), `/tasks/p/:project/new`, `/tasks/p/:project/delete`, `/tree/p/:project`, `/types/p/:project`; dashboard widget. A global page and its per-project twin share one view file. Why a path segment: the shell's breadcrumb links each crumb to the current address up to that page, path params substituted, QUERY DROPPED (`navHelpers.ts` `routeChain`, `href: match.pathnameBase`; confirmed in a browser on app-core-cli 075 and the prebuilt 128). `?project=` on a page address is ignored.

- `:project` is the registry id (8 hex) of the project, never a folder nor a slug (`projectRef.ts`: `pageRef` / `apiRef` return the id): the crumb prints the value cut at 16 characters, so a folder would read the same for every project of a workspace. `GET /projects` resolves it (the views feed it with `$route.project`); `hrefs.ts` builds every page address; the route layer never writes `?project=` in a page link. An unknown project on a page shows `unknownProjectText`.

Projects page (`/projects`, no `?project`): a READ-ONLY list of the registry projects. `GET /projects` gives `projectRows` (`id`, `name`, `path`, `openText`, `problemText` with its fix; no registry column), `openLinks`/`hasOpenLinks` (the table has no row click), `attentionText`, `registryProblem` (the shared registry could not be read: no project is listed, danger badge on the page and the widget; also in `GET /summary`), `noProjectsText`. The view has one source and no action.

Global view (all registered projects): the widget (`GET /summary` without `?project`: open/total plus `projectRows`, one row per project with its tasks link or its error; nothing registered is a 200 with `noProjects`, not an error) and the Tasks page without `?project` while several projects are registered (`GET /tasks?allProjects=true`, Project column, rows link to the per-project address; `/projects` gives `globalQuery`, `allProjectsHref`, `unknownProjectText`). With `?project`, or a single registered project, the Tasks page is the per-project page. Per page without `?project` and with several projects:

| Page     | Scope                                                                                                                                                                                                                  |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tasks    | global list, Project column                                                                                                                                                                                            |
| Tree     | `GET /tree?allProjects=true`: `projects` (see Tree page), `task:ProjectAccordion`; the scope text counts open tasks and names the closed parents kept above them; `warning` is one line naming the unreadable projects |
| Types    | `GET /types?allProjects=true`: Project/Type rows with a Remove button each (the row carries project and type, no cascading select; no row click); add through a project select (readable only, none preselected)       |
| New task | project select (readable only; preselected when exactly one is readable, else the project of the last created task if still readable); parent list only when the URL names the project                                 |
| Delete   | never global: project select without default; the project is named in the preview, in a banner and in the confirm button label; `allProjects` is ignored by the delete routes                                          |

No page has a back link ("All projects", "All tasks", "Back to the task" are gone, with `allProjectsHref`, `globalHrefs`, `tasksHref`): the breadcrumb carries the context (yaml test `no link whose purpose is going back` has an allowlist of the links kept: forward features only). An address naming an unregistered project shows `unknownProjectText` on every per-project page. The detail and history pages (`GET /tasks/:id`, `/history`, `/links`) answer `?blank=true` like the list routes.

Title and description (`taskText.ts`, `createTask`, `setTaskText`): `description` is stored in the task file only when it differs from `title`; readers use `taskDescription` (`description ?? title`), old files holding the title twice stay valid. The CLI JSON of a task record (`show`, and the record printed by `new`, `set-status`, `link`/`unlink`, `set-title`, ...) ALWAYS has `description` (`withDescription`: the resolved text), whatever is stored; summaries (`list`, `tree`, `children`, `parents`, `links`, `find`) never had it. `createTask({title?, description?})`: a single text (title alone, or description alone as the module and flows send it) longer than `HEADLINE_MAX_LENGTH` (90) is split by `splitHeadline` (first line, else first sentence, else a word boundary + `...`; description = full text); an explicit title + description is stored as given. `task new <text> [--description <text> | --description-file <path|->]`, `set-title`, `set-description` (empty clears), `unset-meta`, `unset-type`, `find <query> [--limit 1-20] [--json]` (`searchTasks`, index only, rank id prefix > title word prefix > substring; text lines or JSON `{id, headline, status}`), `labels [--json]` (`listLabels`, reads every task file: 1 000 tasks measured 60-190 ms median, so no label index, see D3 in the page review plan). `find` and `labels` print text unless `--json`.

CLI parity (task-cli `GlobalViewCommands.ts`, parsing and output only over the same service reads; neither needs a project):

- `task list --all-projects [--all] [--json]`: text table PROJECT / ID / STATUS / TITLE; `--json` is the `listTasksAcrossProjects` answer as is (`tasks` tagged with `project`, `readableCount`, `unreadable`). Unreadable projects: warning on stderr in text mode (in `unreadable` in JSON), the others are still listed; exit 1 (`NoReadableProjectsError`, reasons + fix) only when none can be read; nothing registered is exit 0 with the `project add <dir>` hint. Fails with an actionable error when combined with `--follow`/`-f`, `--tree`, `--parent`, `-p` or `TASK_PROJECT` (same exit code and message shape, the message names the source; empty value = unset). `--project-dir` is an unknown option like everywhere (exit 1). `--config` / `TASK_CONFIG` select no project and are untouched.
- `task projects summary` takes no project, so a project flag or variable there contradicts nothing and is left alone.
- `task projects summary [--json]`: totals line, by-status line, one line per project (`open / total`, or `[unreadable: reason]`, not counted); `--json` is the `summarizeProjects` answer. Exit 1 only when none can be read.
- `--follow` is not implemented for `--all-projects`. It would be feasible with `diffSnapshot` keyed by project path + task id over `listTasksAcrossProjects`, but needs decisions first: cost (every project re-read every 500 ms), and what to print when a project becomes (un)readable or all fail mid-follow.
- JSON errors are `{"error": ..., "hint": ...}` for every command going through `errorOutput` / `failure` (no `hint` key without one). `set-type` has no separate hint: its message already lists the valid types. `task cli register` and `task plugins config` keep their own error shapes.

View conventions (app-core DSL, checked against the real shell):

- Mutations: Form + `$actions` + `onSubmit: $ctx.<action>`; the form data is the body and fills `{placeholders}` of the action URL. Placeholders are not URL-encoded: forms carry `projectParam` (encoded by the route) and use `?project={projectParam}`.
- The shell drops the answer of a failed action and discards ALL source answers when one source fails (blank page). Every request of a view therefore adds `inlineErrors=true`: the route answers a failure as 200 with `failed`, `httpStatus` and `errorText` (message, plus the hint unless it explains the JSON API), and the view shows `errorText` in a `variant: danger` Badge. Actions publish with `resultKey` per section, so the message sits next to its form.
- Zero registered projects: `/projects` answers `noProjects` + `noProjectsText` (the next step: `project add <dir>`) and `forms: null`; every page shows that text in an info Badge (a page with only a bound title and no badge renders blank). `forms` is also null when the selected project is unreadable (invalid config, broken parent chain). The widget shows its figures only `$if: summary.projectCount`, so a failure leaves the error alone. A registered project whose folder vanished stays readable (`exists: false`: its data is in the registry; `project paths move` fixes the path).
- Sources use `?{query}`. The shell keeps the last answer of a skipped source (reproduced: unknown project, Tasks menu, browser Back left the 6 rows of the global list), so no query may be empty: a page with several scopes (Tasks, Tree, Types) has ONE source fed by `scopeQuery` (project, global, or `blank=true`), the others (New, detail, history) by `projectQuery` (project or `blank=true`); a yaml test enforces it. `?blank=true` makes `/tasks`, `/tree`, `/types` answer `{blank: true}`, which replaces the previous scope's data (verified: global -> back -> unknown project leaves no rows).
- Forms (shell 2026.10.24-094): typing in the New task description, then waiting 12 s across `/api/modules` polls, kept the focus (`document.activeElement` is the textarea) and the value; the earlier "forms reset within seconds" does not reproduce. Shell 147 (app-core-cli 2026.10.31-147, dsl-ui 306; browser, isolated app-core): after a successful add the forms ARE reset (New task: description empty AND parent back to "No parent"; label, metadata and link forms of the task page: fields empty, relation back to the first option). Not checked: the other forms (types, delete).
- The shell reloads on a URL change only the sources naming a `$urlParam.*`/`$route.*`: a source waiting for `projects` also takes `reload: $urlParam.reload` (always empty, so never sent), else filter links and project choice leave the page stale or blank until F5.
- Installed shell (app-core-cli 2026.10.24-094, dsl-ui 2026.10.24-175; verified in a browser on an isolated app-core): a YAML DataTable column honours `mono`, `nowrap`, `truncate` (ellipsis) and `title` (tooltip, `{field}` of the row); the ID columns render monospace. `width`, `muted`, `format`, `sortable`, `badge` are accepted by the compiler but were not exercised. Also working: `type: actions` columns, `navigateTo`, `onRowClick`, `onAction`, `expansion`, `selectable`/`batchActions`, `fontMono`, `emptyMessage`. Title columns (`titleText`) carry `truncate: true, title: '{title}'` (test-enforced); routes still give display texts (`titleText`, `created`, `time`, `projectText`). Columns of short codes carry `nowrap: true` (test-enforced). Row action URLs substituting the clicked row's `{key}` (dsl-ui >= 2026.10.20) were not re-tested: the Types Remove button keeps pick-then-confirm. A row action without `icon` renders a text button and logs `[DataTable] action "pickRemove" has no icon` once per render: kept on purpose (an icon would make it icon-only, unlabeled). A `PageHeader` with `headerActions` drops its `subtitle`.
- Live figures (app-core-cli/sdk 2026.11.8-179, `count` in `manifest.json`, `routes/figureRoutes.ts`, `figures.routes.test.ts`): path-only GET routes answering `{ count }` (`field: count`, `refreshSeconds: 60`): menu Tasks `/tasks/open/count` (open tasks of every readable registry project with a path; an unreadable project is skipped as in the widget; the route FAILS, so the shell shows nothing, when none can be read or the registry cannot, since 0 would read as "no tasks"), tab Tasks `/tasks/p/:project/open/count`, tab Types `/types/p/:project/count` (project = id, name or alias in the path; 404 unknown, 409 virtual). Tree has none. Each `count` has a manifest `label` ("open tasks", "types"): the shell writes the tooltip `<count> <label>` ("11 open tasks"; the menu badge shows the label alone), so the label never holds the number, and a `label` in the route answer is ignored when `field` is set. Not pushed with `useEntryIndicator` / `refreshSeconds: -1`: a pushed figure is cleared when the component leaves, so it would vanish on the other tabs of the project, and the Tasks page list is filtered (`showAll`, global scope), not the open count. `useEntryHidden` is not needed (no tab group on the task page). The figure follows a change at the next poll (up to 60 s; observed 11 after a deletion, 8 a minute later). No `inlineErrors` (the shell sends none), no `ctx.unchanged` (app-core adds the body ETag itself). Verified in a browser: menu `Tasks , 6`, tabs `Tasks , 4` / `Types , 0`, refreshed after deletions.
- Header row of the task page designs: every element of a row with controls is 32px (`CONTROL_H`, same top and centre, measured light and dark in github and gitlab; jira holds the id badge alone above its action row). The state badges and the id are `task:StatusBadge` with `size: control` (the id also `mono`), never a dsl-ui `Badge` (22px). dsl-ui `Notice` uses the control radius, `px-3 py-2` and `text-sm`; every message of the page (`$notices` of `_page.yaml`) is a Notice, the delete answer before "task not found". Link groups are plain `task:Panel` with a count (a dsl-ui `Section` title was larger than its parent). The delete dialog has no switch (a view reads no form state, so a sentence could not follow it): one sentence of what both outcomes share (links, blocked tasks) and one button per outcome, each stating the fate of the children ("Delete task, its 2 children become root tasks" with `forms.delete`, "Delete task and its 3 descendants" with `forms.deleteCascade`, shown only with descendants). Tests: `controlTokens.test.tsx`, `taskPageVariants.test.ts` (header row).
- Dashboard widget size (dashboard grid: square cells of 100px, 16px apart; in the published app-core-cli 147 since dsl-ui 306): `manifest.json` gives the widget `width: 3` (measured 330px in 147); no `height` (a height is a minimum, the shell grows it by whole rows to fit). The installed app-core-cli 094 `check`/`package` and the SDK schema already accept `width`/`height` (1-12, `width: 0` fails with `must be between 1 and 12`) and its server passes `width` to `/api/modules`; a shell without the grid just ignores it. Tests: `manifest.test.ts` (width 3, size only on the widget), `allProjectsViews.test.ts`.
- Widget content in 3 cells (verified in a browser on the dev shell, isolated app-core): figures are labelled `Open` / `All` (one word, no wrap). The `DataTable` `width` column option is only a MINIMUM and `truncate` caps a cell at 320px (`max-w-xs`, not the tile), so a long name pushed Open/Total out of the tile (clipped, horizontal scroll). The route therefore cuts the project text itself: `projectRows` `label` is at most `WIDGET_LABEL_MAX` (24) characters ending with `...`, an unreadable project keeps its gist (`broken... (invalid config)`, the name gives way), and `labelTitle` (full name, plus the full reason for an unreadable project) is the tooltip (`title: '{labelTitle}'`, column `nowrap` + `truncate`). The two figure tiles carry `itemSizes: [flex, flex]` on their `HorizontalStack` (each fills half the tile; without it a tile keeps its ~70px and the right half stays empty). Open/Total fit at 3 cells and stretch at 4. At 2 cells they stay clipped by the table's horizontal scroll (measured: table 317px in a 198px box, the 24-character label alone is 201px) and the YAML cannot fix it: a column `width` is only a minimum, `truncate` caps at 320px, and a cell without `nowrap`/`truncate` is `break-all` (measured: `a-very-long-project-na|m...` at 3 cells), so never drop them. Only a label under ~8 characters or one column less would fit 2 cells, both worse at 3-4. The installed shell has no widget resize UI: to see 2 or 4 cells edit `width` in a packaged copy's `manifest.json` and run one `app-core-cli dev` per width (the manifest is read at start). The tile height rounds up to whole rows, so blank space remains under the table. The first loads after a cold Vite start left the tile one row high with its content clipped (not reproduced in 5 later loads, cause unknown: app-core's `useRowsToFit`).
- A `FieldSelect` showing its first option while the form holds `''` makes picking that option a no-change (Save stays off): selects that act on an existing item (remove label/type) need a `placeholder`.
- `FieldSelect` crashes the page until its options load: guard with `$if`. `$if` has no negation and `[]` is truthy: routes give boolean flags (`hasLabels`, `noTypes`...).
- A row action WITHOUT url stores the clicked row under its `resultKey` (`$ctx.<key>`): used by the Types Remove button (pick the row, then a confirm form takes it as `initialData`; the removal answer shares the key and clears the confirm). A row action WITH url requests `{id}` unsubstituted in the installed shell (404 on `/tasks/%7Bid%7D`, verified). A button in a row also fires the row click (installed and 123): a table with row actions has no `navigateTo`.
- A form cannot cascade: `FieldSelect` has no dependent options, no component publishes `$outputs`, sources read only `$ctx`/`$vars`/`$source`/`$urlParam`/`$route` (no `$form`). Pick-then-confirm (above) replaces a dependent select.
- A view cannot loop: a block repeated per project (Tree) is a list of DSL nodes built by the route (`dslNodes.ts`: `Section`, `ButtonLink`, `DataTable`; a text starting with `$` is made literal) rendered by `ExtensionSlot` `items`.
- Persisted state: none for views (no `$persist`, `$vars` live in memory, nav links drop `?project`, shell localStorage is internal). The last created-in project (registry id) is kept by the module in `ctx.dataDir/last-project.json`; a corrupt file is reported (`lastProjectProblem`), a failed write is a warning on the create answer.
- Narrow screens (390px). Shell 147 (browser): the menu collapses to a ~70px rail of two-letter entries (TA, TR, PR, TY), the page gets ~320px, the document is still 450px wide (the top bar icons are cut at the right edge), and tables stay clipped at the Title column (Tasks: Project, ID and the start of the title visible). The task page wraps its chips and puts History / Children beside the title; the dock of the former A/B experiments covered the lower third (measured with the former fork; the page has no dock any more). The widget shows at one column with Open / All and the project table. Shell 094 (earlier): the menu kept its 240 px, the page ~150px and tables showed their first column(s) only; `PageHeader` has no wrap or gap (title and actions touch). With `nowrap` + `truncate` rows are one line (before: ids and titles cut one character per line, rows hundreds of px tall). Both remaining problems are app-core's (menu collapse, table overflow).
- Breadcrumb: minimum shell for it is app-core-cli >= 2026.10.19-063 (062 only behind a dev A/B test); older shells have no back navigation on New/Delete. Rule: no back link anywhere (see Pages above); the project lives in the path so every crumb keeps it. Trail read in a browser: `Task > Tasks > Project <project> > <id capitalised>` (the label "Task" of `/tasks/p/:project/:id` is dropped by the shell), `Task > Tasks > Project <project> > New task`, `Task > Tree > Project <project>`, `Task > Tasks > New task` (global). A yaml test replays the shell's trail algorithm on the manifest. Known: the crumb of a vanished or unknown project is still shown (and links to a page saying so); per-project pages highlight their section in the menu.
- Not expressible: URL-writing filters, TreeView navigation (installed; `CompactSelect`/`SearchBar` `urlParam` exist in dsl-ui >= 2026.10.19).
- Test against a real shell: package the module to a temp folder (`app-core-cli package packages/app-module-task --out <tmp> --version 0.0.0-ui`; `dev` on a source module writes `.app-core-dev` into the repo) then `app-core-cli dev <tmp> --port <free> --no-tray` with `APP_CORE_PORT`, `XDG_CONFIG_HOME`, `HOME`, `USERPROFILE` in a temp dir (registry built with the SDK's `addProject`) and `QUEUE_SDK_OFF=1` (events end up undelivered instead of pushed). `--ab-tests` shows the dock of `AbTest` nodes; no page has one since 2026-11-14. ## GET /health (update test of app-core-cli)

`routes/healthRoutes.ts`, answers `{ ok, checks: [{ name, ok, detail? }] }` (module-authoring.md, "Update test of app-core-cli"): read only, no network (projects are opened, never read), no event. `registry` fails (ok false) only when the shared registry cannot be read; `projects` is always ok and names the projects whose own config or parent chain is broken (user data, not this version of the module). Tests: `health.routes.test.ts`. Not seen in a real shell yet.
