## Task components (to be transferred to dsl-view)

`packages/dsl-lib-task` holds React business components, loaded by the shell as `task:<Name>` through the module's `src/dsl-components/index.ts` (`createTaskLibEntries({ apiBase, routeBase })`, manifest `dslLib.shared`). Modelled on orchestrator's `dsl-lib-orch`; written to move to dsl-view unchanged. Browser code: architecture rule allows only react, react-dom, dsl-ui, dsl-renderer, lucide-react and relative imports; never task-service, task-core, the module backend or a `node:` module.

- Actions: controls call `onAction(name, params)` (default `ctx.onAction`, `@ctxDefault`). The installed shell (dsl-ui 175) passes NO body: the action url carries the value (`POST /tasks/{id}/status/{status}`) and every placeholder (`id`, `projectParam`, the value) comes from `params`. The handler publishes the answer under the action's `resultKey` and reloads the sources, so the page's error and `undeliveredText` badges keep working. A control with an action but no page is disabled with a tooltip and one console error.
- Answers and focus of adds (`useRefocus.ts`, `actionProblem.ts`): the shell reads every non-204 answer with `response.json()`, so an empty body (app-core restarting; a Vite dev proxy whose target is down answers `500 text/plain` empty, reproduced) fails the action with the browser's own "Failed to execute 'json' ... Unexpected end of JSON input" and no status. No module route can produce one (`mutatingRoutes.json.test.ts` table: every mutating route answers a JSON object on success and typed errors, plain and `inlineErrors`; `routeKit.ts` turns an undefined/null body into `{}`; `createSubtask.contract.test.ts` ties the yaml action, the component props and the route). `useAction.run` keeps `lastFailure()`; TaskChecklist and CommentComposer then show a `role=alert` sentence ("The sub-task was not added. The server did not answer with JSON: ..., Your text is kept") instead of the raw text. Focus: after a SUCCESSFUL add the field is cleared and refocused by `useRefocus` (TaskChecklist add row, CommentComposer, TaskPicker search field), also when the field is drawn again (first sub-task of an empty list remounts it: measured `activeElement` = body before the fix); only when the focus is on body, the field or inside the component, never after a failure (text stays) and never from a field the user went to. Label and meta adds close by design; `ChipField` then focuses "+ Add" after the render (the button is still `busy`-disabled when the panel closes).
- Also: `ChipRow` (chips that wrap; `HorizontalStack` never does; `justify: between` pushes a second group to the end and still wraps; a row of several chips is a `ChipRow`, test-enforced), `TabPanels` (tabs + content, counts in a `counts` prop because the renderer resolves expressions in `items` only), `KeyValueList` (metadata pairs), `Notice` (feedback text that wraps and clamps to 3 lines, for narrow columns). Every `errorText` / `undeliveredText` result of the task page (all variants, `feedback.*`) and `undeliveredText` of New task and Delete is a Notice, never a Badge (a Badge keeps one line and the replay command ran off the column; tests enforce it).
- Body-sending components (`TaskPicker`, `LabelCombobox`, `PropertyPopover`, `MetaEditor`, `TaskChecklist`, `InlineText`; dsl-ui >= 318, spike in `.claude/plans/2026-11-07_task-page-review.md` section 8): they call `onAction(name, params, { body })`; `pageActionHandler` sends a body through `ctx.onAction` (which publishes `resultKey` and reloads on 318). On a shell that ignores the third argument (<= 175) the body is lost, so these need 318. `ctx.onAction` resolves `{error, status}` instead of rejecting on 318; `useAction.run` treats that (or `false`) as failure, so inputs keep their text. Forms are not reset by the shell: the components clear their own input after a successful run. Fetching components use `getJson` (`src/apiFetch.ts`, `apiBase` from `configureTaskUi` or the `apiBase` prop; errors carry the route's message and hint) and expect `/tasks/search` -> `[{id, headline, status, statusText, tone, href}]` and `/labels` -> `[{label, count}]`. Popups put messages outside the `listbox` element (only options inside). Test helpers live in `src/testHelpers.ts` (the architecture rule exempts that file name).
- Which handler runs an action (verified in the installed shell 094): `ctx.onAction(name, row)` reloads but does NOT publish the action's `resultKey`, so `errorText` / `undeliveredText` never show. The generated entries therefore default `onAction` to `pageActionHandler(ctx)` (`src/compat/actions.ts`): the page's named handler `ctx.<action>(data)` (what a Form's `onSubmit` calls; publishes the `resultKey`), else `ctx.onAction`. The named handler fills url placeholders WITHOUT encoding: each string param is also given as `<key>Encoded` (`/labels/{labelEncoded}`). Object props holding expressions (`params`) need `@resolveDeep` in their JSDoc, else the literal `$route.id` reaches the url. A label with `/` or `%` cannot travel in a url path (app-core answers 404), so the chip x and the Label select remove by key: `DELETE /tasks/:id/label-keys/:key`, `:key` = base64url (no padding) of the label in UTF-8, given by `labelKeys` (label -> key) and `labelOptions` of `GET /tasks/:id`; `LabelChips` sends it as `<labelParam>Key` (`{labelKey}`), computing it when `labelKeys` lacks the label. Adding goes through the body action.
- Installed shell renderer (dsl-renderer 175) does not export `coerceProp`, `resolveExpressionsDeep`, `coerceDate`, `coerceStringList`: `scripts/generate-entries.ts` rewrites those imports to `src/compat/dslRenderer.ts` (the shell's own when present, else a local copy tested against dsl-renderer 260).
- Entries are generated (`npm run entries --workspace=packages/dsl-lib-task`, committed, freshness-tested); the stylesheet is built by `npm run css` (part of `bundle`, gitignored `src/dsl-components/style.css`).
- Visual tokens: `src/ui/tokens.ts` holds the one control height (`h-8`), radii, border, text, icon size, `gap-2` / `gap-4` rhythm and the shared classes (field, pills, icon button, popover panel, results box); `ui/ChipField` and `ui/SuggestBox` are the shared blocks. `ui/controlTokens.test.tsx` fails on another control height or another gap in the listed components. Rule for pickers and suggestions: the input stays on top (sticky) and results, "No match" and loading rows are drawn in the flow BELOW it, never over it; a `PropertyPopover` focuses its first field on open, grows to `max-h` then scrolls, and is a bottom sheet below 640 px; a chip field inside a popover (`InsidePopoverContext`) stays in the flow of the outer panel.
- Navigation uses plain `<a href>` (dsl-ui's `AppLink` is not exported): full page load. Using react-router needs `react-router-dom` added to `BROWSER_LIB_IMPORT` in `architecture/rules.ts`.
