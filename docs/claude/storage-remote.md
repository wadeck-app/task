## Storage strategy: remote (`task serve`, stage 4)

The tasks of a project live on ANOTHER computer. That computer runs `task serve -p <project>` over a project of ANY storage (local files, github, gitlab, migrating; only a `remote` project is refused: no server of a server); this one has a project whose config says `type: remote`. The server is the single writer (R6) and the only emitter of the queue events of those tasks (R7); this computer raises none for the project. Plain HTTP on a trusted LAN in v1: TLS and tunnels are deferred (a wrapper plugs in later as a `transport` plugin). Verified on loopback only: no second real machine was available. Plan: `.claude/plans/2026-11-08_storage-strategies.md`, "Stage 4 progress".

```yaml
# client project (this computer)
strategy:
    type: remote
    options:
        project: shop # optional: id, unique id prefix (>= 4) or name of the project the server serves; checked before the first call
        transport:
            type: plain-http # default type
            options:
                url: http://nas.lan:7788 # no credentials in it; https:// is accepted for a wrapper that provides TLS
                tokenEnv: TASK_REMOTE_TOKEN # the NAME of the variable (or tokenFile: <absolute path>, POSIX mode 600); exactly one
                timeoutSeconds: 10 # whole exchange, default 10
```

```
# server computer
export TASK_SERVE_TOKEN=<>= 16 random characters>
task serve -p shop [--port 7788] [--host 127.0.0.1] [--allow-lan] [--token-env NAME | --token-file PATH] [--json]
```

`task serve --stdio` (`serveStdioRequest`, `server/stdioServer.ts`): no network and no token, for a caller that runs a command on this computer and carries the request on stdin (`machine run <peer> -- task serve -p <project> --stdio`; the allow entry and its stdin declaration are `machine`'s). ONE request `{"method","path","headers"?,"body"?}` (exactly these keys, 1 MiB body, 64 KiB allowance for the rest), ONE answer line `{"status","headers","body"}` (headers: `X-Task-Protocol`, `Allow` for a 405); a malformed request is a 400/413 answer, never a stack; exit 0 whenever an answer exists, exit 1 only when the process fails (a `remote` project, an unreadable stdin). One process = one request: the events of a write are delivered and the sink flushed BEFORE the answer is printed. The pipeline is `server/requestHandler.ts` (`createRequestHandler`: protocol, route, body, validation, write queue, events, error codec), shared with the HTTP server, whose only own parts are the socket, the body reader and the token check (`admit`); `--stdio` excludes `--port/--host/--allow-lan/--token*`. Threat T18 (no token: the caller is the trust boundary).

`task serve` (`ServeCommand.ts` over `startTaskServer`): foreground until Ctrl+C / SIGTERM (finishes the writes in flight; no daemonizing, no daemon manager); serves ONE project, refused only when its strategy is `remote` (no chaining; the answer of `info` carries the capabilities of the served backend and the client reports them, events stay `server`; an operation that backend lacks answers 422 `unsupported`); loopback by default; any other host needs `--allow-lan` and prints a loud stderr warning BEFORE binding (plain HTTP: traffic and token readable on the network, trusted LAN only); a token is required (default variable `TASK_SERVE_TOKEN`, at least 16 characters, never on the command line; `--token <value>` is an unknown option explaining why); prints the URL, protocol, project, token origin (never the value), events; `--json` prints one line `{listening, url, host, port, lan, protocol, project, auth, events}`. Port in use, short token, unreadable token file: exit 1 with the fix.

Code: protocol in `task-core/src/remote/` (`protocol.ts` route table + headers + payload types, the single source for both ends; `wireErrors.ts` error codec); server in `task-service/src/server/` (`taskServer.ts` node:http, `serverOperations.ts` operation + derived events, `requestValidation.ts`, `serverAuth.ts`, `writeQueue.ts`, `serverToken.ts`); client in `task-service/src/plugins/remote/` (`RemoteBackend.ts`, `remotePlugin.ts`, `remoteCheck.ts`) over the transport `plugins/plain-http/` (`plainHttpPlugin.ts`, `plainHttpTransport.ts`, `transportToken.ts`). Both ends meet only through task-core (architecture rules `server-imports-client-side`, `server-folder-import`, `node-network-outside-server`, `server-makes-requests`).

Protocol 1 and 2 (JSON only; `GET /v1/info` first, then one route per `TaskBackend` operation; the table is `ROUTES`, each route has `since`, 1 or 2; protocol 2 only ADDS routes):

| Group              | Routes                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| reads              | `GET /v1/info`, `/v1/tasks`, `/v1/tasks/:id`, `/v1/labels`, `/v1/forest[?parentId]`, `/v1/tasks/:id/{links,links/lenient,children,tree,descendants,full-tree,ancestors}`, `GET /v1/query/prefix/:prefix`, `POST /v1/query/{page,many}` (body = query)                                                                                                                                           |
| writes             | `POST /v1/tasks`; `PUT /v1/tasks/:id/{status,title,description,type,parent}`; `DELETE /v1/tasks/:id/{type,parent}`; `POST /v1/tasks/:id/{labels,links,comments}`; `DELETE /v1/tasks/:id/labels/:label`; `PUT\|DELETE /v1/tasks/:id/meta/:key`; `DELETE /v1/tasks/:id/links/:type/:target`; `PUT\|DELETE /v1/tasks/:id/comments/:commentId`; `DELETE /v1/tasks/:id` (path parts percent-encoded) |
| writes, protocol 2 | `PUT                                                                                                                                                                                                                                                                                                                                                                                            | DELETE /v1/tasks/:id/priority`(body`{priority}`), `PUT | DELETE /v1/tasks/:id/assignee`(body`{assignee}`), `POST /v1/tasks/:id/claim`(body`{assignee, leaseMs, force?, renew?}`, answers `{task, outcome, previousAssignee?}`), `POST /v1/tasks/:id/release`(body`{assignee?, force?}`, answers `{task, previousAssignee}`); `If-Match`and`X-Task-Events: suppress` as for the other writes |

- Headers: `Authorization: Bearer <token>` and `X-Task-Protocol: <route.since>` on every request (1, or 2 for a route protocol 2 added; the server accepts 1..2, answers the version the request named on every response, errors included; a v2 route named with 1 is 426); `If-Match: "<revision>"` on a write = `expectedRevision` (412 stale); `X-Task-Events: suppress` on a write whose events the caller does not want raised (a migration); `Content-Type: application/json` with a body. A write answers `{result, events: {enabled, delivered, undelivered[{event, reason, status}]}}`, a read the bare result; `create` is 201. Authentication is checked FIRST (an unauthenticated peer learns nothing about routes or versions), then the protocol (426 with `{supported: {min, max}}`), then the route (404 / 405 with `Allow`), then the body (415 not JSON, 413 over 1 MiB, 400 malformed or any unknown key), then the input.
- Errors: `{error: {type, message, hint?, ...}}`, no stack, the token and the server's data folder removed from every text. `not-found` 404 (`TaskNotFoundError`), `comment-not-found` 404, `ambiguous` 409, `conflict` 409 (`TaskConflictError`), `stale` 412 (`StaleRevisionError`), `invalid-comment` 400, `rejected` 400 (`BackendRejectedError`), `unsupported` 422 (`UnsupportedByBackendError`, said to be the remote backend's), `invalid-request` 400 (client side: `BackendRejectedError`), `unauthorized` 401 (`RemoteUnauthorizedError`), `incompatible` 426 (`RemoteIncompatibleError`: both versions, which machine to update), `too-large` 413, `unsupported-media` 415, `not-allowed` 405 and `unknown-route` 404 (client side: incompatible), `unavailable` 503 (shutting down), `internal` 500 (a plain `Error`, message kept). Transport failures: `RemoteUnreachableError` (refused, DNS, reset, a redirect: never followed, the token would follow it; or an answer without `X-Task-Protocol`), `RemoteTimeoutError` (a read can be repeated, a write MAY have been applied and the hint says to check with `task show`). `RemoteProjectMismatchError` when `options.project` is not what the server serves. All have hints; `describeError` maps them (unavailable / invalid), `isRemoteFailure` is true for them, so cross-project views list such a project as unreadable.
- Validation (server side, every input): ids match `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$` (the local store builds a file name from an id: `../x` never reaches it), statuses and types are checked against the SERVED project's config, link types against `LINK_TYPES`, labels / keys / comment ids are non-empty and at most 1024 characters, bodies hold exactly the keys of their operation.
- Single writer: writes run one at a time through a per-process promise queue (`writeQueue.ts`), in arrival order, a failed write does not block the next; reads are not queued (the local backend is synchronous inside). The queue protects against concurrent REQUESTS of this process only; nothing else may write the data folder (the local write lock `<data>/.write-lock` covers other processes, see Priority, assignee and claim; a CLI process of the SERVER machine holding it blocks the server event loop up to 10 s, then 503, threat T17). Events leave in the order the writes completed (a separate ordered chain; the answer waits for its delivery, the write queue does not). A client never retries automatically (a create is not idempotent).
- Events: the server derives them from the record before and after each write (`serverOperations.ts`) with ITS project in the payload (`taskProjectId/Name/Path` of the server machine, so the queue cwd is right); `serverEvents.parity.test.ts` runs one scenario through the use cases over a local backend and over a remote one and requires the same events from all three (local use cases, client use cases, server). The client sink is a no-op for a project whose capabilities say `events: 'server'` (`eventSinkFor`, CLI; `routeKit.deliver`, module). An event the server could not hand to its queue is saved-but-undelivered: the client prints `warning: the change is saved on <host>, but the server could not deliver the event ...` (and the module adds it to `readNotices`); the replay is on the server (its task log). The `capabilities.events` row (`client` | `server`) is new for every backend.
- Protocol 2 (priority, assignee, claim, release; same validation and typed errors as the local store, events = `onTaskPriorityChanged` / `onTaskAssigneeChanged` with outcome `claimed|renewed|takeover|released`, in the parity test): THE SERVER DECIDES THE TIME. The client sends `leaseMs` (`leaseUntil - now` of the port input; the bounds, 1 s to 7 days, are `LEASE_MS_MIN` / `LEASE_MS_MAX` in task-core, enforced by `normalizeClaimRequest` for EVERY backend and reused by the server validation: the same refusal, the same text, locally and remotely), never an instant (`now`, `leaseUntil` in a body are unknown keys, 400); the server starts the claim at its clock (`TaskServerOptions.now`) and `TaskClaimedError.remainingMs` is judged on it. A client whose clock is an hour off gets the right lease (tested). Client side: `RemoteBackend.claim` checks the request with `normalizeClaimRequest` first (same errors, no round trip); a closed task is refused by the client use case AND by the server. New wire errors: `claimed` / `closed` (`TaskClosedError`, now in task-core) / `not-claimed` / `release-refused` 409, `invalid-field` / `unknown-priority` 400, `lock-timeout` 503 (`WriteLockTimeoutError`, holder only, never the lock path): each comes back as the same class with its hint (an `invalid-field` of a newer server keeps its field name and text verbatim; without a field it is a `BackendRejectedError` with the server's text). Limits: `list --available` and `next` choose candidates with the CLIENT clock; the claim itself is judged by the server.
- Upgrade story: both machines should run the same task version. A v1 client works unchanged against a v2 server. A v2 client against a v1 server works for everything v1 had; priority, assignee, claim and release fail with a `RemoteIncompatibleError` naming the feature ("does not support claiming a task: it needs protocol 2, the server supports 1..1") and the fix (update task on the machine that runs `task serve`, restart it, `task strategy check`); `strategy check` shows that as a `protocol` warning and its `capabilities` line says priority, assignee and claim are unsupported (fix: update the machine that runs `task serve`); once the first `info` exchange (or the first such refusal) told the client, `ctx.store.capabilities` reports them unsupported too (`StrategyInstance.currentCapabilities`), so capability gates fail early; before that the first call fails with the feature error. `task migrate` to a v1 remote target that has priorities or assignees stops at the first write with that error (resume after updating the server).
- Capabilities: `REMOTE_CAPABILITIES` = the local ones (priority, assignee, claim included, since protocol 2) with `events: 'server'`. `getOpenBlockers`, `getUnblockedBy` and `getForest` with a predicate are computed on the client (a function cannot travel) by the store's own rules (tested against the server's store). `syncLabels` is absent.
- Identity: `locationOf` = `remote <origin><path>` of the URL (a server serves one project, so the address is the storage; two client projects on one server are refused by `task migrate`). The client stores nothing; `options.project` is only a safety check.
- `task strategy check` (remote): `reachable` (round trip in ms, warns above 500), `auth`, `protocol` (both versions), `project`, `capabilities` (equal to a local project's), `statuses` (names must be equal: the server refuses an unknown status; terminal flags and types are compared too), `events` (warns when the server has no queue), plus the generic `token` and `security` (plain `http://` to a non-loopback host is a warning). A wrong token, a stopped server, another protocol each stop the list at the line that explains it.
- Migration: `task migrate` works with a remote side (read, write, markers, read-back, resume). For a remote target the server is asked to raise nothing for the writes (`suppressEvents`, header `X-Task-Events: suppress`, also on priority and assignee writes) unless `--emit-events`; the summary `onTasksMigrated` is NOT raised for a remote target (a warning says so), and with `--emit-events` the server raises the per-task events itself, the `migratedFrom` marker included. The journal stays on the migrating machine.
- Security (v1, plain HTTP, one shared token; full table in `docs/threat-model-task-serve.md`): threats and answers. Sniffing the LAN reveals the token and every task: accepted, warned loudly at start and by `strategy check`; use a trusted network or a TLS wrapper. Token replay by a sniffer: same exposure, no per-request signature in v1. Token guessing: constant-time compare, a 500 ms delay and a counter per address on every failure, logged without the token; no lockout (a typo must not lock the owner out), the token needs 16+ characters. Path traversal and injection: strict id pattern, exact-key bodies, JSON only, no shell, no file name from a payload. Resource exhaustion: 1 MiB body limit declared and streamed, 30 s to receive a request, 16 KiB of headers. Browser abuse: no CORS (a preflight is refused), `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`. Token in logs or bodies: never logged, removed from every error body, the server's data folder too. Deferred: TLS, tunnels (as transport plugins), per-token project scope and several users, rate limiting beyond the delay, request signing.
- THE TOKEN (single source: `plugins/remote/remoteRequirements.ts`): one shared bearer token, no read-only token, no per-capability permission (whoever holds it reads and writes the served project). `strategy check` prints one line per row; a failure is `disabled (<why>): <title>: <message>` with the fix, never silence. All rows verified on loopback only.

| Row            | Needs                                                                                         | Probe                                           |
| -------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| `reachable`    | server: `task serve` running; client: `transport.options.url`                                 | `GET /v1/info`                                  |
| `auth`         | server token and the SAME value in `tokenEnv` / `tokenFile` (401 = `RemoteUnauthorizedError`) | `GET /v1/info` with the bearer token            |
| `protocol`     | overlapping protocol ranges (426 = `RemoteIncompatibleError`)                                 | `GET /v1/info`, `X-Task-Protocol`               |
| `project`      | `strategy.options.project`, when set, equals what the server serves                           | `GET /v1/info`                                  |
| `server-token` | server: at least 16 characters, no spaces; token file absolute, mode 600 on POSIX             | none: `not tested` (only `task serve` knows it) |

How to create it: `openssl rand -hex 32` (any random text of 16+ characters without spaces); server: `export TASK_SERVE_TOKEN=<token>` (or `--token-env NAME` / `--token-file <absolute path>`, `chmod 600`), then `task serve -p <project>`; client: the SAME value in the variable named by `transport.options.tokenEnv` (or `tokenFile`).

- Testing: `plugins/remote/RemoteBackend.contract.test.ts` runs the shared `runBackendContract` through the real plain-http transport and a real server on a free loopback port over a `LocalFileBackend` (36 cases, writes included); `server/taskServer.test.ts` (auth, protocol, routes, bodies, traversal, every operation, typed errors, concurrency, events, shutdown, unhandled rejections), `plugins/plain-http/` (options, timeouts, unreachable, redirect, token sources, fake timers), `plugins/remote/remotePlugin.test.ts` (a swappable fake transport through the registry, `strategy check` lines), `migrate/migrateProjects.remote.test.ts` (local to remote, remote to local, resume), `TaskIndex.remote.test.ts` (the CLI over a remote project, no event from this process), `commands/ServeCommand.test.ts`, `remoteProject.routes.test.ts` (module). Test helpers: `server/testHelpers.ts`, `plugins/remote/testHelpers.ts`. Live check through the bundle: `scripts/live-remote-smoke.mjs` (steps in its header; not in CI).

## Transport `machine` (through the `machine` CLI)

PARTIAL until machine ships its stdin channel (machine repo, spec `.claude/specs/2026-11-13_machine-network/stdin-input.md`, decision 114: decided, NOT built): the installed `machine` CLI has no `run --stdin` yet, so this transport REFUSES today (`this machine CLI has no stdin channel for run yet: update machine / ask machine-owner`; `task strategy check` prints it). It needs no change in task when machine ships: the runner reads the LOCAL `machine run --help` once per process (no connection, nothing woken; only the `run <machine>` entry of that help counts, because the allow side already names `--stdin`; a help of an unknown shape is an error, never "absent"), keeps a positive answer, looks at a negative one again after a minute (a long-lived module sees an update), and then sends the request with `--stdin -`. Everything else is built and tested against a fake `machine`; the live check below is still to do. Nothing is sent by any other route (argv, file, environment): the request never goes in the command line.

- Config: `strategy: { type: remote, options: { transport: { type: machine, options: { peer, project, wake?, shell?, timeoutSeconds? } } } }`. `peer` = machine name, alias or id; `project` = name or id of the project ON the peer (letters, digits, `.`, `_`, `-`, up to 64, no space: it is put in a command line the peer's shell receives unescaped, so any other character is refused at config time AND again before a run). `wake: auto` (default) or `never` (`--no-wake`). Leave `strategy.options.project` unset: the project is already pinned by the command, and the safety check would cost one extra `machine run` per command (each run does the revocation hello, 6 a minute per peer today).
- One request = one `machine run <peer> --no-wait [--no-wake] [--shell s] --json --stdin - -- "task serve -p <project> --stdio"` (`--no-wait`: a command the peer does not allow yet is refused at once with the entry to create, never held for ten minutes). The stdio envelope of `task serve --stdio` is the stdin, the answer envelope the stdout; the answer becomes a `Response`, so the remote backend and its typed errors are unchanged. No token: `machine` authenticates the peer (mutual TLS) and an admin allowed this exact command (T19).
- Allow entry to create once, on the machine that holds the admin key: `machine admin allow <peer> [--shell <s>] --stdin json --stdin-max 64k --stdin-chars <families> -- "task serve -p <project> --stdio"` (printed in the hint of a refusal; typed `<name>` templates can cover several projects). `<families>` are the character families `machine admin allow --help` lists: task does not guess them (a text with accents needs the family that covers them). The entry DECLARES the input, so data stays data: machine checks size and shape only; whether a request is correct is the job of `task serve --stdio` (strict validation, same as HTTP).
- Input cap: the first machine release carries at most 64 KiB per call (`MACHINE_INPUT_MAX_BYTES`, 512 KiB planned): a request whose UTF-8 stdio envelope is larger is refused BEFORE any run, with its size, the limit and the fix (a shorter text, or a larger `--stdin-max` once machine supports it). An accent counts as two bytes. The output stays capped at 1 MiB.
- Wake policy: NEVER a probe, ping, poll or keep-alive; nothing runs unless a command needs the peer. A sleeping peer is woken by `machine run` itself (it wakes a peer configured for Wake-on-LAN that is unreachable) for a real operation; `wake: never` forbids it and the error says the peer may be asleep. `task strategy check` asks the peer ONE `GET /v1/info` and only when the user runs it; `strategy show` and `--dry-run` never run anything.
- Failures (machine's own failures are exit 255 with plain text on stderr, told apart by their words until machine has a code): `refused by` -> `RemoteUnauthorizedError` + the allow entry; `could not connect` / `no answer` -> `MachineUnreachableError` (a `RemoteUnreachableError`) saying the peer may be asleep; `timedOut` or our time limit -> `RemoteTimeoutError` (a write MAY have been applied); output over 1 MiB (cut by `machine run`) -> `BackendRejectedError` (smaller page); the command exiting non-zero -> `MachineUnreachableError` with its stderr; an answer that is not an envelope -> `RemoteIncompatibleError`. The content of a request is in no error and no log.
- Windows: the machine CLI is an npm `.cmd` shim that Node cannot spawn directly, so there (and only there) it goes through `cmd.exe /d /s /c machine ...`; safe because every word is validated and the request is on stdin. Not tried against a real `machine` (the installed one has no stdin channel).
- Code: `plugins/machine/` (`machineCommand.ts` the names and the command, `machineRunner.ts` the seam, `machineTransport.ts`, `machinePlugin.ts`, `nodeMachineRunner.ts` the only file that spawns, `machineBuiltin.ts`). Tests: the command builder with injection attempts, every failure mapping, the plugin options, `RemoteBackend.machine.contract.test.ts` (the shared backend contract through the transport over the in-process stdio pipeline, 36 cases), `machineStrategy.test.ts` (`strategy show|check`).
- Live check once machine has the channel: allow the command on the peer, `task strategy check` (ok lines, one request), `task list`, a write with an accented comment, a peer asleep with `wake: auto` and `never`, a refused command (no entry): each message names the fix.
