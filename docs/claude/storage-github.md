## Storage strategy: github (stage 2, read and write)

Reads AND writes (stage 2; stage 1 was read-only, R3). Every write is an official REST call (GraphQL only for `fills.delete: hard`); an operation GitHub cannot hold natively is an `UnsupportedByBackendError` that names the `strategy.options.fills` key to declare (R4, R5, R9, R10), never a silent emulation. Not done yet (migration: see Migration): `GET /projects` exposing `capabilities`, Projects v2, changes made ON GitHub emit no event (R7). Plan and what stage 3 needs: `.claude/plans/2026-11-08_storage-strategies.md`, "Stage 2 progress".

Token step by step (creation, organization approval, tokenFile recipes, errors of `task strategy check`): `task strategy help github` = `docs/github-strategy-token.md`, both rendered from `plugins/githubTokenGuide.ts` (`githubTokenGuide.test.ts` fails when the file differs, or when a message the guide quotes is gone from the code; rewrite the file with `UPDATE_GUIDE_DOC=1`); the token errors of the github strategy end with "Step by step guide: task strategy help github" (`GITHUB_TOKEN_GUIDE_POINTER`).

Shared with gitlab: `plugins/forge-common/` (`managedBlock.ts` block read/compose, `revisionParts.ts` hash/parts check, `forgeToken.ts` token reader, `httpHelpers.ts` redaction/limiter/write spacing/address checks, `optionParsing.ts`, `wantedLabels.ts`); each forge passes its names, field groups and case rule as parameters.

Code: `task-service/src/plugins/github/` (plugin `githubPlugin.ts`, backend `GitHubBackend.ts` (reads), writes `githubWrites.ts`, revision `githubRevision.ts`, labels `githubLabels.ts`, options `githubOptions.ts`, status map `statusMapping.ts`, JSON mapping `issueMapping.ts`, the one HTTP client `githubClient.ts`, cache `responseCache.ts`, token `githubToken.ts`, check `githubCheck.ts`). Official REST API through Node `fetch` only: no gh CLI, no octokit; one GraphQL mutation (`deleteIssue`, `fills.delete: hard`). Registered as `plugins.github.default` / `github`.

```yaml
strategy:
    type: github
    options:
        repo: owner/name # required
        baseUrl: https://api.github.com # GitHub Enterprise Server: https://HOST/api/v3 (REST base, sub-issues and dependencies need a version that has them: check probes)
        tokenEnv: GITHUB_TOKEN # the NAME of the variable (or tokenFile: <absolute path or ~/...>, POSIX mode 600); exactly one; fine-grained token: Issues read AND write, Metadata read
        statusMap: # EVERY status of the project; checked at load (file + key); exactly one open status has no label
            backlog: { state: open }
            in-progress: { state: open, label: 'status:in-progress' }
            done: { state: closed } # positive terminal -> closed completed (default reason)
            cancelled: { state: closed, reason: not_planned } # negative terminal -> not_planned (or duplicate)
        typePrefix: 'type:' # default; typeMap: { bug: { issueType: Bug } | { label: x } }
        metaPrefix: 'meta:' # default, used only with fills.meta: labels (labels meta:key=value)
        priorityStorage: auto # auto (default) | field | label: where the priority lives, see the table; no fill is declared for priority, assignee or claim
        priorityFieldId: 123 # optional, the numeric id of the issue field (full_database_id): skips the definitions request; only with auto|field
        priorityFieldName: Priority # default, the field auto looks for among the organization definitions; not with label
        priorityPrefix: 'priority:' # default, label prefix with label storage; not with field
        priorityMap: { urgent: Critical } # optional: task priority -> option or label name; keys must be project priorities (checked at load)
        pageSize: 100 # 1..100
        maxPages: 50 # a read that needs more fails loudly (BackendLimitError), never a silent cut
        cache: { ttlSeconds: 60 } # 0 = revalidate every read
        timeoutSeconds: 15
        writeSpacingSeconds: 1 # least time between two writes (0..); GitHub asks integrators to go slowly
        fills: # optional; what GitHub cannot hold natively. NOTHING is emulated unless declared here (see the fills table)
            meta: labels # or { use: body-block, fidelity: degrade }
            delete: hard # or { use: tombstone, fidelity: degrade }
            linkTypes.duplicateOf: { use: duplicate-marker, fidelity: degrade }
```

Priority storage (`githubPriorityStorage.ts`, `PriorityResolver`; code shared with gitlab is in `forge-common/`: `taskFieldBlocks.ts`, `priorityNames.ts`, `managedBlock.ts` claim key): `label` never asks GitHub; `priorityFieldId` set means the field with that id, no request (GitHub judges the value, so the option names are the ones of `priorityMap`); `field` without an id, and `auto`, read the definitions `GET /orgs/{owner}/issue-fields` (ORGANIZATION permission `issue_fields=read`). `auto`: a readable single-select field named `priorityFieldName` = field; a 403 or 404, or no such field = LABELS, with the reason and fix shown by `strategy show` / `check`; `field` with no usable id fails at the first priority write with the fix. A READ never waits for this question (`known` / `forRead`): explicit settings first, then what an earlier command remembered (ANY age), else, in `auto` with nothing known, the issues are read with the default version and ONLY a priority label among them (the `priorityPrefix` or a `priorityMap` name) makes it worth asking; a failure to ask (unreachable, rate limit) does not fail the read: it reads as label storage with a notice `priority storage could not be resolved (reason)`, one attempt per process. A priority WRITE (and `strategy check`, always fresh) resolves strictly and fails loudly. The resolution that needed a request is remembered in the project cache folder (`task:priority-resolution:<baseUrl>:<owner>:<storage>:<fieldId>:<fieldName>`), used as is by a write for 10 minutes and by a read at any age, and NEVER used when `priorityFieldId` or `priorityStorage` is explicit (a config edit takes effect at once). A write that went to a label through the `auto` fallback warns on every such write (`warning: priority stored as label priority:high because the native issue field is not usable: <reason>. Fix: ...`, kind `emulated`); a read says nothing more. API version: `X-GitHub-Api-Version: 2026-03-10` goes ONLY on the definitions request, the issue-field-values writes and the issue and issue-list reads in field storage (per request); everything else (timeline, comments, sub-issues, dependencies, labels, writes) keeps 2022-11-28 as recorded in the conformance fixture; the cache is keyed per version. Which labels are reserved follows the resolved storage: in field storage no label is reserved (`High`, `priority: low` stay ordinary labels, nothing is removed on a write); in label storage and while `auto` is unresolved the prefix is reserved. A write is ONE `POST .../issue-field-values` `{issue_field_values:[{field_id, value}]}` (its answer is checked), `DELETE .../{field_id}` to clear. An unreadable value is reported as `ignored` once per distinct text. Limits: priority, assignee and claim changes do NOT show in the timeline; sub-issue and dependency lists are read with the default version, so a CHILD's priority stored in the field is not shown in those lists; a PLAIN read of an `auto` project whose priorities are only in the field reads no priority until something resolved the storage, so every dispatch read calls the optional port member `TaskBackend.prepare({priority: true})` first (`listTasks` when it has an order, a status/priority/assignee/available filter or a limit, hence `task next` too; absent on local, remote and gitlab, then not called): github resolves the storage (memory of an earlier command, else the one definitions request) and the list that follows carries the field values; there a resolution failure is LOUD like a priority write (`priorityStorage: field` without a usable id: the error with the fix), while `auto` with the definitions refused (403) is label storage, quietly on reads; nothing is emulated and no fill is needed. Claims: github has no conditional write, so two workers can both pass the check; the record read after the PATCH is compared with what this call wrote (assignee, `claimedAt`, `leaseUntil`; for a release: no claim) and a caller that does not hold the issue gets `TaskClaimedError` naming the real holder (a `release` / `clearAssignee` overwritten by another claim is a `TaskConflictError` "task <id> was claimed by <holder> while you were releasing it"); the last write wins; a worker that reads back after the winner's write is told, the first writer is not: a dispatcher needing a hard guarantee keeps its own lock or uses `task serve`. The claim write replaces ONLY the managed block slice of the raw body (no trim, no CRLF change of the visible text; the text is byte-identical outside the block, a release removes the `

`task put before the block). Migrate: the options of the target's Priority field are unknown at plan time, so a migration into a github project whose Priority field lacks an option for a project priority fails at the first affected task (status`failed`, with the resume command), and a dry run cannot tell.

Capabilities (`GITHUB_CAPABILITIES` = no fill; `githubCapabilities(fills)` adds what a declared fill enables and is what `ctx.store.capabilities` reports; `task strategy show` prints the static ones and the fills as `emulated via <technique> (<quality>, fidelity <f>)`): hierarchy `limited`, linkTypes `[blockedBy]` (+ `duplicateOf` with the marker fill), status `mapped`, history `derived`, activity `native`, delete `no` (`close-only` with tombstone, `yes` with hard), search `native`, concurrency `check-then-write`, ids `assigned`, labels yes, meta no (yes with a meta fill), priority / assignee / claim yes (with `capabilityNotes`, shown `partial` by `strategy show`), comments yes (author = the token user), writes `full`, indexedGraph no. `strategy show` prints `hierarchy`, `history`, `activity`, `search` and `linkTypes.duplicateOf` as `partial` with a one-sentence note (`StrategyPlugin.capabilityNotes`), `delete` / `meta` / `linkTypes.causedBy` as `unsupported`.

Client (`githubClient.ts`, injectable `fetch`, clock and `sleep`): `write(method, path, body)` and `graphql(query, variables)` serialize writes (one in flight, `writeSpacingSeconds` between the start of two), wait out a secondary limit whose `retry-after` is <= 15 s (twice at most; the request was refused, so sending it again is safe) and otherwise throw `RateLimitedError(secondary, retryAt)`; a 5xx or a lost connection is never retried and never trusted (see Writes); every write expires the read cache (`ResponseCache.expire`, a marker file `.expired-at` in the cache folder shared by the processes; entries stay for their ETag and the stale fallback). Reads: `Authorization: Bearer`, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`, redirects followed only inside `baseUrl` (max 3), `Link rel=next` followed verbatim and refused when it leaves `baseUrl` (cursors the same); ETag cache (memory per process, plus files `<data dir>/cache/github/<sha256 of the URL>.json`, created at the first write, never holding a request header or the token; entries whose last confirmation `cachedAt` (file time if unreadable) is older than 30 days (`CACHE_ENTRY_MAX_AGE_MS`) are deleted once per process at the first disk-cache access, one directory listing, only `<40 hex>.json` files, never `.expired-at` or `.recent.json`; a failure to delete is a `warn` line in the task log naming the file and never fails a read); inside `ttlSeconds` a read costs nothing, then `If-None-Match` (a 304 costs no quota: measured); at most 6 requests in flight. Quota: `x-ratelimit-*` of the last answer per bucket; an empty bucket fails WITHOUT sending (no busy retry): `RateLimitedError(primary|search|secondary, retryAt)`; 403 with `retry-after` = secondary; 429; 403 otherwise = `BackendAuthError(forbidden)` naming `x-accepted-github-permissions`. 401 = `BackendAuthError(unauthenticated)` (names the variable and the permissions to give). Network failure = `BackendUnreachableError(host, cause code)`, no answer = `BackendTimeoutError`, 5xx = unreachable with the status. 404 on an issue = `TaskNotFoundError`. Stale: on unreachable / timeout / rate limit, and only then, a cached answer is served and labelled: `ReadNotice` `stale` (CLI: one `warning:` line on stderr, text and `--json`; module: `readNotices` in the answer), a record gets `stale: true` + `cachedAt`; never on a refused token.

Token: `githubToken.ts`. Missing or empty variable / file: `BackendAuthError(missing)` at the FIRST backend call (so reads fail too, no anonymous fallback) naming the project, the config file, the key, `export VAR=<token>` / `setx`, the permissions to give. The token appears in no message, no log, no cache file (`redactToken` on every error text; tested). `TASK_DEBUG=1` writes one line per request (`GET /path -> status (ms, rate limit remaining n)`, no header) to the task log.

THE TOKEN (single source: `github/credentialRequirements.ts`, same design as gitlab). `task strategy check` prints one line per row (`metadata read labels labels-write write delete expiry`, plus `reachable auth repo ...`): `enabled: <title> (needs <permission>)`, `disabled (missing <permission>)` with the fix and docs link, or `not tested (<why>)`. A 403 names the permission: the `x-accepted-github-permissions` header (`issues=write`) is also written as the token page prints it (`Issues: Read and write`, `namePermissions`), raw header kept in the hint.

How to create it: GitHub > Settings > Developer settings > Personal access tokens > Fine-grained tokens > Generate new token; Repository access: only select repositories (the project's); Repository permissions: `Issues: Read and write`, `Metadata: Read` (granted by default); set an expiration date; put it in the variable named by `tokenEnv`. `fills.delete: hard` needs the administrator's token. Classic token: scope `repo` (`public_repo` for a public repository): DOCUMENTED, NOT LIVE. UNVERIFIED: how GitHub combines several names in `x-accepted-github-permissions` (all or any of); the check lists them only. Docs: docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens.

Errors in `describeError`: new kinds `unsupported` (CLI exit 1 / module 422), `rate-limited` (429, `details.retryAt`), `unavailable` (unreachable, timeout, token missing or refused: 503, not written to the server error log), and `BackendDataError` / `BackendLimitError` = `conflict`. `PluginCreateError` keeps the kind and text of a cause it knows. `isRemoteFailure(error)` is true for these: `summarizeProjects`, `listTasksAcrossProjects` and the module's `readAcrossProjects` report such a project as unreadable (reason + fix) and carry on with the others; any other failure stays fatal.

Module: every route runs in `runInRequestScope` (`requestScope.ts`, AsyncLocalStorage): the contexts `openProject` opens are disposed once when the answer is ready or the handler failed (a failing dispose is a stderr warning, never silent); the project listing and `readAcrossProjects` release each project right after reading it. Read notices are added to an object answer as `readNotices` (texts).

`task strategy check` on github (lines `reachable auth repo expiry issues limits statuses labels hierarchy dependencies search writes`, GET only, cache bypassed, stops at the first line that makes the others meaningless): token accepted, repository found / visible (404 = "not found or this token cannot see it" with the two things to check), archived warning, token expiry (warn <= 7 days, error when past), Issues enabled and readable (403 names the permission), quota (warn when low), the statuses mapped, labels the config needs (status, type, tombstone) that do not exist (warn with the names and the exact command: `task labels sync -p <project>`), sub-issues and dependencies probed on an existing issue (warn when the server lacks them), `writes` (the pace and the quota left, "optimistic, not atomic"; warn when the repository reports `push: false` for the token, or `admin: false` with `fills.delete: hard`), plain `http://` to a non-loopback host.

Limits worth knowing: one `get` is up to 3 requests (issue + timeline + comments, +1 for blockers), so `task show` takes 3 to 4 s on github.com (measured, 0.3 to 1 s per request); a status change is 2 to 4 s (read, label check, one PATCH, the record read again), `delete` 9 to 12 s (it lists several times); these seconds were measured BEFORE `resolve` (below) and not re-measured live; request counts per command are pinned on the fake server (`GitHubBackend.requestBudget.test.ts`, fresh process per command, `ttlSeconds: 0`): create 3, set-status 6, set-title 5, add-label 6, set-parent 7, link blockedBy 9, comment 7, delete tombstone 9 (before: 3, 7, 6, 7, 9, 11, 9, 14); set-priority (label) 6, unset-priority 5, set-assignee 5, claim 5, release 5; in `auto` the first priority WRITE of a project costs +1 (the definitions request, 7 total), the next 5; plain reads and other writes never pay it, and a list stays 1 request per 100 issues. Id resolution is `TaskBackend.resolve(prefix)` (the fields of the task, no links/history/activity/comments; github: ONE issue read; other backends: same as `findByPrefix`), used by every use case that only needs an id or the value a write replaces; `findByPrefix` stays for `show`, `history`, `activity`, `comments`. The conditional re-read before each write, the label probe and the record read after the write are kept (revision check, label existence, what GitHub holds); the full list is read is read for the forest, `find`, labels and parent titles (1 request per 100 issues, revalidated with 304); a status change is one history entry only if the events of its request fall within 1 s (two changes made closer than that read as one); GraphQL-only data (body edit history) is not read. `--follow` polls the cache: it refreshes at most every `cache.ttlSeconds` (60 s), and with `ttlSeconds: 0` it revalidates twice a second (free of quota, not of requests); no minimum interval is enforced yet.

### github: writes (stage 2)

| Operation                         | GitHub calls (always after a conditional re-read of the issue)                                                                                                                                                                                                                            |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `updateStatus`                    | ONE `PATCH` with the new `state`, `state_reason` (`state: closed` must be in the body for a reason to apply) and the whole label set (old status labels out, new one in); none when nothing changes                                                                                       |
| `setTitle` / `setDescription`     | `PATCH title` / `PATCH body`; the managed block of the body is kept; a description equal to the title clears the body; > 65536 characters is a `BackendLimitError`; same value: nothing sent                                                                                              |
| `setType` / `clearType`           | label `typePrefix+type` (or `typeMap`): a swap is one `PATCH labels`, an addition one `POST`; `typeMap.issueType`: `PATCH type` (`null` clears); the label name is checked (50 characters) before any request                                                                             |
| `addLabel` / `removeLabel`        | missing label created grey, `POST .../labels` (batches of 10) / `DELETE .../labels/{name}`; names > 50 characters, with a comma or a space at an end, or reserved (status, type, meta prefix, `task:deleted`) are refused before any request                                              |

An approximate fill under `fidelity: strict` is a config error at load; `strategy show` / `check` list each as `emulated via ... (<quality>, fidelity ...)`. The technique name `duplicate-marker` replaces the design's `close-duplicate`.

Consistency (`githubRevision.ts`, `githubWrites.ts`):

- Every write first reads the issue again (a conditional GET, free when unchanged) and, with `expectedRevision`, compares the parts it changes (revision row above): `StaleRevisionError` (a `TaskConflictError`, kind `stale`) before anything is written; a revision this backend did not issue is stale for every write. GitHub has no conditional write, so a race of about the duration of the PATCH remains and `strategy check` says "optimistic, not atomic" and, for a claim, the last write wins; a worker that reads back after the winner's write is told, the first writer is not: a dispatcher needing a hard guarantee keeps its own lock or uses `task serve`. The use cases do not pass a revision today (last write wins, like local); the backend honours it for the callers that do.
- A write made of several calls (create + close / attach, tombstone, duplicate marker + close) runs its steps in order; a failure after the first applied step, or a call whose outcome is unknown (5xx, lost connection: never retried), reads the issue again: a step that did apply counts, otherwise `PartialWriteError` (`applied`, `notApplied`, `hint` = the command that finishes it, `cause`; the module answers 500 with them, the CLI exits 1). A refusal of the first call is the original error (`BackendRejectedError` for a 4xx, nothing changed). After every write the record is read again and returned, so the caller gets what GitHub holds.
- Lags measured on the real API, handled: the issue LIST shows a new issue about 4 s late (task remembers its creations 30 s in the cache folder, `.recent.json`, and the reads of the whole list add them by number, so `list`, `delete`, forest, `find` see a task created a moment ago); the dependency COUNTS of an issue lag 1 to 2 s (the dependency lists do not: a read ignores the counts for 10 s after task changed them); the sub-issue counts (`sub_issues_summary`) of a parent lag the same way (the `/sub_issues` list does not), handled by the same memory (`RecentKind` `subIssues`, noted by `setParent` and `create` with a parent): for 10 s the children, tree, descendants, delete plan, tombstone detaching and the 100-children check read the list whatever the count says. Evidence in the recording: the answer of a sub-issue removal still carries the counts of before it (ledger G093); the lag after an ADD was reported by the owner, not isolated in the fixture. Updates do not lag.
- Activity: the timeline of GitHub is the only source (no local log): a write made through task shows in `history --all` after the re-read; GitHub mirrors a parent and a link on the other issue itself, so no `child-added` entry is written by task.
- Events: the use cases build them after the awaited write exactly as for a local project (same names and payload keys, `taskProjectId/Name/Path` included; `TaskIndex.githubEvents.test.ts`); the one difference is `onTaskCommentAdded.author`, always the token user. A refused or failed write emits none. A change made on GitHub emits nothing (R7).

Errors (`describeError`): `BackendRejectedError` = invalid / 400 (GitHub refused the content, nothing changed), `PartialWriteError` = internal / 500 (details `applied`, `notApplied`), `StaleRevisionError` = conflict, `UnsupportedByBackendError` = unsupported / 422 with the fill to declare in the hint, `RateLimitedError` (secondary: the `retry-after` instant), `BackendLimitError` (label name 50, labels 100, body 65536, sub-issue depth 8, 100 children), `BackendAuthError(forbidden)` for a token without Issues write (the hint names the header `x-accepted-github-permissions` or "Issues: Read and write").

Architecture: `plugins/github/responseCache.ts` and `plugins/forge-common/forgeToken.ts` are in the `fsAllowlist` of task-service (answers of GitHub as files in the project data folder; the token file). Nothing else in the plugin touches the file system.
