# Storage strategy (core)

Moved from CLAUDE.md; CLAUDE.md keeps the digest.

## Storage strategy (stage 0b of `.claude/plans/2026-11-08_storage-strategies.md`)

Installed: `local` (the default), `github` (read and write, stage 2: next section), `gitlab` (read and write, stage 5, Free tier only, verified live on gitlab.com: "Storage strategy: gitlab") and `remote` (the tasks live behind a `task serve` on another computer, stage 4: "Storage strategy: remote"). A project chooses where its tasks live with the `strategy` section of its own `config.yml`; no section = `local`, silently, exactly as before. Opening a project (`openTaskContext`) resolves it; `ctx.store` is created by the strategy plugin at its FIRST call (`lazyBackend.ts`; `kind`/`capabilities` come from the plugin before that), `ctx.strategy` is the resolution, `ctx.dispose()` releases it (the CLI calls it after each command, the cross-project views per project; the module once per request, see the github section).

- Shape (`strategyConfig.ts`, scope `local`, nothing inherited; the SDK checks the key `strategy`, task checks everything inside): `strategy: { type, fidelity, options }`. `type`: `local` (default) or a plugin ref/alias. `fidelity`: `strict` (default) | `degrade`. `options`: read by the plugin (`validate`), except `fills`, which the host reads. Every problem is a `StrategyConfigError` (a `ConfigSchemaError`: file + dotted key + `hint`, `invalid`/400). A parent layer is checked structurally in its own file but only the own layer is resolved; a `strategy` in the global `~/.task/config.yml` is an error.
- `fills` (`options.fills`): `<capability>: <technique>` or `{ use, fidelity }`; keys are `BackendCapabilities` names (`BACKEND_CAPABILITY_NAMES` in task-core) that have a technique in `strategyFills.ts` (`status meta hierarchy delete history activity search ids`, and `linkTypes.<blockedBy|duplicateOf|causedBy>`); an unknown capability or technique lists the valid ones. A non-exact technique under `strict` needs its own `fidelity: degrade`. The plugin must implement the technique (`StrategyPlugin.fillTechniques`; `local` implements none, so any fill on `local` is an error).
- Secrets: a key named `token|password|secret|apiKey|...` with a value, or a credential-looking value (`ghp_`, `github_pat_`, `glpat-`, `xox`), is a hard error with the fix `tokenEnv: <VARIABLE_NAME>` / `tokenFile: <path>`; `tokenEnv` must be a variable NAME; `strategy.pluginsDir` is an error (no external plugins, R11).
- Types known to the schema (`BACKEND_KINDS`: github, gitlab, remote) but with no plugin (none in the built-in list now; the path stays for a registry built without one, tests use `registryWithout`): `strategy type <t> is declared but no plugin is installed; built-in types: ...`, never a local fallback. A `remote` strategy validates its `options.transport` slot first (`plain-http` options: `url`, `tokenEnv` or `tokenFile`, `timeoutSeconds`); both are real since stage 4 (next sections).
- Plugin host (`task-service/src/plugin-host/`, extractable seam): generic `Plugin` (`extensionPoint`, `validate` -> string with optional `key: ` prefix, `create(options, ctx)`, `describe()`), `createPluginRegistry` (instance, refs `plugins.<id>.<impl>` + aliases, conflicts throw and register nothing, unknown id lists the registered ones of that kind, wrong kind names the right one), `resolveSlot` (`{type, options}` -> `PluginSlotError` `<file>: <dotted key>: <problem>` + hint listing the plugin's options), `createInstance` (30 s limit, `Plugin "<ref>" failed to create its instance: ...` with cause, dispose once). Kinds (`plugins/kinds.ts`): `strategy` (instance = `{backend, describe(), check(), dispose()}`), `transport` and `ordering` (instance = `{compare(a, b, facts), dispose()}`; see Priority, assignee and claim). Built-ins are listed once in `plugins/builtinPlugins.ts` (`createBuiltinRegistry()`); tests inject their own registry through `OpenTaskContextInput.registry`.
- Architecture rules: `plugin-host/` imports only its own files and `node:` (tests also vitest; `seam-imports-task`); `plugins/<id>/` imports the seam, `plugins/kinds`, its own files, task-core and `node:` (`plugin-imports-outside-seam`); `plugins/forge-common/` (code shared by github and gitlab, no plugin, nothing registers there) follows the same list and is imported by `plugins/github/` and `plugins/gitlab/` only (`forge-common-import`); only `builtinPlugins.ts` imports a `plugins/<id>/` folder (`plugin-folder-import`); no computed `import(...)` in any package (`NO_COMPUTED_IMPORT`).
- Commands (`StrategyCommand.ts` over `showStrategy` / `checkStrategy`; they open the project themselves so a config problem is an answer, not a failure before the command): `task strategy show [-p] [--json]` (type, fidelity, fills, tokens as NAME + set/unset, capability table native/emulated/unsupported; opens no backend, creates nothing) and `task strategy check [-p] [--json]` (lines `config strategy fills token security` plus the plugin's lines: local = data, writable, task counts; each warning/error has a `fix`; exit 1 on any error; warns on plain `http://` to a non-loopback host; a `tokenFile` must be absolute and, on POSIX, mode 600 (Windows: a warning, permissions cannot be read)). `--json` failures keep the full result on stderr with exit 1. `task plugins list|config` (the stale flow mirror) is removed: unknown command.
- Host additions of stage 1: `StrategyContext` also carries `source` (the config file), `statuses` / `types` (`ProjectFacts`, from `projectFactsOf(config)`) and `log` (task log writer); a plugin may implement `validateForProject(options, facts)`, run by `resolveStrategy` at load (message `key: problem` becomes file + `strategy.options.<key>`); a `StrategyInstance` may implement `takeNotices()` (`ReadNotice`: `stale`, `ignored`, or `emulated` for a write done through an approximate fill), exposed as `ctx.takeNotices()` (the CLI prints each as a `warning:` line on stderr, the module adds the texts as `readNotices`); a fill the plugin lacks says what it does implement (`describeImplemented`).
- Remaining: `GET /projects` does not expose `strategy`/`capabilities`; `fills` keys outside `BackendCapabilities` (`type`, `fields`, `events`, `writes`, `origin` of design 2A) are refused until the design maps them to capabilities (`writes` now IS a capability, with no fill: see below).

## Storage strategy: migrating (plan `.claude/plans/2026-11-15_migrating-wrapper.md`, phases P0 to P4)

PARTIAL: P4 done (`finalize`, `abort`). Verified on fakes, over local+local and local+fake GitHub, and one real spawn; NEVER live (`scripts/live-migrating-smoke.mjs`, written, not run). Not supported: finalizing a pair whose `new` keeps its task files in the project folder (see P4 limits).

```yaml
strategy:
    type: migrating # plugins.migrating.default
    options:
        current: { type: <strategy> } # full strategy blocks, same schema and secret rules as a project section
        new: { type: <strategy>, options: { ... } }
        budget: { requestsPerMinute: 30 } # optional positive integer; the worker never exceeds it (sliding window)
```

- Agnostic (D13): the plugin reads capabilities, traits, `locationOf` and the port, never a storage kind. Rule `migrating-names-a-storage` forbids `local|github|gitlab|remote` (any case, any substring) in code of non-test files of `plugins/migrating/`.
- Host seam: `StrategyPlugin.strategySlots` names the options that are strategy blocks. `resolveStrategy` checks each like a project section (errors name `strategy.options.<slot>...`; a block needs `type`; a meta-plugin inside one is refused), keeps them in `ResolvedStrategy.subs` and passes `SubStrategyViews` (capabilities, `traits(facts)`, location; NO_TRAITS when a plugin declares none) to `capabilitiesFor`, `traitsFor`, `locationOf`, `validateForProject` and `validateSubStrategies`. `StrategyContext.openStrategy(slot, { dataSubdir? })` (`strategyInstance.ts`) opens a block lazily, once per slot and folder, and disposes it with the parent. `new` uses `<data>/migrating/new`.
- Capabilities = intersection (`capabilityIntersection.ts`, one rule per capability, compile-checked): weaker enum value, both sides for booleans, common link types, `delete` only when equal, `ids` generated only when both. Conflicts the wrapper cannot honour (`events` client vs server, history/activity none vs something) are refused at load. Same location on both sides is refused. `locationOf` = both locations joined with `+`. `traitsFor` = `combineTraits`: tighter limits, pessimistic cost without a model, no `foldsCreate`.
- Enforcement: an operation whose capability the intersection lacks is refused with `UnsupportedByBackendError` naming the side to change, even if `current` could do it. Trait limits (depth, text lengths, label rules, comment authors) are NOT enforced yet.
- `strategy show` prints each side and its capability table; `check` prefixes each side's lines (`current.`, `new.`) and adds a `state` line (counts per state, stale copies, open transactions; error when recovery could not settle one). `labels sync` is not forwarded to `new`.
- Routing (P1, `routingIndex.ts`, `routedReads.ts`, `idTranslation.ts`, `summaryGraph.ts`): `<data>/migrating/index.json` `{format: 1, rows}`, row `{publicId, a?, b?, state: in-a|moving|in-b|deleted, since, version}`. A task of `current` with no row is `in-a` and its public id is its own id (a project that never moved a task has no file; a missing file is "no row"). Rules checked at load: `in-a` needs `a` and no `b`, `moving` both, `in-b` needs `b`, `publicId` = `a` when `a` exists, public ids and per-side ids unique. A damaged file is a `BackendDataError` naming the file (hint: do not delete, restore or rebuild), never recreated. Re-read at every read (parsed only when the text changed); writes (`mutate`, `replaceFromRebuild`) are atomic through the host writer, run under a `ProjectWriteLock` on `migrating/index.lock` (separate from the task lock, which `current` takes itself) with the rows re-read inside it. Limit: the lock blocks the event loop while waiting (up to 10 s).
- Reads by state: `in-a` and `moving` read `current`, `in-b` reads `new`, `deleted` is not found. While every row is `in-a` (or none) reads go straight to `current` and `new` is not asked. Otherwise listings are `current`'s tasks minus `in-b`/`deleted` rows, then `new`'s `in-b` tasks (order: current's, then new's; not stable across a move); each public id once. A row whose task is missing from its side, or two tasks under one public id, is a `BackendDataError` naming it (fix: rebuild). Ids in records (`id`, `parentId`, link targets, parent/link activity) are translated to public ids; a relation to a task of `new` the index does not know is an error naming it. `listPage` merges both sides' filtered pages and pages with its own cursor (`migrating:<offset>`); `text` is pushed to each side's own search. Hierarchy (children, tree, forest, descendants, ancestors, full tree) is computed from the merged summaries with the local store's rules; links ask both sides: outgoing links from the authoritative copy, inverse links from both sides but only for tasks that side is authoritative for, shown with the authoritative summary. Labels: both sides' counts minus the labels of non-authoritative copies (a task of `new` with no block still counts in `new`'s labels). Invariant a later phase must keep: a task in `new` has its parent's copy in `new`.
- Prefix lookup: an exact public id wins; else the unique public id starting with the prefix (current answers for its tasks, the index for tasks only in `new`); several = `AmbiguousTaskPrefixError`.
- Identity block (`identityBlock.ts`): metadata every copy in `new` carries, through the generic meta capability only: `migrating.publicId`, `migrating.fromId` (absent for a task made in `new`), `migrating.hash` (16 hex of title, description, status, type, labels, meta without the block, priority, assignee). `identityCarrierProblem(capabilities, ref)` returns the problem plus fix when `new` has no metadata or no writes; P4 `start` must call it (not called at load, since the P0 pairs may lack a meta fill). Label-based carriers cap key+value at 50 characters: ids of 8 characters fit.
- Rebuild (`rebuildIndex.ts`): `rebuildIndex({current, next})` lists `current`, lists and resolves each task of `new`, reads only. Copy of a task still in `current` = `moving`; made in `new` = `in-b`; copy whose origin is gone = `in-b` plus a note; no block = `unindexed`. Authority cannot be known from the block: a copy that differs from the hash is rebuilt as `moving` with a note (compare before going on). `deleted` rows are not rebuilt. Damaged or inconsistent blocks, duplicate public ids and id collisions are loud errors. `adoptIndex(index, input)` writes the rows, keeping a damaged file as `index.json.damaged-<stamp>`, and notes the old rows it could not rebuild. No command calls them yet (P4).
- `strategy check` adds an `index` line (counts per state, or the damage with its fix).
- Writes (P2, `routedWrites.ts`): `create` goes to `new` (identity block with no `fromId`, public id = id in `new`, row `in-b`; refused with the meta-fill fix when `new` cannot hold the block, also by `moveTask`). Every other write routes by state: `in-a` writes `current`; `in-b` writes `new` (the copy in `current` is kept, D17); `moving` writes `current` (truth) then mirrors the same operation to `new` (comments: copier diff, `mirror: 'sync'`; `expectedRevision` is not mirrored). A failed mirror, or a `current` write with unknown outcome, marks the row `stale` and never fails the person's write. A clean refusal changes nothing. `delete` in `moving`: `current`, then index `deleted` (commit point), then the copy (best effort, tx stays open if it fails). Relations (parent, link, create under a parent) are checked BEFORE any write: the primary side must hold an id for each related task, else `BackendRejectedError` naming the task and the move to wait for. Errors of `new` about a task (stale revision, not found) are renamed to the public id; other error texts may still show ids of `new`.
- Concurrency: per-task `KeyedMutex` (in process), state read inside it, so a move step and a write never interleave in one process. Across processes only index row `version` (the switch is a compare-and-set, `IndexConflictError` = outcome `busy`), the `stale` flag and the log protect. Residual: a second process writing in the narrow window of the switch can leave a copy behind; the next `moveTask` re-syncs before switching, so the loss is a delay, not data.
- Write-ahead log (`migrationJournal.ts`, `nodeWalFiles.ts`): `<data>/migrating/wal.ndjson` (protocol, appended and fsynced) and `log.ndjson` (people, never fails an operation). A transaction (`move write create delete catch-up`) writes `begin` (with `pid`), an `intent` BEFORE each step (a failed append stops the step: nothing is applied that is not logged), `done`/`failed` after, `end`. It is left open whenever the outcome is uncertain; `end` means consequences known. A torn last line is dropped and reported; a damaged earlier line is a `BackendDataError`. Compacted at open when nothing is open; a project that never moved has no file.
- Move (`taskMover.ts`, `moveTask(publicId, {acceptedLosses})`): copy via the host's `copyTasks` (`migrate/taskCopier.ts`: `mapTask`, loss ledger, `createMigrated`, read-back; injected through `StrategyContext.copyTasks`, no import of the migrate engine by the plugin) -> row `moving` -> catch-up + verify -> marker (hash, authority `new`) -> ONE index write `in-b`. Outcomes: `moved`, `already-moved`, `skipped-claimed` (live lease), `blocked-losses` (nothing written), `deferred` (a relation target has no copy yet: stays `moving` + `stale`; move the parent/blocker first), `verify-failed`, `busy`. `catchUp` equalizes without switching. Every task with activity has a `history` loss, so real moves need accepted kinds (`all` in tests). Row `moving` also carries `stale?` and `accepted?`.
- Authority in the stores: identity block gains `migrating.authority` (`current`|`new`); the copier writes fromId, hash, authority, publicId last. `rebuildIndex`: authority `new` -> `in-b`; `current` -> `moving` + stale; a block without the key (older) -> `moving` + a logged note. Identity entries are hidden from records and `migrating.*` meta keys are refused.
- Recovery (`migrationRecovery.ts`, run at plugin open and before a move of the task; skips transactions of another live pid): move = adopt the orphan copy (found by `fromId`, else the one bare unrouted task of `new` with the same title; several = unsettled), complete its identity block, mark `moving`+`stale`; markers rolled back to `current` when the switch had not reached the index; a written switch is completed. write = mark stale. create = finish identity and row. delete = roll forward. Each action is one warn line; what cannot be settled goes to `unsettled` (writes to that task are refused with the reason) and stays open.
- Contract: `runBackendContract` runs over both pairs with tasks made in `new`, `in-a`, `moving` and `in-b`. New `ContractOptions`: `freshStampsEqual` (a moved or identity-stamped task has a later `updatedAt`) and `systemCommentAuthor`. Fault matrix `migrationFaults.test.ts`: crash at each boundary, refused and lost-answer store calls, index and log full, for move, write while moving, create, delete, then restart + recovery + invariants (no task lost or doubled, public id stable, acknowledged writes kept, WAL empty, rebuild agrees with index).
- Limits (P2): the stale flag is a hint, safety comes from every `moveTask` re-syncing before the switch; a lost-answer create in a non-folding `new` is adopted by title (heuristic); comments of a moved task carry the migrate header text; while a task is in `current`/`moving` a comment author is accepted though `new` may refuse it after the move (no trait enforcement yet); `updatedAt` of a moved task is the move time; claims on `in-b` rely on `new`'s claim semantics; no `prepare` forwarding; cross-process mutex absent; other-host pids are not judged by recovery.
- Background migration (P3, `startMigration.ts`, `migrationWorker.ts`, `migrationState.ts`, `moveRate.ts`, `workerLock.ts`, `migrationControl.ts`; no CLI import, no storage name): files in `<data>/migrating/`: `state.json` (status, accepted losses, pace), `control.json` (run|pause|stop), `worker.json` (heartbeat, counters, last errors, rate), `worker.lock` (pid, host; a dead pid on this host is taken over, a live or foreign one refused naming it), `worker.out.log` (stdout/stderr of the process), plus the P2 files.
- Start (`task strategy migrate start [--allow-loss <kinds>] [--dry-run] [--json]`): plans ALL tasks through the copier loss ledger, refuses without the accepted kinds (hint names `--allow-loss` and `--dry-run`), calls `identityCarrierProblem`, writes every missing `in-a` row at once, stores the accepted losses, launches the worker. A second start is refused. `--dry-run` writes nothing and prints plan, losses and estimate (from traits, not measured); a blocked plan exits 0 in a dry run, 1 otherwise.
- Worker (`runMigrationWorker`, internal command `task strategy migrate worker`): per pass one list, candidates ordered depth then `createdAt` then id (link targets first), `moveTask` each, sleeping so that a sliding window never exceeds `budget.requestsPerMinute` nor the target's `contentCap` (per minute and per hour); the cost of a move comes from `traits.cost.model`, else per counted write, else 1. `RateLimitedError` sleeps until `retryAt` (60 s without one) and is no failure. A claimed task is waited for when its lease ends within 5 min, else the worker stops with the `task release` fix; a deferred task is parked and retried. Stops after 5 consecutive failures; a task fails at most 3 times. Pause/stop in `control.json` is read between tasks and every second; SIGINT/SIGTERM ends as a pause. Ends `ready-to-finalize` (statuses: running, paused, stopped, ready-to-finalize; finished and aborted are reserved for P4).
- Launch (`workerLaunch.ts`): detached spawn of the same entry (`process.execPath`, its `execArgv`, `argv[1]`), output appended to `worker.out.log`. On Windows a VBScript run by `wscript.exe` with window style 0 (no console window); arguments holding `"`, `%` or a newline are refused. The spawn is injectable. `start` and `resume` wait up to 10 s for the worker lock and exit 1 with the log path when it does not appear.
- Commands: `status` (counts, percent, worker, pace, ETA, parked, last errors, problems, next action; reads files only, opens no backend, never repairs a torn log tail), `pause`, `resume` (cancels a pending pause, or relaunches a gone worker), `log [--tail n] [--follow]`; all take `--json` (`{error, hint}` on failure). `finalize` and `abort`: see P4.
- Limits (P3): a `pause` in the first seconds after a launch can be lost (the worker resets `control` to run at startup); the lock is advisory (a dead-pid takeover has a micro-window, the move mutex is in process); a worker on another host is never judged dead; the charge of a rate-limited move is not refunded; the ETA is not refined by what the worker measured; `log --follow` re-reads the log each poll; Windows hidden launch verified by one real spawn only.
- P4 (`migrationFinish.ts`, `finalizeVerify.ts` in the plugin; `migrationEnd.ts` in the service; both reach the CLI through the seam: `MigrationApi.finalize`, `MigrationControlApi.finalizeStage|completeFinalize|abortStage|abort|completeAbort`). Both end a migration the same way: refusals first (nothing written), then a write-ahead record in state.json (`finalize` / `abort`: fingerprints of config.yml before and after, `switchStarted`), then the config switch (shared with `task migrate --in-place`: `writeConfigWithBackup`), then status `finished` / `aborted`. A run that dies after the config write is recognised by the fingerprints and the rerun only completes the bookkeeping (no side opened, event raised once: `finalize.summaryEventRaised`). `status` reports the interrupted case with the command. Steps go to `log.ndjson` (`step: finalize|abort`). Nothing is deleted anywhere.
- `task strategy migrate finalize [--json]`: refused (each blocker with its fix, ids listed) unless status `ready-to-finalize`, no live worker, no `in-a`/`moving` row, no open transaction. Then, under the worker lock, it re-reads the STORES (`rebuildIndex`, not the index): each `in-b` row has its copy in `new` with an identity block, authority `new`, same copy id; `new` holds no in-b task the index lacks; `current` holds no task the index lacks (created meanwhile = blocker). The identity hash is NOT compared with the content (a task is edited in `new` after its move). Then: `<data>/migrating/idmap.json` (`[{from,to}]`, old public id -> id in `new`), config.yml gets the `new` block as `strategy` (other keys kept, YAML comments are not; the block is validated as a project section first), backup `config.yml.before-migration` (refused when it exists with other content), `onTasksMigrated` (`created` = moved tasks). Finished: `already-finished`, exit 0, no event.
- Old ids: NOT resolved after finalize. A resolver would need an id-translating wrapper around every backend of the project context (touching every read and write path), which is out of scope for P4; the id map is written, the output and `warnings` say the old id answers "not found" and where the map is.
- `task strategy migrate abort [--keep-moved] [--json]` (D19): files only, opens no side (works with a missing token or a down server). Refused while a task is `in-b` (moved, or created in `new`) unless `--keep-moved`; the refusal happens before the worker is touched. Then: control `stop`, wait up to 60 s (refused naming the pid when it does not stop; another host = refused), take the lock, re-read the index, record `abort` in state.json (leftovers = copies of `moving` rows; moved = in-b tasks with ids; unsettled = open transactions), config.yml gets the `current` block, backup `config.yml.before-abort`, status `aborted`. The index is left as it was. With `--keep-moved` a moved task is not copied back: it shows its OLDER copy kept in `current` (without later edits), a task made in `new` is invisible; both are listed and warned.
- P4 limits: finalize refuses when `<data>/migrating/new/tasks` holds files (the strategy of `new` keeps its task files in the project folder, e.g. a files-based `new`): the plain strategy would read `<data>/tasks` and not find them; use `task migrate --in-place` for that move. Start over a `finished`/`aborted` migration is refused (move `<data>/migrating` files aside); no automatic archive. A failed save of state.json after the config write is a loud `BackendDataError` with the rerun command. Abort cannot judge a worker on another host. The fault matrix (`migrationFinish.test.ts`, both pairs) injects faults at every step through a fake config switch and the memory files; the real config write is covered by `migrationEnd.test.ts` (real files, fake GitHub) and the CLI tests. Never live.
- Tests: `runBackendContract` over local+local and local+fake GitHub (`MigratingBackend.contract.test.ts`); P1 suites run over both pairs (`testHelpers.ts`, `MigratingBackend.routing.test.ts`, `rebuildIndex.test.ts`).
