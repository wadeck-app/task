# Storage strategy (core)

Moved from CLAUDE.md; CLAUDE.md keeps the digest.

## Storage strategy (stage 0b of `.claude/plans/2026-11-08_storage-strategies.md`)

Installed: `local` (the default), `github` (read and write, stage 2: next section), `gitlab` (read and write, stage 5, Free tier only, verified live on gitlab.com: "Storage strategy: gitlab") and `remote` (the tasks live behind a `task serve` on another computer, stage 4: "Storage strategy: remote"). A project chooses where its tasks live with the `strategy` section of its own `config.yml`; no section = `local`, silently, exactly as before. Opening a project (`openTaskContext`) resolves it; `ctx.store` is created by the strategy plugin at its FIRST call (`lazyBackend.ts`; `kind`/`capabilities` come from the plugin before that), `ctx.strategy` is the resolution, `ctx.dispose()` releases it (the CLI calls it after each command, the cross-project views per project; the module once per request, see the github section).

- Shape (`strategyConfig.ts`, scope `local`, nothing inherited; the SDK checks the key `strategy`, task checks everything inside): `strategy: { type, fidelity, options }`. `type`: `local` (default) or a plugin ref/alias. `fidelity`: `strict` (default) | `degrade`. `options`: read by the plugin (`validate`), except `fills`, which the host reads. Every problem is a `StrategyConfigError` (a `ConfigSchemaError`: file + dotted key + `hint`, `invalid`/400). A parent layer is checked structurally in its own file but only the own layer is resolved; a `strategy` in the global `~/.task/config.yml` is an error.
- `fills` (`options.fills`): `<capability>: <technique>` or `{ use, fidelity }`; keys are `BackendCapabilities` names (`BACKEND_CAPABILITY_NAMES` in task-core) that have a technique in `strategyFills.ts` (`status meta hierarchy delete history activity search ids`, and `linkTypes.<blockedBy|duplicateOf|causedBy>`); an unknown capability or technique lists the valid ones. A non-exact technique under `strict` needs its own `fidelity: degrade`. The plugin must implement the technique (`StrategyPlugin.fillTechniques`; `local` implements none, so any fill on `local` is an error).
- Secrets: a key named `token|password|secret|apiKey|...` with a value, or a credential-looking value (`ghp_`, `github_pat_`, `glpat-`, `xox`), is a hard error with the fix `tokenEnv: <VARIABLE_NAME>` / `tokenFile: <path>`; `tokenEnv` must be a variable NAME; `strategy.pluginsDir` is an error (no external plugins, R11).
- Types known to the schema (`BACKEND_KINDS`: github, gitlab, remote) but with no plugin (none in the built-in list now; the path stays for a registry built without one, tests use `registryWithout`): `strategy type <t> is declared but no plugin is installed; built-in types: ...`, never a local fallback. A `remote` strategy validates its `options.transport` slot first (`plain-http` options: `url`, `tokenEnv` or `tokenFile`, `timeoutSeconds`); both are real since stage 4 (next sections).
- Plugin host (`task-service/src/plugin-host/`, extractable seam): generic `Plugin` (`extensionPoint`, `validate` -> string with optional `key: ` prefix, `create(options, ctx)`, `describe()`), `createPluginRegistry` (instance, refs `plugins.<id>.<impl>` + aliases, conflicts throw and register nothing, unknown id lists the registered ones of that kind, wrong kind names the right one), `resolveSlot` (`{type, options}` -> `PluginSlotError` `<file>: <dotted key>: <problem>` + hint listing the plugin's options), `createInstance` (30 s limit, `Plugin "<ref>" failed to create its instance: ...` with cause, dispose once). Kinds (`plugins/kinds.ts`): `strategy` (instance = `{backend, describe(), check(), dispose()}`), `transport` and `ordering` (instance = `{compare(a, b, facts), dispose()}`; see Priority, assignee and claim). Built-ins are listed once in `plugins/builtinPlugins.ts` (`createBuiltinRegistry()`); tests inject their own registry through `OpenTaskContextInput.registry`.
- Architecture rules: `plugin-host/` imports only its own files and `node:` (tests also vitest; `seam-imports-task`); `plugins/<id>/` imports the seam, `plugins/kinds`, its own files, task-core and `node:` (`plugin-imports-outside-seam`); `plugins/forge-common/` (code shared by github and gitlab, no plugin, nothing registers there) follows the same list and is imported by `plugins/github/` and `plugins/gitlab/` only (`forge-common-import`); only `builtinPlugins.ts` imports a `plugins/<id>/` folder (`plugin-folder-import`); no computed `import(...)` in any package (`NO_COMPUTED_IMPORT`).
- Commands (`StrategyCommand.ts` over `showStrategy` / `checkStrategy`; they open the project themselves so a config problem is an answer, not a failure before the command): `task strategy show [-p] [--json]` (type, fidelity, fills, tokens as NAME + set/unset, capability table native/emulated/unsupported; opens no backend, creates nothing) and `task strategy check [-p] [--json]` (lines `config strategy fills token security` plus the plugin's lines: local = data, writable, task counts; each warning/error has a `fix`; exit 1 on any error; warns on plain `http://` to a non-loopback host; a `tokenFile` must be absolute and, on POSIX, mode 600 (Windows: a warning, permissions cannot be read)). `--json` failures keep the full result on stderr with exit 1. `task plugins list|config` (the stale flow mirror) is removed: unknown command.
- Host additions of stage 1: `StrategyContext` also carries `source` (the config file), `statuses` / `types` (`ProjectFacts`, from `projectFactsOf(config)`) and `log` (task log writer); a plugin may implement `validateForProject(options, facts)`, run by `resolveStrategy` at load (message `key: problem` becomes file + `strategy.options.<key>`); a `StrategyInstance` may implement `takeNotices()` (`ReadNotice`: `stale`, `ignored`, or `emulated` for a write done through an approximate fill), exposed as `ctx.takeNotices()` (the CLI prints each as a `warning:` line on stderr, the module adds the texts as `readNotices`); a fill the plugin lacks says what it does implement (`describeImplemented`).
- Remaining: `GET /projects` does not expose `strategy`/`capabilities`; `fills` keys outside `BackendCapabilities` (`type`, `fields`, `events`, `writes`, `origin` of design 2A) are refused until the design maps them to capabilities (`writes` now IS a capability, with no fill: see below).

## Storage strategy: migrating (plan `.claude/plans/2026-11-15_migrating-wrapper.md`, phases P0 and P1)

PARTIAL: reads only. P1 routes READS by a routing index; `new` is never written (except by tests), no task moves, no worker, no `strategy migrate` commands (P2 to P5). Writes behave as in P0 (to `current`), and are refused for a task that is not plainly in `current` (see Routing).

```yaml
strategy:
    type: migrating # plugins.migrating.default
    options:
        current: { type: <strategy> } # full strategy blocks, same schema and secret rules as a project section
        new: { type: <strategy>, options: { ... } }
        budget: { requestsPerMinute: 30 } # optional positive integer; validated, not used yet
```

- Agnostic (D13): the plugin reads capabilities, traits, `locationOf` and the port, never a storage kind. Rule `migrating-names-a-storage` forbids `local|github|gitlab|remote` (any case, any substring) in code of non-test files of `plugins/migrating/`.
- Host seam: `StrategyPlugin.strategySlots` names the options that are strategy blocks. `resolveStrategy` checks each like a project section (errors name `strategy.options.<slot>...`; a block needs `type`; a meta-plugin inside one is refused), keeps them in `ResolvedStrategy.subs` and passes `SubStrategyViews` (capabilities, `traits(facts)`, location; NO_TRAITS when a plugin declares none) to `capabilitiesFor`, `traitsFor`, `locationOf`, `validateForProject` and `validateSubStrategies`. `StrategyContext.openStrategy(slot, { dataSubdir? })` (`strategyInstance.ts`) opens a block lazily, once per slot and folder, and disposes it with the parent. `new` uses `<data>/migrating/new`.
- Capabilities = intersection (`capabilityIntersection.ts`, one rule per capability, compile-checked): weaker enum value, both sides for booleans, common link types, `delete` only when equal, `ids` generated only when both. Conflicts the wrapper cannot honour (`events` client vs server, history/activity none vs something) are refused at load. Same location on both sides is refused. `locationOf` = both locations joined with `+`. `traitsFor` = `combineTraits`: tighter limits, pessimistic cost without a model, no `foldsCreate`.
- Enforcement: an operation whose capability the intersection lacks is refused with `UnsupportedByBackendError` naming the side to change, even if `current` could do it. Trait limits (depth, text lengths, label rules, comment authors) are NOT enforced yet.
- `strategy show` prints each side and its capability table; `check` prefixes each side's lines (`current.`, `new.`) and always warns `state` (nothing moves yet) with a fix. `labels sync` is not forwarded to `new`.
- Routing (P1, `routingIndex.ts`, `routedReads.ts`, `idTranslation.ts`, `summaryGraph.ts`): `<data>/migrating/index.json` `{format: 1, rows}`, row `{publicId, a?, b?, state: in-a|moving|in-b|deleted, since, version}`. A task of `current` with no row is `in-a` and its public id is its own id (a project that never moved a task has no file; a missing file is "no row"). Rules checked at load: `in-a` needs `a` and no `b`, `moving` both, `in-b` needs `b`, `publicId` = `a` when `a` exists, public ids and per-side ids unique. A damaged file is a `BackendDataError` naming the file (hint: do not delete, restore or rebuild), never recreated. Re-read at every read (parsed only when the text changed); writes (`mutate`, `replaceFromRebuild`) are atomic through the host writer, run under a `ProjectWriteLock` on `migrating/index.lock` (separate from the task lock, which `current` takes itself) with the rows re-read inside it. Limit: the lock blocks the event loop while waiting (up to 10 s).
- Reads by state: `in-a` and `moving` read `current`, `in-b` reads `new`, `deleted` is not found. While every row is `in-a` (or none) reads go straight to `current` and `new` is not asked. Otherwise listings are `current`'s tasks minus `in-b`/`deleted` rows, then `new`'s `in-b` tasks (order: current's, then new's; not stable across a move); each public id once. A row whose task is missing from its side, or two tasks under one public id, is a `BackendDataError` naming it (fix: rebuild). Ids in records (`id`, `parentId`, link targets, parent/link activity) are translated to public ids; a relation to a task of `new` the index does not know is an error naming it. `listPage` merges both sides' filtered pages and pages with its own cursor (`migrating:<offset>`); `text` is pushed to each side's own search. Hierarchy (children, tree, forest, descendants, ancestors, full tree) is computed from the merged summaries with the local store's rules; links ask both sides: outgoing links from the authoritative copy, inverse links from both sides but only for tasks that side is authoritative for, shown with the authoritative summary. Labels: both sides' counts minus the labels of non-authoritative copies (a task of `new` with no block still counts in `new`'s labels). Invariant a later phase must keep: a task in `new` has its parent's copy in `new`.
- Prefix lookup: an exact public id wins; else the unique public id starting with the prefix (current answers for its tasks, the index for tasks only in `new`); several = `AmbiguousTaskPrefixError`.
- Writes in P1: a task with a row other than `in-a` (also as parent or link target) is refused with `BackendRejectedError` naming its state (a deleted one is not found); other writes go to `current` as in P0. `create` still goes to `current`.
- Identity block (`identityBlock.ts`): metadata every copy in `new` carries, through the generic meta capability only: `migrating.publicId`, `migrating.fromId` (absent for a task made in `new`), `migrating.hash` (16 hex of title, description, status, type, labels, meta without the block, priority, assignee). `identityCarrierProblem(capabilities, ref)` returns the problem plus fix when `new` has no metadata or no writes; P4 `start` must call it (not called at load, since the P0 pairs may lack a meta fill). Label-based carriers cap key+value at 50 characters: ids of 8 characters fit.
- Rebuild (`rebuildIndex.ts`): `rebuildIndex({current, next})` lists `current`, lists and resolves each task of `new`, reads only. Copy of a task still in `current` = `moving`; made in `new` = `in-b`; copy whose origin is gone = `in-b` plus a note; no block = `unindexed`. Authority cannot be known from the block: a copy that differs from the hash is rebuilt as `moving` with a note (compare before going on). `deleted` rows are not rebuilt. Damaged or inconsistent blocks, duplicate public ids and id collisions are loud errors. `adoptIndex(index, input)` writes the rows, keeping a damaged file as `index.json.damaged-<stamp>`, and notes the old rows it could not rebuild. No command calls them yet (P4).
- `strategy check` adds an `index` line (counts per state, or the damage with its fix); the `state` warning text changes when rows route reads away from `current`.
- Tests: `runBackendContract` over local+local and local+fake GitHub (`MigratingBackend.contract.test.ts`); P1 suites run over both pairs (`testHelpers.ts`, `MigratingBackend.routing.test.ts`, `rebuildIndex.test.ts`).
