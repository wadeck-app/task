# Migration (task migrate)

Moved from CLAUDE.md; CLAUDE.md keeps the digest.

## Migration (`task migrate`, stage 3 of the storage design)

`task migrate --from <project> --to <project> [--dry-run] [--allow-loss <kind>[,...]] [--resume] [--history-comment] [--only-open|--status] [--ids] [--limit] [--comments] [--emit-events] [--json]` copies every task between any two backends through the async port (local files, github). Both sides are REGISTERED projects (id, unique prefix >= 4, name, alias; never a path); each project's own `strategy` picks its backend. To move a project onto GitHub: `project add` a second project, give it a github `strategy`, migrate into it. Same project, or two projects on the same repository (`StrategyPlugin.locationOf`), is refused. `-p` is an error, `TASK_PROJECT` is not read. There is no `task import`: migrate covers it (decided, no alias). The source is only read, with fresh reads (`freshReads`: the github cache is bypassed); a source answered from a stale cache is refused.

- Code: engine `task-service/src/migrate/` (`migrateRun.ts` run, `migratePlan.ts` plan, `mapTask.ts` per-task mapping + losses, `hierarchyPlan.ts` order/limits, `lossLedger.ts` rows, `migrateJournal.ts` journal + lock, `migrateVerify.ts` read-back, `migrateProjects.ts` registry entry); CLI `task-cli/src/commands/MigrateCommand.ts` (parsing, text, progress). `BackendTraits` (task-core `backend/traits.ts`; `StrategyPlugin.traitsFor`) says what a backend keeps and its limits (creation instant, comment authors, text/label/hierarchy limits, cost per write); a plugin that declares none is assumed to keep nothing. `CreateTaskInput.createdAt` is honoured by the local backend only.
- Flow: read the source (paged), plan (mapping, loss table, estimate), `--dry-run` stops (exit 0, no write, no journal, no lock). Blocked plan = exit 1, nothing written. Run: tasks parents first (create with final status, then type, labels, metadata, marker), links once both ends exist (a status a link changed, e.g. GitHub duplicate, is put back), comments in order, then every task written to is read back and compared (differences are reported, never repaired; status `failed`, no resume command).
- Loss kinds (`--allow-loss`; a group covers its kinds, `all` everything): `status`, `status-outcome`, `type`, `labels`, `meta`, `comments`, `history` (history/activity cannot be replayed through the port), `created-at` (target assigns it), `marker`, `text-length`, `hierarchy:{unsupported,depth,children,orphan,cycle}`, `hierarchy:excluded`, `links:{blockedBy,duplicateOf,causedBy,dangling,excluded}` (the two `excluded` ones: see Subsets, phase 2). `--history-comment` writes a note comment per task (creation instant, status history, counts) and so resolves `history` and `created-at` when the target has comments. Comments are written by the migrating user: first line `Originally posted <iso> [by <author>] [migrated from <qid>#<id>]` (author in the line only when the target cannot store it).
- Ids and marker: target ids are new; `meta.migratedFrom=<source project id>/<source task id>` is written when the target has metadata (github needs `fills.meta`), else kind `marker` applies. Texts are not rewritten (references counted in notes). `updatedAt` is the migration time.
- Journal: `<target data dir>/migrate-journal-<from id>-<to id>.json` (SDK `writeFileAtomic`): per source task `{target, phase: created|fielded|linked|done}`, `status` running|stopped|completed, `lastError`, `pending` (a creation started and not recorded: title + target clock; the next run takes back the one matching task, none = created again, several = refused). A creation is written to the journal at once, other phases at most every 250 ms. Damaged journal = loud `MigrationStateError`, never replaced. Lock `migrate.lock` (pid) in the same folder; a dead pid is taken over, an unreadable lock refused. Fields of a resumed task are only filled in, never replaced.
- Idempotence: journal first, else the marker (target tasks not in the journal are read to find it); a second run creates nothing and writes nothing. An unfinished journal needs `--resume` (refused otherwise, with the hint); `--resume` without journal is refused. Rate limit (`RateLimitedError`): stops cleanly, prints `Retry after <iso>` and the exact command; other failures stop at the first one (status `failed`, `resumeCommand`). Exit 0 = done or dry run; 1 = blocked, stopped, read-back differences, or error.
- Events (decided): none per task by default (a bulk copy is not a user editing tasks; a flow on `onTaskCreated` would run once per task, which R7's "no surprise events" spirit forbids). One `onTasksMigrated {fromProjectId, fromProjectName, toProjectId, toProjectName, created, resumed, skipped, failed, remaining, complete}` after the last write (project fields = the target's; none for dry run, blocked, or a run that did nothing), declared in `queueEventDeclarations` (new hash: the CLI redeclares by itself). `--emit-events` adds `onTaskCreated`, `...TypeChanged`, `...LabelAdded`, `...MetaChanged`, `...Linked`, `...CommentAdded` for what THIS run wrote, in order, before the summary (the marker raises no event); events of a run that crashed are lost.
- Cost into GitHub (fake-server counts, labels already in the repository): plain open task 1 write / 5 requests (was 2 / 10); closed task with type, label, priority label, marker and history note 3 writes / 16 requests (was 7 / 32); parent + blocker + child with a link 5 writes / 24 requests (was 8 / 39). How: (1) `TaskBackend.createMigrated?` (optional, `MigratedCreateInput` = create + type, labels, priority, meta) is implemented by the GitHub backend only and called only when `BackendTraits.foldsCreate` is true (a lazy wrapper cannot tell a missing member, so the engine never tests it): type label, plain labels, priority AS LABEL and metadata (marker included; body block or `meta:` labels) ride in the one create POST; labels missing in the repository are created first (probe + create, once per process), and every label/type/meta/priority/body-limit refusal happens BEFORE any request with the error of the separate write. Not folded, written afterwards by `fillFields`: the close of a terminal status (PATCH), the sub-issue attach, a priority in the issue field, a native issue type (`typeMap.issueType`), the assignee, links, comments. `fillFields` still computes what is missing, so journal phases, resume and idempotence are unchanged; with `--emit-events` the folded fields raise their events as before (`onTaskCreated` describes the task without them). (2) Because the marker now lands with the create, a task is `adopted` (parent and status checked and put back) only with journal evidence that the creation is ours and unfinished: the journal entry is at phase `created`, or it is the creation the journal left `pending`, and the target folds. A task found by its marker with NO such evidence is left as it is (a person may have closed or detached it), a note says `found by marker, not touched` and the final check reports any difference. (3) The final check reads a task with ONE request (`resolve`) when it has no link and no comment (cost trait `resolve` cheaper than `read`; other backends keep `getMany`, a remote answers a chunk in one request), the whole record otherwise; `compare` is unchanged (`Observed`).
- Estimate (dry run), FROM THE PLAN, not measured (printed so): `estimateMigration` (migratePlan.ts) asks the target's `cost.model` (GitHub: `githubCostModel.ts`, counts per call pinned against the fake: create 3 requests, close 1, attach 2, a separate field write 4, link 7, comment 5, label probe + create 2, check read 1 or 2-4) for writes (requests that change the target) and requests, adds the reads of the source, of the marker scan and of the target list; a target without a model pays `cost.requests`/`cost.seconds` per counted write. Labels are counted as new (upper bound), `priorityStorage: auto` as a separate write, a resumed task as what its journal phase has left (`created`: fields as separate writes, links, comments; `fielded`: links, comments; `linked`: comments). The model throws on a resumed task without a phase, a status the statusMap lacks, or metadata with no meta fill (no silent guess). The final check reports a task that cannot be read through `resolve` as a `read-back` difference and goes on. Time = writes x (write spacing + 3 s): the 3 s is an ASSUMPTION (about 4 requests at 0.3 to 1 s), not re-measured. `estimate.hours` = the longest of that time, writes / the hourly cap and writes / the per-minute cap (`cost.contentCap`: GitHub documents 80 content-generating requests a minute and 500 an hour, docs.github.com rate limits for the REST API; the hourly one is the stricter for a sustained run); when a cap, not the pace of the writes, is the limit, a warning naming both caps says "expect at least N h", to use `--resume` (progress is per task) and that the 5000/h primary quota is separate. Tests: `migrateGithubCost.test.ts` (budget per task, resume, events, verify detection through `resolve`, estimate vs fake: writes exact, requests within 5%), `githubCostModel.test.ts`, `migrateEstimate.test.ts`, `GitHubBackend.createMigrated.test.ts`. No real GitHub run since this change.
- Tests: `migrateRun.test.ts` (two local backends, `RestrictedBackend` via `createRestrictedBackend`, wrappers that fail or lose answers), `migrateProjects.test.ts` (registry + fake GitHub both ways), `MigrateCommand.test.ts`. `migrate.testkit.ts` is in the `fsAllowlist`, `migrateJournal.ts` too.
- Live: `npm run build`, then `GH_TEST_TOKEN=<token> GH_TEST_REPO=<throwaway repo> node scripts/live-github-migrate.mjs` (not in CI; exit 2 when a variable is missing): seeds a local project, dry run (asserts no write request), blocked, real run into the repo (reads GitHub back through the API), again (0 created), back into a third local project (compared task by task), cleanup (issues closed `not_planned`, created labels deleted, both asserted). The target repository is read whole: its older issues are migrated back too, and a state no status maps (a duplicate close) fails the read with the fix, so the project config maps `duplicate`.
- Not done: `--follow`, per-task events for a crashed run, restoring links that other tasks held to a task deleted from the target.

### Subsets and comment modes (phase 2)

Origin: a test factory migrating ~25 tasks into GitHub (content writes capped at 80/min and 500/h). Code: `migrateSelection.ts` (validation, selection), `migratePlan.ts` (`buildPlan`, `relinkOf`), `migrateRun.ts` (`relinkPass`), `mapTask.ts` (`digestComments`), journal `deferred`. Every flag below works in both forms of migrate; without them nothing changes (the pre-existing tests pin it).

- Flags: `--only-open` (non-terminal statuses of the SOURCE config), `--status a,b` (source statuses; unknown = `InvalidStatusError` listing the valid ones; not with `--only-open`), `--ids a,b` (exact source ids; unknown = refusal), `--limit <n>` (1 to `LIST_LIMIT_MAX`), `--comments each|digest|none`. Filters combine with AND. A value flag given twice, empty or with an empty entry is refused by the CLI; the engine re-checks everything before any lock or read of the target.
- Selection decides only which NEW tasks join. A task the journal (or a marker) already knows stays in the run: unfinished ones are finished and count first against `--limit`, finished ones are kept. A creation the last run left `pending` is always in. So the same command, run again, copies the next `n` and never copies twice.
- Order for `--limit` is the plan order (roots in source order, then breadth first), so a parent always precedes its children.
- Report: `result.selection {total, selected, alreadyMigrated, excluded, excludedBy {status, ids, limit}, deferred {parents, links}}` (absent without a selection); `counts.source` stays the number of tasks read. A task excluded for several reasons counts once, under the first (status, ids, limit). The dry-run estimate covers the selected tasks only.
- Losses `links:excluded` and `hierarchy:excluded` (groups `links`, `hierarchy`, `all` cover them): a link or parent of a SELECTED task whose other end is outside the run. Blocking unless allowed; the row names the tasks. A link held by an excluded task is not reported (the task is not copied). The child is created as a root.
- The relation is kept in the journal (`tasks.<id>.deferred {parent?, links?}`, source ids) and written by the first later run whose plan has the other end (`relinkPass`: get the record, write what is missing, then forget). Idempotent; a crash repeats it harmlessly. Events (`--emit-events`): `onTaskParentChanged`, `onTaskLinked`. A relation to a task never selected stays a loss on every run (pass `--allow-loss` each time, as for any loss). The estimate counts relinked links, not parent attachments (a note says so).
- `--comments digest`: ONE comment per task, blocks in order separated by `---`, each with its `Originally posted <iso> [by <author>] [migrated from <id>#<cid>]` header (the author is always in the text), ending with `[migrated from <id>#digest-1]`. Split into `digest-2`... only when `traits.commentTextMax` forces it (a single block above the limit is cut: `text-length`). With `--history-comment` the note is the last block (a task with no comment keeps its note as before). The read-back checks the digest marker(s), not one comment per source comment (it never compared texts). Cost models count the digests (`MigrationTaskFacts.comments` = comments written).
- `--comments none`: no comment written; loss kind `comments` (detail `--comments none`, fix points to `digest`). Refused with `--history-comment` (the note is a comment).
- `result.comments {mode, planned, saved}` (modes other than `each`) says the writes saved against one comment each. Switching the mode between runs of one migration can duplicate comments on tasks that were unfinished: not guarded.
- In place with a selection that leaves tasks out: status `partial` (exit 0; scripts test `inPlace.switched`), config.yml NEVER switched, source not re-read, only the tasks written by the run are read back. The journal ends `stopped`, so the next run needs `--resume` (the printed command has it and keeps the selection flags). The switch happens in the run whose plan has every source task (a run with no selection, after any number of partial ones): it reads back ALL tasks, checks the source against the content hashes of each copy, and relinks what the partial runs deferred before the read-back. `onTasksMigrated.complete` is false while tasks are left out.
- Limits: depth/children limits of the target are not checked for a parent written by a relink; a parent that is on the target but outside the plan (marker-found, no journal entry) counts as excluded; not run against a real GitHub (fake server only).
- Tests: `migrateSelection.test.ts`, `migrateComments.test.ts`, `migrateSelection.units.test.ts` (service), `migrateGithubCost.test.ts` (estimate writes exact vs the fake, digest/none/only-open), `MigrateCommand.phase2.test.ts` (CLI parsing, text, in-place partial then final).

### In place (`task migrate --in-place --to-config <file> [-p <project>]`)

One registered project changes storage (id, name, aliases, paths unchanged); the alternative is a second registered project and the two-project form. `--from/--to` are refused with it, `--to-config`, `--accept-differences` and `--accept-draft-change` without it are refused (`--accept-draft-change` also needs `--resume`); `-p`/`TASK_PROJECT`/cwd select the project (plain migrate still refuses `-p`). The printed resume/next command uses `-p <project id>`. Code: `migrate/migrateInPlace.ts` (`migrateInPlace`), engine hooks `InPlaceHooks` in `migrateRun.ts`, CLI in `MigrateCommand.ts`.

- Draft = the WHOLE new config.yml (contract): the top-level keys of the current file it lacks are a warning in the dry run, the run and `--json` (`inPlace.configKeysDropped`) with the fix (copy config.yml, add the strategy section); not blocking, the backup keeps them. It is read ONCE (`TaskConfigLoader.parseConfigText`): the text validated is the text written; a file edited meanwhile is reported (`draftChangedOnDisk`, warning). Validated like a layer (schema, secrets, hooks, `strategy`; errors name the draft) and must hold a `strategy`.
- Source = the project as it is (fresh reads). Target = the same project opened with the draft IN PLACE OF its own layer (`ownLayer` of `OpenTaskContextInput`/`loadProjectSetup`/`StrategyTarget`; nothing written; parent layers stay). So statuses/types/strategy are the draft's; a status or type it lacks is the ordinary blocking loss.
- Refused before any write (dry run too): draft missing/without strategy; both sides `local`, or the same `locationOf`; a remote target whose server `info` names this project's registry id (a loop; an `info` without id is a warning; a dry run runs the strategy checks first and asks `info` only when reachable; a real run turns an `info` failure into a refusal with the `describeError` message and hint); `config.yml.before-migration` existing with other content than the current config; config already equal to the draft (unless the crash case below).
- Lock first: a real run takes `migrate.lock` before any check and passes it to the engine as `heldLock`. Only the taker releases it, in `migrateInPlace`, after both contexts are disposed and the result is built; the engine never releases a lock it was handed. A dry run takes none.
- Journal `<data>/migrate-journal-<project id>-inplace.json`, `inPlace: {targetHash, parts, location, kinds, switched, verified, switchStarted, acceptedDifferences?}`; each task entry also holds `content` (hash) and `parts` of what the source held when copied (`sourceContent.ts`). `targetHash` covers the strategy section as parsed WITHOUT its connection-only options (`tokenEnv`, `tokenFile`, `timeoutSeconds`, `cache`, `pageSize`, `maxPages`, `writeSpacingSeconds`, `rateLimit`; also inside `transport.options`), plus the statuses with their flags (default, terminal, negative), the types, `priorities` and `defaults.priority` of the project with the draft (not comments, `leaseMinutes` or other keys); `parts` hashes each piece (`type`, `options.<key>`, `statuses`, `types`, `priorities`, `defaults.priority`...) to name what changed. `switchStarted` is saved right before config.yml is written and cleared when that write failed without replacing it. An unfinished journal with another hash: same `location` (`locationOf`, else `kind:<kind>`) needs `--resume --accept-draft-change`, another location is always refused; a dry run only prints a note. A COMPLETED journal is archived with the id map (`<name>.archived-<time>.json`, never deleted) by the engine hook `beforeWrite`, right before the run's first write: the pair moves through temp names and is put back whole if any rename fails, and a refused, blocked or failed-preflight run leaves both files untouched (a dry run ignores them, `--resume` on a completed journal is refused).
- Id map `<data>/migrate-idmap-<project id>.json`: `[{from, to}]` in creation order, atomic, after every creation and before the switch; no `url`. `--json` `idMap` stays `{source, target}`.
- Switch: only after every task of the plan is read back (not only what the run wrote) with no difference, the source is unchanged (every task is re-read IN FULL and its content hash compared with the journal's, else the plan's; added, changed (parts named) or removed tasks stop the run before the read-back result is judged), and journal (`verified: true`) and id map are saved. `switchConfig` re-reads config.yml: equal to the draft = nothing to do; different from the snapshot taken at the start = refused (step `switch`, hint: review, `--resume` re-snapshots); else the fresh text goes to `config.yml.before-migration` (none when there was no file), then the draft text replaces config.yml, atomically. Local task files are never deleted; rollback = copy the backup back.
- Resume cases: a switch that failed, or a crash after config.yml was replaced (journal `verified`, all tasks `done`, config = draft): `--resume` decides from the journal, opens no backend, creates nothing, only marks switched and raises the summary event (also with no config file/backup). Source changed before the switch (task added, removed or changed): status `stopped` (step `source-changed`, ids and changed parts named), nothing switched; `--resume` copies added tasks only; a changed task keeps the copied version and a removed one keeps its copy, so the next runs stop again until `--accept-differences`.
- Third review rules: the target context is opened `freshReads` (the read-back and the pre-switch source check never use a cache still valid); a `stale` read notice from either side during the read-back or the source check stops the run (`stopped`, step `stale-read`, nothing switched). Before the first write the target is listed: tasks claimed by neither the journal nor a marker are a blocker (`MigrationRefusedError`, count + ids + hint + `--allow-non-empty-target`; the list is the one `buildPlan` read, `MigrationPlan.targetSummaries`, no second request; the flag records the accepted ids as `inPlace.acceptedForeignIds`: a resume accepts only those, a task that appeared since is a blocker again and the flag then records it too, and an accepted task is never adopted as the pending creation of a crash; never copied into printed commands). A `stale` notice of the TARGET after the plan and the foreign check stops a real run before the first write (`stopped`, step `stale-read`, no journal); a journal that has an `inPlace` without `source` is refused on a resume (it predates source recording: move it aside, the id map stays). The journal records `inPlace.source` (`{kind, location}`): a resume whose current source differs is refused. `recoverArchives` completes a `*.archiving-<stamp>` left by a crash (the partner file is archived with the same stamp; a notice says so; the renames are all or nothing and a failure, or a folder that cannot be listed (not ENOENT), is a `MigrationStateError` that stops the run). `inPlace.backup`/`rollback` appear only when the config was replaced and the backup file exists; a not-switched run says `would be gone` for dropped keys. The id map is written on the journal's 250 ms throttle (only when behind it), always before the switch and on a stop or failure; the start of a run rewrites it from the journal. The id map's dirty flag is cleared only after the write succeeded; a map that cannot be written blocks the switch (`MigrationStateError`, nothing switched). A journal that cannot be saved AFTER the switch gives `switched: true`, `inPlace.bookkeepingPending`, a warning with the `--resume` fix, NO event (the `--resume` that finishes the bookkeeping raises it, once) and CLI exit 1; a completed run records `inPlace.summaryEventRaised` when it returns the event, and a bookkeeping resume skips the event when that is set. `canonicalJson.ts` holds the one `canonical`/`sha256Hex` (golden-tested).
- `--accept-differences`: read-back differences that cannot clear (a forge normalising a text) and source changes or removals of already-copied tasks (`field: source-changed: <parts>` / `source-removed`; a task ADDED is never accepted) no longer stop the switch; they are printed in full, stored in the journal and in `--json` (`inPlace.acceptedDifferences`), plus a warning, and the text output says so. The flag and `--accept-draft-change` are NEVER copied into a printed resume/next command. Without it the stop names the flag and the risk.
- Bookkeeping-only resume (crash after config.yml was replaced) is taken only when the journal says `switchStarted` AND config.yml equals the draft; a draft copied by hand over config.yml after a failed switch is refused with the fix (restore `config.yml.before-migration`, or delete the file if there was none) and then runs the full path. Its answer and the normal one come from one function (`assembleResult`: remote events dropped with a warning, `configKeysDropped` from the backup, `draftChangedOnDisk`, accepted differences, rollback text).
- Dry run: the answer always carries `blocked` and `blockers` (loss kinds not allowed, `targetNotEmpty`, `stale-read`); the text says `BLOCKED: a real run will be refused`; the exit code stays 0 unless `--fail-on-blocked` (dry run only, both forms of migrate) is given. No journal, lock, id map or config; runs `checkStrategy` on the draft first (`{backend:false}` skips the backend lines for gitlab, whose check sends a no-op write); an error line stops with a `MigrationRefusedError` carrying the fixes. Every context of a dry run (source, target, the check) is opened with `memoryCache` (`StrategyContext.memoryCache`, github uses `MemoryResponseCache`), so nothing is created under the data folder (tested: a fresh project's data folder does not exist afterwards).
- Events: rules unchanged; `onTasksMigrated` (same project both sides) is built after the switch attempt (`complete` false if it failed or stopped), also when a resume only finished the bookkeeping.
- Not verified: no real GitHub run (fake server only); the `info`-without-project-id warning for a remote target has no test.
