## Storage strategy: gitlab (stage 5, read and write)

FREE TIER ONLY, by owner decision: what needs a paid tier (blocking links, epics, weight, scoped-label exclusivity, tier detection) is not supported and fails with `requires a paid GitLab tier, which task does not support`. There is no `tier` option (a `tier:` key is a load error). VERIFIED LIVE on gitlab.com Free (2026-11-09, throwaway project, one FINE-GRAINED personal access token): the findings are in the storage plan (`.claude/plans/2026-11-08_storage-strategies.md`, "2.3.1 Live GitLab findings"), the mock behind the tests is guarded by recorded live exchanges (below). NOT SUPPORTED (owner decision 2026-11-14, to be read as a support statement, not only as a verification gap): classic personal access tokens (`api` / `read_api`) and self-managed instances (`baseUrl` accepts another host but nothing is tested or promised there); only a FINE-GRAINED token on gitlab.com is supported. NOT verified: other GitLab versions, a token weaker than the test token (its permissions could not be listed).

Shared with github: `plugins/forge-common/` (see the github Code paragraph).

Code: `task-service/src/plugins/gitlab/` (plugin `gitlabPlugin.ts`, backend `GitLabBackend.ts` reads, writes `gitlabWrites.ts` over `gitlabWriteHost.ts`, work items (GraphQL hierarchy, type conversion) `gitlabWorkItems.ts`, options `gitlabOptions.ts`, mapping `gitlabMapping.ts`, status map `gitlabStatusMapping.ts`, revision `gitlabRevision.ts`, labels `gitlabLabels.ts`, client `gitlabClient.ts` (REST and `graphql()`), token `gitlabToken.ts`, what the token needs `credentialRequirements.ts`, check `gitlabCheck.ts`, migrate traits `gitlabTraits.ts`, API types `gitlabTypes.ts`). Official REST API v4 and GraphQL through Node `fetch` only: no glab CLI. Registered as `plugins.gitlab.default` / `gitlab`.

```yaml
strategy:
    type: gitlab
    options:
        project: group/subgroup/project # required: path, or the numeric id
        tokenEnv: GITLAB_TOKEN # NAME of the variable (or tokenFile); PRIVATE-TOKEN header; see "The token"
        baseUrl: https://gitlab.com/api/v4 # self-managed: https://HOST/api/v4 (must end with /api/v4)
        statusMap: # every status; ONE open and ONE closed status without label (GitLab has no close reason)
            backlog: { state: open }
            in-progress: { state: open, label: 'status::in-progress' } # 'status:in-progress' works the same: both are plain labels
            done: { state: closed }
            cancelled: { state: closed, label: 'status::cancelled' }
        # typePrefix 'type:', typeMap { bug: { issueType: incident } | { label: x } }, metaPrefix 'meta:', pageSize 100, maxPages 50
        # priorityPrefix 'priority:' ('priority::' is a plain label on Free too), priorityMap { urgent: 'P0' } (task priority -> the WHOLE label name); no priorityStorage: a priority is always a label
        # cache { ttlSeconds: 30 } (memory only), timeoutSeconds 15, writeSpacingSeconds 1, rateLimit { maxWaitSeconds: 70 }
        fills: {} # meta: labels | body-block; delete: hard | tombstone; linkTypes.duplicateOf|causedBy: relate-block
```

| Task concept          | GitLab                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| id                    | issue `iid` as a string (`ids: assigned`: exact only; `#12` accepted); API paths use the project path URL-encoded or the numeric id; the global `id` of the issue (GraphQL) is read from the issue                                                                                                                                                                                                                                                                                              |
| title / description   | title (at most 255 characters, refused before sending), description without the managed block (`<!-- task:begin v1 -->{json}<!-- task:end -->`), CRLF as LF, at most 1,048,576 BYTES (not characters)                                                                                                                                                                                                                                                                                           |
| status                | `state` (opened/closed) + status labels through `statusMap`; a combination no status maps, or two status labels, is a `BackendDataError` naming the issue (the whole list fails)                                                                                                                                                                                                                                                                                                                |
| labels / type         | labels minus status, type, priority and (with the fill) meta labels; type = type label (`typePrefix`, `typeMap.label`) or native `incident` (`typeMap.<t>.issueType: incident`). `test_case` is refused at load (GitLab turns it into `issue` on create and ignores it on update), `task` too (a native Task is the hierarchy child, so it never defines a type)                                                                                                                                |
| priority              | ALWAYS a label: `priorityPrefix` + the priority (default `priority:`, `::` allowed) or, for a priority named in `priorityMap`, that whole name; exact case (labels are case sensitive: `Priority:high` is an ordinary label). Both spellings are reserved. Two priority labels are a `BackendDataError` naming the issue (a read AND the whole list, like two type labels); a label of a priority the project does not have reads as no priority with an `ignored` notice naming the valid ones |
| assignee, claim       | the `claim` key of the managed block of the DESCRIPTION: `{"claim":{"assignee":"w1","claimedAt":"<iso>","leaseUntil":"<iso>"}}` (a hand-made assignee has no instants); `assignee` free text, no GitLab user is read or written (the issue `assignees` stay empty). A block that cannot be read is an error naming the issue on a read and on a claim, and reads as unheld (with a notice) in a LIST, so one bad issue never fails the list                                                     |
| meta (fill only)      | label `meta:key=value` (`::` prefixes allowed), or `body-block`                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| parent, children      | native, depth 2 (below)                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| links                 | `relates_to` only. `blockedBy` is refused (paid tier); `duplicateOf` / `causedBy` exist only through `fills.linkTypes.<type>: relate-block` (managed block + `relates_to` link); items of other projects are skipped with a notice                                                                                                                                                                                                                                                              |
| comments              | notes with `system: false`; author = the token user                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| history / activity    | status replayed from `resource_label_events` + `resource_state_events` (events within 1 s are one change: the state event of a PUT is about 0.5 s BEFORE its label events; GitLab does not record the initial state); activity = label events plus the system notes of title (HTML diff, read as from/to), description (no diff exists), type, parent and child changes                                                                                                                         |
| createdAt / updatedAt | `created_at` / `updated_at`                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| revision              | `<updated_at>#<9 hashes>` (title, body, status, type, labels, meta, links, priority, claim); a write compares only the parts it changes; `body` is the visible description WITHOUT the managed block (the block is covered by `meta`, `links` for duplicateOf / causedBy, `claim`), so a claim is no conflict for a description edit and the other way round; the `relates_to` links and comments are not in it (a note does not move `updated_at`)                                             |
| list rows             | every summary of `list` / `listPage` carries `priority` (the label), `assignee` and `leaseUntil` (the block) from the ONE list answer (labels and description are in it): N issues cost one list request per 100 and no request per issue (`GitLabBackend.requestBudget.test.ts`: 150 issues = 2 list requests, no `GET /issues/N`)                                                                                                                                                             |
| search                | `listPage({text})` sends `search=` (the server matches title AND description, every word must start a word, case-insensitive, no lag) and keeps the issues whose TITLE contains the text; `find` ranks over the full list                                                                                                                                                                                                                                                                       |

Capabilities (`gitlabCapabilities(fills)`): hierarchy `limited` (2 levels, 99 children per parent), `linkTypes` none natively, status `mapped`, history `derived`, activity `native`, search `native`, concurrency `check-then-write` (GitLab ignores `If-Match` / `If-Unmodified-Since` on a PUT), ids `assigned`, labels yes, comments yes, writes `full`, indexedGraph no. By fill: `meta` (`labels` exact, `body-block` approximate), `delete` (`hard` needs `Work Item: Delete`, `tombstone` is close-only), `linkTypes.duplicateOf|causedBy` (`relate-block`, approximate, needs `degrade`).

Priority, assignee and claim (stage 3b; code `gitlabPriority.ts`, `gitlabWrites.ts` "priority" and "assignee and claim", shared `forge-common/taskFieldBlocks.ts` and `priorityNames.ts`, the same rules as the local store: `decideClaim`, `normalizeClaimRequest`, typed errors): capabilities `priority`, `assignee`, `claim` are true, noted `partial` by `task strategy show` ("always a label"; "hidden block ... the last write wins and the first writer is not told"; "optimistic").

- Options: `priorityPrefix` (default `priority:`, no edge space or comma, may be scoped `priority::`) and `priorityMap` (task priority -> whole label name, checked at load against the project `priorities` through `validateForProject`: a key the project lacks, an unusable label, two priorities on one label). A key `priorityStorage` is a load error "GitLab Free has no native priority field ... remove priorityStorage"; `priorityFieldId` / `priorityFieldName` are plain unknown options. Collisions are refused at load, naming the key: the prefix against `typePrefix` / `metaPrefix` (equal or one starting with the other), a status or type label (or a mapped name) that starts with the prefix or equals a mapped name, a mapped name starting with `typePrefix` / `metaPrefix`, anything that would read as the reserved `task:deleted`.
- Writes: `setPriority` swaps the label with ONE `PUT labels` (the whole set: no moment with two priority labels or none), none when the issue already has exactly that label, a stray second one is removed by the same PUT; `clearPriority` ONE PUT, none when there is no priority label. `add-label` and `remove-label` of a priority label are refused BEFORE any request (`BackendRejectedError`, hint `task set-priority`; remove is refused too, unlike status and type labels which are skipped silently). `setAssignee` / `clearAssignee` / `claim` / `release`: after the usual conditional re-read and revision check (part `claim`, or `priority`) ONE `PUT description` that replaces ONLY the managed block slice of the RAW description (the other keys kept; every other byte of the text kept: no trim, no CRLF change, no quick-action check of text the claim did not change; a text without a block gets the block after `

`, and a release removes the block with that `

`; GitLab itself still turns CRLF into LF and strips trailing blanks of what it receives, which is not task's doing); a request that changes nothing sends nothing. A bad claim request (blank or multi-line assignee, lease not after now) is refused before any request. A claim on a task in a terminal status is refused by the use case (`TaskClosedError`) before the backend.

- Race: GitLab has no conditional write, so two workers can both pass the check and both PUT, the last description wins. After the write the record is read again and compared with what was written: a caller that does not hold the issue gets `TaskClaimedError` naming the real holder (a `release` or `clearAssignee` that another worker's claim overwrote is a `TaskConflictError` "task <id> was claimed by <holder> while you were releasing it", not a refusal with an empty requester; a `TaskConflictError` "nobody holds it now" when the block was erased); never "claimed". The last write wins; a worker that reads back after the winner's write is told, the first writer is not: a dispatcher needing a hard guarantee keeps its own lock or uses `task serve` (`strategy check` says "optimistic, not atomic" plus that sentence). `task next` handles the loser like github: it moves to the next candidate.
- QUICK ACTIONS: the block is ONE line starting with `<!--` (JSON never holds a raw newline), so a name like `/close`, `a/b` or `/label ~x` cannot make GitLab run anything (tests assert `quickActionsRun` 0 and the issue still open; NOT yet seen on the real GitLab: smoke phase). The visible text is NOT checked again by a claim (a fenced `/etc` line GitLab already holds does not block it); the length is. The one way a name could still start a line with a slash is a Unicode line separator (U+2028, U+2029, U+0085; CR, VT and FF are control characters, already refused by the name rules): such an assignee is refused before any request with a message naming the quick action. Whether GitLab splits lines on those characters is NOT verified; the refusal is a precaution.
- Labels: `task labels sync` creates the priority labels after the types and before the tombstone, in the order of the project priorities, colour `#fbca04`, description "Task priority (set by the task tool)" (`strategy check` `labels` line lists the missing ones). The `labels` listing and `labels` of a record leave them out. Activity: a priority label event is an activity row of kind `priority` (a swap is two events, the added label first).
- `task strategy check`: a new line `fields` (after `links`): where the priority, assignee and claim live and that NO permission beyond `Work Item` and `Label` is needed (the credential table has no new row: the labels are `Label`, the block is a description update, `Work Item: Update`); a claim is optimistic, not atomic (the race sentence above). A second new line `priority-labels` (warn, only when it applies): the project ALREADY has labels starting with `priorityPrefix` that are no priority of the project (names listed, 10 at most, "and N more"), with the fix (another `priorityPrefix`, rename those labels, or `priorityMap`). Existing `priority:` labels become RESERVED: `add-label` refuses them, and an issue that holds one together with a priority label fails its read (`BackendDataError` naming the issue), exactly as for type labels.
- Migrate (`gitlabTraits.ts`): priority and assignee are carried (a label, the description block) when the target project lists the priority; `claimedAt` and `leaseUntil` are never migrated (loss kind `lease`); the label rules refuse the priority prefix and the mapped names (reserved). Fix texts of the loss ledger name gitlab as a target that carries them; `remote` still does not.
- Not verified: nothing of this against the real gitlab.com (the fake server and the mock ledger only; no new ledger row except one test hook, `beforeNextWrite` / `afterNextWrite` / `editDescription`, UNVERIFIABLE "tooling": a label and a description are plain behaviours the existing LIVE-VERIFIED lines cover). Not testable on Free: `next` skipping a blocked task (blockedBy is refused). Smoke: the phase `priority, assignee, claim` of `scripts/live-gitlab-smoke.mjs` (below).

Hierarchy (GraphQL work items; no REST route, `project(fullPath)` is null without `Project: Read` so only `workItem(id:)` is used, with aliases to read a page in ONE request): parent = native Issue or Incident, child = native Task.

| Operation                | Rule                                                                                                                                                                                                                                                          |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `create` with `parentId` | the parent must be an Issue/Incident (a native Task parent is refused before anything is created); the child is created with `issue_type: task`, then attached; a failure after the creation is a `PartialWriteError` naming `task set-parent`                |
| `setParent`              | refused: self or cycle (`TaskConflictError`), parent already a child (depth), parent a native Task, child with children, Incident child; an Issue child is converted to a native Task first (`workItemConvert`), then attached; replacing a parent is allowed |
| `removeParent`           | `parentId: null`; the child stays a native Task (documented, not reverted)                                                                                                                                                                                    |
| reads                    | `list`/`listPage` carry `parentId` (one aliased query per 50 tasks, native Tasks only); `getChildren`, tree, ancestors, forest follow; without `Work Item: Read` for GraphQL the list degrades to "every task is a root" with ONE notice, never silently      |
| `delete`                 | children of a tombstoned parent are detached first                                                                                                                                                                                                            |

QUICK ACTIONS: GitLab RUNS and strips a `/command` line written in a description or a note (also case-insensitive), except in a code fence, backticks or after a backslash. Text with a line starting with `/` and a word is refused before any request (`BackendRejectedError`); no escape is promised.

Writes: every write re-reads the issue (a conditional GET), compares the parts it changes with `expectedRevision` (`StaleRevisionError`), sends, then reads the record again. `updateStatus`: ONE `PUT` with `state_event` and the WHOLE label set (old status label out, new in), so exclusivity is the wrapper's on every label style (`::` names are plain labels on Free). `create`: `POST` (unknown labels are created by GitLab with a default colour; `labels sync` creates them with colour and description), a terminal status then `PUT state_event=close` (a failure of the second step is a `PartialWriteError`). Label add/remove: `add_labels` / `remove_labels`; swaps: one `PUT labels`. `updated_at` is never sent (GitLab accepts it as a parameter and SETS the stamp). Refused before any request: more than 100 labels, a title over 255 characters, a description over 1 MiB or a comment over 1,000,000 characters, a label with a comma or an edge space, reserved labels (status, type, priority, meta, `task:deleted`), a quick-action line. Delete: `hard` (204), or `tombstone` (ONE `PUT state_event=close, add_labels=task:deleted`; hidden from every read). Comments: `POST/PUT/DELETE .../notes`; an `--author` is refused; a system note cannot be edited or deleted.

Client (`gitlabClient.ts`, injectable `fetch`, clock, `sleep`): `PRIVATE-TOKEN` header. Reads cached in MEMORY only (TTL; `If-None-Match` with the weak ETag GitLab sends on every GET (a 304 is answered for an issue and for a list); every write expires the cache; stale served only after unreachable/timeout/rate limit, labelled). Rate limit (gitlab.com Free: 100 requests per window of about 60 s, `RateLimit-*` headers on every answer): when `ratelimit-remaining` is 0, or after a 429, the client WAITS for `ratelimit-reset` (not `Retry-After`, which is misleading: 2 s while the window stays closed) up to `rateLimit.maxWaitSeconds` (default 70; 0 = never wait), printing ONE notice line per wait on stderr; a longer wait is `RateLimitedError` with the reset time. Errors: 401 = `BackendAuthError(unauthenticated)`; 403 `insufficient_granular_scope` = `GitLabPermissionError` naming the denied permission and the fix; other 403 = `forbidden` with the role hint; 404 `Project Not Found` = `GitLabProjectNotFoundError` (unknown project, or a private one the token cannot see), other 404 on an issue = `TaskNotFoundError`; 5xx or a lost connection = unreachable, never retried and never trusted (multi-call writes re-read, then `PartialWriteError`); the token is in no message, log line or cache. `TASK_DEBUG=1` logs one line per request.

`task strategy check` (GET only, plus ONE no-op write): lines `reachable auth read`, then one line per row of `credentialRequirements.ts` (`write`, `delete`, `labels-read`, `labels-write`, `hierarchy`, `project-info`, `token-info`, `server-info`), then `limits statuses labels links fields writes verification`. A row is `enabled`, `disabled (missing <permission>)` with the exact fix and the docs link, or `not tested` when only a real change could prove it (`delete`, `labels-write`, `Work Item: Create`). The `write` probe is a PUT of the title the first issue already has: nothing in the issue changes, but an issue never edited since its creation gets its `updated_at` refreshed once (live behaviour). The optional rows (`Project: Read`, `Personal Access Token: Read`, `Metadata: Read`) only add facts (access level, expiry, version); "not readable with this token" is an `ok` line.

THE TOKEN (single source: `credentialRequirements.ts`; docs.gitlab.com/auth/tokens/fine_grained_access_tokens/, beta in GitLab 18.10, GA in 19.2): create it with Edit profile > Access > Personal access tokens > Generate token > Fine-grained token, group and project access limited to the project, an expiration date (default and maximum 365 days; the token expires at midnight UTC and the failure is a 401, so renew it before: `strategy check` shows the date only with `Personal Access Token: Read`), and the permissions `Work Item` (Create, Read, Update, Delete: issues, notes, links, events, work items) and `Label` (Create, Read, Update, Delete) on the project. The user of the token needs a role that may edit issues (the access level of the test user could not be read; deleting an issue needs the Planner or Owner role per the docs, and `Work Item: Delete`). A classic token needs the scope `api` (`read_api` reads only): DOCUMENTED, NOT LIVE. A denied call answers 403 `insufficient_granular_scope` naming `[Resource: Action]`; task prints it with the fix. The strategy never needs `Project`, `User`, `Metadata`, `Namespace` or `Member` permissions.

Migrate: `gitlabTraits.ts` (creation instant and comment author not kept, text limits, label rules, hierarchy depth 2, cost estimates); `locationOf` = `gitlab <baseUrl> <project as written>` (a path and the numeric id of one project count as two locations). Losses: history, created-at, `hierarchy:depth` for a third level, `links:blockedBy`, and `lease` for a task that holds a claim lease (priority and assignee are kept).

THE MOCK (`fakeGitLab.testkit.ts` + `fakeGitLabGraphql.testkit.ts`, node:http, free port, in memory) reproduces the REAL Free behaviour: status codes, error bodies and messages, headers (`ratelimit-*`, weak `etag`, 304, `x-gitlab-meta`, pagination `Link` and `x-*`), limits (title 255 characters, description 1 MiB bytes, 100 labels), label and state events and their instants, system notes (exact texts), quick actions, links, labels (case sensitive, group labels), search (word start), the first-PUT `updated_at` quirk, a GraphQL executor for `workItem`, `workItemUpdate` (hierarchy) and `workItemConvert`, the fine-grained permission model (`permissions` option; the default is exactly the live test token's: `Work Item` and `Label` only, so `/user`, `/version`, `/projects/:id`... are 403 as live), the rate limit (`rateLimit: {limit, windowSeconds}` enforces; without it only the headers). Fault injection (`failNext`, `dropNext`, `forceRateLimit`) and `quickActionsRun` for tests. What it does not know answers `501 {"message":"mock: not modelled: ..."}` with `x-mock-not-modelled: 1`, never an invented behaviour. LEDGER (`fakeGitLabLedger.testkit.ts`, `MOCK_LEDGER`, about 300 lines; table in the storage plan, "GitLab mock ledger"): every behaviour is `LIVE-VERIFIED` (date + fixture steps), `DOCUMENTED-NOT-LIVE` (docs page + why it cannot be probed: classic tokens, roles) or `UNVERIFIABLE` (reason), and none may be `ASSUMED` (a test fails otherwise). CONFORMANCE (`gitlabConformance.test.ts`): `fixtures/live-conformance.json` holds 614 requests recorded LIVE with their sanitized answers (ids, instants, users normalized; the project is the disposable one); the test replays them against the mock and requires the same status, key headers and body, that every LIVE-VERIFIED ledger line names fixture steps that exist, and that no line is ASSUMED. To record again: `npm run build`, then `GL_TEST_TOKEN=<token> GL_TEST_PROJECT=<group/project> node scripts/live-gitlab-probe.mjs scenario --record packages/task-service/src/plugins/gitlab/fixtures/live-conformance.json` (about 800 requests, 10 minutes: the project allows 100 per minute); a step added to `scripts/gitlab-conformance-scenario.mjs` can be recorded alone with `GL_SCENARIO_FROM="<step name>"` and merged.

Mock by hand (no Docker, no network): `npm run build`, then `node scripts/gitlab-mock-server.mjs [--port N] [--project acme/shop] [--token T] [--seed] [--rate-limit 100] [--latency MS] [--permissions all|a,b]`; it prints the URL (`http://127.0.0.1:PORT/api/v4`), the project, the token, the `GITLAB_TOKEN=...` line and a ready `strategy:` block to paste in a task project's `config.yml`; Ctrl+C stops it.

Live scripts (never in CI or `npm test`; they read `GL_TEST_TOKEN` and `GL_TEST_PROJECT` from the environment, never write them, redact the token, create only `[task-api-test]` objects and clean up): `scripts/live-gitlab-probe.mjs [section ...]` (discovery: identity, crud, labels, events, notes, links, workitems, pagination, search, errors, delete, misc, scenario, ratelimit) and `scripts/live-gitlab-smoke.mjs [--mock] [--only <section>] [--json FILE]` (every read and write through the real strategy and the bundled CLI entry, `labels sync`, `strategy check`, `task migrate` local -> gitlab -> local; about 1,400 requests, so 15 to 25 minutes against the 100-per-minute limit). `--only "priority, assignee, claim"` runs the sections whose name contains the text (case-insensitive) and skips the rest, cleanup included; no match is exit 2. The phase `priority, assignee, claim` is self-contained (about 250 requests, a few minutes) and checks with the real API: `labels sync` creates the priority labels, `set-priority` swaps in ONE PUT with exactly one priority label, unset, the reserved refusals send nothing, `set-assignee` writes the block and no GitLab assignee, `claim` (takeover of an assignee without lease, conflict naming the holder, `--renew`, `--force`, `release` and its refusals, claim on a closed task refused), a claim as `/close` that GitLab must NOT run, `list --available --order priority-then-oldest` / `--assignee` / `--priority` with no request per issue, and `next`; the issues it creates are titled `[task-api-test] pac ...` and closed by the cleanup. Its full run and the phase itself were NOT run against the mock or live by their author. `--mock` runs the SAME assertions against the local mock in seconds; `node scripts/live-gitlab-smoke-diff.mjs a.json b.json` compares two result files (assertion names and ok flags must be equal).

Tests: unit tests per module, the shared `runBackendContract` (strict, fills with tombstone delete, fills with hard delete, body-block; its priority, assignee and claim cases run on gitlab since stage 3b), `GitLabBackend.priority.test.ts`, `GitLabBackend.claim.test.ts` (quick actions, races through the fake hooks, revision parts), `GitLabBackend.requestBudget.test.ts`, `gitlabRevision.test.ts`, `gitlabPriority.test.ts`, hierarchy tests, migrate local -> gitlab -> local, CLI and module tests, `scripts/gitlab-fake-smoke.mjs` (bundled CLI against the mock; not in CI).

Not done: keyset pagination (offset only), events for changes made on GitLab (R7), a `blockedBy` fill (nothing on Free carries it), a measured cost model for `migrate`, classic-token and self-managed support (declared unsupported, see above).
