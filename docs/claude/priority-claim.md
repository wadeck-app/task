## Priority, assignee and claim (stages 1 to 4a: local, github, gitlab and remote)

Plan and open stages: `.claude/plans/2026-11-14_priority-assignee-claim.md` (decisions D9 to D11 in `.claude/session/decisions.md`). `local`, `github` (stage 3a), `gitlab` (stage 3b) and `remote` (stage 4a, protocol 2: see Storage strategy: remote) support these fields in the service, the CLI and the module (stage 4b, below; routes and yaml tested, NOT yet seen in a real shell). Stage 2 (sorted and filtered list, ordering plugin, fresh reads, `task next`) is done and works on all four. Remote: verified on loopback only (contract suite, parity test, `scripts/live-remote-smoke.mjs` through the bundled CLI), no second machine. Live: github verified on a real repository (stage 3a), gitlab NOT YET (fake server only; run `node scripts/live-gitlab-smoke.mjs --only "priority, assignee, claim"`).

- Fields (task-core `TaskRecord`, optional, no migration): `priority` (one of the project's `priorities`), `assignee` (free text, 1 to 100 characters, no control character), `claimedAt`, `leaseUntil` (ISO). `TaskSummary` mirrors `priority`, `assignee`, `leaseUntil`. An absent priority means the project default (`defaults.priority`, `medium`): callers resolve it, nothing is stored.
- Config: `priorities` (ordered, highest first, scope `local`, default `urgent, high, medium, low`); entries have no edge space (`ConfigSchemaError` naming file and `priorities[i]`); a `defaults.priority` written by a PROJECT layer must be one of them (`ConfigSchemaError` naming that file). Without one, the default is the global value if listed, else `medium` if listed, else the LAST entry; `defaults.leaseMinutes` (1 to 10080, default 30, inherited, also valid in the global config).
- Commands: `task set-priority <id> <priority>`, `unset-priority <id>`, `set-assignee <id> <name...>`, `unset-assignee <id>`, `claim <id> --as <name> [--lease <n>m|h|d] [--renew] [--force] [--json]` (`--as` falls back to `TASK_WORKER`; lease grammar strictly `<digits><m|h|d>`, up to 7d; default from config), `release <id> [--as <name>] [--force] [--json]`. `show` gains `leaseExpired` when a lease is set. JSON of `claim`: `{taskId, outcome, assignee, claimedAt, leaseUntil, previousAssignee?, revision, task}` (the revision is exposed by `claim` only, so a worker can pass it back); `release`: `{taskId, previousAssignee, task}`.
- Claim rules (`TaskStore.claim`, evaluated against the clock the caller passes): free task, or a lease already expired, or no lease: `claimed` / `takeover` (previous holder recorded in the activity); same holder with `--renew`: lease extended, `claimedAt` kept; same holder without `--renew` on a live lease, or another holder on a live lease: `TaskClaimedError` (conflict, names the holder and the time left, hint `--renew` / wait / `--force`); `--force` overrides a live lease; `claim` of a task in a terminal status is a `TaskClosedError` (conflict, even with `--force`; hint: reopen with `task set-status` first; nothing written, no event; `set-assignee` stays allowed); `release` of a task nobody holds is a conflict, `release --as <other>` needs `--force`. `set-assignee` to another name drops `claimedAt` and `leaseUntil`.
- Atomicity of the local backend: EVERY mutation takes the project write lock `<data dir>/.write-lock` (created with `wx`, holds pid, host, time; taken once at the outermost mutator, reentrant) around its read-compare-write and the index write, so two processes cannot lose an update. A contender waits with backoff up to 10 s (sleeping, no spin), then `WriteLockTimeoutError` (`unavailable`) naming the holder pid, host and age. A lock whose pid is dead on the same host is taken over with a warning; a lock of another host is never judged stale. This lifts the former "no lock on task data" rule for the local backend only (D10).
- Activity kinds `priority`, `assignee`, `claim` (`field` = lease end, `oldValue` = previous holder on a takeover, equal to the holder on a renewal), `release`; texts in `taskActivity.ts`.
- Migrate: loss kinds `priority`, `assignee` and `lease` (every source task with a `leaseUntil`, blocking unless allowed); `claimedAt` / `leaseUntil` are never migrated.
- Tests: `TaskStore.claim.test.ts`, `projectLock.test.ts` (task-core), `taskPriorityAssignee` / `taskClaim` (task-service), `PriorityAssigneeCommands.test.ts`, `TaskIndex.claim.spawn.test.ts` (real processes, two sequential claims). GitHub probe of native issue fields: `scripts/live-github-fields-probe.mjs` (not in CI).
- Stage 2, `task list` (`listTasks`, task-service; the CLI only parses): new flags `--status a,b`, `--assignee <name>`, `--unassigned`, `--available`, `--priority a,b`, `--order <name>`, `--limit <n>` (1 to 1000), `--fresh`. A value that is missing or starts with `-` is refused (as `--as`), as is an empty comma entry. `--assignee`, `--unassigned` and `--available` exclude each other (`InvalidListQueryError` naming the pair, `invalid`). `--status` replaces the hiding of terminal statuses (`--all` is then moot); unknown status = `InvalidStatusError`, unknown priority = `UnknownPriorityError`, both listing the valid ones; unknown order lists the registered ones. `available` = no assignee, or `leaseUntil <= now` (an assignee with no lease is NOT available); a lease that cannot be parsed is never over. Filtering, ordering and the limit run in task-service over the summaries for every backend, the limit AFTER the order; works with `--parent` and `--all`; refused (naming the flag) with `--tree`, `--follow` and `--all-projects` (same message shape as the other `--all-projects` conflicts). The output stays JSON only. With any of the new filters, `--order` or `--limit` each row is the summary plus `priority` (the EFFECTIVE one: stored, else `defaults.priority`, never absent) and, only when a lease is set, `leaseExpired` (a stored `leaseUntil` that is not a valid date gives `leaseProblem: "leaseUntil <value> is not a valid date"` instead, never `leaseExpired`; the task is never `available`; the CLI prints one `warning: task <id>: ...; fix with: task release <id> --force` per such task on stderr); the summary already has `id, title, status, createdAt, links?, parentId?, assignee?, leaseUntil?`. Without any of them (and with `--fresh` alone, `unassigned: false`, `available: false` or empty `statuses`/`priorities`, all counted as absent) the answer is the historical one, byte for byte: no `priority` key unless stored. A value flag typed twice (`--status a --status b`, `--as`, `--lease`, ...) is refused naming the flag; `--limit` is validated against the service's `LIST_LIMIT_MAX`. Without `--order` the backend's order is kept. `statuses` is not pushed to `listPage` (the whole list is read anyway).
- Ordering plugin kind `ordering` (`plugins/kinds.ts`: `OrderingPlugin = Plugin<'ordering', OrderingInstance, {}>`; `OrderingInstance.compare(a, b, facts)`, `OrderingRow` = `{id, status, createdAt, priority (effective), assignee?}`, `OrderingFacts` = `{priorities}`, highest first; the plugin's own `describe()` documents it; option-less: `validate` refuses any option). Built-in `priority-then-oldest` (`plugins/ordering/`), registered as `plugins.ordering.default` with alias `priority-then-oldest`: rank = index in the project's `priorities` (a priority outside the list sorts last), then older `createdAt` (ISO text compare), then id ascending (total, stable). Looked up in `ctx.registry` (set by `openTaskContext`; a hand-built context uses the built-ins), tests inject their own registry. `task strategy show` does not list orderings. No `list.order` config default yet.
- Fresh reads: `ListTasksInput.fresh` / `--fresh` runs the read on `ctx.openFresh()` (the same project opened again with the `freshReads` of the strategy context, the mechanism of `task migrate`, github/gitlab cache TTL 0) and disposes it; the context given is untouched, so the next default read is cached again; its read notices reach `ctx.takeNotices` when it is disposed. No-op for `local` (reads its own files) and `remote` (the client keeps no cache: each read asks the server; checked in `RemoteBackend`/plain-http, no response cache). A forge context without `openFresh` (hand-built) fails loudly. Test: `listTasks.fresh.test.ts` on the fake GitHub (TTL 600 s: a default list inside it sends no request, `fresh` sends one).
- `task next --as <name> [--status a,b] [--priority a,b] [--order <name>] [--lease <n>m|h|d] [--fresh] [--json]` (`nextTask`, task-service; `--as` falls back to `TASK_WORKER` like `claim`; `--lease` grammar of `claim`): candidates = `available` tasks that are NOT blocked (an open `blockedBy` link, checked with `store.getOpenBlockers` lazily per candidate right before its claim; a skipped one is no attempt and is counted in `skippedBlocked`; `--include-blocked` / `includeBlocked` opts out) in the given statuses (default: every non-terminal status), ordered (default `priority-then-oldest`); claims the first through `claimTask`; `TaskClaimedError` (another worker won) moves to the next candidate, at most 10 attempts (`NEXT_MAX_ATTEMPTS`), then `NextTaskContentionError` (conflict, exit 1, names the count) when candidates remain; every candidate tried and lost within the cap is an empty answer that still carries `lost`; any other error (closed task, unsupported strategy...) stops at once. Output = `claim`'s (text line or JSON `{taskId, outcome, assignee, claimedAt, leaseUntil, previousAssignee?, revision, task, skippedBlocked}`); no claim: exit 0, text `no available task` (`lost` 0) or `no available task: N candidate(s) were claimed by other workers meanwhile, retry`, JSON `{"task": null, "lost": N, "skippedBlocked": M}` (`nextTask` always returns `lost` and `skippedBlocked`; a lost race is never reported as an empty queue). Events: the claim's `onTaskAssigneeChanged` only. Exit codes: 0 claimed or nothing available, 1 any error. Tests: `ListAndNextCommands.test.ts`, `nextTask.test.ts`, `listTasks.dispatch.test.ts`, `plugins/ordering/orderingPlugin.test.ts`, `TaskIndex.next.spawn.test.ts`.
- Lock takeover: a dead holder's lock is removed under a second exclusive guard `<lock>.takeover` (`wx`, replaced after 5 s or when its pid is dead), after re-reading the lock and checking its token is still the dead holder's; the new lock is then created with `wx`. `--as` / `--lease` refuse a value starting with `-`.
- Known limits: (i) set/clear priority and assignee compute their event from a read taken before the write (outside the lock): under concurrent writers the event may name a stale old value or be missing (the stored value is always right; `claim` and `release` events come from the locked write). (ii) The write-lock wait blocks the event loop of a long-lived process (`task serve`, app-core module) for up to 10 s when a CLI process holds the lock. (iii) A global `defaults.priority` outside a project's list is ignored.

### Module (stage 4b: app-module-task and dsl-lib-task)

- Routes (`routes/fieldRoutes.ts`, same conventions as the others: `?project=`, `inlineErrors`, `undelivered` / `undeliveredText`): `POST /tasks/:id/priority {priority}` and `/assignee {assignee}` (empty string clears) answer `{task, ...}`; `POST /tasks/:id/claim {assignee, leaseMinutes?, renew?, force?}` answers `claim --json` WITHOUT `revision` (`taskId, outcome, assignee, claimedAt, leaseUntil, previousAssignee?, task`); `POST /tasks/:id/release {assignee?, force?}` (body optional) answers `{taskId, previousAssignee, task}`. `leaseMinutes` is a number or digits (a form select holds text); `renew` / `force` must be booleans (400 otherwise). A conflict (live lease, closed task, nobody holds it) is a 409 with the service's message and hint; the hint keeps the CLI wording (`--renew`, `--force`).
- `GET /tasks`: `priority=a,b`, `assignee=<n>`, `unassigned=true`, `available=true`, `order=<name>` (`routes/listQuery.ts`, validation is `listTasks`'s, 400 with hint; an empty value is no filter). With `allProjects=true` any of them is a 400 naming it. Rows gain `priority` (effective), `priorityText` (`medium (default)` when not stored), `priorityIsDefault`, `assignee` (`''` when none), `leaseText`.
- `GET /tasks/:id` gains `priority`, `priorityIsDefault`, `priorityTone`, `priorityOptions` (`None (default: x)` with value `''` first, then the project's priorities; tone by RANK: first `danger`, second `warning`, others `neutral`), `assignee`, `hasAssignee`, `noAssignee`, `claimedAt`, `leaseUntil`, `leaseExpired`, `leaseText` (`held until 14:30 UTC, 12 min left` / `lease expired 3 min ago`; null without a lease), `leaseHeld` (live lease, or one that is not a date: never over) / `claimOpen`, `takeOverText`, `leaseOptions`, `claimDefaultLeaseMinutes`, `supportsPriority` / `supportsClaim` (storage capabilities: the rows are hidden otherwise), and `forms.{priority,claim,takeOver,renew,release}` (the claim forms carry `id`: a Form fills the url from its own data). Code: `taskFieldViews.ts`.
- Task page sidebar rows (first in the list): Priority (`PropertyPopover` pill, action `setPriority`, result `priorityResult`) and Assignee (`PropertyPopover` field holding the lease sentence and, by state: a Claim form when `claimOpen`; a renew form and a "Take over" `Dialog` whose own form sends `force: true`, when `leaseHeld`; a Release form when assigned; actions `claimTask` / `releaseTask`, result `assigneeResult`). The page has no user identity: the name is typed. Tasks list (per project only): columns Priority and Assignee (lease as tooltip). `ActivityFeed` draws `priority`, `assignee`, `claim`, `release` rows (flag, user, user-check, user-minus icons) and counts them in History.
- Not done: no filter links or controls in the list view, no set-assignee form (a claim or release sets and clears it), no widget change; the take-over dialog, claim form and popover nesting were never rendered in a real shell.
