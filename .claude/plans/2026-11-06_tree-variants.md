# Global Tree page: 5 variants for dozens of projects (A/B experiment)

Page: `/modules/task/tree` without `?project` and with several projects (`GET /tree?allProjects=true`, `tree-page.yaml`). Per-project `/tree/p/:project` is unchanged.

## 1. What is wrong today (seen in a browser)

Sandbox: 36 registered projects, 34 readable, 1054 tasks (one project with 300 tasks, depth 8; 6 empty; 2 with an invalid config). Isolated app-core 4891 + Vite 5195, agent-browser at 1440 px.

- The page is **41 220 px tall**: one full table per project, no cap. Reaching the 20th project means scrolling about 20 000 px.
- No overview: nothing says which projects are big, empty, or fully done; no search, no jump to a project, no collapse.
- Empty projects take a full section (title, button, empty table) each.
- The two unreadable projects appear only as one orange paragraph of raw paths and YAML errors at the top, far from where the project would be.
- Every row weighs the same; a project with 3 tasks and one with 300 look alike. The 300-task project pushes everything else away.
- The answer is 199 KB for 1054 tasks (all rows of all projects, as DSL nodes). Server time is small (see section 5).

## 2. Mechanism

- `task:VariantSwitcher` id `task-tree-design`, `initial: current`, bottom-centre dock, dev shell only; production renders `current` only (same as the task-page experiment).
- Source: `src/dsl-views/tree-variants/` (`_page.yaml` head + `$notices` + `$after`, `_shared.yaml`, one `<variant>.yaml` = `label`, `hint`, `view`). `tree-page.yaml` is GENERATED by `scripts/generate-tree-page.mjs` (`npm run views`, freshness-tested). The task-page generator is untouched.
- The switcher sits where the `groups` slot is, inside a `VerticalStack` carrying `$if: $sources.tree.groups` (global scope only); the per-project table and every notice stay outside it. The `$if` is NOT on the switcher itself: in the dev shell that combination logged "Maximum update depth exceeded" on the first choice.
- `current` = today's body (`groups` slot), compared with the committed fixture `__fixtures__/tree-page.head.yaml`.
- Non-initial variants render `$if: $sources.tree.overview`.

## 3. Data contract (additive; `groups` unchanged)

`GET /tree?allProjects=true[&rowCap=N]` gains `overview`:

| Field                 | Content                                                                                                                                                           |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `overview.totals`     | `projects`, `readable`, `unreadable`, `open`, `total`, `done`                                                                                                     |
| `overview.rowCap`     | rows per project actually sent (default 60, `?rowCap=` 1..500, else 400)                                                                                          |
| `overview.projects[]` | every project, readable or not, sorted by name                                                                                                                    |
| per project           | `id`, `name`, `path`, `readable`, `treeHref`, `problemText` (unreadable only: reason and fix)                                                                     |
| readable only         | `open`, `total`, `done`, `percent`, `empty`, `allDone`, `summaryText`, `lastAddedAt`, `lastAddedText`, `rows[]`, `rowCount`, `hiddenCount`, `moreText`, `roots[]` |
| `rows[]`              | `id`, `titleText`, `title`, `status`, `tone` (success when closed), `depth`, `href` (depth-first, first `rowCap`)                                                 |
| `roots[]`             | up to 5 root tasks that have children: `id`, `titleText`, `href`, `status`, `done`, `total`                                                                       |

- `lastAddedAt` is the newest `createdAt` of the project (the index has no `updatedAt`): the label says "Last task added".
- Empty registry: `projectCount` 0 and `noProjects` as today; `overview` has no projects. All unreadable: the route still answers the existing `NoReadableProjectsError` as `errorText`. Registry problem: unchanged banner.
- Cost: figures from `summarizeProject`, last-added from the index; no task file is read. Nothing is cached.

## 4. The five variants

All run on the same `overview` and components of `packages/dsl-lib-task`. Closed-parent kept-for-context rows are marked by status only.

| #   | Id              | Strategy                                                                                                                                                                                                                     | Component             | Options (nested switchers)                 |
| --- | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- | ------------------------------------------ |
| 1   | `accordion`     | One collapsible per project (name, open/total, mini bar); filter box; expand all / collapse all; last opened project is remembered and reopened                                                                              | `ProjectAccordion`    | `accordion-open`: last used / first / none |
| 2   | `master-detail` | Left: searchable project list (counts, unreadable flagged, scrolls); right: tree of the selected project; selection in `?treeProject=` and localStorage                                                                      | `ProjectMasterDetail` | `master-detail-list`: wide / narrow list   |
| 3   | `picker`        | Search-select of projects plus an "All projects" overview of compact summary rows; choosing one shows its tree; deep link `?treePicked=`                                                                                     | `ProjectPicker`       | `picker-start`: overview / first project   |
| 4   | `cards`         | Responsive grid of project cards (progress bar, open/total, top parents with child progress, last added), sortable (buttons; the option sets the order); card opens `/tree/p/:project`; unreadable card shows reason and fix | `ProjectCards`        | `cards-sort`: last added / name / open     |
| 5   | `flat`          | One list with sticky project group headers, project text filter, status filter, first N rows per project then "N more" link, hard cap of projects per page with "Show more projects"                                         | `ProjectFlatTree`     | `flat-cap`: 5 / 15 / 40 rows per project   |

Per variant:

- **Empty / error states** (all five): zero projects shows the shared welcome badge (outside the switcher); a project with no tasks says "No tasks" in its row/card/panel; an unreadable project is listed with its reason, never dropped; a filter without match says so with the active filter.
- **Scaling**: the browser receives at most `rowCap` rows per project (60 by default); the full forest stays one click away at `/tree/p/:project` (`treeHref`). Accordion/master-detail/picker render only the open project's rows. Cards render no rows (roots only, 5 per card). Flat renders at most 40 projects at a time.
- **Keyboard**: every control is a native button/input/link (tab order = visual order); the accordion headers are `aria-expanded` buttons; the master list is a `listbox` with arrow keys; the picker is a text input + button list.
- **Narrow (390 px)**: `SplitLayout` stacks (list above tree); cards go to one column; the flat list and rows truncate titles. The shell menu limit (CLAUDE.md "Narrow screens") still applies.

## 5. Measured

Route `GET /tree?allProjects=true`, warm, 5 runs, curl on localhost, nothing cached:

| Registry                                                | Route time | Answer                                                       |
| ------------------------------------------------------- | ---------- | ------------------------------------------------------------ |
| 34 readable projects, 1054 tasks (largest 300, depth 8) | 15-25 ms   | 300 KB (overview about 100 KB)                               |
| 34 readable projects, 9600 tasks (about 300 each)       | 45-57 ms   | 1.78 MB: `groups` (current page) 1.32 MB, `overview` 0.41 MB |

- The overview adds an index read and the figures per project; the cost is dominated by `groups`, which only `current` uses. The answer cannot skip `groups` because the data source is shared by every variant; baking a winner drops it.
- Not measured: render time in the browser for the 9600-task registry per variant (screenshots only), a registry beyond 40 projects.
