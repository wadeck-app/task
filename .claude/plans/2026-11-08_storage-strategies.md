## 1. The seam

### 1.1 Premise (owner): ONE async port, local adapter included

Decided premise: make the store async; the local file adapter wraps today's sync `TaskStore` in already-resolved promises (local latency is negligible, so no UX change). Goal: switch or migrate between systems with almost no visible difference. Alternatives, rejected:

| Alternative                      | Why rejected (one line)                                                                                             |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| (b) Sync cache + background sync | Writes "succeed" before the remote accepts and reads can be stale as truth: silent divergence, violates fail loudly |
| (c) Mirror / import-export only  | Not a database: edits do not flow back; kept only as a by-product (migration, 1.8)                                  |

Known consequences of the async port, not fixed here:

- A use case is no longer atomic with respect to other requests of the same process (the module): two requests can interleave between the read and the write of one use case. Task data has no lock by design (Q30); a per-backend queue is a decision for 0.7 or later.
- A failing `--follow` poll now ends the command with `Error: <message>` (exit 1) instead of an uncaught-exception stack.

Design choice inside the port (applies to step 0.7): do NOT mirror the 35 TaskStore methods 1:1. Remote backends cannot atomically do "setParent with cycle check + activity append". Split:

- Port = primitive persistence (below). Domain rules (cycle detection, `duplicateOf` single target, status validation, activity/history synthesis, link inverses) stay in one shared layer (`TaskStore` becomes the rules engine over a `TaskBackend`), so local and remote behave identically where the remote can express it.
- Backends decide only what they persist and what they refuse (capabilities).

### 1.2 Port (derived from what the service really needs)

```
interface TaskBackend {
  readonly kind: 'local' | 'github' | 'gitlab' | 'remote'
  readonly capabilities: BackendCapabilities
  // reads
  list(query?: {parentId?, statusIn?, label?, text?, limit, cursor}): Page<TaskSummary>
  get(id): TaskRecord & { revision: string }          // revision = etag / updated_at / local mtime hash
  getMany(ids): TaskRecord[]                           // avoids N+1 (listLabels)
  listLabels(): {label, count}[]                       // backend-native when cheap
  // writes (each takes expectedRevision, throws TaskConflictError on mismatch)
  create(input): TaskRecord
  update(id, patch: {title?, description?, status?, type?, labels?, meta?, parentId?|null}, expectedRevision)
  setLinks(id, links, expectedRevision)                // outgoing set replaced
  addComment / editComment / removeComment
  delete(id)
  // activity
  readActivity?(id): ActivityEntry[]                   // only if capabilities.activity === 'native'
  // lifecycle
  check(): Promise<BackendCheckReport>                 // for `task strategy check`
}
```

Rules:

- `TaskSummary` shape stays the unit of lists; `parentId`/`links` in summaries only if `capabilities.indexedGraph` (local always; remote: lazily, see 2.x).
- Pagination is part of the port from the start (local returns one page); the current `list(): TaskSummary[]` is the problem for remote (all issues).
- `getForest/getTree/getDescendants` become service-level algorithms over `list` + `parentId`, not backend methods; remote may override with a native call if capable.
- Events remain service-level, emitted after a successful backend write. Unchanged contract.

### 1.4 Failing loudly

- Every service use case that depends on a capability checks it first and throws `UnsupportedByBackendError(kind, operation, capability, hint)`. `describeError` maps it (CLI exit 1 with hint, module HTTP 409/422). No fallback to "store it in the body".
- Config validation at load: if `statuses` in the project config contain a status the backend cannot represent (no mapping entry), `ConfigSchemaError`-style error naming the file and key, not at first use.
- Where degradation is deliberate (GitHub `delete` = close), it is declared in capabilities and printed in the command result ("closed #12 (GitHub cannot delete issues)"), never silent.
- The UI hides controls for missing capabilities from the same flags (`GET /projects` exposes `capabilities`).

### 1.5 Identity

| Strategy | Native id                                                  | Task-visible id                                                                                  | Notes                                                              |
| -------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| local    | 8-hex                                                      | same                                                                                             | prefix lookup kept                                                 |
| GitHub   | issue number + repo (`owner/repo#12`); node id for GraphQL | `12` inside the project (numeric string); full ref in `meta.remoteRef` / `TaskRecord.remote.url` | project already scopes the repo, so project-local id is the number |
| GitLab   | `iid` per project (global `id` also exists)                | `iid` as string                                                                                  | work-item global id kept internally                                |
| remote   | server's local id                                          | same                                                                                             | server resolves prefixes                                           |

- Cross-project: `formatQualifiedId(project.id, taskId)` is already the shared convention; use it in cross-project lists, events and links. Project id is the registry id (8 hex), never the repo name.
- Prefix resolution: numeric ids are exact only; `findByPrefix` for remote backends accepts exact ids and refuses prefixes (typed error) unless the backend has a local cache of ids.
- Id stability: a repo transfer changes `owner/repo`; the config holds the repo, ids stay numbers, so only `strategy.repo` needs editing.

### 1.6 Consistency

- Every read returns `revision`; every write carries `expectedRevision`; mismatch = `TaskConflictError` (already exists for "unchanged status") with `kind: 'stale'`, message "task 12 changed on the server since it was read; re-run".
- GitHub has NO conditional writes (VERIFIED-LIVE 2026-11-08: If-Match 400, see 1.3 and 2.2.1; the revision of a record should combine `updated_at` with the written field, since comments and label changes bump `updated_at`) and GitLab documents no optimistic-lock parameter on issue edit (VERIFIED absence on the issues page), so neither has compare-and-swap: the backend re-reads `updated_at` right before PATCH and documents a residual race window. State it in `task strategy check` output as "optimistic, not atomic".
- Multi-step operations (setParent + activity) are not transactional remotely: ordering rule = do the primary mutation first, record activity only if native; on partial failure report a typed `PartialWriteError` (pattern already used by `PartialDeleteError`).

### 1.7 Contract test suite (enforces "almost no difference")

One suite, `backendContract(makeBackend)`, exported from task-core as a test helper. Every backend runs it unchanged:

| ------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |

| Group         | Cases                                                                                                                                                       |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CRUD          | create/get/list/paging; title vs description split; update title/description; exact and prefix id resolution; not-found and ambiguous errors (same classes) |

| Fields        | type set/clear, label add/remove idempotence, meta set/remove, comments add/edit/remove                                                                     |

### 1.8 Migration through the port (`task migrate --from <ref> --to <ref>`)

Reads everything through the source port, writes through the target port; no file or API shortcuts. The source is never modified or deleted. Supersedes the `import`/`export` pair of section 4.2 (they become aliases of `migrate` with a fixed side).

| Aspect                 | Design                                                                                                                                                                                                                                                                                                         |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Addressing             | Source and target are registry projects, or one project with an explicit strategy override on one side (so a project moves local -> GitHub, then its config is switched by the user). Same source and target is refused                                                                                        |
| Plan phase             | Always runs first and is printed; `--dry-run` stops after it. Reads everything (paged), builds creation order, id map and loss report, writes nothing. Exit 1 on any BLOCKING loss unless `--allow-loss <kind>` names it                                                                                       |
| Creation order         | 1 tasks, parents before children (topological on `parentId`); 2 labels, type, meta, status per task; 3 links (all tasks exist, `duplicateOf` single target kept); 4 comments, chronological; 5 activity only if the target stores it and `--keep-activity` is given (native-activity targets cannot import it) |
| Id mapping             | `source id -> target id` in `<data dir>/migrations/<runId>.json` (atomic write). Also `meta.migratedFrom = <qualified source id>` on the target task when the target has meta. Ids change local -> forge: references inside titles/descriptions are NOT rewritten, they are counted in the report              |
| Resumable / idempotent | The journal records each completed step per task. `--resume <runId>` continues. A rerun without it matches targets by `meta.migratedFrom` or by the journal; when neither can match and the target is not empty, it refuses and lists the conflicts                                                            |
| Timestamps / authors   | Forges assign `createdAt` and authors; originals go in a header comment or meta when the target allows, else are listed as lost                                                                                                                                                                                |
| Failure                | Stops at the first non-transient typed error with the journal saved and the resume command printed; rate limits wait up to `--max-wait`, else stop                                                                                                                                                             |
| Events                 | Suppressed by default; `--emit-events` opts in                                                                                                                                                                                                                                                                 |
| Report                 | Text and `--json`: migrated count, per-kind losses with task ids, unmapped items, id-map path                                                                                                                                                                                                                  |

Losses when the target has fewer capabilities (always listed per task, never silent):

| Source feature                                  | Target lacking it                 | Rule                                                                                         |
| ----------------------------------------------- | --------------------------------- | -------------------------------------------------------------------------------------------- |
| Custom statuses                                 | forge without a `statusMap` entry | BLOCKING until the map exists (config load error)                                            |
| `causedBy` links                                | GitHub, GitLab                    | blocking unless `--allow-loss links:causedBy`; then dropped and listed (no invented content) |
| Meta                                            | forge with `meta: refuse`         | blocking unless `--allow-loss meta`                                                          |
| Status history and activity                     | forge (timeline is read-only)     | dropped, counts in the report; `--history-comment` writes one summary comment per task       |
| Comment author and time                         | forge                             | recreated by the migrating user with a quoted header; listed                                 |
| Hierarchy deeper than the target limit, or none | GitHub depth cap, no capability   | blocking with offending ids                                                                  |
| Forge -> local                                  | local accepts everything          | native activity kinds that map are stored, others dropped and listed                         |

Effort: M-L. Two-way sync is not proposed: migration is one-shot and idempotent; sync is a different problem (conflict model).

Rate limits and pagination (VERIFIED 2026-11-08):

- GitHub REST: 5,000 requests/h for a PAT user, 60/h unauthenticated, 1,000/h per repository for `GITHUB_TOKEN` in Actions (docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api). VERIFIED-LIVE 2026-11-08: the headers and `GET /rate_limit` (free; separate `core`, `search` 30, `graphql` buckets) are as documented; `x-ratelimit-used` is not monotonic across calls, so budget on `remaining` + `reset` of the last response. Measured cost: reads about 0.3 s, writes about 1 s, a 100-label POST times out (502), see 2.2.1; the secondary limits were not stress-tested, so the 80 writes/min figure stays documented-only (sequential writes at about 1 s each stay near 60 per minute, i.e. close to that limit, so the backend must still honour `retry-after`).
- GitHub search: 30 requests/min authenticated for all search endpoints except code search (10/min), 10/min unauthenticated; at most 1,000 results per search, 100 per page (docs.github.com/en/rest/search/search).
- GitHub GraphQL: 5,000 points/h per user; every connection needs `first`/`last` within 1-100; at most 500,000 total nodes per call (docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api).
- GitLab.com (docs.gitlab.com/ee/user/gitlab_com/rate_limits.html): currently in effect 2,000 requests/min per authenticated user, issue creation 200/min, note creation on issues 60/min; the page also lists plan-based hourly limits (Free 5,000, Premium 15,000, Ultimate 25,000) marked "proposed, not yet in effect". 429 carries `Retry-After` and `RateLimit-ResetTime`; all responses carry `RateLimit-Limit`, `RateLimit-Remaining`. - GitLab pagination: offset by default (`per_page` default 20, max 100, `Link` header and `x-total*` headers; omitted above 10,000 records); keyset only on selected endpoints, for issues `GET /projects/:id/issues` since 18.3 (docs.gitlab.com/ee/api/rest/index.html, ee/api/issues.html).

Consequences: (1) list pages are cursor/page based and capped per page (100), `list()` returns a page; (2) `listLabels` must use the labels endpoint, never N `get`; (3) the backend honors `Retry-After`/`X-RateLimit-Reset` and, when exhausted, fails with `RateLimitedError(resetAt)`, not a hang; (4) summaries for tree views require sub-issue data: use GraphQL (GitHub) / work items GraphQL (GitLab) to fetch parent ids in bulk.

## 2A. Filling unsupported capabilities

GitHub/GitLab API facts in this section were checked against the official docs on 2026-11-08 where the Verification log (end of file) says so (and corrected in 2.1-2.3); a fact still marked UNVERIFIED stays so. A fill replaces a missing native capability with an existing forge feature. It never invents behaviour silently.

### 2A.1 Rule (declared, listed, never silent)

| Rule           | Detail                                                                                                                                                                                                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Declared       | Each fill is named in the strategy config: `fills: { <capability>: <technique> }`. No fill is active by default except those listed as "default" in 2A.3                                                                                                                |
| Fidelity mode  | `fidelity: strict \| degrade` globally under `strategy`, overridable per capability (`fills.meta: { use: body-block, fidelity: degrade }`). Default `strict`                                                                                                            |
| `strict`       | The capability stays unsupported; the operation throws `UnsupportedByBackendError` whose hint names the fill that would emulate it and the config key to set                                                                                                            |
| `degrade`      | The fill is used; every command that relied on an approximate or lossy fill prints a warning on stderr ("meta emulated via body block, approximate: edits made on the forge page may be overwritten"), and `--json` carries `emulated: [{capability, via, fidelity}]`   |
| Listed         | `task strategy show` and `task strategy check` list each capability as `native`, `emulated via <technique> (<fidelity>)` or `unsupported`, plus the probes that failed (feature missing on this instance/tier)                                                          |
| Checked        | `check` verifies the prerequisites of each declared fill (permission scope, label exists or can be created, feature present on the instance) and fails with a fix; a declared fill whose prerequisite is missing is an error, never a quiet downgrade to something else |
| Contract suite | Cases for an emulated capability run with the fill enabled and assert the declared fidelity (exact fills must pass the same case as local; approximate/lossy fills assert the documented deviation)                                                                     |
| Migration      | `task migrate` reports per fill: written via fill, idempotent or not (column in 2A.3), and treats `lossy` as a loss needing `--allow-loss`                                                                                                                              |

Fidelity scale: exact = indistinguishable from local for the contract suite; approximate = same data, but concurrent human edits or forge behaviour can alter or lose it; lossy = part of the information cannot be stored or read back.

### 2A.4 Config shape

```yaml
strategy:
    type: github
    fidelity: strict # strict | degrade, global default
    options:
        repo: owner/name
        tokenEnv: GITHUB_TOKEN
        fills:
            status: label # or: projects-field
            meta: { use: body-block, fidelity: degrade }
            hierarchy: native
            delete: tombstone
            links:
                causedBy: relate-block
            events: poll
```

- A `fills` key naming an unknown capability or technique, or a technique that this backend cannot provide, is a `ConfigSchemaError` naming the file and the dotted key.
- Under `strict`, any approximate or lossy fill must carry its own `fidelity: degrade`, so the owner of the project explicitly accepts it per capability.
- A fill cannot silently replace a native feature: if the backend has the native capability, a fill for it is allowed only as an explicit override (for example `delete: tombstone` although `hard` is available).

## 3. The remote strategy (tasks on another computer)

| Option                                             | Mechanism                                                                                               | Pros                                                                                                                          | Cons / what breaks                                                                                                                                                                                                                                                                                         |

Recommendation: (a), with a deliberately small, versioned protocol that is NOT the module routes:

- `task serve --listen <host:port> --token-env TASK_SERVE_TOKEN`: serves ONE or several registered projects of that machine, each addressed by registry id.
- Protocol: `GET /v1/info` (protocol version, capabilities, project list), then `/v1/projects/:id/tasks...` mirroring the TaskBackend port. JSON only, `revision` on every record, `If-Match` header for writes (412 = `TaskConflictError`).
- Server reuses `task-service` with the `LocalFileBackend`; the HTTP layer is a third adapter (never imports the CLI or the module; add to dependency-direction rules).
- Versioning: client sends `X-Task-Protocol: 1`; server answers 426 with supported range; mismatch is a typed error with "update task on <machine>".
- Network assumption (owner decision): the remote host is simply REACHABLE (machines on the user's local network). No tunnel, VPN, TLS terminator or reverse proxy is implemented or required in v1; they are added later only if needed.
- Security baseline (independent of the network): bearer token required (the server refuses to start without one, no anonymous mode; the client reads it from an env var NAMED in the config, never the value); `task serve` binds `127.0.0.1` by default; binding a LAN interface needs the explicit flag `--listen <addr:port> --allow-lan`, and every start prints a loud warning on stderr: "serving task data over plain HTTP on <addr>: traffic and the token are readable on the network; trusted LAN only". The same fact is shown by `task strategy check` on the client for any `http://` non-loopback URL (warning line, not an error). No token in URLs or logs; failed-auth rate limit; the client does not follow redirects; `X-Task-Protocol` header on every request; single writer; per-request timeout (`timeoutSeconds`, default 10) with the stale/offline behaviour of 1.9.
- Deferred, explicitly: TLS (`https://` URL accepted by the client when a wrapper provides it, no server-side TLS flags now), tunnels/VPN, multi-user auth and per-token project scope (one shared token per server in v1).
- Typed client errors, each with an actionable hint: `RemoteUnreachableError` (DNS/refused/timeout: names URL, "is `task serve` running on <host>? check the address and the firewall"), `RemoteUnauthorizedError` (401/403: names the env var read and whether it was set), `RemoteIncompatibleError` (426 or protocol range mismatch: "update task on <machine>/<this machine>", shows both versions), `TaskConflictError` (412).
- Transport plugin point (owner decision): the remote client talks only through a named transport plugin; v1 ships exactly one, `plain-http`, the default. Details in 3.1. A later wrapper plugs in without touching the backend, the protocol or the contract suite.

- orchestrator: `orchestrator-cli/src/progress/registry.ts` is a fixed in-code list of `ProgressStrategy` objects; its comment says "no external code is loaded, there is no plugin setting in config.yml". Same idea as a built-in list, with no registry class.
- project-sdk: `ConfigSchema` can declare a nested section such as `plugins.github` (`config.ts`, one nested level); it validates key names only, it is not a plugin loader.
- app-core: a different concept, the module platform (`manifest.json`, `dslLib`, `app-module-*`); task's `app-module-task` is one. Not a candidate for transport or strategy plugins.
- No shared package holds the plugin concept today: flow's `PluginRegistry<T>` / `PluginModuleLoader<T>` are generic but live inside `flow-cli` and are a copy of queue's `plugin-api.ts`. They are the nearest thing to the extraction target.
- No shared plugin-contract test suite exists in queue or flow (each package tests its own registry and its own plugins).

#### 3A.2 Common denominator and the choices where they differ

Common: a plugin is a JS object (default export, `plugin` export or the module itself) with a string identity and functions, validated by a shape guard at registration; built-ins are statically imported and registered at startup under a name plus aliases, resolved before any `import()` (needed by single-file bundles); an external plugin is an absolute path or a package installed next to the CLI; registration conflicts throw naming both sides; an unknown name lists the available ones with a fix; plugins run in-process with no sandbox; workspace packages are private, versioned 0.1.0 and bundled in the CLI.

#### 3A.7 Tests (queue/flow list, adapted)

Registry: finds by ref and alias; duplicate ref names its owner; alias equal to another ref; repeated alias; malformed id; wrong shape; nothing registered when a call throws; `lookup` with the wrong kind names the right slot; two instances are independent. Per plugin: its own options table and `describe()`. Strategy plugins additionally pass `backendContract` (1.7); transport plugins pass the loopback contract run (3.1).

## 4. Per-project configuration

### 4.1 Location and schema

`<registry>/projects/<id>/task/config/config.yml`, new section `strategy`, scope `local` (a child never inherits the parent's repo; a parent's value is valid there):

```yaml
strategy:
    # a strategy plugin (kind `strategy`, 3A): ref `plugins.<id>.<impl>` or its alias.
    # local (default) | github | gitlab | remote
    type: github
    fidelity: strict # strict (default) | degrade, see 2A.1
    options: # owned and validated by the plugin (3A.3)
        repo: owner/name
        baseUrl: https://api.github.com # GHE: https://host/api/v3
        tokenEnv: GITHUB_TOKEN
        statusMap: # task status -> remote representation
            todo: { state: open }
            in-progress: { state: open, label: 'status:in-progress' }
            done: { state: closed }
            cancelled: { state: closed, reason: not_planned }
        typePrefix: 'type:'
        # one shape for every non-native capability (2A.4, R17): a capability not
        # listed here and not native is unsupported and throws with a hint
        fills:
            meta: labels # exact fill, allowed under strict; body-block needs fidelity: degrade
            hierarchy: native
        cache: { ttlSeconds: 60 }
        pollSeconds: 0 # 0 = no polling


# other strategies, same shape (options differ per plugin):
#   type: gitlab
#   options: { baseUrl, project: group/proj, tokenEnv, statusScope: "status", ... }
#   type: remote
#   options:
#     project: <remote registry id or name>
#     transport: { type: plain-http, options: { url, tokenEnv, timeoutSeconds } }   # kind `transport`, see 3.1
```

- One plugin per slot: `strategy.type` selects the plugin and `strategy.options` is read by it only. The former per-type blocks (`strategy.github`, `strategy.gitlab`, `strategy.remote`, "a block for another type is allowed") are gone: flow and queue configure one instance per slot with `type` + `options`/`with`, and switching is a change of `type` plus `options`. Cost: the options of the previous strategy are not kept in the file (use the project config history of the user's VCS or keep a commented block).
- Schema integration: add `strategy: { scope: 'local' }` to `TASK_CONFIG_SCHEMA`; `validateLayer` already names the file for unknown/misplaced keys (VERIFIED: the SDK validates one nested level, so `strategy.type` and `strategy.options` can be declared; everything inside `options` is task's). The deeper validation is the plugin's `validate` (3A.3), wrapped with file + dotted key path (e.g. `config.yml: strategy.options.statusMap.done: unknown state "clsoed"`); the host checks `type` against the registered strategy refs. Unknown keys inside `options` fail like top-level ones because a plugin never strips silently.
- `statuses` stay in `statuses:` (local layer). For forge strategies, every configured status MUST have a `statusMap` entry and exactly the terminal ones map to `closed`; checked at load, naming file + status. Exactly one open status must be mappable to "no status label" (the default), otherwise opening an issue with no label is ambiguous.
- Inheritance: nothing in `strategy` inherits (consistent with `statuses/types/fields/hooks`). Global `~/.task/config.yml` may only provide `defaults` as today; a global `strategy` is a schema error with hint (a repo is per project).
- Secrets: schema rejects keys named `token`, `password` (with the hint to use `tokenEnv`).

### 4.3 Migration

Superseded by 1.8 (`task migrate` through the port; `import`/`export` are `migrate` with one side fixed). The table below keeps only the direction recommendation: one-way, idempotent, no two-way sync in v1. Roadmap: stage 1 delivers `migrate --from <forge> --to <local>` (read-only forge), stage 2 adds the reverse; the contract suite (1.7) is a stage 0b deliverable and gates every later stage.

| Direction      | Recommendation                                                                                                                                                              |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| local -> forge | `task import`-like `task export --to github` creates issues, maps ids (writes a `meta.localId` or a mapping file `id-map.json` in the data dir), one-way, `--dry-run` first |
| forge -> local | `task import --from github`: one-way, idempotent via `meta.remoteRef`, ids new 8-hex, parents/links resolved in a second pass                                               |
| two-way sync   | NOT in v1 (needs conflict model, tombstones, per-field merge). Revisit only after read/write backend is stable                                                              |

Imports go through the normal service (`createTask`, `setParent`...) with events suppressed by default (`--emit-events` opt-in) since they are not user changes.

## 8. Top 3 recommendations

1. Do stage 0 first: async `TaskBackend` port with a local adapter, domain rules kept in one shared layer, capability flags with enums; no behaviour change, golden-file test.
